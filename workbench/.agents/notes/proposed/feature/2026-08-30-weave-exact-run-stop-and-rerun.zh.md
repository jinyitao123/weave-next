# Agent Note: 第一期精确 run 停止与纠正后尝试

Status: proposed

[English](2026-08-30-weave-exact-run-stop-and-rerun.md) | 中文

## 问题

当前 Workbench 可以从持久 DSH Session 投影 Weave 工作，但无法诚实地停止精确远程 TeamRun，也没有提供足够的精确 run 事实来支持纠正后尝试。本地 Agent 取消、Browser 请求取消和停止轮询都不会停止 Weave。

第一期必须在不预先建设独立任务平台的情况下完成首个真实 FDE 闭环。所需结果很简单，即启动工作、离开并恢复、检查工作、停止一个精确 run、修订完整简报、启动新 run，并取得这个新 run 的交付物。

## 提案

只用精确 run 活动读取、幂等整 run 停止、交付物 `run_id` 过滤、一个未解决本地动作以及通过现有 API 完成的纠正后派发，扩展当前由 Session 支撑的工作投影和现有 Weave 执行权威。当这条窄路径经受真实取消竞态并完成一条真实 FDE 任务后，第一期即为完整。

## 对抗互审结论

第一版因为范围过大被否决。它增加了独立 WorkTask 领域、WorkStream、两类存储记录、命令 worker、六种控制状态、独立命令状态和交付物接口、成员定向纠偏、重跑谱系字段以及通用重放策略。

通过审查的设计删除了这些新增项。第一期只有：

- 一个现有的 Session 工作投影；
- 一个权威 Weave TeamRun 状态；
- 一个本地新鲜度事实；
- 零个或一个未解决的 `pendingAction`；
- 一个精确 run 活动读取；
- 一个幂等整 run 停止；
- 一次完整简报修订，随后使用普通派发。

这是[最小 WorkTask 架构](../architecture/2026-08-30-weave-workbench-durable-work-task-domain.zh.md)的第一个实施切片。

## 产品承诺

确认团队和简报后，用户可以关闭对话或应用，Weave 继续执行。重新打开工作时，可以看到团队、当前阶段、已知成员活动、运行时分配、HumanTask、精确 run 交付物和数据新鲜度。

用户可以选择`停止这个 run`。Workbench 会指出精确 run，并说明已提交输出会保留、进行中工作可能丢失、继续工作需要新 run。只有 Weave 处于 `cancel_requested` 或存在已经持久化但尚未解决的停止动作时，界面才从事实推导出`正在停止`。只有 Weave 报告 `cancelled` 或 `abandoned` 后才显示`已停止`。

取消后，Workbench 展示观察到的事实和完整简报编辑器。确认修订会创建新的 request 和 run。旧 run 保持不可变且继续可见。第一期不会把这个过程称作暂停或恢复。

## 包含范围

第一期包含：

- 通过现有 MCP 工具直接选择团队和基于事实的推荐；
- 没有匹配团队或已发布工作流时明确失败；
- 无需模型轮次的持久 Session 工作恢复；
- 精确 run 阶段、成员、运行时、HumanTask 和交付物检查；
- 幂等整 run 停止和未知响应恢复；
- 带明确未知项的终态观察事实；
- 完整简报纠偏和一次新派发；
- attempt 历史和精确 run 交付物隔离；
- 一条真实无副作用日冕工作流测试。

第一期排除独立 WorkTask 存储、一个工作项内多个团队、仅成员纠偏、同 run 恢复、检查点重启、因果影响计划、自动回滚、副作用账本、跨设备恢复和多人审批。

## 状态模型

Workbench 不持久化新的控制枚举。它从三个事实渲染动作：

| Weave 状态 | 本地事实 | 产品视图 |
|---|---|---|
| 非终态 | 没有 pending action | 工作中或等待输入 |
| 非终态 | pending stop | 已请求停止 |
| `cancel_requested` | 任意 | 正在停止 |
| `cancelled` 或 `abandoned` | 无 | 已停止，可修订 |
| 终态成功或失败 | 无 | 已完成或失败 |
| 任意 | 新鲜度陈旧 | 最后已知状态并显示陈旧警告 |

`pendingAction` 不是执行状态。它记录已经在本地受理但远程结果尚不明确的意图。一旦权威活动或派发状态解决该意图，投影就会清除它。

## Weave 改造

### 精确 run 活动

增加一个经过认证的精确 TeamRun 活动查询并通过 MCP 暴露。响应包含：

- 精确 TeamRun id、团队和已发布工作流身份；
- TeamRun 状态和可单调比较的 revision 或 ETag；
- 带已知完成、活动、中断或未开始状态的阶段；
- 稳定的已知成员及其当前或最近业务活动；
- 运行时分配以及可披露的引擎或节点事实；
- HumanTask 引用和状态；
- 归属于精确 run 的交付物引用；
- 各部分完整度和更新时间。

私有 provider reasoning、凭据、无界原始 trace 和猜测出的成员身份都不返回。终态取消响应直接提供观察到的影响事实，不存储独立 `stop_summary` 对象。

现有 MCP `team_run_status` 可以扩展为返回这个有界活动快照，不再增加另一个重叠读取工具。HTTP 路由可以保留为同一个应用服务之上的 TeamRun 专用适配器。

### 幂等停止

增加一个经过认证的整 TeamRun 停止应用服务、API 路由和 MCP `team_run_stop`。输入是精确 run 身份、有界原因和调用方生成的幂等 key。

它复用现有 TeamRun 转换：

| 当前状态 | 结果 |
|---|---|
| `queued` | 取消排队工作并变成 `cancelled` |
| `running` 或 `parked` | 变成 `cancel_requested`，终止工作，然后进入 `cancelled` |
| `cancel_requested` | 重放相同请求，或拒绝变化后的载荷 |
| 终态 | 返回现有终态结果，不重新打开 run |
| 宽限过期 | 变成 `abandoned` 并推进 execution lease epoch |

响应丢失时重复相同请求和 key，然后读取精确 run 活动。第一期不增加命令状态接口或 MCP `team_run_stop_status`。

取消特征测试必须证明旧 generation 或 lease 的工作不能成为当前成功结果，也不能静默提升迟到交付物。

### 交付物隔离

为现有 `deliverable_list` 增加可选的精确 `run_id` 过滤。正文继续使用 `deliverable_get`。不增加另一个精确 run 交付物资源。

活动快照包含交付物引用，因此 Workbench 不需要扫描或连接 workspace 范围列表。已停止 run 的输出留在该 attempt 下，永远不会成为纠正后 attempt 的主交付物。

### 纠正后派发

使用现有 `team_dispatch` 和 `dispatch_status`。纠正后 attempt 使用新的 `client_request_id`、相同的已确认团队，除非用户显式更改团队，以及完整修订后的任务文本。Workbench 保留本地前序关联；第一期不向 Weave 增加 `supersedes_run_id`、correction digest 或成员目标字段。

第一期只为一条已配置且确定没有不可逆外部写入的工作流启用。这是发布范围限制，不是新的通用重放策略子系统。每次纠正后派发仍然需要显式确认。

## Workbench 改造

### Session 投影

扩展现有 Host 投影，不创建新领域。一个投影存储简报、所选团队和工作流快照、按顺序排列的 attempts、最新活动快照、新鲜度和可选 `pendingAction`。

停止前，Host 把规范停止意图和幂等 key 追加到持久 Session 状态。纠正后派发前，Host 追加完整已确认简报和新的 `client_request_id`。只有该事件持久化后才进行网络调用。

应用启动时，Host 扫描已知非终态工作投影和未解决动作。它使用相同停止 key 重放，或用同一个 request id 查询 `dispatch_status`。不需要模型轮次。

### UI

实现继续放在现有 Workbench bundle 和 `ui-weave` 包中。只增加：

- 当前工作面板中的 attempt 历史；
- 有界成员和运行时活动细节；
- `停止这个 run`确认；
- 陈旧和数据不完整标记；
- 观察到的终态事实；
- 完整简报修订和派发确认；
- 精确 run 交付物卡片和内容访问。

第一期不增加第二套任务导航、通用活动流框架、专用 controller 包或新命令数据库。

## 交付计划

### Slice 1——证明 Weave 事实

固化所有现有 TeamRun 取消状态和竞态。增加精确 run 活动、幂等停止、交付物 `run_id` 过滤、授权、审计、HTTP 覆盖和最小 MCP 变更。

### Slice 2——完成现有 Workbench 投影

在现有投影和 UI 中增加 attempt 历史、一个 `pendingAction`、启动恢复、活动检查、停止、修订、纠正后派发和精确 run 交付。验证 Browser 关闭和前台 Agent 取消不会改变 Weave 执行。

### Slice 3——验证真实 FDE 工作

通过 Codex MCP 和 Workbench 运行一条持续时间足够长的日冕分析任务。执行期间检查成员和运行时，制造一次停止响应丢失，关闭并重新打开应用，到达权威取消终态，修订简报，启动新 run，并验收属于该 run 的纠正后交付物。

如果这个场景暴露 run 身份歧义、取消后迟到结果获胜、跨 run 交付物或需要模型轮次才能恢复，发布就停止。

## 验证

所需测试只覆盖可能证伪产品承诺的失败模式：

1. queued、running、parked、cancel-requested、所有终态、宽限过期、旧 generation、旧 lease 和迟到完成；
2. 未知响应前后相同 key 重放和载荷变化冲突；
3. 活动、HumanTask 和交付物的精确 run 隔离；
4. 停止和纠正后派发期间的 Session 销毁、Browser 关闭、Host 重启和应用重启；
5. 工作中、陈旧、已请求停止、正在停止、已停止、已完成和失败的 UI 真值表；
6. Codex MCP 与 Workbench 对同一真实 run 的一致性；
7. 真实日冕纠正后交付物场景。

## 考虑过的替代方案

**现在创建独立 WorkTask 领域。** 它改善未来多团队聚合，却在首个单团队控制闭环得到证明前复制持久化和恢复。

**增加命令状态接口。** 重放同一幂等停止并读取活动可以解决相同的不确定性，同时少一个合同。

**增加成员级纠偏。** 没有服务端栅栏时会制造误导性承诺；完整修订简报和新 run 才是诚实做法。

**增加通用重放策略。** 把试点限制在一条已知无副作用工作流，比发明不完整的副作用治理更小。

## 验收条件

- 一个已确认的单团队工作项在关闭对话和应用后继续存在，同时 Weave 持续执行。
- 重新打开后无需模型调用即可看到权威团队、阶段、已知成员活动、运行时、HumanTask、交付物和新鲜度。
- 整 run 停止具有幂等性，并且在 `cancelled` 或 `abandoned` 前绝不报告已停止。
- 未知停止响应使用同一个 key 恢复；未知派发使用同一个 `client_request_id` 恢复。
- 观察到的终态事实不包含因果、回滚或制品有效性声称。
- 修订从完整已确认简报创建新 run，并保留旧 run 和输出。
- Workbench 不持久化重复 run 状态机，每个工作项最多有一个未解决本地动作。
- 第一条真实日冕场景以属于纠正后 run 的纠正后交付物结束。

## 风险

使用 Session 投影意味着第一期持久性依赖保留的本地 Session 数据。这符合当前单安装产品，并会被诚实说明。

停止整个 run 可能浪费未提交工作。是否值得为无损干预另做设计，由产品证据决定，而不是由架构偏好决定。

把第一条工作流限制为没有不可逆写入会缩小试点范围。它避免把一个布尔值或三态策略假装成真正的副作用账本。

现有内部取消路径可能还没有保护所有迟到制品竞态。特征测试失败会阻断发布，必须在 Weave 中修复，不能藏在 Workbench 里。
