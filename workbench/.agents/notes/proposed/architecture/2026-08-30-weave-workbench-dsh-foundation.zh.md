# Agent Note: 基于 DeepSeek Harness 构建 Weave Workbench

Status: proposed

[English](2026-08-30-weave-workbench-dsh-foundation.md) | 中文

## 问题

Weave 已有可靠的团队执行服务，但产品界面重复实现了编码智能体已有的能力，包括对话、任务理解、规划、工具呈现和项目导航。保留第二套通用应用会迫使用户学习两种交互方式，也会让 Weave 持续维护核心职责之外的产品代码。

Codex 已经通过 MCP 证明了预期的 Weave 使用流程，但只依赖 Codex 无法提供由 Weave 自己发行的桌面应用、模型供应商选择和交互设计。从空壳开始构建这套应用，则必须先重新实现会话持久化、模型流式输出、工具调用、审批、终端、设置和打包，之后才能验证第一项 Weave 任务。

## 提案

Weave Workbench 是一个从 DeepSeek Harness 派生的独立应用仓库。仓库固定上游提交 `cd5ef8148158c3a752a658978873241fdf8e2bbc`，通过只读的 `upstream` 远端跟踪官方项目，并将 Weave 修改保存在自己的分支和未来的私有 `origin` 中。部分克隆保留该提交的完整 Git 树，源码内容按需下载。

DeepSeek Harness 负责前台交互运行时，包括对话、模型供应商、会话、工具调用、审批呈现、终端访问、设置和桌面打包。Workbench 修改品牌并组装 Weave 配置，不替换 DSH 智能体循环，也不创建平行的应用框架。

Workbench 只在自己的 profile 边界移除面向开发的 DSH 呈现，不显示内测与官方提供方首次引导弹窗、预览版标记、官方品牌、Subagent 呈现、消息反馈和轨迹检查器。底层运行服务保持完整，非 Workbench 的 DSH 构建继续保留原有行为。

Weave 继续作为业务执行服务。Workbench 智能体通过公开 Weave MCP 工具执行业务动作，Host 侧强类型客户端则按照[持久 WorkTask 提案](2026-08-30-weave-workbench-durable-work-task-domain.zh.md)观察和控制已经关联的工作，无需模型轮次。普通诉求遵循唯一产品流程，即检查团队、确认执行简报、通过所选团队的默认工作流派发、仅在人工任务暂停时请求用户输入，并在完成后读取最终交付物。Workbench 可以把多次团队运行聚合到一个复杂 FDE 目标下，但每项持久运行和交付物都由 Weave 负责。

MCP 集成通过操作系统凭据或进程级环境值，只向本地 Weave MCP 子进程提供 `WEAVE_API_KEY`。该密钥用于授权产品 API 调用，并且可以轮换或撤销。`WEAVE_SECRET_KEY` 始终留在 Weave 服务端，因为它用于加密由服务端管理的凭据；Workbench 进程、模型、工具输出、日志和设置都不能收到该密钥。

面向用户的运行状态只有 `queued`、`running`、`yielded`、`completed` 和 `failed`。Weave 自有的浏览器插件会逐步用范围明确的产品卡片替代通用 MCP JSON，同时始终以已记录的工具结果作为唯一权威。团队卡片把 `team_list` 呈现为候选事实与默认工作流可用性，既不虚构选中结果，也不显示内部健康度观察。最终交付物卡片把 `deliverable_get` 呈现为带标题的文件，直接显示已记录的完整正文，并提供浏览器下载操作，但不会暗示远端 Weave 产物已经存在于本地工作区。后续的派发和人工任务卡片呈现五种产品状态，并保留运行标识和人工任务标识。Weave 的详细生命周期分类继续作为诊断元数据，不扩展为额外的产品状态。

Workbench 不增加团队编辑、工作流编辑、评测运行、构建候选或治理页面。团队创建仍由 MCP 对话完成，并在用户确认后进行一次声明式提交。现有 Weave 应用暂时保留为运行时运维台，直到 Workbench 能够呈现节点注册、连接状态、容量、引擎支持和故障状态，并且不导入 Weave 的内部编排代码。

实现分为三个可独立使用的增量。第一个增量构建未修改的 DSH 桌面和 Web 应用并记录冒烟基线。第二个增量加入 Workbench 品牌、内置 Weave MCP 配置、凭据设置和产品状态工具卡，同时保持上游智能体循环不变。第三个增量只把多运行时运维视图迁入 Workbench，并在完成等价性验证后移除独立的 Weave 控制台。每个增量都基于具名上游提交执行变基或向前合并，并保持 Weave 修改可以与上游代码分离审查。

## 备选方案

**只使用 Codex 作为界面。** 这仍是最快的集成方式，也是 MCP 行为的参考客户端，但产品无法控制发行、模型供应商选择和 Weave 专属交互。因此 Workbench 必须保持 Codex 兼容，而不能取代 Codex。

**扩展现有 Weave Web 应用。** 这套代码已经拥有运行时数据，但要成为编码智能体界面，仍需新增会话运行时、工具协议、审批模型、终端、供应商系统和打包层，也容易让 Weave 内部管理概念重新进入用户流程。

**从零构建最小桌面壳。** 更小的初始代码库可以提供完全控制，但早期工作主要是在复刻已有的 Harness 基础设施，而不是验证 Weave。只有当 DSH 上游集成成本反复高于保留能力的重建成本时，这个方案才更合适。

**只嵌入 DSH 软件包而不派生仓库。** 软件包级复用能减少显式分叉，但 DSH 是预发布单体仓库，受支持的应用启动由配置负责，相关软件包也会共同演进。派生仓库能够保留经过测试的组装方式，并让上游变化作为 Git 历史接受审查。

**把团队和工作流编排移入 Workbench。** 这可能让客户端看似自包含，但会为重试、人工等待、终态和交付物建立两个权威来源。Workbench 协调用户意图，Weave 仍是唯一的持久执行权威。

## 验收标准

- Workbench 仓库标明固定的 DSH 提交，保持 `upstream` 只读，并能从该提交物化任何省略的源码路径。
- 在开始 Weave 专属运行时修改前，未修改的基线构建可以启动受支持的 DSH Web 或桌面入口。
- 内置配置可以启动本地 Weave MCP 服务，且不会把 `WEAVE_SECRET_KEY` 复制到应用配置、模型上下文、工具结果或日志中。
- 用户可以在一次 Workbench 对话中完成 `team_list`、`team_dispatch`、可选的人工任务处理和 `deliverable_get` 流程。
- `team_list` 以候选业务事实而非原始 MCP JSON 呈现，不会声称某个候选已经被选中，普通界面也不会显示内部健康度观察。
- `deliverable_get` 直接呈现标题、推断出的文件名、完整记录正文和下载操作，用户无需检查原始 MCP JSON。
- 运行呈现只依据 `queued`、`running`、`yielded`、`completed` 和 `failed` 分支；诊断生命周期数据可以检查，但不阻塞使用。
- Workbench 不包含重复的团队、工作流、评测、候选或治理应用页面；多运行时界面迁移必须先取得明确的等价性证据，才能移除独立控制台。

## 风险

DSH 是不提供兼容承诺的 alpha 基础。上游变化可能调整软件包、配置、会话格式和界面组合，因此 Workbench 必须固定每个集成点，把修改限制在狭窄的插件或配置中，并为定期上游协调预留成本。

本地配置的 MCP 子进程仍可能通过不当诊断或子进程继承泄露 API 密钥。集成必须遮蔽授权值、限制密钥权限、只把它传给 Weave MCP 进程，并验证会话日志和模型可见事件不包含任何凭据材料。

DSH 的默认产品假设可能与 Workbench 术语或任务流程冲突。如果工具结果仍以基础设施为中心，仅修改品牌并不足够；但深入修改智能体循环又会提高上游同步成本。因此，在反复出现的用户证据证明需要插件级呈现改动以前，Workbench 接受部分通用 DSH 交互。

同时保留 Codex 和 Workbench 两种客户端，会增加 Weave MCP 的合同压力。这项成本是有意承担的，因为任何客户端都不能依赖隐藏数据库状态或客户端专属回退，而且两者必须观察到相同的运行和交付事实。
