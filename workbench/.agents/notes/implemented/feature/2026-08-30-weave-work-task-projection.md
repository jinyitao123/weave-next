# Agent Note: Weave work-task projection in the conversation shell

Status: implemented

English | [中文](2026-08-30-weave-work-task-projection.zh.md)

## Problem

Workbench recorded team discovery, dispatch, status, human-task, runtime, and deliverable calls as separate conversation rows. A user had to inspect tool names and opaque ids to determine which team was working, whether the workflow had started, where it was blocked, and whether a visible deliverable belonged to the current run. The details column stayed empty until the user selected one tool call, so the page hid the operational state that a long-running FDE task requires.

## Decision

`ui-chat` declares `conversation.details.summary` and renders it whenever no individual tool call is selected. `ui-weave` occupies that slot with a work-task projection and contributes a compact status control beside the Session title. Task detection does not open the surface by itself. Activating the status control uses the layout's explicit focus-details action: the global sidebar remains, the conversation yields its track, and the work scene becomes the primary content surface. Selecting a generic tool call can still use the ordinary details geometry and replace the summary with the existing input/output inspector.

The team overview presents members as compact navigation rows rather than expanding their full traces inline. Selecting a member opens a dedicated in-surface work view with that member's assigned runtime, workflow stages, bounded tool input/output, observed inputs, and output references. The view is derived from the same WorkTask projection and does not create a second Session or invent private reasoning. When Weave reports that the run can accept a correction, the member view targets the existing correction request at that member; otherwise it states that intervention is unavailable at the current stage.

The projection folds the loaded Chat nodes without querying Weave. It correlates team discovery, the unique dispatch, status reports, human tasks, runtime records, and deliverables by their recorded fields. Dispatch status owns workflow lifecycle and progress; terminal-run status supplies secondary runtime health, so a `terminal_missing` projection cannot overwrite an authoritative `queued 0/9` dispatch. A deliverable contributes to the task only when its `run_id` equals the active run. Opaque ids remain in a collapsed diagnostic section. A queued dispatch, failed run, missing terminal, or failed attempt to treat the selected team as an agent becomes an explicit blocker instead of generic tool history.

The shared layout keeps its center-width concession rule for ordinary details. When that rule reduces an explicitly opened ordinary details track to zero, the details surface becomes a right-side drawer instead of disappearing. Focus details deliberately bypass that drawer: it assigns the space after the sidebar to details, hides the center track, and removes the details drag handle until ordinary details is opened again.

The Session log remains the durable source for this presentation. The Workbench Host registers a `workTask` projection that folds team discovery and dispatch results, then uses the dispatch's `client_request_id` to poll Weave independently of the foreground agent turn. Every synchronized update is appended as a whole `weave/work-task` snapshot and flushed before publication. Weave remains the execution owner; Workbench owns only durable correlation, status recovery, and presentation. Transient network failures preserve the last known state instead of inventing a terminal failure.

Initial dispatch obtains its brief from Host-frozen original user messages. A model-authored copy cannot establish that it contains the current invoice, attachments, or constraints, even when it matches the text shown in the task panel. The Host owns the input revision and dispatch request identity; Weave fixes the published workflow and consumes the revision atomically with admission. The panel reads the resulting Host event. Explicit reruns share this path and retain the exact edited brief from the user action. Interface-generated instructions use the existing plugin source with `ui-control`, including child-session forwarding, because their conversational role does not make them user-authored business material.

Before every request or accepted-result replay the Host flushes the Session, including after a prior flush failure. Retrying an unknown result reuses the same registration and request, including after authentication or transport rejection. Only explicit pre-registration selection errors release an unregistered request. New user input changes that retry into atomic reconciliation: Weave returns the admitted run or closes the unused revision under the same admission lock. A late dispatch cannot reopen a closed revision. This operation does not cancel an admitted run and does not establish that earlier user material may be discarded.

One Session retains ordered run attempts and at most one `pendingAction`. A team-card selection asks the conversation to prepare a complete dispatch brief but creates no remote side effect. The Host persists whole-run stop commands before calling Weave. A fanout stage that Weave classifies as an infrastructure failure remains attached to its parked parent and exposes one exact-stage retry. The team overview promotes that recovery above whole-run rerun, identifies the affected member and stage, and states that successful sibling stages and outputs remain preserved; the same action remains available in the member work view. Workbench requires the stage to be failed, infrastructure-classified, and explicitly retryable before either the browser route or the model-free command can enqueue recovery. Work-product and verification failures never receive that retry control. After Weave reaches a terminal state, the user can edit the complete brief and confirm a new request and run. The prior run and its outputs remain visible. Member-level pause remains outside this phase.

The global DSH sidebar exposes the Weave runtime registry in every Session, while an active WorkTask shows only the nodes used by that task. Its entry projects available and registered counts with a health signal. An authenticated Host route returns only node display, health, capacity, engine identity, authentication mode, binary version, and scheduling facts and accepts bounded create, configure, and delete requests. The business API key remains on the Host; only a new runtime token crosses to the creating browser, once. Task controls use a dedicated Host route that appends WorkTask actions directly instead of creating command records in the conversation. Earlier command-backed action records receive a business-event presentation, while complete task briefs remain collapsed until requested. Runtime registration and scheduling belong to this surface, while starting or stopping a machine-local worker remains outside its authority.

Session list rows consume the same projection and show the owning team plus stage count. The right panel prefers the Host projection for lifecycle facts while retaining richer stage detail from loaded Chat nodes. Closing or navigating away from the conversation therefore no longer freezes the task status.

The Host correlates the nested `team` record in `team_status` with the dispatch team ID, including teams created from YAML. Replay restores that observed name even when an earlier persisted task snapshot omitted it; a missing name can also be resolved by an authenticated exact-team read. A poll publishes the current member failures independently of supplemental read success and settles a terminal run only after member activity and deliverables are read. Its own snapshot event cannot schedule an immediate poll: the active operation retains ownership of the configured interval. This prevents changing elapsed-time fields from turning durable publication into an unbounded request loop. Recorded-event projection snapshots and Host tests cover team-name recovery, failure retention, retry settlement, and polling cadence.

## Alternatives considered

**Replace the conversation with a dedicated task application.** Rejected because the existing three-column shell already provides navigation, conversation, and a resizable details column; replacement would discard working input, history, tool inspection, and deliverable presentation before the task lifecycle exists on the Host.

**Let the model summarize task state in assistant messages.** Rejected because model prose can omit, confuse, or stale run identity. The browser derives task state from recorded tool facts and keeps assistant prose as explanation only.

**Let the model submit both task text and its digest.** Rejected because two matching model-controlled values do not prove which user message authorized the work. Host-owned source references and exact bytes remain necessary.

**Treat a missing status lookup as proof that dispatch never happened.** Rejected because a concurrent request can enqueue after the read. Reconciliation closes an unused revision atomically with admission, while preserving an already admitted run.

**Count every visible deliverable.** Rejected because `deliverable_list` can return files from another run. The panel prefers an empty current-task state over displaying an unverified file.

**Expand complete member traces inside the team list.** Rejected because long tool activity turns an overview into a narrow debugging accordion, makes adjacent members hard to compare, and causes the right-side surface to obscure the conversation. Compact navigation preserves the overview while the dedicated member view gives detailed activity enough space.

## Consequences

Input identity is independent of the chosen CLI or Loom executor. The implementation preserves a window of unconsumed user messages; it does not infer whether a later message starts an independent task or amends earlier work. Closing an unused revision therefore preserves its source material. Explicit task targeting, independent delivery verification and free-collaboration input binding are separate obligations. Legacy raw HTTP dispatch remains outside this input-source guarantee.

Weave sessions expose team, progress, runtimes, blockers, failure classes, human decisions, completeness, ordered attempts, and exact-run deliverables without requiring users to expand tool calls. Opening the work scene is an intentional navigation action and no longer interrupts an active conversation; member activity remains inspectable and targetable without forcing the whole overview into a narrow column. The same surface manages registered runtime nodes without exposing the Weave business credential or pretending to control local processes. A user can stop the whole run, request an allowed member correction, recover an externally disconnected stage directly from the team overview, and create a new run from a complete revised brief without a model call; persisted pending actions recover unknown network outcomes. Exact-stage retry deliberately preserves the original frozen stage input, completed sibling stages, and prior outputs, and does not apply to professional or verification failures. The member work view is a projection-scoped interaction, not an independent durable agent conversation. This phase remains bounded to one team and workflows without irreversible external writes.
