# Agent Note: Workbench wait and delivery facts

Status: implemented

English | [中文](2026-09-05-workbench-wait-and-delivery-facts.zh.md)

## Problem

Workbench collapsed every parked run into one waiting label and retained retry buttons from old failure events after the run resumed or stopped. Execution completion could appear beside stage files without making the absence of final delivery explicit. The team-routing prompt also bypassed the task confirmation requested by the team chooser.

## Decision

The existing WorkTask projection carries Weave's wait kind and exact wait node. A current infrastructure failure with Weave's exact reconnect-and-stop-confirmation reason remains an explained wait even while retryable is false. The conversation, scene, and member record identify the affected stage and explain reconnecting the runtime and waiting for acknowledgement. The retry control appears only after the existing projection reports eligibility; unrelated or historical failure text does not establish this wait. The browser explains timed pauses, team stages, human answers, correction confirmation, and runtime interruption using the existing task status. The Host and browser restrict stage retry to a current recoverable wait and the matching runtime node or fanout branch. Human decision counts use the exact-run response and clear when execution resumes or ends. An abandoned run is not a confirmed stop; only Weave’s explicit `stop_unconfirmed` fact from the matching cancellation transition permits the stop-unconfirmed explanation.

Execution status remains authoritative. A completed run without a final deliverable receives an explicit unconfirmed-delivery label in the task panel and header; stage files remain readable. Final delivery follows Weave's `artifact_kind=final`, including the filename-free deliver-node outputs grouped as summaries. The status label and completeness warning share that definition; a summary does not imply a missing file bundle. Unknown or stage artifact kinds never qualify through their title, node type, or absent filename. The foreground prompt checks final delivery separately from execution completion.

Both the shipped profile persona and the Host routing section require confirmation of the selected team, task scope, and expected deliverables before dispatch. Explicit confirmation already present in the conversation is sufficient. Internal construction and evaluation create no additional user approval steps.

The work scene remains one existing page with Progress and Outputs tabs. Work in flight emphasizes members and available actions. Failed work opens member progress and shows the failing stage and a localized explanation in the scene and conversation receipt, with the original reported cause available on demand. Completed work opens delivery; stopped work opens delivery only when outputs exist. Missing team names on dispatched runs never imply ongoing team matching. Resize separators declare a pixel range matching their pixel value so assistive technology does not clamp every wide column to 100. Documents render in place, with Markdown formatting, inert SVG images, and sandboxed static HTML. The authenticated download route streams the complete retained artifact instead of relabeling a truncated preview as a full file. No generated prose establishes a live application URL. A task with missing final output remains neutral and offers a review of existing work before a separate rerun action.

The existing conversation input dock holds one compact current-run receipt, available actions, and direct output entries. It does not mount the complete scene, deliverable list, member record, or rerun panel. Human and correction forms and durable operation history expand only on request, keeping ended tasks compact without removing in-conversation recovery. Actual layout focus and narrow-mode facts make full-width, side-by-side, and return-to-conversation actions mutually appropriate. The task header preserves visible team and status while stage counts stay in its tooltip. Human questions use the real task schema and exact completion API; complex response schemas stay in discussion instead of receiving a guessed answer field. Corrections retain the request, affected and preserved stages, confirmation, and actual applied/discarded outcome. Member proposals use the existing reference-chip insertion protocol, preserve existing draft text and references, and serialize exact run/member/stage/output identities only when the user sends. Ordinary questions do not submit adjustments. Cross-Session project navigation waits until the target task view commits before opening the scene.

Member following is a browser preference for up to three members, not another conversation or execution owner. Status dots pulse only for fresh execution facts, including fanout with an observed running member; active member names and a brief highlight on the latest public record make actual work visible. Stop-confirmation waits, stale facts, stopping, and terminal states disable this feedback. Reduced-motion preferences disable both animations. No timer produces invented progress or placeholder text, and these effects neither move focus nor change the reading position. Public updates contain only observed public text and tool events; actual runtime capability controls whether updates arrive during execution or after stage completion. The reader's historical scroll position survives incoming records. Transport completeness and truncated records remain visible and independent of final delivery. Read-only project activity derives solely from explicitly associated Workspace Sessions, deduplicates identical runs by observation, excludes archived or unassociated Sessions, and links back to the same task and outputs.

The shell defaults to a remembered side-by-side split, offers explicit full width and narrow-screen view switching, and preserves the composer and mounted scene. Keyboard resizing and storage-unavailable fallback remain usable. The sidebar separates current task status from historical conversation entries, recognizes stopping/stopped, retains active tasks beyond a collapsed history limit, and requires final delivery before labeling a task delivered. Workbench folds technical usage into an optional disclosure and uses business-language permission labels without changing permission enforcement.

Each Session serializes background polling and guards writes with the current run and pending-action identity. Delayed reads preserve new user actions and local assessments. Only actual action responses create acceptance or rejection receipts. Retry requests retain one durable idempotency key across response loss, and human answers retain the server’s stable interaction identity, including when a later question replaces an old form. Disposal aborts in-flight reads and prevents rescheduling.

CSV/TSV previews use the existing parser with a visible 200-row/40-column limit and an actual complete download; SVG images provide bounded zoom. Member and tab navigation retain selection and up to 100 reading positions, including unread state while scrolling away from new updates. Project links select the exact artifact.

## Alternatives considered

**Introduce a separate recovery lifecycle.** Rejected because Weave already owns run status, wait identity, and stage retry eligibility. A second lifecycle would give the browser another state to reconcile.

**Treat every retained infrastructure failure as retryable.** Rejected because a historical failure does not authorize retrying a running, stopping, or terminal task.

## Consequences

Users can distinguish why work stopped and which action is available. A server response without an identified recoverable wait does not expose a retry button. An absent final deliverable remains an explicit delivery gap without changing the recorded execution outcome. Owning regression cases cover exact-run projection, response payloads and receipts, repeated updates, keyboard navigation, reference insertion, deferred project navigation, safe content handling, and the shipped CLI profile. The earlier three-batch verification closed 482 distinct focused cases across the initial run and targeted reruns, plus the shipped profile check; offline frozen installation, type checking, focused lint, and the Workbench build passed. Subsequent real-interface feedback exposed an oversized input dock, so that surface was reopened. The final visual integration passed 109 UI/projection cases, 32 frame and 24 conversation-shell cases, the shipped profile check, type checking, focused lint, and a fresh Workbench build. The UI cases include 31 recovery/component checks, with eight added compact-receipt and in-conversation action cases. These checks used no model calls and do not substitute for actual browser acceptance of the rebuilt interface, which remains with the coordinating agent.
