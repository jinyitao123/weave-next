# Weave 经 Codex 使用的产品方向与合同

> 日期 2026-08-29  
> 状态 v1 定稿  
> 适用范围 Codex 桌面端经本地 Weave MCP 使用团队

## 产品位置

Weave 是 Codex 背后的团队执行层。用户向 Codex 说明想完成的工作，Codex 理解诉求、拆分工作并选择团队。Weave 保存可以重复使用的团队，按冻结的工作流执行任务，在需要人参与时暂停，最后保存可读取的交付物。

这条边界决定了产品应当怎样长。Codex 已经拥有理解上下文、讨论方案和综合多份结果的能力，Weave 无须再增加一个负责理解用户的路由智能体。Weave 要把执行事实保存好，让同一支团队可以反复接活，让一次派发可以追踪，让完成的工作一定留下交付物。

普通用户只接触四个动作。

```text
提出诉求 → 匹配团队 → 必要时人工确认 → 读取交付物
```

建队过程、工作流版本、运行快照、评测报告和健康信号仍可保留。这些内容服务维护和追溯，不进入首次使用的必经路径。

## Codex 与 Weave 各自负责什么

| Codex | Weave |
|---|---|
| 理解用户诉求和当前上下文 | 保存团队及成员配置 |
| 判断一项工作是否需要拆分 | 保存并执行默认工作流 |
| 按工作包匹配合适团队 | 冻结每次派发的版本与输入 |
| 发现能力缺口并同用户讨论 | 记录运行状态和人工等待节点 |
| 组织多个团队之间的先后关系 | 保存阶段产物与最终交付物 |
| 汇总多个团队的结果 | 提供可追踪的运行和用量事实 |

Codex 负责判断，Weave 负责可靠执行。两者之间以 MCP 工具合同连接，不共享一套隐藏的规划状态。

## 产品界面边界

Codex 是普通用户唯一的工作界面。提出诉求、匹配团队、人工确认和读取交付物都在 Codex 中完成。Weave 不再提供与 Codex 重复的对话、项目、团队、工作流、评测或交付物页面。

Weave 只保留多运行时管理台，用来注册和管理分布在不同机器上的运行节点，查看节点连接、容量、引擎能力和故障状态。该页面是基础设施管理入口，不承担业务工作入口。团队、工作流、运行和交付等后台能力继续存在，并通过 MCP 与 API 服务 Codex。

## 一项普通任务怎样完成

Codex 收到诉求后先调用 `team_list`。返回内容应当足够完成匹配，包括团队目标、主要场景、成员职责、成功标准、默认工作流是否可用和近期健康信号。成员内部提示词和冗长上下文不参与匹配，也不应出现在这一步。

Codex 只有在团队与任务明确相符时才调用 `team_dispatch`。默认使用团队已经发布的工作流。找不到默认工作流时，Weave 返回明确错误。系统不能静默改走 `free_collab`，Codex 也不能为了让流程继续而随意换一支只能部分覆盖需求的团队。

派发后的产品状态统一为 `queued`、`running`、`yielded`、`completed` 和 `failed`。短时间内没有完成时，调用返回当前进度，后续继续查询。工作流到达人工节点后进入 `yielded`。Codex 读取人工任务，只把工作流声明的问题交给用户，收到答复后继续执行。

状态变成 `completed` 后，Codex 在 `deliverable_list` 中按运行标识找到对应产物，再用 `deliverable_get` 读取最终内容并返回。运行成功却没有最终交付物属于执行失败，不能向用户报告完成。

## 没有合适团队时怎样处理

Codex 应当说明当前团队覆盖到哪里，还缺少什么。随后在当前对话中讨论团队目标、成员分工、默认工作流和交付标准。用户明确确认后，Codex 生成团队 YAML 与声明式工作流，通过 `team_create` 一次提交。

确认后的团队创建只做确定性检查。模板与工作流结构合法、引用完整、输入输出闭合，团队就可以进入 `ready`。团队将来运行任务时可能产生的预算，不参与这次物化判断。评测也不决定团队能否开始接活。

这段讨论无需单独的团队设计智能体，也无需保存候选提案。当前 Codex 对话已经保留了用户意图和修改过程，再复制一份规划状态只会增加恢复、同步和失败归因的负担。

## 复杂 FDE 工作怎样组织

复杂项目可以使用多支团队。Codex 先把诉求拆成能独立验收的工作包，再为每个工作包分别匹配团队。多个派发使用同一个 `project_id`，各自保留运行与交付记录。

例如，一个完整的 FDE 项目可能先由需求研究团队梳理业务与约束，再由方案设计团队形成实施路径，技术验证团队检查可行性，风险团队独立审查。Codex 决定这些工作包之间的先后关系，也负责把多份交付物整理成用户可直接采用的成果。

Weave 不保存另一套项目监督状态机。工作包的执行事实已经存在于各团队运行中，项目归属由 `project_id` 表达，跨团队判断留在 Codex 当前任务里。只有真实使用证明 Codex 无法稳定恢复这种协调关系时，才讨论新的持久化能力。

## 哪些约束继续保留

轻量化不等于放弃运行边界。以下检查仍然保护真实风险。

- 调用者必须拥有相应权限。
- 团队必须处于可用状态。
- 工作流必须属于被派发团队，并且版本已经冻结发布。
- 工作流引用的成员必须存在且可用。
- 同一幂等键不能代表两组不同事实。
- 人工节点必须由有权处理的人完成。
- 输入输出结构必须符合工作流合同。

评测、认证、候选运行、模板预算配额和构建过程展示不承担上述职责。它们不能阻塞确认后的建队、普通发布或日常派发。

## 评测与健康信号的位置

评测用于回答某个冻结版本在受控场景中的表现。健康信号用于观察近期真实运行是否稳定。两者都可以帮助维护团队，不能代替用户对具体交付物的判断。

首次用户无须了解这些机制。团队列表最多展示简短的只读健康提示。出现告警时，Codex 可以提醒用户，并继续由用户决定是否使用。只有团队核心运行依赖确定性损坏时，团队才进入 `needs_repair`。

## 当前阶段的产品验收

接下来的开发以真实使用结果判断优先级。每次验收只记录四类失败。

1. 匹配错误。Codex 选错团队，或已有合适团队却判断为缺失。
2. 能力缺失。现有团队无法覆盖工作，讨论后需要新建或修改团队。
3. 执行失败。工作流、运行时、成员调用或人工恢复没有按合同完成。
4. 交付失败。运行显示完成，但最终产物缺失、不可读或无法对应本次任务。

新功能必须能修复反复出现的真实失败。单次使用没有遇到的问题，不提前增加 agent、路由层、提案表或治理流程。

## 黄金旅程

一项普通工作应当完整走过下面的路径。

```text
用户提出诉求
Codex 调用 team_list 并解释选择
Codex 调用 team_dispatch 使用默认工作流
如状态为 yielded，Codex 读取人工任务并询问用户
状态完成后，Codex 查找并读取对应最终交付物
Codex 把交付物返回给用户
```

复杂项目重复使用同一条路径。区别只在于 Codex 先拆出多个工作包，并让各次派发共享项目归属。系统仍然只有一套团队创建、一套派发和一套交付合同。
