结论：远程 Host 路线可以落地，但 v0.1 还没有把最关键的授权、持久接收和材料接缝冻结。首期如果直接依照现有工作包推进，容易先完成容器和登录，再返工调用协议。建议先补下列 5 项；它们都具有明确源码依据，所列故障反例尚未实际运行。

1. **先统一身份和组织成员政策，再做个人 Host 委托。**

   已证实：JWT 在 [middleware.go:69](<MAINTAINER_LOCAL_PATH>) 中读取 `weave_users.role`；[UserStore.Update:150](<MAINTAINER_LOCAL_PATH>) 只更新用户表；[RemoveMember:182](<MAINTAINER_LOCAL_PATH>) 只删除成员表。当前成员检查仅用于部分人工任务接口，[human_tasks.go:394](<MAINTAINER_LOCAL_PATH>)；运行与派发路由未统一接入该检查。

   反例：移除组织成员后，JWT 仍能通过认证；调用 `/runs/:id/stop` 时，[runs.go:1284](<MAINTAINER_LOCAL_PATH>) 将用户 ID 记为 `CancelActor`，并不由此证明当前成员资格。通过新网关拒绝访问，也不能改变旧 JWT 直调的政策差异。

   必要修正：在 P0 明确 `user account status`、`membership status/role`、`resource/action policy` 三者关系，建立共同的主体解析及授权入口，让 cookie、JWT、Host 委托消费同一政策。先确定普通成员对组织运行的读、停止、恢复权限，不能全部寄托于现有角色过滤。

   可验证出口：同一用户从 UI、MCP、直调 API 发起相同行为，移除成员或降权后结果一致；设备退出只影响对应会话。源码证明现有不一致，真实撤权行为仍待验证。

2. **动态凭据 provider 不足以表达“哪次操作获得了什么授权”。**

   已证实：[Gateway:203](<MAINTAINER_LOCAL_PATH>) 传递的是 `endpoint/payload/signal`；[MCP tools.ts:80](<MAINTAINER_LOCAL_PATH>) 的 `tools/call` 仅传 `name/arguments`。当前协议没有可信的来源 AuthSession、turn、操作授权上下文。

   更关键的是，[workbench-app:1159](<MAINTAINER_LOCAL_PATH>) 的后台 poll 会执行 stop、rerun、retry、人审答复和纠偏写操作，然后才做状态读取。它还不是方案中的“只读观察器”。

   反例：同账号设备 A、B 共享一个 Host。A 提交待处理操作后退出，B 仍在线。如果 Host 只领取用户级 token，无法判定该操作是否仍被允许；如果 token 绑定 A，后台读取与 B 的正常操作也可能被错误中断。

   必要修正：先冻结可信的 `OperationContext`，至少包含 actor、workspace、来源会话、conversation、operation/turn ID、目标和用途。区分即时用户操作、已持久接受的授权操作、后台只读观察。保留 stdio 可以，但需要受控元数据或本地代理承接每次调用上下文；不能让模型在普通 arguments 中填写授权。把现有 poll 的命令执行与读取拆开。

   可验证出口：双设备共享 Host，分别提交操作并撤销其中一个会话，实际 actor、撤销范围、已接受操作处置、后台观察均符合约定；重启后仍能还原授权来源。该接缝应成为 M0 的主要验证对象。

3. **材料路径必须提前验证，当前唯一产品派发接口没有材料引用。**

   已证实：[teamDispatchRequest:24](<MAINTAINER_LOCAL_PATH>) 和 [weaveclient.TeamDispatch:201](<MAINTAINER_LOCAL_PATH>) 都不包含 `attachment_ids` 或其他不可变材料引用；[workflowDispatchFingerprint:94](<MAINTAINER_LOCAL_PATH>) 因此也不冻结材料。

   已有附件能力可以复用：[attachments.go:67](<MAINTAINER_LOCAL_PATH>) 已保存 SHA256、大小和 created_by；但 [附件列表及读取:80](<MAINTAINER_LOCAL_PATH>) 仅以 tenant 过滤。已有 `ChatRequest.AttachmentIDs` 并不代表团队派发已贯通。

   反例：成员成功上传本机材料，调用团队派发时只能把附件 ID 或 Host 路径塞进任务文本。远端 Runtime 不一定取得字节；同一个幂等键也无法区分“相同任务文字、更换了材料版本”。

   必要修正：将最小材料纵向链路移入 M0，冻结“上传记录 → 明确归属 → 派发快照中的引用和摘要 → Runtime 获取”。优先复用现有附件目录，不另建通用材料平台。扩展派发契约时必须同步幂等指纹、运行快照、MCP 参数和 replay 判定。

   可验证出口：不同机器上的 Runtime 获取同一摘要的文件；改变材料集合后复用原幂等键必须冲突；同 tenant 的个人材料可见性符合明确政策。该缺口不是单独补上传 UI 能解决的。

4. **“服务器已接受”需要持久回执，当前 prompt 回执只代表进入 Agent inbox。**

   已证实：[SessionPromptValue:344](<MAINTAINER_LOCAL_PATH>) 明确定义为 inbox receipt；[commands.ts:303](<MAINTAINER_LOCAL_PATH>) 把 requestId 写入消息来源，调用 `agent.followup/steer` 后直接返回 `accepted: true`。[agent.ts:120](<MAINTAINER_LOCAL_PATH>) 同步插入 inbox 并唤醒运行；持久层则采用默认 200 ms 的后台批写，[coordinator.ts:31](<MAINTAINER_LOCAL_PATH>)。

   反例：客户端收到 accepted 后 Host 崩溃，该消息可能尚未持久保存；响应丢失时再次提交同 requestId，也不能仅因日志保存了 rpcId 就认定已经实现去重。当前入口也没有方案描述的 conversation revision 冲突控制。

   必要修正：将“请求已到达”“已持久接受”“已执行”明确分开。为 prompt 和任务操作建立可查询的持久接收记录；以稳定 operation ID 去重，参数不一致返回冲突；定义多设备的 revision 规则。调用桥只能消费可追溯的已接受授权。

   可验证出口：在回执前后分别强杀 Host、丢失 HTTP 响应、跨设备重复提交，最终恰有一条被接受的用户操作，或者明确显示未接受；不能静默丢失或执行两次。持久层本身有 flush 能力可复用，并不需要重写全部 Session 存储。

5. **数据库租约不能单独保证 JSONL 卷的唯一写者。**

   已证实：[JSONL appendLines:670](<MAINTAINER_LOCAL_PATH>) 使用普通文件追加、fsync，以及失败后的文件长度回滚，写入端没有 Host epoch 校验。方案虽声明 Host 租约和唯一写者，但未定义租约过期后如何阻断旧进程的文件写入。

   反例：旧 Host 与控制面失联或暂停，租约过期，新 Host 启动并挂载同一卷；旧进程恢复后仍能继续追加。旧写入的失败回滚甚至可能截断新写者已经追加的内容。这个风险来自普通文件存储与控制面租约的组合；尚未执行故障注入。

   必要修正：首期 5 个常驻账号可以采用**固定单机 Host 清单、每用户独立卷、串行替换进程**，无需同时交付通用动态 Host 调度。升级和恢复必须先确认旧进程退出、写入及挂载权释放，再开放新实例。若坚持自动租约接管，则要补真正的写入 fencing 或存储独占机制，不能只加 `lease_epoch` 数据库字段。

   可验证出口：暂停旧 Host、让租约过期并尝试启动替代者，再恢复旧进程；始终只有一个进程能改写该卷，日志连续且无双派发。测得常驻容量后，再决定是否值得增加自动按需启动。

建议实施顺序调整为：**统一授权政策 → 持久操作回执与授权上下文 → 两 Host 的身份/MCP/材料纵向小样 → 账号 Web → 桌面包装**。远程 Host 和独立卷值得保留；通用 Host 管理器可以后置。这会比先补齐全部外围状态机更稳，也更简洁。
