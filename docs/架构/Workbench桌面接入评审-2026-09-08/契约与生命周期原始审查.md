结论：v0.1 的方向可以实施，但目前有 **3 个会阻挡身份闭环或恢复验收的契约缺口，以及 1 个应收窄的数据模型问题**。最优改法是明确现有对象的责任和授权边界，减少新增的长期生命周期对象。

1. **“已接受 turn”还不是可用于持续授权的事实。**

   方案第 9.2 节说 turn 可按已记录授权继续，第 9.1 节又要求普通写操作受来源 AuthSession 约束。但目前没有定义：设备 A 提交 turn 后退出，Agent 下一步调用 MCP 是否允许；设备 B 同时在线能否代替 A 的登录态；Host 恢复后凭什么续做原 turn。

   源码的 `accepted: true` 只表示 prompt 已进入 Agent inbox。请求里的 `requestId` 被写成 `rpcId`，没有来源 AuthSession、权限用途或授权回执，返回前也未等待该消息持久化。[prompt 实现](/Users/jinyitao/Developer/weave-next/workbench/packages/api/session-controller/src/commands.ts:283)、[回执定义](/Users/jinyitao/Developer/weave-next/workbench/packages/api/session-controller/src/types.ts:344)。现有 `turn/start` 只记录 turn 序号。[SessionEvent](/Users/jinyitao/Developer/weave-next/workbench/packages/core/session/src/types.ts:223)

   **最简修正**：首期不要新增允许长期写操作的泛化 TurnGrant。由接入层给 prompt 和显式操作绑定不可由前端伪造的 `source_auth_session_id + request_id + principal`；Host/MCP 每次准备提交新的业务写操作，都以原来源会话检查当前权限，不能借用设备 B 的会话。关窗不撤销权限；退出后尚未提交给 Weave 的写操作停止并明确记录原因；已经被 Weave 接受的 run 继续。若确实承诺“accepted 后即使 Host 崩溃也不丢输入”，应增加持久 admission receipt，不能沿用现有 inbox ACK 作为证明。

   验收必须区分三个时间点：Host 排队、Weave 已提交但结果未知、Weave 已返回接受回执。测试在每个点退出账号，明确预期结果。

2. **现有 WorkTask 同步器同时承担命令提交、请求对账和运行观察，不能直接替换成 run 只读权限。**

   同一个 `poll()` 会执行 stop、rerun、stage retry、human complete、correction；随后再读状态。[写操作分支](/Users/jinyitao/Developer/weave-next/workbench/packages/bundle/workbench-app/src/index.ts:1159)。浏览器收到 204 时，仅完成 Host 日志落盘，业务请求由后台再提交。[Host 回执](/Users/jinyitao/Developer/weave-next/workbench/packages/bundle/workbench-app/src/index.ts:1113)

   而且观察目标不总是 run。创建阶段读 `build_id`；派发响应未知时读 `client_request_id`；之后才读 run，并补读团队摘要、人工问题、成果。[build 观察](/Users/jinyitao/Developer/weave-next/workbench/packages/bundle/workbench-app/src/index.ts:1143)、[请求与运行对账](/Users/jinyitao/Developer/weave-next/workbench/packages/bundle/workbench-app/src/index.ts:1242)。文档“仅限定已关联 run”的观察授权覆盖不了前两个阶段。

   还有一个必须修正的现状判断：同步器只监听 live Session，并在启动时遍历 `ctx.sessions.list()`。[启动入口](/Users/jinyitao/Developer/weave-next/workbench/packages/bundle/workbench-app/src/index.ts:1310)。这个 list 明确只返回内存中已经加载的会话。[SessionStore](/Users/jinyitao/Developer/weave-next/workbench/packages/core/session/src/index.ts:1048)。所以“关网页后 Host 持续同步”与“Host 重启后无人打开也恢复所有未终态任务”不是同一保障，后者仍需新增。

   **最简修正**：保留 WorkTask 状态机，拆分内部职责。命令提交器使用来源 AuthSession；观察器只能查询服务器已确认关联的 `build/request/run` 资源；请求结果未知时先查回执。Host 启动从持久历史或可重建索引发现未完成 WorkTask，恢复必要 Session 后启动观察。不要恢复 LLM turn 才恢复状态同步，也不要靠打开页面触发。

   核心验收是：关掉所有页面、重启 Host，任务仍在更新；撤销登录后观察器不能 rerun/stop/answer；派发超时后退出或重启，不会产生第二个 run。

3. **连接切换的 generation 目前只描述了页面竞态，没有闭合服务身份与副作用回执。**

   第 4.3 节的 generation 能防旧响应覆盖新页面，但丢弃 UI 响应不能判定旧写操作是否已经发生。第 11 节先读描述文件、再载入会话分区的方案，也需明确描述检查与请求发出之间发生部署更换的处理。

   当前下游客户端只冻结 URL/API key，并直接发请求，没有期望 instance 身份。[Workbench 凭据闭包](/Users/jinyitao/Developer/weave-next/workbench/packages/bundle/workbench-app/src/index.ts:959)、[请求提交](/Users/jinyitao/Developer/weave-next/workbench/packages/bundle/workbench-app/src/index.ts:1137)。因此 `instance_id` 校验应写入新契约，而不只留在连接设置元数据。

   **最简修正**：把 `{origin, instance_id, generation}` 定为一次连接选择的不可变快照，校验成功后再原子替换活动连接；描述文件检查、续期、上传完成、订阅重连均带 generation 判定。新会话和内部授权必须绑定服务 instance，客户端提交预期 instance，入口发现不匹配时拒绝业务处理并要求重新连接。切换时旧写操作不向新连接重试，其回执保存在旧服务归属下，下次进入旧服务再对账。没有必要为连接切换再造任务状态机。

   应增加“描述检查成功后、业务请求前替换服务”“旧派发提交后立即切换，响应迟到”的验收。文档现有“同一 origin 返回不同 instance_id”用例还不足以覆盖这两个竞态。

4. **ConversationBinding 需要收窄为索引，否则会成为第二个 Session/项目归属真相源。**

   新模型包含 `conversation_id、project_id、revision、created_at`，同时声称记录 Host/Session 映射，但未明确 conversation_id 是否等于 SessionId、revision 对应什么，或创建/分叉时 PostgreSQL 与 JSONL 哪边失败后如何恢复。

   现有 SessionHeader 已有 id、createdAt、cwd、parentSession；项目目录归属还有 WorkspaceRegistry 的 sessionIds。创建流程先生成 Session，再 attach workspace，失败会显式报告“Session 已创建但关联失败”。[创建流程](/Users/jinyitao/Developer/weave-next/workbench/packages/api/session-controller/src/commands.ts:72)。WorkspaceRegistry 还会从持久 SessionHeader 建立历史目录映射。[历史归属恢复](/Users/jinyitao/Developer/weave-next/workbench/packages/workspace/workspace/src/index.ts:421)

   **最简修正**：个人 Host 固定归属时，用户/组织所有权由受信 HostDirectory 和卷绑定证明；`conversation_id = SessionId`。新增平台 conversation 表只能是可重建发现索引，不再保存另一个对话 revision、标题或运行状态。项目映射选定一个权威存储，再由另一侧只读投影；如果首期不需要跨 Host 统一对话列表，可暂缓独立 ConversationBinding 表。这样能避免为账号上线额外承担跨数据库与 JSONL 的一致性协议。
