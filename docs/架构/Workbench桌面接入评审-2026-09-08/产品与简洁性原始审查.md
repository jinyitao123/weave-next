**结论：v0.1 可以作为“云端多用户 Workbench”的目标方案，但还不能称为满足原始需求的最小、优雅方案。主要问题是先加入跨设备连续工作，再用这个新增要求证明远程 Host 架构必要。建议保留远程路线候选，先收窄成静态专属 Host 试点。** 以下均为只读代码审查，未运行小样。

1. **“安装登录、默认连远端”不能直接推出“每用户一个云端 Host”。**

   原始需求要求默认连接与账号接入；文档却在第 15 行加入跨设备工作，并在第 81、238 行把它落实为多个设备共用服务端 Host。应将“对话是否必须跨设备可见、客户端关闭后监督 Agent 是否必须继续”标成新增产品选择。

   三条路径的真实取舍如下：

   | 路线 | 最适合的需求 | 主要代价 |
   |---|---|---|
   | 远程展示客户端＋云端用户 Host | 浏览器/桌面统一、跨设备对话、离线期间监督继续 | 服务器运行大量 Host，承担隔离、生命周期、存储、材料上传 |
   | 桌面内置个人 Host＋远程 Weave | 对话与材料以本机为中心；远程负责团队执行 | 本地依赖发行与升级；休眠时监督暂停；跨设备对话另议 |
   | 远程展示客户端＋静态专属 Host 试点 | 先验证安装、登录、改址、一次业务闭环 | 人工配置少量 Host；不承诺自动扩容和一般多用户服务 |

   第三项是远程路线的实施形态，不应成为另一套产品模型。当前 Compose 已有一个独立 Workbench 服务和持久卷，支持以此为起点：[docker-compose.platform.yml:114](<MAINTAINER_LOCAL_PATH>)、[157](<MAINTAINER_LOCAL_PATH>)。

2. **“业务运行关窗继续”与“监督进程常驻云端”应分开，否则会为错误理由支付最大的成本。**

   当前 Workbench 销毁时只终止自身轮询、清理计时器；这里没有发送取消 Weave 运行的命令。挂载时又会对已恢复 Session 重新安排后台同步：[index.ts:1316](<MAINTAINER_LOCAL_PATH>)、[1469](<MAINTAINER_LOCAL_PATH>)。

   因此代码支持的判断是：**本地 Host 退出本身不等于取消已经派发的 Weave 工作**，运行续行与重开对账仍须实测。真正区分两种架构的是“未完成的前台 turn、后台监督与跨设备对话”，不能拿已经独立的 Runtime 生命周期来替远程 Host 定案。

3. **账号身份贯穿 HTTP、MCP 和后台投影是必要改动；Host 调度平台和第二份对话元数据则尚未证明必要。**

   当前 `apiUrl/apiKey` 在 Host 启动时固定，多个功能共用同一闭包；Go MCP 持有同一个 weaveclient。这是所有路线都绕不过去的接缝：[index.ts:959](<MAINTAINER_LOCAL_PATH>)、[client.go:43](<MAINTAINER_LOCAL_PATH>)、[server.go:21](<MAINTAINER_LOCAL_PATH>)。

   但固定个人 Host 可以把 `instance/user/workspace` 归属绑定在部署配置和受认证路由上。首批静态部署不必同时建设 HostDirectory 数据库、动态 provisioning、分布式租约、自动管理器，以及重复保存全部 Session 映射。当前 Session 已有独立持久日志，而 prompt 已携带 `requestId`；新增 `workbench_conversations.revision` 前应证明它解决了哪个现有序号/提交机制不能解决的问题：[types.ts:61](<MAINTAINER_LOCAL_PATH>)、[commands.ts:303](<MAINTAINER_LOCAL_PATH>)。

   **不能删的是可验证的归属、权限和单写者约束；可以延后的是实现这些约束的通用平台。** 静态模式仍需防止重复进程挂同一卷，不能把“只有一个配置文件”当作证明。

4. **最优雅的首个实现切片应当直接展示用户想要的结果，再决定是否扩大云端化。**

   建议顺序：

   - 一个稳定服务入口、一个具名账号、一个静态专属 Host；验证完整入口认证、正确个人 API/MCP 主体。
   - 同一个桌面小样完成默认地址、显式改址后重启保留、真实登录、上传材料、派发、关闭重开、下载成果。
   - 第二账号使用第二个静态隔离 Host，检验对话、凭据、目录和导出不能互访。若准备向多人发布，这一步是发布前提。
   - 只有规模和跨设备需求成立后，再建设动态 Host 分配、租约/故障接管和集中索引。

   设备会话应保留撤销语义，但完整设备管理页、复杂并发轮换、跨设备写冲突和跨主机调度不必一起成为第一小样的先决条件。现有 BrowserAuth cookie 只包含 authority 与时间，没有个人主体，因此不能直接在现有页面上加登录按钮充当账号完成：[browser-auth.ts:27](<MAINTAINER_LOCAL_PATH>)。

5. **先设停止规则，才能判断方案优雅，原有 35–60 人日只能对应扩大的云端首期。**

   建议明确以下出口：

   - 静态个人 Host 能满足试点人数与资源预算，则停在静态配置，不立即实现 Host 管理平台。
   - 用户无需跨设备对话、需要大量本机材料且不接受上传工作流，则重新评估本地 Host。
   - 任一路线必须共用管理员业务凭据才能工作，则身份小样失败，不能包装发布。
   - 凭据更新必须中断进行中的任务、登录一刷新就要重启完整 Host，则连接接缝未成立。
   - 本地 Host 若不能在目标平台形成包含必要依赖的可安装发行物，则不能仅凭“本地天然隔离”认定更省事。当前运行镜像实际需要 Node、Weave 二进制及若干工具：[Dockerfile.workbench:33](<MAINTAINER_LOCAL_PATH>)。
   - 一个桌面框架通过所需交互与发行验证，另一框架没有可量化优势，就结束双框架比较。

   原计划把远程 Host 隔离、租约、恢复和调用桥合计估成 10–17 人日，总计 35–60 人日。它适用于该版本扩大的范围，不能据此告诉用户“默认远端连接和登录本身就需要这么大工程”。应先把身份接缝、桌面发行与静态 Host 小样做到可检查，再据实更新范围和估算。
