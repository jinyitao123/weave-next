# Weave 产品方案：十分钟拉起一支业务团队

> 日期：2026-08-25
> 状态：v2 定稿（已经 codex 只读审计 + 主审独立反查，见 §9）
> 读者：产品、工程、以及任何想搞清"Weave 到底要成为什么"的人
> 关联文档：[Weave 模块化边界与拆分顺序审定稿](./2026-08-25-Weave-模块化边界与拆分顺序审定稿.md)（工程保护网线，与本方案并行不冲突）

---

## 0. 一句话版本

**Weave 要成为多智能体协同的"电网"，而不是某一台电器。**

Loom 是发动机（五个原语：State/Step/Graph/Store/Hooks），Weave 是电网和变电站（调度、协同、交付、恢复），业务团队是插上来的电器。电器可以是 LLM agent、可以是人工节点、可以是外部系统——电网不关心。

这个方案的终极验收指标只有一个：

> **一个懂业务但不懂平台的人，十分钟内拉起一支能产出交付物的团队。**

---

## 1. 我们为什么必须变（问题陈述）

### 1.1 今天的主路径是一台"自动售货机"，但它只收一种硬币

今天想在 Weave 上得到一支业务团队，主路径是**元团队**（metateam）：一支平台内置的 AI 团队，你用人话跟它聊，它经历"架构师整理 BuildBrief → 冻结蓝图 → ChangeSet → 构建 → 候选运行 → 评测 → 发布"的长流程，最后给你一支团队。

这条路有三个结构性问题：

1. **慢。** 拉起一支团队要先开好几轮 LLM 会议。对"快速业务交付"这个目标，这是收费站，不是大门。
2. **脆。** 763 行的巨型角色 prompt（`internal/metateam/metateam.go`）里焊死了整个建造协议的细则——哪个工具什么时候调、brief 字段怎么填、什么不许说。协议每变一次，prompt 就得同步重写，而且只能靠 LLM 自觉遵守。
3. **焊死了。** 元团队本应是"建造机制的一个客户端"，但它被 `teamorch`、`teamforge`、`api` 共 7 处直接 import，产品和机制长在一起，想绕都绕不开。

### 1.2 但好消息：地基已经是通的

代码库自己会说话（经 codex 互审校正后的精确表述）：

- **合同层已 runtime 无关**：`internal/teamrun/types.go` 的类型体系（Status、Lease、Transition、WaitKind）通篇没有 model、prompt、skill 任何一个词；队列消费侧甚至显式拒绝 task 携带 agent identity（`consumer.go`）。
- **但执行体尚未分离**：`teamrun/executor.go` 内部仍直接解析 Agent 节点配置（LeadConfig → agentID/instruction）并驱动 LLM。这正是审定稿 §2.5 要求区分 `Executor` 与 `WorkflowSerialRuntime` 的那条缝——**"runtime 无关"在 teamrun 是合同层的事实 + 执行体的目标，不是全包既成事实。**
- `internal/streamctx` 的 `EventSender` 是最小流接口：能发事件就行。
- `internal/teambuild` 的蓝图机制（`TeamBlueprintV1`）定义了三种 workflow 模式（template/custom/declarative_v1）和 4 个内置模板；**但当前规划 API 只放行 template，custom 被拒，declarative_v1 走独立规划路径且有前置门槛**（见 §7 风险 2）。

结论：**"runtime 无关的协同基座"不是要新建的东西，而是合同层已存在、需要宣示保护并把执行体拆出来的东西。** 缺的是把建造机制从元团队这个产品下面解放出来。

## 2. 产品分层：谁住在哪一层

```
┌─────────────────────────────────────────────────┐
│ L3 客户端层（可选、平级、可替换）                  │
│   Console（人来操作）  元团队（LLM 来操作）        │
├─────────────────────────────────────────────────┤
│ L2 建造机制层（核心资产）                          │
│   团队模板 → teambuild 编译 → 授权 → ChangeSet    │
│   → 构建 → 运行 → 评测 → 发布                     │
├─────────────────────────────────────────────────┤
│ L1 协同基座层（核心资产，runtime 无关）             │
│   teamrun 状态机 · 任务队列 · fanout · checkpoint │
│   · 交付物 · 流事件 · 会话/恢复                    │
├─────────────────────────────────────────────────┤
│ L0 Loom 内核（已有，不动）                         │
│   State · Step · Graph · Store · Hooks            │
└─────────────────────────────────────────────────┘
```

三个原则：

1. **L1 对"参与方是什么"零假设。** 它只知道参与方合同（见 §4）。
2. **L2 是机制，不含人格。** 蓝图、模板、授权、评测是确定性机制，任何客户端都能调用。
3. **L3 平级且可选。** 元团队和 Console 都是 L2 的客户，谁也不比谁特殊。元团队可以整个关掉，平台功能不受损。

## 3. 核心产品决策

### D1：团队模板快路径（本方案的一号工程）

**一份声明式文档 = 一支团队。** 不经过任何 LLM，直接走 L2 编译管线：

```yaml
# team.yaml —— 一支团队的全部定义
name: 市场调研三人组
template: research_synthesis        # 4 个内置模板之一，或 declarative_v1 自定义
members:
  - name: 调研员
    role: 负责检索与事实收集
    agent: researcher_agent          # 引用已有 AgentRecord
  - name: 分析员
    role: 负责归纳与交叉验证
    agent: analyst_agent
  - name: 主笔
    role: 负责成稿
    agent: writer_agent
delivery:
  contract: 一份不超过 3000 字、含数据来源标注的调研报告
budget:
  max_cost_usd: 2.0
```

用户旅程：

```
写 team.yaml（或从模板库挑一份改两行）
  → POST /v1/teams:from-template（或 Console 粘贴）
  → L2 编译管线：校验 → 蓝图 → ChangeSet → 构建（秒级，无 LLM）
  → 团队可运行，直接派活
```

**实现要点（互审后修订）：快路径不跳过 BuildBrief，而是机器合成。** codex 审计确认 `CreateBuildRun` 把 brief/contract/hash/asset scope/budget/compiler revision 作为硬不变量（`teambuild/store.go`），绕过它们会打破授权与预算体系。因此 from-template 端点的工作是：**服务端把模板确定性地展开为 BuildBrief + 默认 EvaluationContract + compact_blueprint，再走既有管线**。零 LLM，但不变量一个不少。模板 schema 因此定位为**现有 compact_blueprint 的产品化 YAML 包装**（成员/模板/参数与 compact_blueprint 同构）外加交付合同与预算两个产品字段——不新发明一层与 `TeamBlueprintV1` 平行的全量结构。model_ref/provider 等默认值沿用 compact_blueprint 现有的服务端补全逻辑，模板允许留空。

**模板库**是配套的轻量资产：平台预置 4 个内置拓扑模板（delivery_rework_loop / parallel_review / creative_critique_loop / research_synthesis，已存在于 `teambuild/blueprint.go`）+ 若干行业样例（市场调研、内容生产、代码评审、客服质检），每个样例就是一份可以直接跑的 team.yaml。

**关键约束（呼应图约束原则）：模板能表达的拓扑用模板，表达不了的走 declarative_v1，绝不为表达力发明第三种通道。**（注意现状：declarative_v1 规划当前要求已存在 planning build run 与 blueprint revision 才能冻结 spec hash——快路径要支持 declarative_v1 需先打通这一前置，列入 M1 范围。）

### D2：元团队降级为可选的"向导客户端"

元团队不删除——"用自然语言对话生成团队"对不会写 YAML 的人仍有真实价值。但它必须改户籍：

| 维度 | 现在 | 目标 |
|------|------|------|
| 地位 | 平台内置、唯一大门 | 可选向导，与 Console 平级 |
| 调用方式 | 7 处直接 import 机制内部 | 只通过 `tf_*` 公开工具面（与任何外部客户端同一待遇） |
| 生命周期 | 启动时无条件 seed（`cmd/weave/main.go`，当前仅 default workspace） | 启动配置 `metateam.enabled`，可整个关闭 |
| 产出 | 直接驱动长流程 | **产出一份团队模板文档**（人能审、能改、能版本化），再由用户确认提交 |

最后一条是产品形态的关键转变：元团队的终点从"替你把团队建好"变成"帮你起草团队模板，你过目后一键提交"。这同时解决了脆的问题——巨型 prompt 只需教它生成 YAML，不用教它整个建造协议。

### D3：参与方合同（Participant Contract）明示化

L1 层显式定义并文档化参与方最小接口（今天已隐含存在）：

> **一个参与方 = 能接一个任务（输入）+ 能发事件（进度/流式输出）+ 终局必达三者之一（成功交付 / 失败 / 挂起等人）。**

由此派生的产品能力：**异构团队**。同一支团队里，调研员可以是 LLM agent，质检员可以是人工节点（挂起→人操作→恢复），数据拉取可以是确定性 worker。这是"runtime 无关"对业务的真正意义——不是技术洁癖，而是团队组成的自由。

保护条款：任何向 L1 渗入 agent/prompt/model 语义的改动，code review 一票否决（写入审定稿 §5 禁止事项）。

### D4：Team 升为一等公民，Agent 降为实现细节

今天平台的叙事中心是 Agent（AgentRecord、Agent 编译管线、Console 围绕 agent 组织）。目标叙事：

- **Team 是用户面对的第一对象**：创建、运行、交付、预算、评测都挂在 Team 上。
- **Agent 是 Team 成员的一种实现**：仍然重要（它是 LLM 参与方的配置载体），但不再是平台叙事的中心。
- Console 导航随之调整：团队列表成为首页，agent 列表退为"成员资源库"。

### D5：智能体终端是一等客户端（CLI / MCP 暴露面）

L3 不止 Console 和元团队。**分层结构的直接红利是：codex、Claude Code、opencode 这类智能体终端可以成为 Weave 的一等调用方**，路径有两条，共用同一套公开面：

1. **MCP server**：把 L2/L1 公开面包装成 MCP tools——`team_create`（吃团队模板）、`team_run`（派活）、`run_status`（查进度）、`deliverable_get`（取交付物）。智能体终端里的 agent 因此可以"拉起一支业务团队干活并拿回交付物"，Weave 成为它们的多智能体后端。已有基础：`api/runtime_mcp.go` 已存在 MCP gateway 雏形，`chatrequest` 的幂等合同、`streamctx.EventSender` 的最小流接口都是客户端无关的。
2. **CLI**：同一公开面的命令行包装（`weave team up -f team.yaml`、`weave run status <id>`），供终端里的人类和 agent 脚本使用；CLI 本身只是 HTTP API 的薄壳，不引入第二条业务路径。

前提与排序：CLI/MCP 包装的对象必须是**稳定公开面**，所以它排期在 M1（from-template API）之后——先把合同做稳，再开新门。这也再次说明为什么 M1 是整个产品方案的咽喉。

## 4. 三个用户故事（验收场景）

**故事 1：业务专家，十分钟路径。**
运营负责人要一支"每周行业竞品监控"团队。她从模板库复制 `research_synthesis` 样例，改了成员职责和交付合同两处，粘贴提交。40 秒后团队就绪，派了第一个任务，6 分钟后收到第一份报告。**全程没有见到"蓝图""ChangeSet""BuildRun"这些词。**

**故事 2：不会写 YAML 的人，向导路径。**
销售主管对元团队说"我要一个能初审合同条款风险的小组"。元团队对话三轮后产出一份 team.yaml 草稿，高亮展示了它做的关键选择（用了哪个模板、成员怎么分工），销售主管确认提交。**元团队关掉开关后，故事 1 完全不受影响。**

**故事 3：平台工程，异构路径。**
内容团队的"终审"环节必须由人来做。团队模板里把终审成员声明为 `kind: human`，工作流跑到终审自动挂起，终审人在 Console 看到待办、批注、放行，流程继续。**L1 对"这个成员是人是模型"完全无感。**

## 5. 里程碑

### M0：宣示边界（1 周，纯文档+小改动）

- 参与方合同写入 `teamrun` 包文档；禁止事项补进审定稿 §5。
- 实现 `metateam.enabled` 启动开关（改动点在 `cmd/weave/main.go` 一处），**但默认开启**。
- 互审修正：今天关闭 seed 会打断创建团队入口——前端"新团队"硬编码 `__team_architect`（`ConversationPage.tsx`）、后端 `create_team` intent 只允许发给 `__team_architect`（`internal/api/chat.go:817`）。因此 M0 的关闭语义是：**关闭时同步隐藏对话式建团队入口**（而不是报"元团队尚未就绪"）；开关真正有产品意义要等 M1 的模板入口上线。

### M1：模板快路径（2-3 周，本方案核心）

- 定义团队模板 schema（YAML/JSON）：成员 + 模板拓扑 + 交付合同 + 预算，与 compact_blueprint 同构，缺省字段由服务端补全。
- `POST /v1/teams:from-template`：服务端从模板机器合成 BuildBrief + 默认 EvaluationContract + compact_blueprint，走既有 teambuild 管线直达可运行团队；评测不做构建前置，可后置一键触发。
- 打通 declarative_v1 在快路径下的前置（当前要求 planning build run + blueprint revision 才能冻结 spec hash）。
- 4 个内置模板 + 3 个行业样例入库。
- 验收：故事 1 实跑通过，time-to-first-team < 10 分钟。

### M2：元团队改户籍（2 周，依赖 M1）

- 元团队产出改为团队模板草稿；接线收口为只走 `tf_*` 公开工具面（7 处 import 收拢）。
- 验收：故事 2 实跑通过；`metateam.enabled=false` 下全平台回归通过。

### M3：异构团队（3-4 周，设计可并行，实施有前置）

- 参与方合同扩展 `kind: human | agent | worker`。
- 互审修正：人工等待**不能**简单"复用现有 park/resume"——`WaitKind` 当前只有 `timer/fanout` 两个枚举值，workflow Wait 节点只生成 timer wait 且自动恢复、不接收人工输入。需要新增 `WaitHuman`：人工任务待办、权限、resume payload 校验、幂等、超时升级与通知策略，是一整块子系统，不是配置项。
- 排序约束：按审定稿，实施须排在 `teamrun` ABI 冻结与 Executor/WorkflowSerialRuntime 拆分之后，不插队。
- 验收：故事 3 实跑通过。

### 与既有审定稿的关系

审定稿是"保护网与合同冻结"线（阶段 A-F），本方案是"产品形态"线（M0-M3）。两者交汇于 M2：收口 metateam 的 7 处 import 正是审定稿 §2.1/§2.6 治理的一部分。**两条线共用同一原则：先冻结合同，再动代码。**

## 7. 风险与反方意见（诚实清单）

1. **元团队降级可能削弱差异化卖点。** "自然语言→团队"是演示时最抓人的一幕。缓解：降级不是删除，向导路径保留且产出更可审（草稿可视化反而增强信任）；且 M2 之前主路径不动。
2. **4 个内置模板表达力可能不够，且 declarative_v1 现状门槛高。** 已识别缺口（如"固定并行后汇聚再进全局返工"）按图约束原则走 declarative_v1，但 declarative_v1 手写门槛高、且当前规划路径要求 planning build run + blueprint revision 前置。缓解：M1 打通快路径前置；M2 后元团队/Console 的主要增值点就是帮人写 declarative_v1。
3. **参与方合同过弱可能导致上层各自发明语义。** 如果 L1 只有三句话，L2 之上可能长出互相不兼容的"能力声明"方言。缓解：能力声明（capabilities/execution_policy）明确归 L2 蓝图层所有，L1 永不承接。
4. **Team 升为一等公民会触碰 Console 信息架构，波及面广。** 缓解：M1 只加"团队模板"入口不改导航；导航调整放到 M3 之后单独评估。
5. **快路径使用机器合成的默认评测合同，质量防线变浅。** 今天元团队路径的 EvaluationContract 由架构师按业务定制。缓解：合成合同从 `DefaultFloorHardGates()` 起步，快路径团队标记 `unevaluated`，Console 显著提示，评测作为一键后置动作而非构建前置。
6. **模板不是天然自足的。** model/provider/runtime 的默认补全今天来自 API 层与 BuildRun 上下文；若模板要求用户显式填写这些字段，"十分钟"目标会被技术细节击穿。缓解：schema 设计强制"业务字段必填、技术字段全可省略"，补全逻辑复用 compact_blueprint 现有实现。

---

## 8. 本方案不做的事

- 不重写 L1 执行层（它已 runtime 无关，只宣示、保护，不重构）。
- 不删除元团队任何 persona（只改它的产出物和接线方式）。
- 不动 Loom 内核。
- 不在本阶段做 Console 信息架构大改版。
- 不为模板表达力发明内置模板/declarative_v1 之外的第三条通道。

## 9. 互审记录（codex 审计 + 独立反查，2026-08-25）

流程：codex 以只读方式对照代码库审计本方案 v1，随后主审对其每条论断做独立反查（亲自读码验证，不采信自报）。结论：**codex 的全部关键论断经反查属实**，方案据此修订为 v2。

### 9.1 codex 事实核验 vs 独立反查

| codex 论断 | 反查结果 | 处置 |
|---|---|---|

### 9.2 互审带来的三个设计级修正

1. **快路径从"绕过状态机"改为"机器合成状态机输入"**——这是本轮互审最有价值的纠正。原 v1 的"跳过 BuildBrief"会破坏授权/预算/hash 不变量；v2 的合成方案既保住零 LLM 的速度，又不破坏任何机制不变量。
2. **M0 开关与 M1 入口解耦排序**——开关先做但默认开，关闭的产品意义依赖模板入口存在，避免"关掉元团队=平台无法建团队"的假可选。
3. **M3 人工等待从"复用机制"降级为"子系统新建 + 排序约束"**——承认 WaitHuman 是含权限/通知/超时的整块工作，且服从审定稿的 teamrun ABI 先行顺序。
