# 发布工作流的应用调用

状态：2026-10-15 用户批准实施；代码、工程验证与真实模型验收分别记录。

## 范围

服务应用通过已有 capability invocation 接口调用被授权的已发布工作流。单成员资料分析与多角色评审共享固定版本、应用授权、输入输出 Schema、幂等、取消与运行证据。业务规则属于调用方，不恢复 W10 删除的决策路由。

此决定将 2026-10-03 的受限选择例外收敛到既有应用能力调用合同。W10 的本地账号删除与决策路由退役保持有效。应用得到精确能力版本授权，不获得任意团队派发、员工身份或业务资源访问权。首批工作流引用支持确定性节点与纯计算 Loom 模型成员；模型成员全部禁用工具，不启用记忆、技能、MCP、外部运行时或备用模型。主模型凭据只允许精确冻结的 `workspace_service` 引用；用户私有凭据仍只由本人使用，应用授权不隐式委托它们。

## 职责与唯一事实所有者

- Kernel 的已发布 Workflow/Artifact 是唯一执行定义；能力修订只冻结工作流版本引用与输入输出合约，不保存第二份流程图或成员配置。
- 产品层复用 capability application、credential 和 version grant。凭据只证明应用主体，请求不能声明员工身份。
- invocation 保存请求身份、输入与运行关联、取消意图及可选串行通道；publication、TeamRun 和 taskqueue 持有原有执行、恢复、预算、取消确认与终态。
- invocation 的状态、结果、用量和节点证据从关联运行投影，不增加执行循环、队列、自动重派或独立可写终态。
- 平台校验通用输入输出 Schema；业务系统落地前再检查当前业务状态和结果合法性。

## 公开合同

能力定义新增 `workflow: {workflow_id, workflow_version}`，与 inline roles/steps/relations/result 互斥。工作流后续发布不改变既有能力修订的引用。

复用 `POST /v1/capabilities/{id}/versions/{revision}/invocations`，保留 `request_id` 和 `input`，增加可选 UUID `invocation_id` 与 `lane`。调用方可以先确定 invocation ID，响应丢失后查询或取消。相同请求号不同输入、能力修订、通道或调用身份冲突，精确重放返回同次运行。同工作空间与应用的 lane 跨能力互斥。

复用 `/v1/invocations/{id}` 的查询、events 和 cancel。取消先到时保存调用方范围内的停止意图；运行先被接收时交给原 TeamRun 取消机制，只在停止确认后报告终止。

复用 `workflowadmission.ReserveTx/Admit/Reconcile` 保存与恢复同一准入请求。请求关联原子落地，或沿原 receipt 可恢复关联；不确定提交不能成为新建运行的理由。publication authority 必须验证确切应用、能力修订、工作流和冻结资源引用，不使用宽泛 org/chat scope 绕过。

能力层的输入输出使用完整 JSON Schema 校验；工作流仍使用 machine 当前支持的可执行 Schema 子集，两者不要求字节等价。输入先经过能力合约校验，最终交付再按能力输出合约复验；工作流完成但输出不合约时，调用视图保留原运行终态、标记 `result_state=invalid` 并不返回结果，不伪造第二运行终态。

工作空间的 `max_active_invocations` 由 inline 与 workflow 两类调用共同计入，在共享事务锁下受理新请求；精确重放与尚未受理即关闭的调用不占新名额。既有 `max_steps_per_invocation` 属于 inline 执行器的步骤预算，不能表述为工作流全局计步；工作流成员仍执行已发布版本冻结的 StepBudget、Token 和输出预算。本轮不新增第二套计步或重试循环。

用量读取原根运行 V3 audit 的 `SubtreeTotal` 一次，不能再次相加分支用量。缺失审计、未收齐的用量与已知零消耗分别表达，`physical_usage` 与不能证明的 `unreported_attempts` 可为 null，同时返回 `usage_complete`。

## 验证与后续边界

真实 PostgreSQL 覆盖重放和冲突、跨应用隔离、lane 并发、取消先到、准入提交后丢响应及恢复、版本冻结、Schema 拒绝、撤权及来源投影。使用真实服务编排与受控模型验证平台合同，另跑 Go 全套、race 与治理门禁。真实模型整局与部署独立验收。

现有 inline capability 仍有独立的定义执行器，本次不把团队图翻译成 inline Plan，新工作流引用只走原 TeamRun。后续所有能力定义收敛到发布工作流后，删除 inline 编译/执行入口及其专属接线，按实测下调预算。在完成前不宣称两类既有定义已经完全统一。

## 本轮工程核验

- 基于 Weave `main@1e7249f141a5df9c3c8a155bb031eefb0ac46da8`。其 `third_party/loom` 与独立 Loom `main@e4dfa760fe8bd9469f255e032e8ed8376e85b43d` 的所有受跟踪文件逐字节相同。
- 显式指定独立 PostgreSQL 后，全量 `make test` 通过 1751 个测试/子测试；6 个既有的实模型、Forge、特殊进程环境、CLI 限制或进程辅助入口用例按自身条件跳过。新增调用合同和受控模型链路均实际运行，没有跳过。
- 单成员与三路并行评审到最终交付分别执行 1、4 次本机受控模型 HTTP 请求，并在正常池与 `MaxConns=1` 下通过。新路径的精确版本、隔离、取消先到、撤权、重放、配额、严格输出合约、来源与用量投影通过真实数据库回归及必要 race 检查。
- 凭据实时校验复用 resolver 本次事务的只读查询端口，避免内层再取连接；没有扩大连接池或缓存授权。根任务停放后的结果与逐节点输出均读取原交付产物，不写第二份运行终态。
- `go vet`、depguard、base-depguard、productguard、budgetguard 与治理 23 项通过（其中默认 Compose 项另由 `make compose-check` 单独实际通过）。管理端静态资源构建通过；未变更管理端交互。
- 精确增量共 5316 行，其中生产 2492 行；包数与外部依赖数不变，预算无余量，删除触发条件登记在同次 amendment 中。
- 以上受控模型不是提供方验收。本记录不宣称已经调用外部真实模型、部署新版本或完成实体手机/业务验收；调用方的真实模型与部署证据另行记录。
