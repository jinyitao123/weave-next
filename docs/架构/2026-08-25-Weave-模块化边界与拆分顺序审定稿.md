# Weave 模块化边界与拆分顺序审定稿

> 日期：2026-08-25  
> 状态：code review 后审定稿  
> 适用范围：后端模块化、前端会话执行状态拆分、后续重构工单派发与验收  
> 复审方式：主审查 + 子 Agent Copernicus 只读复审

## 1. 结论

当前代码的主要问题不是单个文件太长，而是生产合同散落在入口层、存储层和页面组件里。

重构顺序必须先冻结隐式合同，再拆实现：

1. 先补 characterization tests，锁住现有行为。
2. 先定义 Chat Turn、TeamRun ABI、前后端事件协议，再移动代码。
3. 先消除反向依赖和明显边界污染，再做大文件拆分。
4. 对状态机和授权链路，只做窄接口与同包拆分，不先追求“纯 repository”。

本阶段不以重写架构为目标。每个重构工单必须有白名单、可重复验收命令和真实主链场景检查。

## 2. 当前高风险边界

### 2.1 API 层成为应用容器

`internal/api/server.go` 的 `Server` 聚合了 HTTP、store、runtime、worker、orchestrator、hub 和多类后台进程。`registerRoutes` 又集中注册所有业务域路由。

风险：

- handler 可以跨域直接调用任意 store，边界会继续变松；
- optional dependency 的 nil 判断分散在各 handler；
- 应用装配、HTTP adapter、后台进程生命周期混在一起；
- 后续拆包容易出现 import cycle。

目标形态：

- `cmd/weave` 或 `internal/app` 负责应用装配和后台服务生命周期；
- `internal/api` 只负责 HTTP routing、auth middleware、request/response adapter；
- 各业务域暴露窄 service，例如 `ChatTurnService`、`TeamBuildService`、`RuntimeService`。

### 2.2 Chat Turn 合同散在 `chat.go`

`internal/api/chat.go` 的 `handleChat` 同时处理：

- request bind 和权限上下文；
- runtime 选择；
- create team 特殊入口；
- project/conversation 解析；
- `client_request_id` 幂等、replay 和状态回填；
- team session admission、snapshot、lease、outbox；
- published workflow 分流；
- session history 写入；
- Loom graph 编译执行；
- SSE stream、tool/event segment、terminal payload；
- assistant message、metadata、memory fill。

风险：

- 任何拆分都可能改变 stream/replay/terminal 的隐式顺序；
- 前端断线恢复依赖这些隐式字段和状态；
- team free-collab 与 published workflow 两条路径容易互相污染。

目标形态：

```text
HTTP /chat
  -> ChatTurnService.Send(ctx, ChatTurnCommand)
  -> ChatTurnResult 或 ChatTurnStream
  -> HTTP/SSE adapter 输出
```

`ChatTurnService` 必须明确以下合同：

- admission：什么时候生成 session_id、conversation_id、user_message_id；
- idempotency：同一 `client_request_id` 的 admitting、admitted、running、yielded、completed、failed 语义；
- routing：普通 Loom chat、CLI chat、team free-collab、published workflow 的分流条件；
- terminal：`ChatTerminalPayload` 必须包含哪些字段；
- persistence：用户消息、助手消息、session history、outbox、memory 的提交顺序；
- recovery：客户端断线后如何通过 chat request record 收敛。

### 2.3 `declarative -> api` 反向依赖

`internal/declarative/factory.go` import `internal/api`，只为调用 `ContextSuppressStream`。

风险：

- graph factory 被 HTTP/SSE 细节污染；
- runtime/daemon 复用 declarative graph 时被迫依赖 API 包；
- 后续拆 `api` 时极易引入 import cycle。

目标形态：

- 新增小包，例如 `internal/streamctx` 或 `internal/runtimecontext`；
- `ContextSuppressStream`、`IsSuppressStream` 放入该小包；
- `internal/api/sse.go` 和 `internal/declarative/factory.go` 同向依赖小包；
- `internal/declarative` 不再 import `internal/api`。

### 2.4 `teambuild.Store` 同时承担存储和授权编排

`internal/teambuild.Store` 包注释宣称只拥有 storage layer，但实际持有 `org.Store`、`AgentRegistry`、`workflow.Store`，并在 `AuthorizeBuildRun` 里完成 baseline 捕获、授权 receipt、预算和状态转移。

风险：

- Store 已经是 domain/application service，不是纯 repository；
- 立即贫血化会打散授权、baseline、预算、CAS 状态机的不变量；
- baseline source 通过 setter 注入，真实依赖不明显。

目标形态分两步：

1. 第一阶段只同包拆文件和窄接口，不改变 public API：
   - `authorization.go`
   - `baseline_capture.go`
   - `budget_ledger.go`
   - `rounds.go`
   - `transitions.go`
2. 第二阶段再把跨 store 读取抽为 `BaselineCaptureService` 和 `BuildAuthorizationService`。

### 2.5 `teamrun` 需要先封 ABI

`internal/teamrun.Executor` 是队列、租约、checkpoint、park/resume、fanout、terminal 记录的执行状态机。`WorkflowSerialRuntime` 是 workflow 解释器/runtime。两者不能统称为一个“执行层”。

风险：

- `teamorch` candidate evaluation 依赖 `teamrun` 的 terminal、usage、snapshot 和 task 行为；
- 先拆 `teamorch` 会放大 candidate/published 一致性风险；
- fanout、timer resume、terminal lineage 的行为很难靠人工 review 保证。

目标形态：

- 先为 `Executor.ProcessNext` 建立 ABI 文档和测试；
- 明确 task payload kind、claim/reclaim、park/resume、terminal、usage completeness 的稳定字段；
- 然后再拆：
  - `executor_queue.go`
  - `executor_transition.go`
  - `executor_fanout.go`
  - `executor_terminal.go`
  - `workflow_runtime.go`
  - `workflow_interpreter.go`

### 2.6 `teamorch.PhaseDeps` 过重

`internal/teamorch/phases.go` 聚合 Build、Agents、Teams、Workflows、MCPs、Providers、Runtimes、Tasks、Deliverables、Snapshots、Audit、Delivery、Skills、Schedules、Descriptors、Fanout、Drafts、LLM 等依赖。

风险：

- 每个 phase 都看到全量平台依赖；
- 构建、候选运行、评测、发布、报告装配互相穿透；
- 文件拆分如果不先收窄接口，只会把复杂度平铺到多个文件。

目标形态：

- `BuildPhase` 只依赖 teamforge 写入与 build run store；
- `CandidateRunner` 只依赖 workflow candidate builder、teamrun executor、snapshot/task；
- `EvaluationPhase` 只依赖 gate evaluator、semantic judge、report reader；
- `Publisher` 只依赖 workflow publication store 与 build run transition；
- `ReportAssembler` 只做纯数据装配，尽量无 store。

### 2.7 前端 `ConversationPage` 承担执行状态机

`weave-app/src/pages/ConversationPage.tsx` 同时负责：

- 路由和团队/项目/会话选择；
- 线程主会话解析；
- 消息加载和已读；
- pending turn；
- SSE stream 事件处理；
- chat request polling 和断线恢复；
- 附件上传；
- runtime 选择；
- composer；
- deliverable side panel；
- team build card 操作。

风险：

- JSX 拆组件不能降低状态复杂度；
- pending/reconnect/poll/SSE 的状态迁移散在多个函数里；
- 前端与后端的 terminal payload、event type、chat request status 是隐式协议。

目标形态：

先抽状态和协议，再拆视觉：

- `useConversationSelection`
- `useConversationMessages`
- `useChatTurnController`
- `useChatStreamEvents`
- `useAttachments`
- `useRuntimeSelection`
- `ConversationTimeline`
- `ConversationComposer`
- `DeliverableSidePanel`

### 2.8 `api/types.ts` 是协议集合，需要拆域

`weave-app/src/api/types.ts` 聚合用户、agent、team、workflow、project、runtime、schedule、conversation、chat、run、job 等类型。

风险：

- 前后端合同变更影响面不可见；
- Chat Turn 和 workspace SSE 的协议没有独立拥有者；
- API client 文件拆了但类型仍是全局粘合剂。

目标形态：

- `api/auth.types.ts`
- `api/agents.types.ts`
- `api/teams.types.ts`
- `api/workflows.types.ts`
- `api/projects.types.ts`
- `api/chat.types.ts`
- `api/runtimes.types.ts`
- `api/events.types.ts`

第一步只移动类型和 re-export，不改变调用方行为。

## 3. 拆分顺序

### 阶段 A：保护网和合同冻结

目标：不重构业务，只把现有行为钉住。

工单：

1. 后端补 `chatrequest` / `chat.go` characterization tests：
   - `client_request_id` 首次创建；
   - replay completed；
   - replay in-progress；
   - admitted conversation 和 user message 回填；
   - terminal payload 字段完整性。
2. 后端补 `teamrun.Executor.ProcessNext` tests：
   - queued -> running -> succeeded；
   - running reclaim；
   - runtime error -> failed；
   - park timer；
   - fanout leg terminal；
   - task lease lost。
3. 后端补 `teambuild.AuthorizeBuildRun` tests：
   - create mode 要求 compiler revision；
   - optimize mode baseline 捕获；
   - hash mismatch fail closed；
   - receipt replay facts 不变。
4. 前端为 chat turn controller 准备测试或最小 fixture：
   - stream chunk 合并；
   - tool_call/tool_result segment；
   - aborted 后可 reconnect；
   - completed 后 reloadUntilMessage。
5. 写 Chat Turn 时序文档，覆盖：
   - stream；
   - replay；
   - team session；
   - published workflow；
   - create_team。

验收：

```bash
go test ./internal/api ./internal/chatrequest ./internal/teamrun ./internal/teambuild
cd weave-app && npm run typecheck && npm run lint
```

### 阶段 C：抽 Chat Turn 应用服务

目标：把 `handleChat` 从业务编排中解放出来。

工单：

1. 定义 `ChatTurnCommand`、`ChatTurnResult`、`ChatTurnTerminal`。
2. 抽 `ChatRequestCoordinator`：
   - begin；
   - mark admitted；
   - mark running；
   - replay response；
   - finish。
3. 抽 `ConversationTurnWriter`：
   - resolve project；
   - resolve conversation；
   - append user；
   - append assistant；
   - publish message event。
4. 抽 `TeamSessionCoordinator`：
   - acquire；
   - apply frozen runtime assignment；

验收：


- 旧会话续写；
- 断线后恢复；
- create_team 入口；
- published workflow conversation。

### 阶段 D：拆前端 turn controller

目标：先抽状态机，不动视觉布局。

工单：

1. 从 `ConversationPage` 抽 `useChatTurnController`。
2. 从 `submitTurn` 中抽 stream event reducer。
3. pending turn 持久化和 reconnect 进入 hook。
4. 附件上传抽 `useAttachments`。
5. runtime 列表和选择抽 `useRuntimeSelection`。
6. 页面仍渲染原 JSX，确认行为不变后再拆 `Timeline` 和 `Composer`。

验收：


- 工具调用流式展示；
- 中断等待后继续等待；
- 附件发送；
- runtime 手动选择；
- 线程回复。

### 阶段 E：拆 TeamBuild 和 TeamRun

目标：降低状态机文件复杂度，但不破坏生产不变量。

工单：

1. `teambuild` 先同包拆文件，不改外部 API。
2. 为 baseline capture 定义最小接口，但先由 `Store` 持有。
3. `teamrun` 先拆 executor 文件：
   - queue claim；
   - transition；
   - park/resume；
   - fanout；
   - terminal；
   - frozen attempt。
4. 单独拆 `WorkflowSerialRuntime` 和 workflow interpreter。
5. 每拆一组跑对应 tests 和一个真实 candidate run。

验收：

```bash

```

### 阶段 F：拆 TeamOrch phases

目标：按 phase 收窄依赖，并让每个 phase 可单独测试。

工单：

1. 定义 phase-specific deps：
   - `BuildPhaseDeps`
   - `CandidateRunnerDeps`
   - `EvaluationDeps`
   - `PublishDeps`
   - `ReportDeps`
2. `ProductionPhases` 只做 orchestrating facade。
3. `buildAndRunCandidateFor` 迁到 `candidate_runner.go`。
4. `assembleReport` 迁到 `report_assembler.go`，尽量改成纯函数。
5. `PublishStep` 迁到 `publisher.go`。

验收：

```bash
go test ./internal/teamorch ./internal/teamrun ./internal/workflow ./internal/teameval
```

真实场景：

- create team build round；
- optimize baseline；
- candidate evaluation fail；
- candidate evaluation pass；
- publish。

### 契约：Chat Turn 生命周期顺序

1. 接入准备
   - 前端为每次新提交生成 `client_request_id`；
   - 重试失败 pending turn 时必须生成新的 `client_request_id`；
   - `session_id` 来自当前会话 session key，没有会话时前端生成空路由请求，服务端补齐实际 session；
   - 前端 pending turn 必须先写入 tab-local `sessionStorage`，作为刷新后的恢复 hint。

2. 后端幂等门
   - 非 async `/v1/chat` 在解析 agent、project、conversation、attachment 后进入 `beginChatRequest`；
   - `client_request_id` 为空时不启用幂等记录；
   - `client_request_id` 非空时，以 `(workspace_id,user_id,client_request_id)` 唯一绑定请求；
   - 请求 fingerprint 覆盖 agent、project、conversation、intent、runtime、session、message、channel、profile、effort、stream、async、context、attachments 与 blueprint flag；
   - 相同 fingerprint 为 replay，不重新执行；
   - 不同 fingerprint 返回 `client_request_conflict`。

3. 路由与会话归属
   - 显式 `conversation_id` 必须通过 project、agent、user、channel、read_only 校验；
   - 新会话或 create-team intent 由 `recordIncomingProductMessage` 决定最终 `conversation_id` 与 `user_message_id`；
   - 服务端 `MarkAdmitted` 后，chat request 才拥有 durable `session_id/conversation_id/user_message_id`；
   - 前端收到 admitted/reconnect 记录时，如果服务端给出新 `conversation_id`，必须修正路由。

4. 执行持久化
   - 普通 agent chat：`MarkAdmitted` 后立刻 `MarkRunning`；
   - published workflow chat：workflow admission 后必须通过 `BindWorkflowRun` 绑定 `run_id/task_id`，便于刷新恢复进度；
   - `BindWorkflowRun` 对同一 `run_id` 幂等，对不同 `run_id` 不覆盖既有绑定；
   - 用户消息在 admission 阶段持久化，assistant 消息在 terminal 后持久化。

5. 流式输出
   - SSE `chunk/tool_call/tool_result/step_start/content_block/yield/done` 只负责当前连接的即时呈现；
   - durable recovery 不依赖历史 SSE；
   - 前端 pending turn 的 streamed content、tool calls、segments 不写入 `sessionStorage`，刷新后只保留请求身份、附件、运行时归属和恢复所需字段。

6. 终态
   - chat request 终态只允许 `yielded/completed/failed`；
   - `MarkFinished` 不覆盖既有 `completed/failed`；
   - terminal response 必须携带 project、session、conversation、user message、run/output/stop reason 中的可用事实；
   - stream replay 遇到终态时发送 `done`，非 stream replay 返回 `200`。

7. 恢复顺序
   - 前端刷新后先读本地 pending hint；
   - 若路由与 pending request 匹配，则进入 reconnecting；
   - 前端通过 `GET /chat-requests/{client_request_id}` 或同等 API 读取 durable request；
   - `completed/yielded/failed` 走 converge：拉取会话消息，确认 user/assistant 已落库，清理 pending；
   - 非终态走 adopt/progress：采纳服务端 `conversation_id`、更新 workflow progress，继续轮询；
   - POST replay 遇到 `queued` 返回 `202`，遇到 `admitting/admitted/running` 返回 `409 client_request_in_progress`，前端应改走恢复轮询而不是重复提交。
