## 1. 目标与验收

**codex / Claude Code / opencode 等智能体终端，通过 MCP 或 CLI 驱动 Weave 完成闭环：拉起团队 → 派活 → 查状态 → 拿交付物。**

验收：MCP（stdio）与 CLI 双通道各完成一次全环；认证走 `wv_sk_` API key；CLI/MCP 不含业务逻辑（薄壳原则，§3）。

## 2. 形态

单一 `cmd/weave` 二进制，**子命令分发必须发生在 config 加载与 DB 初始化之前**（早返回，仿 runtime 分支）：

```
weave / weave serve        # 服务端（无参数行为不变，Docker ENTRYPOINT 不动）
weave team samples|up -f team.yaml|dispatch --team <id> --task "..." --wait
weave status build <id> | dispatch <client_request_id> | team-run <snapshot_id>
weave deliverable list|get <id>
weave mcp serve            # stdio MCP server
```

未知子命令非零退出。Dockerfile/安装链不改。

## 3. 工具集与映射（互审修正版）

| MCP 工具 / CLI | 映射端点 | 说明 |
|---|---|---|
| `team_template_list` | `GET /v1/team-templates/samples` | org scope |
| `team_create` | `POST /v1/teams:from-template` | admin+org scope；**幂等键由调用方传入**，tool schema 显式暴露，wrapper 不自动生成 |
| `team_dispatch` | `/v1/chat`（free-collab） | team→lead 用既有团队详情端点只读解析；团队不存在/非 active 明确报错，不允许静默退化为普通 agent chat |
| `build_status` / `dispatch_status` / `team_run_status` | build progress / `GET /v1/chat-requests/:id` / `/v1/runs?view=run&run_snapshot_id=…` | **三态分离**，ID 无法自动判型，不试探 |
| `resume` | `/v1/resume` | yielded 不是终态；需要人工输入的派活靠它闭环 |
| `deliverable_list` / `deliverable_get` | `/v1/deliverables`、`/v1/deliverables/:id` | v1 不支持 team/run 过滤（端点现状）；**交付物仅当 agent 显式 save_deliverable 才产生**——工具描述如实说明，不承诺每次派活必有交付物 |

**dispatch 轮询合同**（写死在 client 包）：固定 UUID `client_request_id`（调用方可传，用于外部重试收敛）+ `async:true` + 轮询 `GET /v1/chat-requests/:id`，处理 202/409/yielded/failed 全状态。已知边界如实写进工具描述：CLI-runtime lead 禁止 async（400 直传）；**同一 dispatch 生命周期内必须不换 API key**（user ID = `apikey:<key-id>`，换 key 查不到原请求）。

## 4. 实现约束

1. **MCP 协议栈复用**：抽取 `mcp_boundary.go` 的 server 端 JSON-RPC/MCP method adapter 为共享 protocol core，stdio transport 只做 IO 适配——禁止另写第二套协议实现（两套协议 = 两个版本漂移源）。
2. **工具描述是外发 prompt 面**：只写用户可见的前置条件、结果、稳定错误码；禁止出现 internal 路径、内部状态机名词、原始 HTTP 错误正文。
3. **薄壳原则**：发现"这里需要一点逻辑"就停下报告——逻辑属于服务端。唯一允许的客户端组合是只读解析（team→lead）。
4. **app 带归属**：CLI/MCP 代码在 app 带；base/kernel/build 零改动是自证目标。

## 6. 互审记录（codex 审计 + 主审裁决，2026-08-26）

| codex 论断 | 处置 |
|---|---|
| deliverable 闭环不存在（无 team/run 过滤；仅 save_deliverable 产出） | 采纳，v1 如实映射现状，工具描述不承诺产出（§3） |
| team_dispatch 不是薄壳（chat 吃 agent 不吃 team） | 采纳，只读解析 + 明确报错，禁静默退化（§3） |
| run_status 必须三态分离，ID 无法判型 | 采纳，build/dispatch/team_run 三工具（§3） |
| 幂等/轮询合同不完整（固定 UUID、async、202/409/yielded、key 轮换破坏恢复） | 采纳，§3 轮询合同 + key 不变约束 |
| 缺 resume 工具（yielded 非终态） | 采纳，§3 增 resume |
| MCP 描述泄露内部状态机语义的风险 | 采纳，§4.2 描述纪律 |
| mcp_boundary 的 server adapter 被漏看，另写 stdio 栈会形成双协议 | 采纳，§4.1 共享 core 抽取 |
| 子命令分发须在 DB 初始化前；无参数启动 server 不变 | 采纳，§2 |
| CLI-runtime lead 禁 async，--wait 会 400 | 采纳，如实记录为已知边界（§3） |
| API key scope 细节（模板建队需 admin+org；chat 需 chat scope） | 采纳，README 写明各操作所需 key scope |
