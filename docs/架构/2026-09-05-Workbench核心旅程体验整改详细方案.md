# Workbench 核心旅程体验整改详细方案

2026-09-05 · 设计方案及实施范围记录 · 仅限 Workbench 现有能力整改

## 1. 结论、依据与方案边界

当前证据足以确定状态表达、确认范围、构建失败、运行信息层级的整改方向。页面的黑白灰视觉基础、持续主对话、紧凑任务回执、工作现场和成员公开更新可以保留。第一轮的目标是让用户随时理解“正在发生什么、是否需要我操作、下一步会发生什么”，再改进排版与动效。

本方案细化既有[工作对话方案](2026-09-05-Workbench-工作对话方案.md)，依据[核心旅程体验走查](../验收/2026-09-05-Workbench核心旅程体验走查.md)中的 WB-0905-001 至 WB-0905-016。保留一项工作一个主对话、现场只有进展与成果两类主内容的结构。本方案中的状态名、字段、组件拆分和尺寸均为待实施设计，不代表代码已经具备。

### 1.1 证据可以支持到什么程度

| 证据类型 | 已覆盖 | 可以支持的判断 | 不应据此声称 |
|---|---|---|---|
| 实时浏览器操作 | 推荐、结构化确认、派发、负责人执行、两人并行、新团队长方案、构建失败、节点中断 | 跨区域状态冲突、操作入口与用户意图冲突、信息密度与反馈问题 | 已覆盖成功构建、完整恢复和最终完成的连续转场 |
| 当前代码渲染的历史记录 | 完成、人审答复、失败重试、停止未确认、阶段与最终成果 | 恢复会话的可读性、历史状态冲突、回执与成果归属表达 | 历史中间状态是本轮实时发生 |
| 当前源代码只读核对 | 任务投影、候选卡、构建查询、公开记录滚动逻辑 | 实施落点、已有能力、需要补齐的数据关联 | 后台一定提供了完整构建阶段、依赖图或成本分项 |
| 截图与动效记录 | 截图曾在会话中展示，文字观察已落地 | 当时观察过程可追溯 | 本地已有截图包或录屏；动效时长经过测量 |

截图未及时落地是本轮材料缺口。后续验收必须把 PNG、状态快照和必要的连续画面直接保存到本地；已消失的瞬时状态只能标为未补证，不能重绘成“实测截图”。

### 1.2 范围约束

- 改进现有团队推荐、创建、派发、运行、人审、纠偏、重试、停止与成果查看。新增展示组件用于呈现这些已有行为。
- 不引入团队市场、团队匹配评分系统、可视化工作流编辑器、成员独立聊天、新调度器、任意节点强制接管或新预算计费能力。
- 构建查询复用现有 `build_status`；恢复和取消复用现有明确归属当前运行的接口。接口不支持的行为不以可点击按钮暗示支持。
- Weave 保留执行事实与约束，Workbench 负责业务表达；不把业务控制台搬到其他页面。保持仓库依赖分层。
- 实施保持现有业务能力与操作协议；不自动创建新的 Codex 验收任务。实时业务运行与历史或模拟验收分别记证。

### 1.3 修正此前建议

此前走查文档中的 P0 是过宽的初步整改归类，本方案采用更严格分级。候选按钮与用户意图冲突已观察到，但尚未通过点击证明它一定绕过确认执行，因此不能直接宣称已经发生未授权派发。默认流程也不固定增加四次确认：用户一次明确确认创建与派发即可继续；只有明确要求分开时才分开。

## 2. 用户旅程和四个区域的职责

用户旅程为“描述工作 → 推荐或设计团队 → 确认明确范围 → 创建或准备 → 派发 → 跟踪与必要干预 → 查看成果”。创建团队是准备工作的一个分支，不是另一个产品入口。

| 区域 | 必须回答 | 默认内容 | 不承担 |
|---|---|---|---|
| 左侧工作导航 | 哪项工作需要关注 | 工作标题、统一主状态；团队名按空间显示 | 全部成员、运行日志和多层错误说明 |
| 顶部任务栏 | 当前任务处于什么状态 | 团队或方案名、主状态；需要用户操作时提供对应入口 | 持续重复正文、通用“准备中”兜底 |
| 主对话 | 我说了什么、确认了什么、下一步能做什么 | 用户要求、精简回复、方案与确认摘要、关键操作回执 | 默认展开完整团队报告或内部调用过程 |
| 工作现场 | 谁在工作、依赖什么、产生什么 | 进展、待处理事项、阶段与成员详情、成果阅读 | 另建一套状态判断，或在失败后回退到候选目录 |

所有区域允许长度不同，含义必须一致。例如侧栏写“并行执行中”，顶栏写“2 名成员并行执行中”；不允许侧栏写“等待团队继续”而任务卡写“运行节点中断”。

### 2.1 默认布局规则

- 保留现有对话与工作现场分栏能力。仅当对话和现场分别能保有约 420px、480px 的有效宽度时采用分栏，比例沿用既有偏好；这些宽度是首轮设计起点，需实测校准。
- 空间不足时以明确的“对话／工作现场”切换呈现单一主视图，提供收起导航入口；不让文字挤到逐字断行，也不在用户阅读中因后台更新改变布局。
- 返回对话恢复输入草稿、滚动锚点和原焦点；返回成员总览恢复原成员所在位置。仅首次主动打开新详情时聚焦详情标题。
- 工作现场只保留一个明确的关闭或返回主出口；成员详情保留“返回团队总览”。二者按层级区分，不出现两个同权重、同目的出口。

## 3. 统一状态：执行事实、用户决定与网络状态分开存储

### 3.1 现有机制与缺口

`workbench-app/src/index.ts` 已有持久 `WorkTaskProjection`，包含 `status`、`waitKind`、`pendingAction`、`actionHistory`、成员、产物与 `observedAt`。`work-task-model.ts` 还会从对话工具记录推导页面模型，`WorkTaskPanel.tsx` 中另有状态解释逻辑。当前持久任务面向已派发运行，派发前方案和构建过程缺少同等完整的关联与投影。

实施时保留当前运行事实来源，在现有会话机制中补充派发前的准备记录；建立一个共享的展示状态解释函数。侧栏、顶栏、对话卡、工作现场不得各自匹配模型正文来判断当前状态。

### 3.2 建议的最小准备记录

以下是设计字段，不是已经存在的 API。实施前逐项映射现有事件与接口，优先复用已有类型。

| 数据组 | 最小字段 | 来源与约束 |
|---|---|---|
| 工作关联 | 会话、方案标识、方案修订号、构建标识、派发请求、运行标识 | 内部保持精确关联；缺少运行标识时不能挂上历史运行 |
| 方案 | 目标、交付、团队选择或成员定义、工作流说明、材料缺口、预算说明 | 保存实际展示并确认的方案；不能在确认后静默更换 |
| 授权 | 已确认修订、允许创建、允许派发、是否明确分步确认、确认时间 | 来自明确用户决定；模型说“已确认”本身不是授权证据 |
| 构建 | 未开始／请求中／已接收／执行中／成功／失败／结果待核实，已知步骤、重试关联 | 依据实际工具结果和 `build_status`；调用超时与构建失败分开 |
| 待处理 | 当前问题或影响确认标识、目标对象、待提交草稿 | 复用已有提问、人审或纠偏机制；只接受当前有效对象 |
| 展示元信息 | 观测时间、数据完整性、网络请求状态、当前可用动作 | 过期不等于失败；可用动作来自当前事实与授权共同判断 |

业务决定需要持久化；展开项、关注成员、选中标签与阅读位置继续作为阅读偏好。不能只在组件内存里保存“已确认”，也不能用浏览器偏好替代业务权限。

### 3.3 页面状态表

| 场景 | 主状态建议 | 次级说明 | 主动作 |
|---|---|---|---|
| 读取已有团队 | 正在读取团队信息 | 根据已声明职责核对当前要求 | 无提交动作，保留补充要求入口 |
| 设计新团队 | 正在整理团队方案 | 当前已知的整理内容；缺步骤就不编造 | 补充要求 |
| 等待方案确认 | 等待你确认方案 | 本次确认将创建／派发什么 | 语义明确的确认按钮 |
| 创建请求在途 | 正在提交创建请求 | 请求结果未返回 | 禁用重复提交 |
| 后台已接收创建 | 正在创建团队 | 已知步骤、耗时与最近更新 | 查看构建详情 |
| 创建结果未知 | 创建结果待核实 | 请求中断，正在查询是否已创建 | 查询状态；不立即新建第二队 |
| 创建明确失败 | 团队创建失败 | 失败步骤、保留方案、已尝试次数 | 重试创建；不可重试时给处理原因 |
| 创建成功但未授权派发 | 团队已就绪，等待派发确认 | 团队与最终任务摘要 | 确认派发 |
| 派发已接收但未执行 | 已接收，等待执行 | 排队或资源不足的真实原因 | 查看进展 |
| 单成员执行 | 负责人正在执行 | 当前具体阶段 | 查看进展 |
| fanout 且成员运行 | 2 名成员并行执行中 | 汇总将在分工完成后开始 | 查看进展 |
| 定时等待 | 已暂停，等待计划时间 | 后台提供的恢复时间 | 查看安排；无时间则说明未取得 |
| 人工或纠偏确认 | 等待你处理：事项名称 | 需要决定的范围与影响 | 处理事项 |
| 原节点离线 | 运行中断，等待原节点确认停止 | 受影响成员与保留工作 | 查看恢复方式 |
| 后台明确允许重试 | 阶段中断，可重试 | 对应阶段和已保留成果 | 重试这个阶段 |
| 用户停止请求已接收 | 正在停止 | 尚未确认所有执行停止 | 查看停止进度 |
| 停止已确认 | 已停止 | 已有成果仍可查看 | 查看保留成果 |
| 后台报告停止未确认 | 停止结果未确认 | 尚未核实的执行及原因 | 查看处理方式 |
| 结束且有最终成果 | 执行完成，成果待查看 | 文件或最终结论摘要 | 查看成果 |
| 结束但缺最终成果 | 执行已结束，最终成果待核对 | 已取得哪些阶段材料 | 查看已有材料 |

“并行执行中”是对现有运行和成员事实的产品解释，不要求把后台 fanout 状态改成另一种调度机制。执行完成不等于用户认可成果，更不等于产品验收通过。

### 3.4 冲突与更新规则

1. 只比较属于当前会话、方案修订、构建或运行的事件。旧运行、人审和重试回执不能覆盖新对象。
2. 明确终态不能被旧的“运行中”响应覆盖；使用后台修订或事件序号排序。只有时间戳时必须核实其语义，不能拿本地响应到达顺序当作执行顺序。
3. 停止请求待确认时，成员可以暂时仍在执行；主状态为“正在停止”，成员如实呈现，不能假装已经停止。
4. 运行中也可能有人工事项。主状态突出“等待你处理”，次级说明仍有几名成员工作，不隐藏后台执行。
5. 网络断连只增加“状态更新中断，最后观测于…”提示，保留最后已知事实并停止代表新鲜执行的循环动画。不能从短时无输出推断失败。
6. 创建失败后，构建失败态一直保留到明确的重试、方案变更或退出准备。再次查询团队列表不应把失败态重置为“匹配中”。
7. 历史文字原样保留；含当时状态的回复标明消息时间或“当时回复”。当前事实集中在任务栏与卡片，不重写历史使其看似一直正确。

## 4. 开始交流与团队选择的详细交互

### 4.1 首次输入与缺少配置

用户描述工作后立即保留消息并显示提交状态。模型不可用时，用可读模型名或“尚未选择可用模型”，提供直达模型设置的入口。保存模型设置后重新验证当前会话选择；无效时让用户选择可用模型，保留草稿。不得继续展示 `unconfigured/unconfigured` 或无有效选项的死胡同。

首页的工作区、项目、会话沿用真实对象关系，文案解释当前选择影响的工作位置。不要为了减少词汇而把本来不同的对象合并成一个概念。

### 4.2 候选目录与推荐结果分开

- 工具仅返回目录时，标题写“可用团队”，不宣称已经完成匹配，也不展示凭空计算的分数。
- 推荐理由来自需求与团队已声明职责的可核对比较。每个推荐显示“适合的部分”“需要补齐的部分”和默认工作流情况；未检查健康度写“尚未核实”。
- 默认显示最相关的少量候选，其他候选按需展开；模型没有给出排序依据时不伪造“最佳”。
- 卡片选择只把团队放入方案，不直接派发。按钮写“选用并查看方案”；缺默认工作流时写“查看补齐方案”，不能写可直接派发。
- 用户明确要求新建时，现有目录查询可以作为内部校验，但页面主视图应呈现新团队方案。已经被排除的团队不能继续出现可操作的推荐入口。
- 同一团队使用同一友好名称。随机标识只留在技术详情；未知名称显示“未命名团队”并用职责摘要辅助辨认，不伪造一个已持久化的名称。

### 4.3 方案卡信息结构

```text
体验验收方案                         等待你确认
目标：评审本地知识库的关键任务链路
交付：问题清单、优先级、改进建议

团队：体验验收团队 · 4 名成员
选择理由：覆盖信息架构、交互与独立复核
分工：负责人 → 两名评审员并行 → 独立终审
材料：尚缺产品入口与测试范围
预算：已确认的上限／建议值，明确其执行约束

本次确认后：创建团队，完成后等待你确认派发
[确认并创建团队]  [调整方案]
职责、完成标准与工作流详情 ▸
```

卡片默认容纳一段目标、最多三条交付摘要、一条工作关系说明和关键限制。详细职责与标准采用已有折叠和阅读组件，不建设新的配置表单。数字、人数和并行关系必须对应真实方案，示意图中的 4 人不是产品固定人数。

材料缺口要提前出现。若任务必须实际操作产品却没有入口，默认先补齐必要材料再派发；用户明确只要求资料缺口评估时可运行该范围。不得擅自替用户扩大成无证据的完整验收，也不能用任务过程测试的缺材料结论推断产品有缺陷。

### 4.4 确认、修改和重复提交

| 情况 | 应有行为 |
|---|---|
| 已明确确认团队、范围和交付，包含创建与派发 | 直接按已授权范围继续，不重复问同一问题 |
| 用户要求先创建、再确认派发 | 创建完成后停在已就绪状态；所有入口均不能自动派发 |
| 用户只选了团队 | 展示任务方案；不能把选中动作解释为授权全部执行 |
| 修改团队、交付、预算上限或执行范围 | 更新方案修订，标明具体变更；只重新确认受影响授权 |
| 仅修改说明措辞，不改变执行内容 | 不制造新的审批层；保存展示修订并保留原业务决定 |
| 双击、刷新后重复发送同一决定 | 复用原请求标识，查询原结果；不重复创建或派发 |
| 旧卡片仍可见 | 标记已处理／已被新方案替代，去掉可提交入口 |
| 网络失败但后台结果未知 | 保留提交中或待核实状态，查询后再决定是否重试 |

提交成功后在对话中生成可读摘要，例如“已确认：创建 4 人验收团队；创建完成后另行确认派发”。摘要关联确切方案修订，点击可查看当时内容。不能只保留“1/1 已回答”。

按钮选中态、禁用态、提交中与失败重试统一复用现有提问/计划审阅组件。自由文本确认仍可用，但由实际决定记录进入同一流程；含糊回复只澄清真正不明确的部分。

## 5. 团队构建与派发的详细交互

### 5.1 构建展示采用实际步骤

提交创建后，原方案卡保持位置，进入构建态。后台返回构建标识后由 Host 跟踪 `build_status`，不让模型在前台长时间循环查询。常见步骤可以解释为定义检查、模板构建、成员与工作流准备、校验就绪，但只有后台提供对应事实时才展示。

若接口只有已接收和最终结果，页面只写“正在创建团队”，显示已耗时与最近更新；不画五个虚构阶段或随时间增长的百分比。实际完成步骤数与总数可展示，但不能把完成 1/4 阶段写成耗时完成 25%。

### 5.2 请求结果与失败类型

| 后台事实 | 显示文案示例 | 后续处理 |
|---|---|---|
| 创建请求尚未返回 | 正在提交创建请求 | 原按钮禁用，防止重复提交 |
| 返回 build_id 且执行中 | 正在创建团队 | 持久关联，后台查询 |
| 超时或连接断开 | 创建结果待核实 | 先按原幂等键或构建标识查询，不能直接重建 |
| 明确 template_build_failed | 团队创建失败：模板构建未完成 | 有可读原因则展示；没有就说明尚未获得更具体原因 |
| 部分步骤成功 | 团队尚未就绪，已保留部分创建记录 | 明确可恢复范围，不能假设失败即完全未创建 |
| 完成且默认工作流可用 | 团队已就绪 | 根据已记录的派发授权决定继续或等待 |
| 团队存在但工作流不可用 | 团队已创建，工作流尚不可用 | 提供现有修复流程；派发入口不可用并解释原因 |

自动重试仅限已有安全重试策略，不新增无上限循环。页面说明“第 2 次尝试”以及正在处理的同一构建；使用已有请求标识重放与明确失败后的新尝试须遵守服务端幂等语义。修改方案后不能复用旧请求键提交不同事实。

### 5.3 失败卡与派发结果

失败卡包括失败步骤、可读原因、已保存的方案或资源、尝试次数、下一步。主操作优先恢复同一工作；重试接口尚不支持时，可通过已有对话恢复入口继续，但必须准确写成“继续处理创建失败”，不能宣称点击即可修复。

原方案已授权自动派发时，创建就绪后先持久记录派发请求再提交；创建成功不是派发成功。只有返回明确派发回执才显示“已接收”，得到运行事实后才显示成员执行。派发失败保留团队与方案，重试不重新创建团队。用户要求二次确认时，在这里显示最终派发摘要。

## 6. 团队运行、干预和成果

### 6.1 进展页首屏

```text
体验验收团队
2 名成员并行执行中
已完成 1/4 个执行阶段 · 独立终审等待评审结果

需要你处理的事项（仅在确实有事项时出现）

阶段关系
✓ 范围整理
  ├ 信息架构评审 · 执行中
  └ 交互动效评审 · 执行中
○ 独立终审 · 等待两项结果

最近进展
19:27 负责人已完成范围整理
19:28 两名评审员开始执行

团队成员 ▸                 已有阶段材料 1 ▸
```

关系来自真实工作流；只有阶段列表而无依赖数据时显示“已记录的执行阶段”，不靠成员姓名、角色排列或“汇总”字样猜拓扑。为同名阶段补充成员名，在技术上保持 nodeId 和执行尝试区分。负责人可能多次参与，不能以一个成员绿点代表整项职责永远完成。

### 6.2 成员列表和详情

- 列表每行呈现姓名、角色/当前阶段、状态及一条近期公开更新，职责最多两行摘要；点击详情查看完整职责与输入。
- 详情顺序为当前阶段与结果、最新公开更新、输入依据、阶段成果、工具活动。运行位置和技术信息放在次级位置，不与状态争抢首屏。
- 工具活动一项一行，明确“读取材料：完成”“检索资料：失败”等具体动作。未知工具用“工具活动”，禁止多项都叫“执行与校验完成”；工具完成不改变成员状态。
- 工具调用数只有在数据完整时显示精确值；未提供记录时写“工具记录暂不可用”，不能把未记录显示成 0 次调用。
- 阶段报告显示已有标题、有限预览和“打开阶段材料”。不擅自生成不存在的摘要；长正文保留完整可访问入口，不继续撑大进展页。
- 关注成员沿用现有能力，明确说明其实际效果；不能暗示会发送系统通知，除非已有通知能力。

### 6.3 关键事件与历史回执

在现有对话与运行历史中统一呈现关键事件：确认方案、开始创建、创建失败/成功、派发接受、阶段完成、人工决定、停止、恢复和最终成果到达。首批复用现有记录，不新增完整事件总线或全局审计平台。

每条事件保留发生时间、对象、动作和结果。重试回执示例为“19:42 已接收重试：信息架构评审员／交互评审阶段”，后续执行开始形成关联事件，不能把“已接收”说成“已恢复成功”。去重键采用真实事件标识或对象＋执行尝试＋修订；不能按相同文案去重。历史记录不完整时标注“部分过程未记录”，不补写缺失故事。

### 6.4 人审、纠偏与停止

| 动作 | 用户先看到 | 提交后 | 失败或过期 |
|---|---|---|---|
| 人工终审 | 问题、待审成果、选择及影响 | 保存草稿到回执，显示已提交并等待后台继续 | 保留输入；旧 interactionId 不能提交到新等待 |
| 对成员提问 | 带成员与阶段引用的原对话输入 | 只形成普通讨论 | 不自动修改运行 |
| 明确提出调整 | 目标与调整要求 | 提交纠偏请求，收到影响后确认是否应用 | 不把受理当作已应用，不重新匹配团队 |
| 确认应用调整 | 影响范围、需重做阶段、保留成果 | 绑定当前运行与 correctionId 提交 | 影响已变化时更新受影响内容后再确认 |
| 停止运行 | 现有停止交互，明确保存已有工作 | 显示正在停止并禁用重复请求 | 未得到确认时保持未确认，禁止显示已停止 |

人工答复渲染成“决定：通过；说明：…”等业务文字。原 JSON 只在允许的诊断详情中呈现，不作为默认操作回执。

### 6.5 中断恢复

中断卡先显示受影响成员和已保留成果，再解释恢复条件。区分原节点重新上线、新节点上线、原执行仍未确认停止、后台明确允许重试四种事实。新节点健康不意味着原执行已停止，也不意味着会自动接管。

首批提供运行节点设置入口和可读恢复说明；若现有数据能精确关联受影响任务，再提供跳转。节点替换、强制释放占用或令牌重新签发若无现有机制，不在此次整改中新增。不能为了让验收走通而改数据库状态、伪造停止确认或让另一节点冒充旧节点。

### 6.6 完成与成果页

任务结束时在原位置更新状态，增加“成果已就绪”入口，不自动切页、不抢焦点。用户第一次主动打开一个已完成任务时可默认成果页；已经在阅读进展的用户保留当前标签。

成果页先显示当前运行的最终成果、可读结论和文件入口，再显示阶段材料，最后是成果评价和运行历史。只有阶段记录时显示最终成果缺口；文件下载失败时保留已有记录并提供重试，不把文件获取失败改写成整项运行失败。评价是用户后续决定，不自动等同于质量通过。

## 7. 视觉与动效细则

### 7.1 视觉层级与文案

| 对象 | 首轮规则 |
|---|---|
| 页面标题 | 沿用现有字体与主题令牌，20–24px 为校准起点，避免与每段 Markdown 一级标题争抢 |
| 正文、次级说明 | 正文以约 14px 为起点，中文行高约 1.6；次级说明不承担唯一关键事实 |
| 空间节奏 | 优先复用 8/12/16/24px 间距体系；减少同层分隔线与空段重复 |
| 状态与按钮 | 每个决策区域一个主操作；危险操作保持次级可发现，不与正常主操作同权重 |
| 状态颜色 | 颜色、图标和文案共同编码；完成、等待、失败不能只靠圆点颜色区别 |
| 职责与名称 | 姓名正常换行；长英文标识只在详情折行；禁止状态被挤成一字一行 |
| 错误提示 | 页首一次原因摘要，阶段详情提供具体事实；不在四处重复同一句红色警告 |
| 数据缺口 | 具体写缺少的活动类型及影响；“尚未开始”与“未被记录”区别处理 |
| 用量与预算 | 分清本轮对话、团队运行、构建用量；缺来源就说明范围未知，不重复加总 |

不把建议预算直接写成系统“硬上限”。只有实际约束执行链路、范围与超限行为经过核对，才使用上限承诺；构建预算和运行预算若范围不同须分别说明。

默认业务流收起底层调用与思考块，保留模型公开的工作说明。错误码和工具详情通过诊断层按需查看；凭据与敏感输入不能因折叠成详情就视为可展示。界面隐藏实现细节不等于删除原始会话证据。

### 7.2 动效候选参数

以下为设计起点，尚未通过录屏校准。实现优先复用现有 motion token；不为每个组件新增独立动画参数。

| 场景 | 候选行为 | 减少动态效果时 |
|---|---|---|
| 按钮选中、禁用、提交 | 约 120–160ms 的背景/边框变化；点击立即给反馈 | 即时样式切换 |
| 当前运行 | 每个可见任务区域最多一处低幅循环状态提示；其他成员用静态状态 | 静态图标与文字 |
| 阶段完成、成员接手 | 约 180–240ms 的状态过渡；新事件短暂背景高亮约 0.8–1.2s | 直接更新，保留事件文字 |
| 等待用户 | 停止思考计时与扫光，稳定呈现问题和主操作 | 同普通模式 |
| 构建重试 | 明确尝试次数，复用当前主要运行信号 | 显示次数与状态 |
| 新活动到达 | 跟随最新时追加；阅读历史时显示新活动提示 | 不强制平滑滚动 |
| 成果到达 | 原位置状态更新与成果入口 | 即时更新，保持标签和焦点 |

不要叠加团队卡扫光、工具扫光、Todo 旋转、输入区思考、多个状态点追逐。提交状态及时显示，但不保证后台在固定毫秒内响应；不能用预设动画掩盖真实等待。

### 7.3 滚动、键盘与读屏

- 保留 `PublicUpdates` 已有的跟随/历史阅读状态；新消息不改变历史阅读锚点。用户主动回到最新才恢复跟随。
- 尽量让页面拥有一个主纵向滚动区域；必须独立滚动的长记录在边界允许合理传递滚动，不能困住触控板操作。
- 对话回看中后台插入长内容，不自动跳底；成员与成果切换恢复各自阅读位置。
- 一个工作视图由一个协调的状态区域播报主状态变化；成员长文本不逐 token 播报。人工事项需要提示，但不反复从多个卡片播报同一问题。
- 提问提交成功后把焦点放到完成摘要或合理的后续入口；仅失败时聚焦当前表单错误。弹层关闭回到触发按钮。
- 所有按钮、标签、折叠和重试可用键盘操作；焦点可见；tooltip 不承载唯一必要信息，不覆盖当前决策区域。
- 对比度按既有可访问性基线实测，当前无测量证据，不宣称所有灰色文本已达标。

## 9. 分批实施与优先级

### 9.1 严重度标准

P0 仅用于已证实的越过明确授权、重复创建/派发导致严重副作用、错误显示停止或完成并可能导致危险操作、跨运行混入成果。当前观察中有相关风险，但未证明所有风险已经发生。复现后按实际影响判定，不能以修复顺序代替缺陷严重度。

P1 用于使主流程难以判断或恢复的问题：状态冲突、构建失败无明确出口、等待用户仍显示思考中、恢复条件不清。P2 用于不阻断任务的排版、名称、重复说明与动效品质问题；若动效影响键盘、读屏或操作，则按影响提升。

| 批次 | 改动范围 | 对应证据 | 完成条件 |
|---|---|---|---|
| A：事实与操作一致 | 共用状态解释；待用户停止思考动画；失败不回退匹配；停止与完成证据约束；操作入口尊重现有授权 | 010、012、015、016 | 同一状态在四处一致；无新建或派发越界；旧回执不能触发新执行 |
| B：准备过程闭环 | 方案摘要、修订与可读确认；创建关联与后台状态查询；创建失败与派发失败区分；重复提交收敛 | 009、011、013、014、015 | 一次确认与用户指定两次确认都可走通；刷新后恢复准确状态；未知结果不重复创建 |
| C：运行现场层级 | 阶段关系、现有事件与回执整理、成员摘要、长阶段材料收起、恢复入口和成果收束 | 004–008、011、012、016 | 能识别并行和交接；成果不串运行；完成不抢阅读位置 |
| D：视觉与动效 | 文案、断字、tooltip、共享动效与减少动态效果、滚动和焦点 | 001–003、006、009、010、012 | 目标视口不破版；关键控件可键盘操作；录屏证明无多重循环竞争 |

批次 A 可先针对已有运行投影和确定失败事实修复；批次 B 再建立完整准备记录。若某个 A 项依赖 B 的持久授权字段，应明确合并交付，不能只隐藏按钮便声称约束已完成。每批按依赖交付，不先同时修改所有共享文件。

## 10. 可执行验收矩阵

每项记录初始条件、操作、预期、实际、证据路径、是否通过及阻断原因。模拟数据可验证稀有状态，但必须标为模拟；真实后台验收与模拟结果分开。

| 编号 | 场景与操作 | 必须验证 | 证据来源 |
|---|---|---|---|
| AC-01 | 未配置模型，写入草稿后配置模型返回 | 可直达设置，草稿保留，会话模型恢复可用 | 浏览器 |
| AC-02 | 现有团队推荐并选择 | 目录不冒充推荐；选中不直接派发；方案理由与缺口可见 | 组件＋浏览器 |
| AC-03 | 要求不复用现有团队 | 不出现可误触的旧团队派发入口 | 回放＋浏览器 |
| AC-04 | 等待结构化回答超过一分钟 | 四处一致显示待用户，思考计时与循环动画停止 | 状态测试＋连续画面 |
| AC-05 | 一次明确确认创建并派发 | 不重复确认；回执明确授权范围；只创建和派发一次 | Host 行为测试＋真实流程 |
| AC-06 | 只确认创建，要求另行确认派发 | 创建成功停在已就绪；其他入口也不能派发 | Host 行为测试＋真实流程 |
| AC-07 | 修改已确认方案的团队或预算 | 旧卡不可执行，变化可见，只确认受影响部分 | 状态测试＋浏览器 |
| AC-08 | 双击提交、刷新、重复发送同一确认 | 收敛到同一请求与结果，草稿/确认不丢失 | 幂等集成测试 |
| AC-09 | 创建请求超时但后台已接受 | 待核实并查询原结果，不产生第二团队 | 故障测试 |
| AC-10 | 创建明确失败并尝试恢复 | 对话、顶栏、侧栏、现场均失败；保留方案和尝试次数 | 浏览器＋投影测试 |
| AC-11 | 创建成功，派发失败后重试 | 保留原团队；仅重试派发，状态不回到团队创建 | 集成测试＋浏览器 |
| AC-12 | 负责人完成，两名成员并行 | 状态明确执行人数；同名阶段可区分；关系来自真实数据 | 真实运行＋连续画面 |
| AC-13 | 工具无记录或工具完成但成员运行 | 不把缺记录变成 0；不把工具完成变成成员完成 | 组件测试 |
| AC-14 | 阅读历史时到达多条更新、长报告、最终成果 | 锚点与焦点不动；新活动可发现；主动回最新有效 | 浏览器录屏 |
| AC-15 | 人工终审提交后重开会话 | 答复人话呈现；已受理与已继续区分；旧表单不能再次执行 | 回放＋真实流程 |
| AC-16 | 对成员提问，再明确要求修改 | 普通提问不修改；修改提交影响后再应用；目标不串运行 | 行为测试＋浏览器 |
| AC-17 | 原节点掉线，再上线新节点 | 主状态仍解释原执行未确认；不冒充自动恢复 | 故障测试＋浏览器 |

| AC-20 | 执行结束但只有阶段产物 | 明确最终成果缺口，无交付成功或采用评价误导 | 回放＋浏览器 |
| AC-21 | 刷新与乱序响应、旧运行更新到达 | 当前对象不串；终态不回退；无数据标明未知 | 投影/同步测试 |
| AC-22 | 减少动态效果、全键盘和读屏 | 无循环动效；焦点恢复；同一事项不多处重复播报 | 浏览器与辅助技术实测 |

| 设计项 | 本轮落点 | 准确边界 |
|---|---|---|
| 四区域状态 | Host 统一解释后提供 displayState，侧栏、搜索、任务栏、对话卡、现场与项目进展使用同一含义 | 旧投影保留兼容回退；待用户交互仍由既有交互机制管理 |
