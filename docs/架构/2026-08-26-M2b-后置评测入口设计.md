## 1. 目标与验收

**unevaluated 团队有真实的评测触发入口：提交真实合同 → 走 candidate+publish 链（评测专用语义）→ 通过则团队原子翻转 evaluated 并获得 published workflow，全程可审计。**

验收：

- unevaluated 团队 → 真实合同 → 通过 → `evaluation=evaluated` + published workflow + 团队记录评测来源（run/contract hash/时间）；
- 评测失败 → 团队保持 unevaluated 且**资产零变更**（评测专用 run 禁止 BlueprintPatch）；
- 占位合同（`post_evaluation_placeholder*` 全字段）提交被拒；
- 同团队并发评测被拒；评测进行中团队被修改触发 CAS 失败而不是错误认证；
- 通用 publish 路径无法再绕过评测（见 §3.6）；
- 回归：元团队路径、模板路径、既有 optimize 路径不变。

## 2. 核心形态：evaluate 语义的 optimize BuildRun

复用 optimize 的 baseline 捕获与 scope 语义，但用**评测专用控制器分支**约束行为：

```
POST /v1/teams/:id/evaluations     （RequireRole("admin")，与 from-template 现状一致）
请求：{ contract: <真实 EvaluationContract>, idempotency_key, budget: { max_cost_usd } }
响应：201 { build_run_id, status } / 422 { problems } / 409（并发评测或幂等冲突）
```

管线：

```
校验：团队存在 + evaluation=unevaluated + 合同合法（占位 ID 全字段拒绝：public ID、perturbation ID、base_scenario_id 及前缀变体）
  → 并发闸：同团队已有 active evaluation run → 409（DB 唯一约束或 advisory lock）
  → 机器合成 brief（mode=optimize，team_id=目标，allowed_assets 从 baseline 实时读取）
  → CreateBuildRun（compiler_v1，标记 evaluation_only）
  → blueprint 派生：读原模板 Blueprint lineage（不是只读 baseline——baseline pin 不含 display_name/职责/能力），
    全 roster preserve_existing；declarative 模板需重新冻结绑定新 run 的 spec
  → max_revisions=1（evaluation_only 硬约束：业务质量失败不触发 BlueprintPatchPlanner，直接 blocked）
  → 授权：人工 admin 授权（v1 不做自动额度，理由见 §3.5）
  → candidate 执行真实合同 → 通过 → publish
  → 原子翻转（§3.3）
```

## 3. 关键决策（互审修正版）

### 3.1 评测不改变资产

`max_revisions=1` + evaluation_only 分支：business-quality 失败直接 blocked，不进入 BlueprintPatchPlanner——**评测的职责是审判，不是修改**。

### 3.2 合同替换 = 新 run 新合同

不触碰原模板 BuildRun 的冻结占位合同（授权会重算 hash 要求一致，不可变）。团队保留 `evaluation_build_run_id`、`evaluation_contract_hash`、`evaluated_at` 三个溯源字段——能回答"由哪份合同、哪次报告认证"。

### 3.3 原子翻转

publication + 团队 evaluation 翻转 + BuildRun passed **同一事务**（补 `MarkPublishedTx`）；团队更新带 `evaluation='unevaluated'` CAS + baseline hash CAS（candidate 冻结时团队被改 → CAS 失败 → run blocked，不错误认证"后来被改过的团队"）。

### 3.4 并发闸

同团队同时只允许一个 active evaluation run（DB 唯一约束）；评测进行中 roster/draft 写入口对 evaluation 状态不加锁（v1 靠 CAS 兜底，不加读写锁）。

### 3.5 预算与授权

**v1 不做自动额度。** 互审证明：compiler candidate 路径缺前/后预算闸（会"先超支后照常发布"）、scenario 循环间无预算检查、tool_calls 记账为零。自动额度上线前必须先把 candidate/scenario/judge 接入预算闸——那是一项独立工作。v1：人工 admin 授权 + 显式 budget + ledger 如实记账。

### 3.6 关闭 publish 绕过

互审发现通用 `handlePublishWorkflowVersion` + published workflow 路由不检查 evaluation，unevaluated 团队可经此获得 published workflow。处置：通用 publish 路径对 unevaluated 团队的 draft 返回明确错误并指向 evaluations 端点；published workflow 路由维持现状（能 publish 的一定是 evaluated 或历史团队）。

### 3.7 M2c 接口预留

本程引入 build 带拥有的 `SemanticJudgeExecutor` 接口与输出 DTO（保留 attempt/run ID/usage ledger 协议），当前实现仍委托 metateam judge——M2c 归建时只换实现，不重拆评测入口。

## 4. Console 入口

unevaluated 团队卡片"未评测"标识旁提供"开始评测"（合同编辑 + 提交 + 进度 + 报告复用既有 BuildRun 报告面）。

## 5. 工作票

- M2b-1：evaluate 端点（校验 + 并发闸 + brief 合成 + lineage 派生 blueprint + 人工授权 + 幂等）；
- M2b-2：evaluation_only 控制器分支（max_revisions=1、禁 patch）+ 原子翻转（MarkPublishedTx + CAS）+ 溯源字段；
- M2b-3：publish 绕过关闭 + SemanticJudgeExecutor 接口预留；
- M2b-4：Console 评测入口 + 全链验收。

```bash
go build ./... && go vet ./... && go test ./internal/... ./cmd/...
```
