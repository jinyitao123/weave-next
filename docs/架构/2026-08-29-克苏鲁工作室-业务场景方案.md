## 1. 业务目标

创作一部洛夫克拉夫特式（克苏鲁）小说的**前三章**，质量目标：三章设定连贯、恐怖递进、文体克制不堆砌、无模仿腔。产出物是可读的三章成稿。

同时是 weave-next 的能力综合验证：M1 建队、declarative_v1 自定义工作流、M3 人工终审、M2b 后置评测、预算账本。

## 2. 团队设计

| 成员 | role | 职责 | 设计理由 |
|---|---|---|---|
| lead-editor（主编，lead） | avatar | 正典一致性、章节节奏、最终裁决 | 有人对"三章是一个整体"负责 |
| mythologist（神话学者） | worker | 设定圣经：实体/教团/禁书/禁忌知识规则、三章恐怖递进曲线 | 克苏鲁的恐怖来自知识体系，先有规则后有故事 |
| writer（主笔） | worker | 逐章执笔、按审校意见修订 | 长上下文装圣经+大纲+前章 |
| critic（批评家） | worker | 风格批评、连续性检查、模仿痕迹清除 | 写作团队没有批评家就是日记本 |
| 终审（人工节点） | — | 全稿终审（用户出演） | M3 WaitHuman |

**核心机制认知**：一致性靠物化的正典文档（设定圣经是节点输出，后续节点经 node_output 引用），不靠主笔记忆；质量靠批评家 + 人工终审 + 后置评测三层约束，不靠自觉。

## 3. 工作流拓扑（declarative_v1，经互审修正）

```
canon(神话学者 consult) → outline(lead 节点，主编)
  → ch1_draft(writer) → ch1_critique(critic) → ch1_revise(writer)
  → ch2_draft → ch2_critique → ch2_revise
  → ch3_draft → ch3_critique → ch3_revise
  → final_review(wait kind=human)
  → assemble(transform: 聚合圣经+大纲+三章+终审意见为单一对象)
  → deliver(交付聚合对象)
```

互审修正的关键语义：

- **顺序 worker 全部 `kind: consult`**（dispatch 只允许 parallel 分支）；lead 节点用 `type: lead` 自动绑定主编（主编不是 TeamWorker，不能走 worker stable_ref）；
- **reject 不自动分流**：人工 payload 只作记录，approve/reject 都走 success 边。v1 的返修语义 = 驳回后**带着批注发起新一轮 dispatch**（批注进 run input），不在图内回返；图内返修循环（condition + loop）留待 v2；
- **交付物只有一个聚合对象**（deliver 是终端节点、单 result）——圣经/大纲/三章先经 transform 聚合；
- **正典只在同一 run 内连续**（ValueRef 仅支持 run_input/node_output/literal）；跨 run 复用需把圣经文本放进新一轮 dispatch 的输入。

完整 nodes/edges/contract 骨架见互审产出的修正版（已验证可通过静态校验），实施票据此落细。

## 4. 团队配置（team.yaml，互审修正版）

```yaml
schema: team-template/v1
name: mythos-atelier
display_name: 克苏鲁工作室
purpose: 创作三章连贯、风格克制且恐怖递进的洛夫克拉夫特式小说
template: delivery_rework_loop      # 占位：独立 declarative_spec 提交后 blueprint 改为 declarative_v1
template_parameters:
  lead_instruction: 明确创作任务，组织写作与审校
  primary_ref: writer
  reviewer_ref: critic
  max_iterations: 1
  result_requirements:
    mythologist: 输出可供后续节点引用的设定圣经
    writer: 输出完整正文或按批评意见修订后的章节
    critic: 输出具体、可执行的风格与连续性审校意见
members:
  - name: lead-editor
    display_name: 主编
    role: avatar
    responsibilities: [正典一致性, 章节节奏, 最终裁决]
    capabilities: [coordination]
  - name: mythologist
    display_name: 神话学者
    role: worker
    responsibilities: [设定圣经, 禁忌知识体系]
    capabilities: [worldbuilding]
  - name: writer
    display_name: 主笔
    role: worker
    responsibilities: [章节执笔, 按审校意见修订]
    capabilities: [prose]
  - name: critic
    display_name: 批评家
    role: worker
    responsibilities: [风格批评, 连续性检查, 模仿痕迹清除]
    capabilities: [critique]
lead: lead-editor
delivery:
  success_criteria: [三章设定自洽, 恐怖递进, 文体克制不堆砌, 无明显模仿腔]
budget:
  max_cost_usd: 8        # 注意：约束建队/评测，不是正式 dispatch 的总成本上限（互审 #24）
```

**配置边界**：`declarative_spec` 属于模板创建请求的顶层字段，不是 YAML 字段。该设计供维护者配置后台工作流时参考，不构成独立业务入口。

**模型**：v1 不写 `model_ref`（未验证 workspace 里存在该 binding，冻结会失败），用服务端默认；CLI 引擎需每成员显式 execution_policy，v1 不动。

## 5. 写作规则（技能包的 v1 替代形态）

互审确认：M1 模板无法给成员绑定技能（schema 无 skills 字段、applier 不接受）。v1 把《洛夫克拉夫特文体》规则写进 writer/critic 的 `result_requirement` 与节点 instruction：

1. **反面清单**：辞藻配额（eldritch/cyclopean 类词每章限一次）、禁"无法名状"滥用、展示而非讲述；
2. **档案体框架**：手稿/信件/证词装置、不可靠叙述者的渐进崩坏；
3. **认识论恐怖**：知识即毁灭，主角是学者不是英雄；
4. **节奏**：慢热积累，每章只揭开一层。

正式技能包（版本化 skill + AgentVersion 绑定）列入后续票。

## 6. 评测（M2b，显式触发）

终审放行后，显式调用 `POST /v1/teams/:id/evaluations` 提交完整 EvaluationContract（自定义 rubric/场景在此表达——模板合成的合同只有 floor + 占位）：

- rubric：恐怖递进 / 文体克制 / 原创性 / 可读性；
- 场景：抽段落与圣经的事实一致性；
- 语义裁判：归建后的 SemanticJudge 首次实战。

## 7. Workbench 验收目标

在 Workbench 选择准备好的团队，确认创作范围后执行；在同一工作对话处理人工终审，再核对已保存的三章正文与运行归属。是否通过必须由实际任务记录证明。

验收判据：

- 链路：建队机制 < 60 秒、节点顺序正确、人工挂起/恢复语义正确、交付物落库（须经正式 conversation dispatch 才投影用户交付物）；
- 质量：用户终审判断 + 评测合同结果；
- 平台：预算账本如实、失败可归因；
- 缺陷产出：跑完必出一份缺陷清单（平台/团队设计二分），零缺陷也要明确记录。

## 9. 互审记录（codex 只读审计，2026-08-29）

审计列出 25 处"方案写法 vs 代码现实"的不支持项，全部采纳修正。要害项：

| 原方案 | 代码现实 | 处置 |
|---|---|---|
| declarative_spec 写在 YAML | 是 API 顶层 JSON 字段；YAML 白名单拒绝 | §4 配置边界说明 |
| `template: declarative_v1` | 模板编译器只认 4 内置拓扑；独立 spec 提交后 blueprint 才改为 declarative_v1 | §4 占位模板 + 完整 template_parameters |
| `model_ref: gpt-5.6` | 无 provider binding 时冻结失败 | v1 删除，用服务端默认 |
| reject 驳回即图内返修 | 人工 payload 不分流，approve/reject 同走 success 边 | §3 v1 语义改为"驳回=新 dispatch 带批注"；原文自相矛盾处修正 |
| 技能包自动注入 | M1 链路无技能绑定 | §5 改写为 result_requirement 承载 |
| 交付物多份 | deliver 单 result 终端节点 | §3 聚合 transform |
| 跨 run 正典 | ValueRef 仅 run 内 | §3 如实标注 |
| budget 控制正式创作花费 | 只约束建队/评测 | §4 注释修正 |

另确认：技能正式绑定需"版本化 skill + AgentVersion + 工作流重发布"链路；完整 spec 骨架（可通过静态校验）已产出，实施票以其为准。
