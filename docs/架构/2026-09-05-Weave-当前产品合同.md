# Weave 当前产品合同

2026-09-05 · Workbench 是唯一业务入口，仓库清理与联合验收进行中

**让用户把多阶段工作交给专业团队，并拿回可以采用的成果。** 当前面向有部署支持的私有试点。第一优先级是入口清楚、任务卡住后有办法继续。

## 入口分工

| 入口 | 用户在这里做什么 |
|---|---|
| Workbench | 选择团队、确认任务，看进度、处理问题、领取成果 |
| Workbench 运行节点设置 | 由维护者接入执行机器、查看连接与容量、撤销失效节点 |

Workbench 是唯一受支持的页面客户端。Weave 只为它提供团队执行、恢复、运行节点接入和成果保存。服务端不再内嵌独立维护页面；诊断、升级、备份和宿主进程管理由 CLI、系统服务或 Compose 完成。独立 Codex/Claude 客户端和业务 CLI 退出现行支持；MCP 是 Workbench 的内部连接，Codex 等执行引擎继续保留。

Workbench 读取平台保存的执行事实，不把聊天摘要当成任务状态。

Workbench 的本轮交互按[工作对话方案](2026-09-05-Workbench-工作对话方案.md)收敛：主对话贯穿工作，顶部持续显示事实，现场按需展开成员与成果；增量成员过程和项目只读汇总在同一方案内分批开发，统一验收。

## 一条日常路径

**选团队 → 确认任务 → 开始执行 → 领取成果**

- 选团队时，说清团队适合做什么。没有合适团队就说明缺口。
- 确认任务时，用户看得见输入、预期成果和需要自己决定的事项。
- 执行中，显示已经做到哪里、是否在等待、下一步由谁处理。建队、编译和评测不成为已有可用团队接活的额外步骤。
- 领取时，直接打开属于本次任务的最终成果。没有可读成果，不能只凭运行状态宣称交付完成。

## 卡住后怎么办

| 情况 | 应向用户说明 | 支持的处理方式 |
|---|---|---|
| 需要用户补充或确认 | 缺什么、为什么需要 | 提交答复后继续 |
| 等待执行机器或外部服务 | 等待原因、已完成到哪里 | 等待恢复，或停止任务 |
| 某个阶段失败 | 哪一步失败、是否可以重试 | 支持时重试该阶段；否则说明需要维护者处理 |
| 用户希望结束 | 正在停止还是已经停止 | 停止后仍可查看已保存的工作 |

重试前应说明从哪里重做、哪些成果会保留；需要从头开始时也要明说。停止请求不能提前显示为已经停止，已经完成的外部动作不会因此自动撤回。关闭页面再回来，应找到同一项工作。

## 当前事实与本轮目标

当前已有团队派发、任务记录、人工等待、停止和交付物能力；8 月 31 日记录过一组固定版本的 Workbench 业务验收。本轮要把入口说明和恢复操作补齐、讲清，再验收当前版本。旧版本记录、单元测试通过或新增工具都不能替代当前 Workbench 的实际体验验收。

本轮完成标准是在 Workbench 交出任务、看懂阻塞、使用可用恢复操作、保留已保存成果并领取正确结果。清理后的源码须重新完成工程检查与 Workbench 联合验收；清理前的构建、旧版本记录和工具测试各自保留适用版本，不能代替这次验证。
