# Workbench 并仓迁移计划

日期：2026-09-05

## 目标

将 `weave-workbench` 合入 `weave-next`，形成唯一产品仓库。合并后，一次变更可以同时约束页面、接口、执行引擎、数据迁移和部署版本。

并仓不改变现有用户数据目录、工作区目录、API 合同和运行方式。DSH 只作为 Workbench 内部实现存在，不再成为产品名称或独立发布入口。

## 目标结构

```text
weave-next/
├── cmd/                    # Weave 服务与维护命令
├── internal/               # Go 执行、编排、存储与产品 API
├── workbench/              # Workbench 的 TypeScript 工作区
│   ├── apps/               # Workbench 服务与网页入口
│   ├── packages/           # Workbench 实际运行依赖
│   ├── native/             # Linux 权限隔离组件
│   └── package.json
├── deploy/                 # 唯一部署入口
├── docs/                   # 唯一现行产品与验收文档
├── Dockerfile              # Weave 后端镜像
├── Dockerfile.workbench    # Workbench 镜像
└── Makefile                # 统一开发、检查和发布入口
```

Go 的四层边界继续生效。TypeScript 工作区保持自己的包边界，不进入 `internal/`，也不与 Go 依赖规则混用。

## 固定决策

1. `weave-next` 成为唯一主仓库，`weave-workbench` 在迁移验收后停止接收变更。
2. Workbench 初始整体进入顶层 `workbench/`，不立即展开或改名数百个内部包。
3. 使用保留提交历史的并仓方式，不复制一个失去来源的代码快照。
4. 并仓后依据 Workbench 的构建与运行闭包删除无关 DSH 包、示例、网站和独立发布能力，不建立额外归档目录。
5. 继续使用同一个 `DSH_HOME` 和工作区卷，避免用户数据搬迁；产品界面、配置示例和现行文档不暴露 DSH 名称。
6. 后端与 Workbench 采用同一版本标识、同一源码提交和同一发布清单。

## 迁移步骤

### 第一阶段：冻结与引入

- 分别整理两个仓库当前工作树，使正在开发的恢复、交付和页面改动形成可追溯基线。
- 记录两个仓库的源码校验值、构建产物校验值和真实 Workbench 验收结果。
- 将 Workbench 历史合入 `workbench/`，保证原提交仍可追溯。
- 增加根目录的 Workbench 构建、检查和测试入口，此时不改变生产部署。

通过条件：并仓后的 Workbench 构建产物与迁移前最终产物一致；两个代码体系都能在新目录独立通过原有检查。

### 第二阶段：删除边界外内容

- 从 Workbench 启动配置、包依赖图和容器运行文件生成实际运行闭包。
- 删除未被 Workbench 产品、构建、测试或发布使用的示例、通用网站、独立 DSH 发布入口和无关包。
- 删除迁入后重复的产品文档、部署说明、贡献入口和品牌说明，现行结论统一放在根目录 `docs/`。
- 为根仓库增加产品边界检查，阻止独立 DSH 入口或名称重新进入用户界面和发布文档。

通过条件：所有保留目录都有 Workbench 用途；删除项没有运行时引用；干净安装、构建、类型检查和关键测试通过。

### 第三阶段：统一构建与部署

- 将 Workbench 镜像定义和网关配置迁到根目录部署体系。
- 根 Compose 一次启动数据库、Weave、运行时、Workbench 和网关。
- 修正容器依赖安装，确保 Linux 架构依赖从锁文件完整安装，不依赖主机预构建产物。
- 统一版本、源码提交、镜像标签、健康检查和发布清单。
- 根 `Makefile` 提供后端检查、Workbench 检查、完整构建和平台验收四组稳定入口。

通过条件：从干净检出可直接构建两张镜像；启动后匿名访问受控、登录可用、后端连通、重启后数据保留。

### 第四阶段：切换与退役

- 暂停独立 `weave-workbench` 仓库写入，在合并仓完成最终差异核对。
- 使用合并仓重新执行派发、人工处理、停止、断线恢复、重复请求和成果领取。
- 将部署与开发入口切到 `weave-next`。
- 删除本机和文档中对独立 Workbench 仓库路径的依赖；独立仓库不再作为开发或发布来源。

通过条件：完整真实闭环全部来自合并仓；没有脚本、CI、容器或现行文档引用旧仓库路径。

## 防止相互覆盖

- 先做纯路径迁移，再做删除和重构，不在同一提交中同时改业务行为。
- 合并期间后端接口合同和 Workbench 投影模型分别设为冻结面；需要调整时必须在同一提交补齐双方测试。
- 每个阶段结束都记录源码校验值和真实运行结果，失败时回到该阶段开始前的提交，不用手工反向复制文件。
- 数据卷、端口、API 密钥读取方式和运行时注册信息在切换完成前保持不变。

## 最终验收

- 根仓库可完成 Go 边界检查、Go 测试、Workbench 类型检查、关键页面测试和两张镜像构建。
- 一个根部署入口可启动完整产品，停止和重启不会丢失登录、工作区和运行记录。
- 真实运行中，任务状态、成员活动、人工处理、断线恢复和成果下载保持现有已验收行为。
- 页面、README、安装说明和容器输出只使用 Weave Workbench 产品名称。
- 独立 `weave-workbench` 路径不再参与开发、构建、部署或发布。

## 实施批次

建议用四个连续批次完成：历史并入、运行闭包清理、统一部署、真实切换。每批都保持主分支可构建，最终再退役旧仓库，避免出现两个半成品同时不可用。
