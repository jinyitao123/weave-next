## 1. 目标与验收

团队工作流里可以有"人"：跑到人工节点自动挂起，workspace 成员在 Console 待办看到任务、查看上下文、提交决定，工作流带 payload 恢复。

验收（故事 3 变体）：declarative 工作流含人工终审节点 → 派活 → 挂起 → Console 待办可见（含待审交付物引用）→ 提交批注与决定 → 流程按决定继续 → 全链在真实 PG 回归。

## 2. v2 与 v1 的关键差异（互审裁决摘要）

1. **不引入 human 成员概念**。v1 的 `kind: human` 成员会贯穿 template/blueprint/baseline/ChangeSet/applier 全链的条件编译，风险与收益不成比例。人工节点是**工作流构件**（wait kind=human），不是团队成员；roster 保持全 agent。团队成员 human 化留待未来真需求。
2. **declarative_v1 先长 wait 能力**。现状 declarative 编译器直接拒绝 wait/handoff 节点，machine 解码也只认 resume_schema/timeout_seconds——M3 必须先扩展这条通道（这是本程的机制本体）。
3. **payload 不落新字段**：合法 payload 作为 wait 节点的 `CompletedOutputs[nodeID]` 写入 + NodeID 推进到 success edge 目标（不推进会无限重新 park）。`ResumeRequest` 仅传输层增加 Payload；checkpoint schema 不升级。
4. **恢复走队列 continuation**，API 不直接执行 runtime（不绕过 lease/heartbeat）；新增 `human_resume` continuation kind + characterization tests。
5. **权限降级为真**：v1 任何当前 workspace 成员可完成；list/complete 端点做实时 membership 校验（JWT 不重查 membership 的洞顺手补上——仅限新端点，旧端点不改）；`assignee_role` 改名 `audience_ref`，纯展示，不做权限承诺；inbox 叫"workspace 人工待办"。

## 3. 核心设计

### 3.1 declarative wait 节点扩展

```jsonc
{ "type": "wait", "config": {
    "kind": "human",                 // 新增枚举；缺省 timer（现状不变）
    "resume_schema": {...},          // machine 既有固定 JSON Schema 子集
    "timeout_seconds": 259200,       // 可选；到期见 §3.4
    "task": { "title": "...", "instructions": "...", "audience_ref": "editor" }
} }
```

- machine `WaitConfig` 增加 `kind`/`task` 解码与校验；declarative_spec 放行 wait 节点（仅 kind=human 需要 resume_schema；timer 维持现状）。
- schema 校验复用 `machine.ValidateRuntimeInput`（既有固定子集），**不新增 JSON Schema 依赖**（base 白名单只有 4 项，撞线）；子集不支持的长度限制在 HTTP 边界强制：payload ≤ 64KiB、WaitDetail ≤ 16KiB、title ≤ 256B、instructions ≤ 4KiB。
- **fanout 内禁止 human wait**：校验规则写死（parallel branch 必须是 dispatch worker 且 may_yield=false 的既有约束不变）；human wait 只能位于 fanout join 之后的串行主图。

### 3.2 resume 与幂等

- `ResumeRequest.Payload`（传输层）；human resume 的 payload 必须先过 resume_schema 校验（**校验在 app/service 边界完成**，不新增第 12 个 base→kernel import 点——ratchet 已顶格 11/11）。
- **payload digest 参与幂等判等**：持久化 canonical payload hash；同 key 不同 payload = 409 冲突（防止 approve 重放成 reject）。
- 恢复后：`CompletedOutputs[waitNodeID] = validatedPayload`，NodeID 推进 success edge；后续节点经既有 ValueRef（node_output + JSON pointer）读取。

### 3.3 待办（inbox）

- 派生投影：`parked 且 wait_kind='human'`；新增 partial index + 稳定 cursor（`updated_at + run_id` 排序编码）。
- `GET /v1/human-tasks`（实时 membership 校验）；`POST /v1/human-tasks/:run_id/complete`（payload + idempotency_key → 转 queue continuation）。
- WaitDetail 在 resume 时清空（现状）；payload 在 checkpoint 持久化（loom_store）——v1 无清理策略，文档如实记录；交付物只存 workspace 内引用，不内联正文/凭据。

### 3.4 超时

- human deadline 进 WaitDetail + partial index + 独立 sweeper（TimerWakeSweeper 只认 timer 的现状不动）；
- **complete 与 timeout 竞态只有一个 CAS 赢家**（竞态测试为硬验收）；
- 到期行为 v1 = 走 timeout edge（与 timer 一致），无升级链。

### 3.5 Console

侧栏待办（计数）→ 详情（标题/指示/交付物引用预览 + 按 resume_schema 渲染表单）→ 提交。

## 4. 明确不做

human 团队成员、邮件/IM 通知、细粒度指派与转派、超时升级链、内置 4 模板加人工节点、旧端点的 membership 重查改造（只覆盖新端点）。

## 5. 工作票

- M3-1：machine WaitConfig 扩展（kind/task）+ declarative wait 放行 + fanout 内禁止规则 + 校验测试；
- M3-2：teamrun human resume（Payload 传输、节点输出落 checkpoint、NodeID 推进、payload digest 幂等、human_resume continuation）+ characterization tests；
- M3-3：超时 sweeper（deadline/index/竞态）+ human-tasks API（membership 实时校验、cursor）；
- M3-4：样例 4（含人工终审的 declarative 团队）+ Console 待办 + 全链验收。

| checkpoint 不推进 NodeID 会无限重新 park | 采纳，节点输出 + NodeID 推进（§3.2） |

| fanout 内 human wait 与既有约束冲突 | 采纳，校验禁止（§3.1） |
