# Weave 内核边界与开发者契约

日期：2026-09-12  
状态：架构提案，待产品、工程、质量三方评审  
适用范围：Weave 内核、Loom 执行适配、Workbench、公开 API/SDK 及开发者工作空间

## 1. 决策摘要

Weave 保持单仓库，先收敛职责和接口，再按依赖关系逐步移动代码。当前不做大规模重写，也不把业务能力硬编码进平台。

Weave 提供开发者可编排的能力内核。开发者定义角色、步骤、输入输出和执行关系；平台负责校验、发布、调度、运行事实、权限约束和结果保存。Loom 是一种原生执行路径，其他引擎通过运行时适配接入；公开契约不绑定某个引擎、模型或供应商。

## 2. 内核边界

### 2.1 内核负责的事实

- 能力定义的结构校验、依赖检查和可执行计划生成。
- 角色、步骤、串行、并行、条件、汇合、有限循环和人工等待的执行语义。
- 发布版本的不可变性、版本选择和调用时的版本绑定。
- 运行时选择、任务分配、租约、心跳、重试、取消和终止状态。
- 输入、输出、事件、产物、用量和审计事实的持久化。
- 工作空间、应用、运行时和资源边界的强制检查。

### 2.2 外围负责的事项

- Workbench 页面、API/SDK、账号登录和开发者体验。
- 成员管理、商业套餐、额度配置、账单和通知。
- License 或 entitlement 的签发、验签、续期和撤销。
- 平台运营策略，例如默认套餐、价格和推广规则。

外围可以决定一次请求是否被允许进入内核，但一旦进入，内核仍必须重新检查工作空间、能力版本、资源范围、预算和并发限制。不能只依赖某个 HTTP middleware 来保证安全边界。

## 3. 开发者可定义的能力

开发者在一个工作空间内创建能力定义。定义至少包含：

| 部分 | 开发者可声明的内容 |
|---|---|
| 角色 | 角色名称、职责说明、可见输入和输出 |
| 步骤 | 步骤名称、指令、输入映射、输出 schema、超时和预算 |
| 关系 | 顺序、并行、条件、汇合、有限循环、人工等待 |
| 运行选择 | 能力需求、允许的运行时或运行时池、失败策略 |
| 资源 | 允许使用的工具、数据连接、文件范围和密钥引用 |
| 结果 | 对外返回的结果 schema、产物类型和可见性 |

平台私有提示词、供应商凭据、其他工作空间的配置、内部调度细节和未授权数据不属于开发者契约。开发者自己声明的角色、关系、输入输出和运行事件必须可查看，否则无法调试和维护自己的能力。

公开语义可被观察和复现是可编程平台的正常结果。保护实现应依靠服务端保存私有内容和资源隔离，不应承诺开发者无法推断公开行为。

## 4. 生命周期与可修改范围

### 4.1 草稿

草稿可以修改全部开发者声明内容。保存时做结构校验；调试运行只允许进入隔离的开发者调试空间，不得改变已发布版本、生产运行或其他工作空间的数据。

### 4.2 调试

开发者可以提交测试输入、单步查看角色和步骤的输入输出、查看工具事件、重跑失败步骤，并比较不同草稿版本。调试运行必须标记为 `debug`，拥有独立的运行 ID、预算和产物命名空间。

调试不能绕过权限、资源范围、并发、预算或工具审批。调试使用的密钥应通过引用注入，页面和日志不得回显原文。

### 4.3 发布

发布操作对草稿执行完整校验并生成不可变的 `published_revision`。发布记录至少包含：能力 ID、修订号、定义摘要、输入输出 schema 摘要、运行选择约束、资源声明、发布者和发布时间。

发布后，以下内容不可原地修改：角色与步骤语义、步骤关系、输入输出 schema、资源声明、运行时约束、预算和失败策略。任何变化都必须从该版本创建新草稿，再生成新的修订号。

可调整的外围内容包括显示名称、说明、标签、文档链接、默认的调用端展示文案和停用状态。停用只阻止新的调用，不删除历史运行和产物。

### 4.4 调用

应用调用必须明确指定能力 ID 和发布修订号，或者使用平台提供的稳定别名。稳定别名的变更必须产生审计记录；运行事实始终保存实际命中的修订号。

应用凭据只能调用、读取本应用有权访问的运行，并在授权范围内取消运行。应用凭据不能修改草稿、发布版本、运行时资源或成员权限。

## 5. 最小身份与权限模型

第一版只保留两种开发者人员角色：

- `admin`：管理工作空间成员、应用、资源授权、额度和发布策略，同时拥有开发者权限。
- `developer`：创建和修改草稿、调试、发布、查看自己工作空间的运行和产物。

应用和运行时使用机器凭据，不继承人员登录态。应用凭据先提供 `invoke`、`read`、`cancel` 三个范围，并绑定工作空间、应用和可调用的发布能力。暂不引入自定义角色、部门继承、复杂 ABAC 或逐字段授权。

每次请求都要同时检查主体、工作空间、资源归属、能力版本和操作范围。默认拒绝，授权结果应由一个统一的授权服务计算并被 HTTP、MCP、SDK 和运行时入口共同使用。

能力定义和发布版本是工作空间内的共享组织资产，拥有管理权限的成员可以协作维护；它们不按人员复制。人员身份必须记录创建、修改和发布归属。客户端若只配置一个 Host 凭据，则该 Host 只能代表一个人员身份；多人共享部署必须先完成逐用户委托身份，不能用 Host 身份代替最终操作者。

## 6. License 与商业授权

云端服务优先保存服务端 entitlement，记录工作空间可用的运行时、并发、用量、能力数量和有效期。License 不进入执行状态机；内核只接收已经解析好的授权约束，并在调用和资源分配处执行。

私有部署需要离线授权时，再增加非对称签名的 license 文件。签名用于证明签发者和防篡改；加密只用于隐藏授权内容，不能替代权限检查，也不能保证防逆向。授权到期后阻止新的执行，同时保留查看、取消、导出和有限的在途任务收尾策略。

## 7. 稳定开发者契约

公开 API/SDK 至少保证以下不变量：

1. 同一 `request_id` 在同一应用范围内幂等，重复提交不会产生第二个业务运行。
2. 每个运行返回稳定的 `invocation_id`、能力 ID、发布修订号和终止状态。
3. 运行状态只能按定义的状态机前进；取消请求在尚未终止时可重复提交。
4. 结果可用性和结果内容分开表达，不能用“请求已接受”冒充业务完成。
5. 运行事件、工具调用、产物和错误都带有运行 ID 与步骤标识。
6. 发布修订号、输入摘要、输出摘要和资源授权可用于事后复核。

平台可以增加字段，但不得改变上述字段的含义。破坏性变化必须生成新的 API 版本和迁移说明。

## 8. 验收方式

第一阶段用一条真实的开发者旅程验收边界：开发者创建多角色能力，定义串行和并行步骤，使用调试输入查看中间结果，发布修订，应用调用该修订，运行时完成执行；随后修改草稿并再次发布，证明旧运行仍绑定旧修订，应用也不能越权修改定义。

验收必须分别证明：开发者契约可操作、发布冻结有效、权限在 API 和运行时入口一致、运行事实可恢复、产物与实际修订对应。单元测试、健康检查或只返回 HTTP 202 都不能单独证明这条闭环成立。

## 9. 实施顺序

1. 先把本文件和公开类型整理成评审基线，列出当前实现与目标契约的差距。
2. 为定义、调试、发布和调用建立 characterization tests，先保护现有运行事实和幂等语义。
3. 收窄 `internal/base`、`internal/kernel`、`internal/build`、`internal/app` 的依赖，保持单仓库和现有组合根。
4. 接入统一的开发者授权服务和应用凭据范围，暂不扩展复杂角色模型。
5. 用真实 Workbench/API/运行时旅程完成发布冻结验收，再决定私有部署 license 的包装和离线策略。

本文件只冻结边界和契约，不授权立即删除旧入口或进行大规模目录搬迁。任何实现迁移都必须先列出共享接口、保留兼容期和可重复的验收命令。
