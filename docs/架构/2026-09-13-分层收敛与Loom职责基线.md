# 分层收敛与 Loom 职责基线

日期：2026-09-13

状态：B0 已落档，B1 职责提取和 B3 中 capability 迁出基础层已实现并完成工程验证；后续批次及真实产品验收未完成。用户已明确后续独立分仓；当前先在现仓建立可分仓边界。实现与证据见[第一批验收记录](../验收/2026-09-13-分层迁移第一批验收.md)。目标仓库、契约和迁移顺序见[理想架构详图第 8 至 12 节](2026-09-13-Weave理想架构详图.md)。

本文细化[内核边界与开发者契约](2026-09-12-Weave内核边界与开发者契约.md)的实现归属。原契约的发布冻结、身份、幂等与结果边界继续有效。这里的目标结构不得表述为当前结构已经符合。

多运行时是需要保留的核心能力。执行器、推理来源、部署位置和工具环境是独立维度；Loom 可直接接模型服务，也可通过 Codex 等提供推理，Codex 等还可独立执行成员任务。本文的收敛指平台治理职责收敛，不要求所有执行通过 Loom。详见[理想架构详图](2026-09-13-Weave理想架构详图.md)。

## 1. 为什么先收敛边界

### 当前实施决策

本轮先收敛职责分层，并落实重试、超时、额度和取消的责任契约。轻量执行路径、运行时能力抽象的具体形状以及推理适配的默认推荐策略保留为待验证提案，不因理想架构图或历史设计而直接实施。

用户已明确本次迁移不考虑老数据及其他存量兼容。直接切换到新契约，不增加旧数据读取、旧快照转换、旧 Host 适配或双轨执行路径。发布后冻结、身份隔离、幂等、取消及新系统自身的恢复仍是必须满足的不变量。

简单机械任务、混合运行时任务、中断恢复和多人共享场景用于逐批回归及最后验收。迁移保护的是明确保留的产品能力和新契约，而非全部旧行为。第一批尝试前端页面路径时，浏览器工具连接失败；本轮只完成工程验证，不将其记作四类真实场景通过。场景结果决定后续产品调整。

文档同步盘点并收敛：当前规则保留单一权威入口；重叠内容合并并保留来源；被替代方案标记为历史并退出默认阅读入口；真实验收、发布与迁移证据保留。删除前检查引用及独有内容，不能凭日期或运行时名称判断过时。此处确定清理原则，不表示全量清理已经完成。

[订单真人验收](../验收/2026-09-13-Workbench目标驱动真人验收记录.md)发现了修订材料丢失、复核失效和过度确认。这些是产品观察，尚不能仅凭观察认定是某个内核函数的缺陷。

修复前先区分通用执行机制、平台治理、团队策略和任务规则。订单金额 295、重复项排除及运费口径只能进入验收材料或团队规则，不能进入通用执行代码。增加复核角色、方法研究或返工也不能成为所有团队的默认必经步骤。

本次未读取订单运行的冻结执行快照和成员运行轨迹，因此不判断该次运行每个成员实际走了哪条路径。上述结论是当前源码审计，不是新的运行验收。

## 3. 各层唯一职责

| 层次 | 负责 | 禁止下沉或混入 |
|---|---|---|
| Loom 核心 | 状态增量、步骤、路由、图、检查点及 yield/resume 原语 | 团队、租户、订单、套餐、成果采纳、跨成员调度 |
| Loom 通用组件 | 模型与工具循环、通用暂停与循环限额、通用日志及核验扩展点 | Workbench 会话、平台授权账本、商业规则 |
| Weave 基础契约 `internal/base` | 引擎无关的身份、版本、事件、结果与存储契约，以及无编排行为的基础设施 | 工作流解释器、模型调用、运行时选择、团队策略；已有耦合按批迁移 |
| Weave 执行与治理 `internal/kernel` | 编译、版本绑定、团队执行状态机、跨成员调度、执行器适配、租约与终态、授权和资源约束的强制执行 | 页面文案、如何询问用户、商业定价、特定任务的正确答案 |
| 团队构建 `internal/build` | 从目标形成团队和可执行定义、选择协作及核验策略、构建评估 | 自建执行循环、队列或终态；通过提示词替代平台约束 |
| 产品服务 `internal/app` | 任务材料与修订意图、成员与应用管理、共享策略、交付版本与采纳、套餐及额度配置 | 再实现通用调度、租约、重试和工具执行机制 |
| Workbench 与传输适配 | 自然语言和页面交互、认证上下文接入、参数转换、进度和成果呈现 | 作为运行状态、权限或验收事实的唯一保存位置 |
| 团队定义与任务输入 | 角色职责、方法选择、业务规则、允许副作用和本次交付标准 | 修改平台身份、扩大授权、覆写已发布版本或强行宣告通过 |

依赖仍按 `app → build → kernel → base` 向下；Loom 是 kernel 使用的外部执行库。目标上 base 的公共契约不暴露 Loom 状态类型。存储实现放置不是本轮重构的起点，先迁出其中的执行决策，再处理包位置。

这里的“内核”必须写明是 Loom 执行内核还是 Weave 平台内核。团队并行由 Weave 管理，Loom 的通用循环由 Loom 管理；不为统一名称把两者改造成重复调度器。

## 4. 接口和运行事实约束

以下是接口必须表达的语义，不要求立即新增同名类型或建立一个万能框架。

1. **定义与计划**：绑定已发布修订、输入输出、执行要求和资源引用；原定义与实际执行计划可追踪。业务规则来自定义或任务材料。
2. **执行请求**：携带可信主体、工作空间、任务和父运行关联、冻结版本、输入版本引用、预算与资源范围。Host 身份与最终操作者分开，服务端校验委托关系；调用者填入用户 ID 不构成授权。
3. **执行回执**：区分逻辑运行与实际尝试，关联真实用量、工具回执、输出及停止原因。Loom、外部智能体和纯工具执行器遵守相同的平台边界，但各自声明支持哪些恢复粒度；不支持时不能伪装成功。
4. **唯一事实所有者**：Weave 保存平台任务和成员执行事实，Loom 保存其图内检查点，产品保存用户交付与采纳事实。三者通过稳定标识关联，不互相重写终态。能力 invocation 是业务调用记录，不能无限发展成独立的平台调度内核。
5. **材料与修订**：产品层选择有权访问的材料、上版成果和修改范围；执行层绑定本轮实际使用的版本。按需传递引用及内容，不默认复制所有聊天给所有成员。修订与恢复是不同动作：修订生成新的输入版本，恢复继续原来的冻结执行。
6. **核验**：平台统一检查结果、来源和版本关联的表达；具体检查由可选核验器或团队定义承担。检查结果应区分通过、未通过、缺少依据和未执行，不以成员自述代替证据。用户采纳也不覆写独立核验结果。
7. **重试与副作用**：每条路径明确重试由谁负责、幂等键和外部操作回执如何关联。检查点不能单独保证外部副作用恰好一次；结果未知时保留未知状态，避免上下两层同时自动重试。

### 已确定的控制责任契约（部分实现，尚未整体验收）

| 控制项 | Weave 平台责任 | 成员执行器责任 | 必须保留的事实 |
|---|---|---|---|
| 重试 | 授权新的成员尝试，校验剩余额度与旧尝试状态 | 在本次授权内处理内部失败，不自行扩大整项任务重试次数 | 同一次失败的重试所有者明确；内部恢复与平台重派不同时生效，外部结果未知时先核对 |
| 超时 | 下发期限，阻止期限外的新派发并使迟到回执不能覆盖有效终态 | 在期限内执行，停止内部工作或报告尚未停止 | 平台超时、进程退出和外部操作结果分别记录；租约过期不证明执行已停止 |
| 额度 | 分配额度并按物理尝试核对用量，明确父子汇总关系 | 内部重试使用同一份已分配额度，上报实际消耗 | 不重复计费；缺失用量不记为零，不支持硬限制时不得宣称硬保证 |
| 取消 | 保存取消意图，阻止后续派发并管理停止确认 | 接收取消，停止可停止的工作并回报实际状态 | 取消请求、停止确认、已发生的外部影响分开；取消不等于回滚 |

第一批已实现：能力 Runner 不自行重派整项任务；过期租约不再自动重新派发；运行关联和续租拒绝失效、取消或不匹配的执行凭据；执行上下文传递取消和期限。真实 PostgreSQL 回归同时修复了检查点写入的参数错误。尚未实现或证明统一执行所有权、恢复时累计总期限、跨运行时硬额度和远程物理停止确认，详见第一批验收记录。

责任契约允许 Loom、Codex 等有不同的内部实现。适配层证明各项控制可落实的边界，不能通过统一接口的命名掩盖不支持的行为。

## 5. 如何约束后续 AI 修改

- 开始修改前，写明责任层、现有事实所有者、复用入口、影响的公开契约和验收方式。信息不足先追踪调用链，不凭页面症状指定内核补丁。
- 新业务案例优先成为输入、团队定义、检查器或验收材料。进入通用机制的改动需要说明至少两个不同场景为何共享同一语义；不能用特殊分支匹配测试答案。
- 不新增独立任务队列、执行循环或终态来源来绕开现有实现。确需替换时明确唯一新入口、被移除的职责和验证方式，直接完成切换，不为存量保留双轨。
- 不扩张 depguard 反向依赖白名单。不用薄转发包、类型别名或改名掩盖原有依赖；移除耦合后同步删除对应白名单。
- API handler、Workbench 页面只消费产品服务和执行事实。对已有混合文件做增量提取，不在其内继续加执行决策。
- 方法研究、独立复核、人工等待和自动返工均按明确需求启用；固定机械任务的默认路径保持直接执行。
- 新系统中已发布定义不可原地改写，运行必须绑定实际修订与输入。迁移无需解释旧系统记录或接续旧在途运行；不要把这个豁免扩大成新系统可以丢失版本关联或取消意图。
- 收尾报告区分规则已落档、代码已迁移、工程检查通过和真实产品验收通过。现有门禁不能声称覆盖它尚未检查的语义边界。

## 6. 按可验收批次迁移

以下为职责迁移顺序，不是新产品功能清单。四类场景分别记录可用证据和阻塞，不将浏览器或环境不可用写成通过；控制责任契约随相关批次落实。B4 的具体产品实现由实际复验决定，B5 是最终收口，不能替代逐批验证。

| 批次 | 输入与范围 | 完成判据 |
|---|---|---|
| B0 职责审计 | 当前代码、既有契约、Loom 接入点、分层门禁 | 本文和 AGENTS 入口落档；记录现存债务与证据。此批已完成文档工作 |
| B1 收窄 API 的执行职责 | `api/capability_runtime.go` 的运行时选择、成员与工具适配；与应用服务、kernel 的边界 | 已完成提取与工程回归：传输入口只组装和调用服务，kernel 接收无产品 Store 的执行请求，应用服务保存带租约约束的记录。工具直接执行及真实浏览器验收未完成 |
| B2 收敛平台执行所有权 | capability 的执行器、独立 invocation 队列、既有 teamrun/taskqueue | 先对照两条路径的条件、并行、人工等待、恢复、取消与用量语义，选用或补齐既有通用路径；所有新调用接入共同执行机制，移除被替代的执行入口，无双重执行。不承担旧记录读取与旧在途运行收尾。无需盲目合并业务记录表 |
| B3 迁出基础层编排 | `base/teamrun` 的解释、fanout 和 kernel 反向依赖；原 `base/capability` | capability 已整体进入 kernel；teamrun/fanout 及 11 条反向边待迁移。无编排行为的基础事实留在 base；相关跨进程恢复和迟到回执必须回归 |
| B4 沿既定边界修复产品缺口 | 修订材料绑定、可选核验、修订版本展示 | 原始材料可追踪，修订不丢依据，核验能拒绝错误结果；产品服务不再新建运行机制 |
| B5 多场景产品验收 | 订单计算、文档整理、固定工具步骤；Loom 与外部执行器分别覆盖其支持范围 | 通过桌面 Workbench 正常路径交付并独立核验；简单任务不被强制研究；中断恢复与多用户身份各有真实证据。才可宣称分层改造完成 |

每批独立提交，列出共享接口、删除的入口和新契约验证方法。旧路径、旧表或旧解释器可随职责切换直接退役，不安排存量转换或双写；修改只覆盖本次迁移对象。各批依赖前一批结论，但不要求先移动整个包才能提取一个职责。

本轮已包含 Go 迁移，执行 `make test depguard productguard base-depguard`，并补充能力内核竞态检查和真实 PostgreSQL 回归；Workbench 变化按项目要求执行 `make workbench-install workbench-check`；涉及持久化、取消、恢复和外部工具的批次补真实 PostgreSQL、进程中断及操作回执验证。平台验证使用 `docker-compose.platform.yml`。工程通过与业务验收分别报告。

## 7. 尚未证明的部分

- 订单实际运行中各成员的循环所有者、工具执行者和恢复粒度。
- 两套执行路径对新契约的覆盖情况，以及通用执行所有权的统一实现。
- 远程 Loom 检查点的跨进程恢复闭环。
- 这次修订材料丢失的确切发生位置；必须沿 Workbench 到执行输入逐段定位。
- 同层职责约束的自动化覆盖；当前以本文件及逐批审查执行，现有 depguard 不是完整架构验证器。

这些缺口不通过改文档、重新命名包或一次成功输出消除。
