# Workbench 桌面接入与账号体系产品技术方案

日期：2026-09-08  
版本：v0.4，明确本地共用前端与独立桌面预览

状态：macOS 本地桌面预览已实现；完整账号、真实业务链路与正式发行尚未完成。

本版在 v0.2 的小范围交付路线之上，补充单仓、职责、接口与发布物约束。[v0.1 原文](2026-09-08-Workbench桌面接入与账号体系产品技术方案.v0.1.md)与 [v0.2 原文](2026-09-08-Workbench桌面接入与账号体系产品技术方案.v0.2.md)原样保留；[深度评审与逐项裁决](2026-09-08-Workbench桌面接入方案可落地性与简洁性评审.md)记录此前独立审查结论。实施顺序以配套[实施验收计划](../计划/2026-09-08-Workbench桌面接入与账号体系实施验收计划.md)为准。[v0.3 原文](2026-09-08-Workbench桌面接入与账号体系产品技术方案.v0.3.md)保留。v0.4 明确本地打包共用前端和独立预览范围，未再次执行独立互审。

执行顺序补充：Loom 与 CLI 闭环修复期间，按[并行任务计划](../计划/2026-09-08-Workbench桌面接入并行任务计划.md)划分独立准备与后续接入；最终账号与业务验收条件不变；原生预览和共用 UI 调整可在独立分支先行，锁文件在汇合时顺序处理。

## 1. 本版结论

用户明确提出的核心体验是：安装桌面 Workbench，登录后直接连接预置的 Weave；只有显式修改连接时才改用另一服务，后续启动保持这个选择。

这项需求需要完整的个人身份与连接边界，但不能独自证明必须建设一个云端多用户 Host 调度平台。v0.1 将“跨设备完整对话连续”直接加入首期验收，扩大了架构前提。本版将它恢复为待确认的产品选择。

目前仍建议优先验证远程展示客户端与**静态专属 Workbench Host**，理由是已有服务端部署和 Web 界面最接近这条路径。每个试点用户一个固定 Host、独立卷、固定路由；先不建设动态分配、自动迁移和弹性回收平台。这是远程路线的首期部署方式，不是另一套业务模型。

如果首期更重视本机工作目录，又不需要跨设备完整对话，本地 Workbench Host 仍是有效候选。不能在没有本地发行小样的情况下认定它一定更轻，也不能以“关窗后远程任务继续”为理由排除它。

必须先补的是统一授权、可信操作来源、持久接收回执及材料派发接缝。桌面外壳在这条最小链路上尽早验证，不必等整个云端管理平台建完。

总体结构采用一个仓库维护完整产品，内部按协同机制、产品装配、工作对话和执行节点划分职责，按实际需要独立部署。首期不新增独立框架仓库或公开 SDK；分层改进跟随本次真实接缝推进，避免将全部历史重构变成桌面交付的前提。

## 2. 范围与产品承诺

| 层次 | 内容 | 本版处理 |
|---|---|---|
| 用户明确需求 | 默认连接、真实账号登录、显式改址并记住 | 首期必须交付 |
| 正确性所需 | 账号及服务不串数据、请求来源可追踪、权限一致、未知写操作不重复提交 | 不能省略 |
| 建议首期业务闭环 | 上传一份真实材料，派发给远程节点，关窗再开后取回成果 | 用来证明产品可用 |
| 待确认的产品扩展 | 跨设备完整对话、用户离线期间持续监督及通知、本机项目编辑 | 不用于暗中扩大首期 |
| 规模化增量 | 动态 Host 调度、自动故障接管、集中对话索引、多组织、SSO、完整设备管理页 | 有需求与实测依据后进入 |

必须区分四件事：

1. **Weave 已接受的业务运行继续执行。** Workbench 关闭本身不能发出取消命令；实际续行仍需测试。
2. **Workbench 前台 Agent 继续思考或调用工具。** 本地 Host 退出会影响它，远程常驻 Host 才有继续的运行条件。
3. **工作对话跨设备可见。** 需要对话存储或同步安排，不能从运行在服务器上直接推出。
4. **Host 重启后无人打开页面也继续监督。** 当前 live Session 轮询不提供这个完整保证；这是新增恢复能力。

首期无需同时承诺第 2–4 项。采用静态云端 Host 时，第 3 项可作为该路线的附加验证；无人在线时通知和 Host 冷启动主动监督仍单列。

## 3. 架构取舍

| 判断项 | 远程专属 Host | 本地个人 Host |
|---|---|---|
| 安装登录后连远端 Weave | 可以 | 可以 |
| 客户端退出后已派发运行 | Weave 继续承担 | Weave 继续承担 |
| 完整对话跨设备 | 同一 Host 数据可复用，仍需多设备测试 | 需要另做同步；首期不承诺 |
| 本机目录和大批本地材料 | 需要上传或后续连接能力 | 文件位置自然，但远端任务仍需材料传输 |
| 运维成本 | 服务器为用户提供 Host 资源和隔离 | 用户设备承担 Host 进程及依赖 |
| 发行成本 | 桌面壳较薄；服务端维护 Host | 需要随客户端分发 Node、Weave、插件及实际使用的工具 |
| 主要风险 | 云端多用户权限、文件隔离、容量、升级单写者 | 目标平台发行、休眠、凭据保护、账户配置分区 |
| 当前建议 | 先用固定少量 Host 验证 | 需求偏本地时，以可安装小样重新比较 |

不采取“桌面直接重写全部 Go API 调用与监督 Agent”的路线。当前 Session、MCP、工作对话和 WorkTask 投影已有实现，重写没有与本需求对应的收益。

### 3.1 首期远程形态

~~~mermaid
flowchart LR
  D[桌面 Workbench] --> G[统一 HTTPS 入口及 Weave 账号认证]
  B[浏览器 Workbench] --> G
  G --> H1[固定用户 A Host + 独立卷]
  G --> H2[固定用户 B Host + 独立卷]
  H1 --> W[Weave API 与统一授权]
  H2 --> W
  W --> R[远程 Runtime]
  W --> S[(任务 / 附件 / 成果)]
~~~

接入路由与账号解析优先放在现有 internal/app 装配中，不为了图上一个框再部署一个通用身份平台。Node Host 继续承载现有 Workbench；Go Weave 保持业务与授权真相源。

固定路由清单将 instance/workspace/user 映射到一个受控内部 Host 和卷。不由客户端提供 host_id、任意 URL、镜像、目录或启动参数。普通用户无法直接访问内部 Host 端口及其启动 token。

第一批 Host 由部署配置创建与升级。禁止同卷自动副本数扩张。替换先确认旧进程退出并释放写入权，再启动新进程；无法确认时宁可显示 Host 暂不可用，也不根据数据库租约超时启动第二个写者。

### 3.2 桌面框架与首发平台

Electron 44.2.0 已用于本地原生预览。桌面随应用打包现有 Workbench 前端，复用同一对话、侧栏、输入框和工作现场组件；主进程负责原生窗口、菜单、连接与下载。网页版共用相同的紧凑样式和工作现场图标入口，连接服务与页面资源分开。真实账号及业务链路仍须另行接入。只有它在实际目标平台、包体或交互约束上遇到关键问题时，再以 Tauri 做针对性对照，不把双框架全面竞赛列为必经步骤。

首发操作系统尚未确定。macOS Apple Silicon 只是上一版提出的试点假设，不是用户已批准的发布平台。正式安装、签名、更新的完成结论只适用于实测平台。

业务视图不得直接获得 Node、任意文件、shell 或通用 IPC 能力。当前预览只允许加载本地打包资源，连接设置使用独立的可信窗口和窄 IPC；真实 Host 传输后续按同一账号与来源上下文合同接入。框架机制参考 [Electron 官方安全指南](https://www.electronjs.org/docs/latest/tutorial/security)和 [Tauri capability 说明](https://v2.tauri.app/security/capabilities/)；版本和发行配置在实施时固定。当前已具备可运行的 macOS arm64 预览；其中认证、会话和下载样本均为隔离夹具，不能作为多人账号或业务执行通过的证据。

### 3.3 单仓中的职责、接口与发布边界

| 范围 | 应承担的职责 | 必须守住的边界 |
|---|---|---|
| internal/base | 运行身份、状态与持久协作合同 | 不引入页面、cookie、桌面偏好；具体执行适配应位于适当上层 |
| internal/kernel | Agent、工作流、引擎、执行与恢复机制 | 通过声明的上下文和接口工作，不识别 Workbench 页面或连接设置 |
| internal/build | 团队构建、评估、编排与修复 | 复用运行合同，不为某个客户端建立特殊团队生命周期 |
| internal/app | 用户/成员政策、业务用例、API/MCP 适配、装配与运维入口 | 登录 cookie、公开 origin 和固定 Host 路由留在产品装配边界；业务状态变化调用所属领域服务 |
| workbench | 监督 Agent、用户讨论、方案呈现、操作意图、Session 和 WorkTask 投影 | 通过受控 API/MCP 操作 Weave；不访问 Weave 数据库，不独立判定团队运行终态或执行恢复 |
| Runtime 进程 | 领取授权任务、执行并报告结果 | 通过现有节点协议访问服务，使用节点/任务凭据；不接管用户登录和工作对话 |

这是目标责任分配，不等于当前每个模块已完全符合。工作对话本身需要监督 Agent、模型调用和输入队列；保留这些能力不构成重复团队编排。重复的判断标准是：Workbench 是否自己选择执行节点、推进团队阶段、恢复业务 run，或在没有 Weave 事实时宣布最终交付。此类行为应返回 Weave 的业务入口处理。

Workbench 持久输入回执证明对话已接收；Weave 命令回执证明业务动作已接受。两者有不同职责，前者不得冒充后者。OperationContext 的个人身份和权限校验位于应用边界；传入运行内核的是明确 actor、目标和已校验的操作合同，不让 cookie 或桌面会话协议进入通用运行机制。

一次跨端合同变更在同一仓库中同时修改服务端、Workbench HTTP/MCP 调用方和相应验收。先定义输入、回执、事件、授权与幂等语义，再提取实现；不为每个函数提前造可替换接口，也不把新的调用桥扩展成第二套业务编排服务。

当前依赖检查登记了 11 条 base/teamrun 指向 kernel 的历史反向依赖，具体以 [depguard 规则](../../tools/depguard/check_depguard.py)为准。相关文件因本次工作需要修改时，应评估将具体执行适配移至合适层或收窄现有接缝；不新增反向边，也不把清零全部历史边设为本次账号/桌面的上线前提。清理债务必须保持运行状态、幂等和恢复语义可验证，不能仅靠移动目录达到检查通过。

代码仓库、运行进程和发布物分别管理。现有 Workbench、Weave、Runtime 可以继续独立运行，单仓不要求同进程。中心服务和 Runtime 的镜像瘦身列为条件性运维工作：先盘点中心端实际执行职责和构建依赖，证明某些引擎只被 Runtime 使用后，再拆构建目标。保留中心服务仍需的构建/评估/本地执行依赖；保持 Workbench 的 weave mcp serve 所需二进制可获取。轻量中心镜像不是本次桌面交付的前置条件。

只有出现第二个真实独立产品消费协同核心、团队需要独立发布，或共同构建发布产生了可量化成本，才重新评估分仓或公开 SDK。届时应以稳定合同和真实调用者为依据，并单独设计版本兼容与发行责任。

## 4. 最小且清楚的产品对象

| 对象 | 唯一职责 | 权威位置 |
|---|---|---|
| ConnectionProfile | 选择 origin 与预期 instance，保存用户偏好 | 客户端非敏感配置 |
| AuthSession | 当前设备登录有效性、到期与撤销 | Weave 账号服务 |
| Principal | 当前用户、组织成员身份和允许动作 | Weave 每次解析，不存一份永久复制角色 |
| Workbench Host 绑定 | 确定该进程与数据卷归属哪个用户/组织 | 首期受控部署清单 |
| Conversation / Session | 工作对话、已接受输入与本地投影 | 既有 Session 持久层，conversation_id = SessionId |
| WorkTask | 当前业务目标与 Weave 运行的关联/展示 | 既有 Session 投影；执行事实以 Weave 为准 |
| TeamRun | 已接受的业务运行、状态迁移、恢复和交付引用 | 现有 Weave 执行系统 |
| Attachment | 文件版本、摘要、归属及授权引用 | 优先扩展现有附件目录 |

组织工作区、Weave 项目和 Workbench 工作目录保持不同概念。首期不自动从目录名创建项目，不建立第二份项目归属数据库。已有 project_id 的任务继续显式绑定；目录分组属于 Host。

不新增另一份对话标题、状态或 revision 真相源。需要跨 Host 列表时再构建可重建索引；索引丢失后从权威日志恢复，不承载授权决策。新增输入回执所用的序号必须复用或明确映射 Session 的持久序列。

## 5. 统一权限基础，先于登录界面

已核实的现状：JWT 读取 weave_users.role；成员信息保存在 weave_members；删除成员只改成员表；API key 验证目前读取 key 自身角色、owner 和过期时间。它们没有统一构成“当前有效成员对当前资源是否可以做某动作”的判定。

本版规定统一调用链为：

`认证凭据 → 当前账号状态 → 当前组织成员资格 → 资源及动作权限 → 命令接受`

cookie、新设备授权、旧 JWT 及个人 API key 入口都使用同一主体和成员政策。旧运维凭据如有系统级用途必须显式分类，不能通过兼容路径绕过个人账号禁用或成员移除。

角色治理的首期建议：weave_users 负责身份、账号启停及明确的账号管理权限；组织成员资格和组织动作以 weave_members 及对应资源政策为准。现有 admin/owner 的含义要做迁移对照，不能机械取两套角色的并集。存在冲突的记录先报告并确定迁移值，不静默选权限更大的记录。

普通成员的默认动作范围建议先限定为授权资源的读取、派发，以及本人发起运行的控制；组织管理、节点管理和跨用户运行控制按明确管理权限开放。若当前运行没有足以证明发起者/项目授权的字段，须沿现有请求与运行关联补查询或最小归属记录，不以用户名字符串或前端隐藏按钮替代。发布前必须把所有受支持动作落实成接口矩阵。

管理员引导、创建账号和重置密码复用现有用户存储。开放注册、邀请邮件和多组织全局账号后置。账号组与目录型工作区不参与互相猜测。

## 6. 一套设备会话，贯穿 HTTP、MCP 与后台

### 6.1 登录

远程薄客户端采用同源第一方登录与 opaque cookie 会话。服务端存会话摘要、用户、组织、创建/到期时间、撤销状态；浏览器不获得业务 API key。首期包括登录、当前账号、退出、受控续期和撤销机制；“查看全部设备”的完整页面可后置。

当前 /v1/auth/login 和 /auth/refresh JWT 契约不无版本覆盖。新的账号版入口显式选择设备会话模式，原 BrowserAuth 启动 token 仅留在明确的个人开发入口，不能作为公网兜底。

cookie、CSRF、可信代理、HTTP/RPC/WebSocket/下载的认证策略一次定义，各入口复用。长连接必须响应会话撤销，具体延迟目标在试点环境冻结。服务端会话不可用时不继续执行受保护命令。

若转为本地 Host 路线，设备会话由本地主进程或凭据代理保管，通过明确的第一方认证协议调用服务器。不能把 cookie 方案原封不动当作原生授权，也不能把长期密钥写进渲染页面。若使用 OAuth，遵循系统浏览器与 PKCE 的 [RFC 8252](https://www.rfc-editor.org/info/rfc8252/)，不自创近似协议。

### 6.2 操作来源

引入一个可信 OperationContext，而不是多个互相重叠的长期授权对象：

- instance_id、workspace_id、user_id、source_auth_session_id；
- conversation_id、input_request_id、具体 operation_id；
- 目标资源及用途，在命令处解析并检查。

上下文由受认证入口生成，在受控 Host 通道和后台处理间保留；模型普通工具 arguments 不能填写或修改授权来源。MCP 的受控元数据/代理是传输接缝，必须同时调整发送和接收两端，并验证与工具执行的关联。

当前 Go weaveclient.Config.Validate 只接受 wv_sk_ 前缀，不能仅把 JWT 放入 WEAVE_API_KEY 就认定身份接通。需要真正的 credential provider 或受控请求代理；TypeScript HTTP、Go MCP 和后台任务命令共用主体解析规则。

同用户的设备 B 登录不会代替设备 A 的旧操作来源。设备 A 退出后，其尚未被 Weave 接受的新写操作停止；用户重新授权某项待处理操作时必须指定该操作，并先对账原 idempotency key。

内部上下文是可验证的来源信息，不自行赋予超过当前用户的权限。首期不新增泛化 TurnGrant、永久 Host 写入委托或另一套 refresh token 平台。每次准备接受新业务写入时，仍检查原会话与现行资源权限。

### 6.3 拆分已有同步器的职责

保留 WorkTask 模型，在内部区分三个函数/服务职责，不新增三种产品任务：

1. **提交命令**：持有来源会话的具体操作，检查权限后提交精确目标。
2. **对账请求**：按原 operation/client_request_id 查询是否被 Weave 接受，不盲目重发。
3. **读取状态**：观察已关联 build、request、run、人工问题和成果，并更新投影。

当前 poll 同时执行写操作和读取，必须先分开，才能谈只读观察。观察范围不能只写 run，因为构建中和未知派发结果时尚无 run_id。

首期不承诺用户完全退出后继续个人后台观察。没有有效个人观察授权时暂停读取，下次进入后对账；Weave 已接受的运行仍继续。若后来要求无人登录也推送任务进展，再为明确关联资源增加独立只读观察授权及撤销机制。这样可以暂时删除 v0.1 的长期观察凭据体系。

## 7. “已接受”与故障语义

现有 prompt 的 accepted: true 是 Agent inbox 回执，不能当作已经持久保存或恰好执行一次。新的用户承诺必须区分：

| 阶段 | 权威事实 | 退出/崩溃后的含义 |
|---|---|---|
| 客户端草稿 | 尚未发出 | 不执行；仅已同步草稿可跨设备 |
| Host 已持久接收输入 | 记录 input_request_id、主体、内容摘要与接收序号，并完成持久化 | 输入可找回；不等于 Weave 已派发 |
| Host 待提交操作 | 确定目标和 operation_id，尚无业务接受回执 | 提交时重新检查原会话；撤销后停止并保留原因 |
| Weave 已收到但响应未知 | 可能已提交 | 在原服务对账；不能直接标记失败或复制运行 |
| Weave 已接受运行 | 现有幂等请求/运行回执成立 | 客户端关闭或退出不等于取消运行 |

最小实现优先在已有 Session 持久层增加接收事件与可查询回执，单写者串行处理同一会话的接收；先持久化，再将该条输入交给 Agent。相同 request_id + 相同内容返回原回执，内容不同返回冲突。恢复从权威事件重建未处理队列，不能新增一个与 Session 双写且没有恢复协议的独立任务库。

这是需要验证的接缝，不声称现有 flush 调用本身已解决所有入队竞争。若当前 API 不能做到“落盘后才进入执行”，应修改 admission 接口的最小边界；不能先自动运行再补回执。首期保证输入接收与业务副作用去重，不保证模型计算绝不重复。

账号撤销与业务命令接受的先后以 Weave 的持久接受点为界。竞态必须在同一授权/接受事务或等价可验证序列上处理：撤销先完成则拒绝新命令；业务先接受则保留既有运行。仅在浏览器发请求前检查一次登录态无法实现此规则。

当前离线重试机制不是充分的跨设备写控制。首期以每会话单一活跃提交者、明确 busy/conflict 响应和幂等接收为边界，不增加协同编辑的独立 revision 系统。

## 8. 材料必须成为派发契约

已有 /v1/attachments 保存 SHA256、大小、created_by 等，可复用。当前 teamDispatchRequest 和 weaveclient.TeamDispatch 没有结构化材料引用，派发指纹也不包含材料；这比上传界面更早影响可用性。

最小链路为：

`上传完成 → 可访问的不可变附件引用 → 派发校验与快照冻结 → Runtime 获取并校验摘要 → 产生对应运行的成果`

实现应在原附件目录和团队派发契约上增加必要字段，贯穿 MCP schema、Go client、API、幂等指纹和执行输入，不另建通用材料平台。

附件可见性必须先明示。当前 tenant 内列表不是个人私有材料库；首期普通上传建议默认个人草稿，明确提交任务时授权给该次运行及其执行节点。需要组织共享时显式选择，现有 tenant 共享附件不能静默重新归为某个个人。

`created_by` 是来源字段，不自动等于访问控制。运行获得材料引用后，应通过现有 Runtime 任务凭据按任务读取；不要求用户一直保持登录才能完成已授权的材料读取。

用相同 request_id 更换材料集合/版本应返回冲突；同一引用不得后来悄悄指向不同字节。M0 就以两台不同主机验证实际字节一致，不能用“把 ID 写进任务文本”代替。

成果沿用现有 final deliverable，下载后实际打开。远端路径、客户端路径、附件 ID 分别表示不同对象。新增权限和读取通路必须复用既有业务成果事实。

## 9. 连接选择与服务身份

ConnectionProfile 持久保存用户选择；安装包只提供首次默认值。成功检查候选服务并完成登录后才提交活动连接，失败或取消时保留原选择。自动更新不覆盖用户选择。

一次活动连接是不可变快照 `{origin, expected_instance_id, generation}`。旧响应不能更新新连接页面，但仍保存在原操作的对账关系中；不把丢弃页面响应当作撤销了服务器副作用。

服务描述、会话、续期、上传完成、订阅和敏感请求都要核对实例归属。入口在业务处理前验证客户端期望的 instance_id；服务换库/重新初始化后拒绝旧会话与旧目标。instance_id 不能取代 TLS。

同一 HTTPS origin 作为外部入口，运行节点安装参数从受控公开地址生成；内部 weave:8080 不发给外部 Runtime。自建服务可以使用独立地址，账户、对话和任务不自动迁移。

桌面会话分区按服务分离，账号退出清理活动业务缓存；用户主动下载的成果不擅自删除。远程页面不能自行改变桌面更新签名信任根。

只保留一个活动服务的业务订阅。无需为了首期改址构建多服务后台聚合、跨服务消息路由或账户联邦。

## 10. 存储、Host 恢复与升级

首期固定个人 Host 的所有权由部署绑定和独立卷证明。对话 ID 直接使用 SessionId，不新增 workbench_conversations 权威表。现有日志和 WorkspaceRegistry 的目录映射继续承担原职责。

数据库 lease 只证明控制面认为谁是 owner，不会阻止旧进程继续向 JSONL 追加。当前 JSONL 追加/失败截断没有 lease_epoch 校验，不能据此设计自动接管。

固定单机试点采用串行停止、确认退出、独占写入、再启动。只有存储侧独占或写入 fencing 已验证后，才允许根据租约自动接管。容器数据卷隔离不意味着同一用户卷可以安全双写。

当前重启后的状态观察仅覆盖已加载到内存的 Session。首期承诺重新打开该对话后对账；如果要求 Host 重启后无人打开也同步，应从持久日志或可重建轻量索引发现未完成 WorkTask，再恢复必要 Session。不要为了读取状态自动恢复旧 LLM turn。

新事件和回执会影响当前 Session 严格事件词汇/版本规则。新旧 Host 不同时写一个卷，升级前备份并验证恢复；旧版本无法理解新事件时，不直接对同一卷降级。桌面与服务器兼容测试按实际支持版本执行，不提前承诺永久支持 N-1。

## 11. 首期保留与后置

| 保留，必要工作 | 后置，需额外理由 |
|---|---|
| 稳定默认入口、个人账号登录、用户选择持久保存 | 企业配置治理、账户联邦 |
| 当前用户/成员/资源统一授权 | SSO、开放注册、多组织全局身份 |
| HTTP/MCP/后台可信操作来源 | 泛化 TurnGrant、永久 Host 写委托、多种长期观察凭据 |
| 持久接收和业务幂等对账 | 通用事件总线、第二任务状态机、协同编辑版本系统 |
| 静态专属 Host、独立卷、单写者验证 | 动态 Host 管理器、弹性回收、跨主机自动迁移 |
| Session 作为对话真相源 | 第二份对话数据库和集中索引 |
| 现有附件链路补进派发契约 | 新材料平台、目录同步、断点续传平台 |
| 一个平台可安装小样、版本/签名验证 | 全平台发行和持续双框架维护 |
| 组织准备好监督模型、匹配任务的可用 Runtime | 本机 Runtime 自动安装、离线业务执行 |

本版不再引用 35–60 人日作为首期估算。该数字对应上一版扩大后的范围，且未经小样拆解。先获得统一身份、持久接收、材料派发和一个目标平台发行的实测结果，再估计剩余工作。

## 12. 实施准入与停止规则

先冻结角色政策和三种回执含义，再实现一条“具名用户 → 专属 Host → MCP → 带材料派发 → 异机 Runtime → 成果”的纵向小样。用桌面壳尽早覆盖默认地址和切换，随后加入第二账号隔离。

以下任一情况出现，都不进入多人正式发布：

- 仍需要共享管理员 key 才能运行；
- 退出设备 A 会误用设备 B 的登录态继续 A 的新写操作；
- accepted 回执后杀进程会静默丢输入或重试造成重复业务副作用；
- Runtime 没有读取到派发冻结的材料字节；
- 替换 Host 无法排除旧进程写同一卷；
- 目标平台仅能在开发环境运行，不能形成可安装发行物。

若固定 Host 能满足实际试点人数和容量预算，就停止扩展部署机制。跨设备、离线监督或本机目录需求改变时，先修改产品合同，再扩大实现。

本版提供可验证的开工方向，仍不是已证明可运行的架构。源码检查支持“这些接缝必须处理”；实际成本、容量、故障行为和产品可用性以实施验收为准。
