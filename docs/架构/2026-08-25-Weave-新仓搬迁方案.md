## 0. 一句话版本

**老仓冻结为参考实现，新仓按四层骨架从零搭建，代码以"测试先行、逐批搬迁、搬家不装修"的方式迁入；谁值得搬谁才活，搬迁结束时新仓通过 parity 门，老仓归档。**

明确不做的事：**不重写任何业务逻辑**。搬迁是唯一目的，语义改动一律搬完后单独开票。

---

## 1. 五条铁律（违反任何一条即烂尾，从上一讨论原样继承）

1. **测试是护照。** 一个包只有在它的测试先落地、且在新仓跑绿之后才算搬完。characterization tests（chatrequest / teamrun.Executor / teambuild.AuthorizeBuildRun）是第一优先搬运物。
2. **搬家不装修。** 搬迁票只允许两类改动：文件位移、import 路径的机械替换。发现想改的行为，记下来，搬完单独开票。
3. **自底向上。** 严格按依赖方向分批：base → kernel → build → app → 前端。每批结束 `go build ./... && go test ./internal/...` 必须绿，中间态永远可编译。
4. **边界规则第一天入 CI。** depguard 在四带骨架就位时就启用，已知违规以 baseline 形式显式记录并只减不增（ratchet），不许新增违规。
5. **parity 门不关，老仓不归档。** 老仓在整个搬迁期保持可编译可运行，只冻结新功能。

## 2. 老仓冻结政策

- 自 B0 起：老仓不接新功能；P0 修复可以进老仓，但必须同步开"移植到新仓"票。
- 老仓的角色：**行为参照系 + 回滚**。新仓行为对不上时，以老仓为准查案。
- B7 parity 门通过后：老仓 README 置顶归档说明，分支保护，转只读。不删除——它是 git 历史和"当初为什么这么做"的唯一完整档案。

## 3. 新仓骨架

### 3.1 Module 路径：保持不变

新仓 go.mod 沿用 `module github.com/jinyitao123/weave`。

理由：带内目录从 `internal/teamrun` 变为 `internal/base/teamrun`，包路径必然要机械替换一次；module 路径再变就是第二次全量改写，零收益。loom 依赖（`github.com/jinyitao123/loom v0.8.0`）原样保留。

### 3.2 四带目录

```
weave/                          # 新仓
├── go.mod                      # module github.com/jinyitao123/weave
├── cmd/weave/                  # 唯一二进制（B5 迁入）
├── internal/
│   ├── base/                   # L1 协同基座（目标：runtime 无关）
│   ├── kernel/                 # agent + 执行引擎机制带
│   ├── build/                  # L2 建造机制
│   └── app/                    # L3 组装根 + 产品面 + 客户端
├── weave-app/                  # Console 前端（B6 迁入）
├── deploy/ scripts/ docker-compose.yml
└── docs/
```

依赖方向规则（depguard 强制）：

| 带 | 允许 import | 禁止 import |
|---|---|---|
| base | base、loom、第三方 | kernel / build / app |
| kernel | base、kernel | build / app |
| build | base、kernel、build | app |
| app | 全部 | — |

**诚实声明：kernel 是"脏带"。** 真实依赖图显示 agent 栈（compiler/registry/skills/mcp……）与执行引擎（workflow/loomruntime）之间存在目录级互依赖（经子包解套，如 `compiler→memory→sessionexec→workflow→compiler` 在包级别并不成环），本次搬迁不在带内重组——那是审定稿后续阶段的事，搬家不装修。kernel 的存在不等于放弃 L1 纯净目标：纯净的边界由"base 不许 import kernel"这条规则守住。

### 3.3 Baseline 例外（仅两条，ratchet 只减不增）

对全部包真实 import 图的全量扫描确认，跨带违规边只有两组：

1. **base/teamrun → kernel/{workflow, workflow/machine, loomruntime}**：executor 内嵌 agent 执行（审定稿 §2.5 已立案，Executor/WorkflowSerialRuntime 拆分后消除）。`workflow/machine` 必须显式列入，否则 depguard 精确匹配会误报。
2. **build/{teamforge, teamorch} → app/metateam**：元团队名字常量耦合（build 带内 15 处 selector、2 个 import 文件；另有 api 侧引用，属带内消费，随 app 带消化。产品方案 M2 改户籍后消除）。

depguard 配置中对这两组以"精确到包对"的 allow 规则记录，任何新的跨带 import 直接 CI 红。

## 5. 搬迁批次

每票格式：内容 / 前置 / 验收。所有票共用底线命令：`go build ./... && go vet ./...`。

### B0：新仓骨架

- 内容：建仓；go.mod（同 module 路径）；Makefile（沿用 `make test = go test ./internal/... ./cmd/...`）；CI workflow；depguard 配置（四带规则 + 两组 baseline 例外）；README。
- **vendor 决策（互审后修订）**：不搬 vendor/，改 go mod 管理。loom v0.8.0 经 goproxy.cn 公开拉取已实测验证（`go mod download` 返回 200，无需 GOPRIVATE 或 git insteadOf；Dockerfile 里"private loom"的注释已过期）。新仓 Dockerfile 同步去掉 `-mod=vendor`；若将来需要 hermetic 构建，`go mod vendor` 一条命令即可重新生成——**vendor 是可再生物，不是资产**。
- 前置：无。
- 验收：空骨架 CI 绿（含真实 `go mod download` 全量依赖）；depguard 对老仓 dry-run 仅报已知两组例外，无第三处违规。

### B1：base 叶子（11 包，不含 teamrun）

- 内容：streamctx、frozen、execution、taskqueue、fanout、deliverable、snapshot、realtime、storeext、db、testutil，连带测试。目录归位 `internal/base/`，import 机械替换。
- 前置：B0。
- 验收：`go build ./... && go test ./internal/...` 绿。

### B2a：kernel 叶子（10 包）

- 内容：engine、grounding、llmrouter、otel、secret、embedder、schedule、audit、runtimeartifacts、config。
- 前置：B1。
- 验收：build + test 绿；depguard 无违规。

### B2b-B2i：kernel 中环与引擎（按包级拓扑分八级，相邻级可合并为一票，顺序不可逆）

互审更正：v1 称"带内环使细分不可能"，不成立——目录级大环（compiler→memory→sessionexec→workflow→compiler）在包级别经子包解套，**包级拓扑序存在**。拆小是技术可行的，分级如下（codex 审计给出，主审复核关键边属实）：

| 批次 | 包 |
|---|---|
| B2b | credentials, declarative/schema, skills, workflow/machine |
| B2c | delivery, revocation, sessionexec |
| B2d | memory, registry |
| B2e | compiler, execenv, mcpregistry, org |
| B2f | declarative（含 designprompt）, loomruntime, runtimes, teamcompiler |
| B2g | freezer, mcphost |
| B2h | mcpprobe, runtimellm |
| B2i | workflow |

- 前置：B2a。每批验收：build + test 绿；depguard 无违规。
- 执行建议：相邻小级可现场合并（如 B2g+B2h），但任何一级不得越序提前。

### B3：teamrun 迁入 base

- 内容：teamrun 全包 + 全部 executor characterization tests；depguard baseline 写入例外 1（teamrun→workflow, loomruntime）。
- 前置：B2b（workflow/loomruntime 必须在场）。
- 验收：`go test ./internal/base/teamrun` 绿——queued→running→succeeded、runtime failed、timer park、fanout leg、lease lost、running reclaim、success/failed terminal replay 八类特征化行为在新仓全部复现。

### B4：build 带（5 包）

- 内容：teambuild（含 authorize_build_run_test）、teameval、teamforge、teamorch、teamrestore；depguard baseline 写入例外 2（teamforge/teamorch→metateam 的 30 处名字常量引用，以现状清单形式记录，只减不增）。
- 前置：B3。
- 验收：`go test ./internal/build/...` 绿（含授权 fail-closed 三类行为）；build 全绿。

### B5：app 带 + cmd/weave（12 包）

- 内容：chatrequest（含 store_test）、conversation、projects、users、apikeys、attachments、ownermem、schedules、webui、metateam、daemon、api（含 chat_request_replay_test）、cmd/weave。
- 前置：B4。
- 验收：全量 `make test` 绿；`docker compose -f docker-compose.platform.yml up --build` 起得来（**互审更正**：根 `docker-compose.yml` 是业务栈，引用 `../../ontology`、`../../spare-parts` 等老仓外部业务目录，不属本仓，验收必须用 platform-only 这份）；冒烟：新会话发送、旧会话续写。

### B6：前端 weave-app

- 内容：weave-app 目录；API base URL 指向新仓后端。
- 前置：B5。
- 验收：`npm run typecheck && npm run lint`（0 error，既有 4 warning 不新增）；对接新仓后端跑通一次完整会话发送+流式展示。

### B7：parity 门

新仓必须通过以下真实场景（前六项沿用审定稿阶段 C/F 的场景清单，后六项为互审增补的高风险生产路径）：

1. 新会话发送 + SSE 流式；
2. 旧会话续写；
3. 断线后恢复（chat request replay 收敛）；
4. create_team 全流程：元团队 brief → blueprint → 授权 → build round → candidate → 评测 → publish；
5. published workflow conversation；
6. 附件发送；
7. remote runtime / daemon 路径（daemon 主入口、runtime 注册与心跳）；
8. runtime MCP gateway（`api/runtime_mcp.go` 路由面）；
9. schedule 定时触发与 admission（`api/schedules.go`、`api/schedule_exec.go`）；
10. API key / JWT 认证链路；
11. memory auto-remember；
12. deliverable 生成与下载。

- 全过 → 老仓归档（§2）；任何一项不过 → 留在对应批次修，不许带病关门。
- 场景 7-12 允许以"最小真实路径"验证（真实请求打到新仓服务、断言关键状态与产出），不要求穷尽参数组合。

## 7. 风险

1. **B2 段票数多、单票小，串行耗时。** 八级拓扑允许相邻合并；每票验收命令统一，机械替换+build 循环应控制在半小时内一票。
2. **搬迁期业务交付停滞。** 已在决策时明示接受；若期间出现必须交付的业务，在老仓交付并同步开移植票，不暂停搬迁。
3. **git 历史断裂。** 缓解：老仓只读保留并在新仓 README 链接；重要文件的"前世今生"靠老仓查。
4. **import 机械替换出错。** 缓解：每批 sed 替换后立即 build；替换 pattern 精确到包路径全段（`weave/internal/teamrun` → `weave/internal/base/teamrun`），不做模糊替换。
5. **depguard baseline 变成永久借口。** 缓解：baseline 两组各挂既有工单（审定稿 Executor 拆分、产品方案 M2 改户籍），ratchet 计数进 CI 输出，任何新增直接红。
6. **Docker 构建失去 vendor 的 hermetic 性。** loom 公开可拉已实测，但 CI/构建机网络策略变化可能回归此风险；兜底：`go mod vendor` 随时可重新生成。

## 8. 与两条既有线的关系

- **产品方案 M0-M3**：搬迁完成后在新仓继续；M1（模板快路径）是新仓的第一个"新功能"票，不与搬迁混票。
- **模块化审定稿**：其保护网（阶段 A-C 测试）随 B1-B5 迁入并继续担任合同；其余构阶段（Executor 拆分、teamorch 收窄）在新仓 kernel/base 带内继续，架构目标不变。

## 9. 互审记录（codex 审计 + 独立反查，2026-08-25）

流程：codex 只读审计本方案 v1，主审逐条亲自读码反查（不采信自报）。结论：**codex 的关键指控全部属实，其中四处纠正了 v1 的实质错误**；方案据此修订为 v2。

### 9.1 事实核验与处置

### 9.2 互审带来的实质修正

1. **db 与 migrations 从"半死码"翻转为生产必搬**——若不互审，B1 会漏搬启动迁移，新仓第一次 boot 即失败。
2. **B5 验收命令从根 compose 改为 platform-only compose**——避免了"验收必然失败却找不到原因"的坑。
3. **B2 从"20 包一票"改为八级拓扑批次**——中间态可编译性从"管理取舍"变成"技术保证"。
4. **vendor 处置从"先验证再决定"改为"已验证 + Dockerfile 同步改写"**——B0 不再有阻塞性未知数。

### 9.3 遗留开放问题（转 B0/B5 调研票）

- CI 环境的 Go 模块拉取网络策略（goproxy.cn 可达性）需在 B0 空骨架时实测确认。
- `docker-compose.weave-remote.yml` 是否现行，B5 前确认（影响 parity 场景 7 的验证方式）。

## 10. 小而美标准：搬迁完成 ≠ 结束，瘦身验收才算

loom 的可比目标（实测：~18k 行、9 包、8 外部依赖、概念表 5 个词）。weave 是平台不是内核，8 倍体量差不会因搬家消失；"小而美"按带操作化，**parity 门之后、M1 新功能之前，插入瘦身阶段 S0**，不过 S0 不开新功能票。

### 10.1 分带标准

| 带 | 现状（含测试） | 小而美标准 |
|---|---|---|
| base | ~17k 行 | **weave 的 loom**：概念表 9 个词（TeamRun / Task / Event / Deliverable / Participant / Lease / Checkpoint / Snapshot / Fanout；归并规则：CreatorLease→Lease，JoinPolicy/ParkIntent/ResumeClaim→Fanout 子概念，Worker/Actor/Executor→Participant）；依赖白名单基线 = loom + pgx + uuid + json-canon（现状即合规，新增逐依赖评审）；executor 按审定稿拆出 WorkflowSerialRuntime 后，核心只剩队列+状态机+合同；**功能冻结带——新能力一律去 app 带或用户模板，永不进 base** |
| kernel | ~60k 行 | 删除优先于整理：deadcode/unused 全量扫描入 CI，**先出报告后定 ratchet，现实预期 5-10%（3k-6k 行）**，-30% 降级为 stretch goal。头号候选：loomruntime 的 terminal reconciler/lineage repair 路径（~2.3k 行，构造器无生产入口，已核实）；该包独占 16k 行、达 kernel 四分之一，是 S0 的主战场 |
| build | ~31k 行 | M2 改户籍即瘦身：元团队 4 个巨型 prompt 从"教整个建造协议"缩为"生成模板草稿"；tf_* 工具面收敛为文档化公开 API |
| app | ~33k 行 | 按审定稿拆 api.Server 为薄 adapter；app 带允许最大，但**只许长薄，不许长胖**——新业务进窄 service，不进 handler |

### 10.2 让"小"不反弹的四条机制（loom 纪律的 weave 版）

1. **预算入 CI**：每带行数、包数、外部依赖数设上限，ratchet 只减不增；base 的依赖白名单逐依赖 code review。
2. **概念表守门**：新概念必须在所属带的词表文档里有名字才能进代码；词表变更 = 架构决策，不是 PR 顺手事。
3. **尸体检测常态化**：deadcode / unused / unparam 进 CI 周报；default-deny 不止用于搬迁，而是永久入境规则。
4. **API 表面积指标**：跟踪 base 带导出符号数（对标 loom：5 原语 + 少量类型）；导出即承诺，新增导出符号需要显式批准。

### 10.3 S0 阶段验收（插在 B7 与产品方案 M1 之间）

- deadcode 扫描报告产出（CI 环境可运行，审计沙箱内无法构建，须真实环境执行）+ kernel 删除票全部关闭；
- executor/WorkflowSerialRuntime 拆分完成（审定稿既有票），base 依赖白名单落地；
- 四带行数/包数/依赖数预算写入 CI 并全绿；
- base 带词表文档（9 个概念 + 归并规则 + 参与方合同）发布。

过了 S0，新仓才算"搬完而且小"；此后 M1 模板快路径、D5 CLI/MCP 都在干净的底子上长。
