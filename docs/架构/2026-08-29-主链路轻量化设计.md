# 设计：主链路轻量化——先可用，后观察

> 适用范围说明（2026-09-05）：本文保留建队与发布机制的设计。日常使用以[当前产品合同](2026-09-05-Weave-当前产品合同.md)中的“选团队 → 确认任务 → 开始执行 → 领取成果”为准；已有可用团队时不重复建队，内部评测不增加用户的必经步骤。

> 日期：2026-08-29  
> 状态：v3 定稿（已完成产品、工程、质量三方互审）  
> 提案来源：用户（2026-08-29）  
> 关联：[当前产品合同](./2026-09-05-Weave-当前产品合同.md)、[M1 团队模板快路径](./2026-08-25-M1-团队模板快路径设计.md)、[M2b 后置评测入口](./2026-08-26-M2b-后置评测入口设计.md)

## 1. 产品判断

Weave 当前把“建队”和“证明这支团队质量足够好”捆在了一起。建队后要先跑完候选场景、语义裁判和发布审批，才能以固定工作流正式派活。只要模型慢、场景长、包含人工节点或超时，整支团队就不可用。

新的产品原则是：

> **建队只回答“能不能按这份配置运行”；质量系统持续回答“它实际运行得怎么样”。**

默认主链路收缩为：

```text
建队 → 派活 → 必要时人工处理 → 取得交付物
```

平台内部仍保留版本冻结、静态校验、运行快照、审计、用量和质量观察，但不再让普通用户穿过 BuildRun、candidate run 和 judge 才能开始工作。

## 2. 对现有决策的变更

### 2.1 M1 的“可用”定义变更

M1 的团队在模板实例化后会立即落库，但它只能通过 free-collab 接活，固定工作流仍是 draft。所以 M1 实现的是“团队对象可用”，不是“模板所定义的工作流可用”。

本设计正式修改为：**模板建队成功，必须同时意味着团队 active，且它的工作流 v1 published。**

### 2.2 M2b 的发布门禁变更

M2b 将“评测通过”设为固定工作流的发布前置。这在原模型下是一致的，但把评测成本、人工等待和超时风险都变成了上线风险。

本设计取消“必须先 evaluated 才能 publish”的通用门禁。发布的必要条件改为：结构合法、引用完整、版本冻结、运行依赖可解析。

M2b 的评测入口、冻结场景、语义裁判和溯源信息仍保留，但改为显式的“认证运行”，不决定团队能否派活。

### 2.3 三类状态不再混用

| 产品问题 | 状态 | 是否阻塞派活 |
|---|---|---|
| 这支团队的核心运行依赖是否完整？ | `active / needs_repair / archived` | 只有 `active` 可派活 |
| 某个冻结版本的控制评测证据如何？ | append-only reports + `never_run / running / latest_passed / latest_failed` 摘要 | 否 |
| 近期真实运行表现如何？ | `unknown / healthy / warning` | 否，v1 只提示 |

认证是针对某个不可变版本的一次性证据；健康度是随真实运行持续变化的观察结果。两者不得互相代替，也不得与可用性合并成一个字段。v1 中二者不双写状态，只在 UI 中并列展示证据。

团队还要有独立的派活策略：`workflow_required / free_collab_only / legacy_compatible`，以及明确的 `default_workflow_id`。“默认工作流不可用”不等于整支团队 `needs_repair`；只有 roster、Agent、凭证或其他核心运行依赖确定性损坏时才进入 `needs_repair`。短暂的 Provider 故障进健康度证据，不改变团队生命周期。

## 3. 产品行为

### 3.1 建队：成功即可按设计运行

模板建队只做快速、确定性的检查：

- 模板 Schema 和工作流图合法；
- 成员、Agent、模型和 Provider 的本地引用与配置可解析（不在建队主链路同步探活远程 Provider）；
- 输入输出路由闭合，人工节点可恢复；
- 所有运行依赖已冻结，可建立完整运行快照。

全部通过后，系统在最终提交中一次性对外显示：

```text
工作流 v1 published + 团队 active + 建队任务 passed
```

“一次性对外显示”不要求把所有资产写入都放进一个超大事务。前置阶段可以创建内部不可见的资产，团队始终保持 `building`。新增模板专用最终提交能力，在同一事务中：

- 锁定 exact draft，运行静态校验和依赖冻结；
- 写入 immutable publication 并更新 workflow `published_version`；
- 写入团队 `default_workflow_id`，将 `building → active`；
- 将 BuildRun 终结为 `passed`，写入 final ref 和审计转移。

这个能力不复用会分两次提交的 candidate publish HTTP handler，而是复用 teamorch publish step 的事务结构。现有 roster_set 不得在模板策略中提前激活团队，现有 `MarkTemplateInstantiated` 不作为新的原子边界。

如果静态检查失败，不创建一支表面 active 的团队；返回具体可修复问题。

### 3.2 派活：模式显式，结果可归因

新建统一派活命令，Workbench 的 MCP 连接与 HTTP API 共用它，不再通过“team 转 lead 再进普通 chat”的间接路径派活。最小契约为：

```text
team_id
task
mode = workflow | free_collab
workflow_id?          # 显式覆盖默认 workflow identity
workflow_version?     # 高级调用才允许指定
client_request_id
```

系统必须在入队前完成模式选择和固定版本快照，入队后不再根据最新数据重新决策。

| 模式 | 语义 | 前置 |
|---|---|---|
| `workflow` | 按已发布的固定工作流执行 | 必须能通过显式参数或团队默认指针选中 identity 及 published version |
| `free_collab` | 由团队自由协作 | 必须由调用方显式选择 |

新团队默认为 `workflow`。默认选择依赖团队持久化的 `default_workflow_id`和该 workflow 的 `published_version` 指针，不通过“全部 published 记录是否唯一”猜测。历史 published 版本不参与候选计数。

如果没有默认指针、指针版本不可用，或显式指定的版本无法准入，系统返回明确错误，不得自动改走 free-collab。只要团队核心 roster 仍完整，默认工作流损坏不影响用户显式选择 free-collab。

这是对外行为契约变更。新客户端同步切换；旧客户端省略 mode 时，在兼容窗口内按团队 `legacy_compatible` 策略保留原 free-collab 语义并返回废弃提示。窗口结束时间必须显式公布，不能让同一个旧请求因补发 draft 而静默改变执行语义。

### 3.3 质量：真实运行后再观察

健康度归属到 `(workflow_id, workflow_version, artifact_content_hash)`，团队卡片只投影当前默认版本的结论。切换 published version 后，新版本从 `unknown` 开始，不继承旧版本的 healthy 或 warning。free-collab 没有 workflow version，必须单独观察，v1 不混入固定工作流健康度。

真实运行结束后，异步观察器先消费可靠事实：TeamRun 终态与时间、terminal audit 中的完整用量和耗时、可明确归因的交付物，以及人工完成/超时。缺失 audit、旧 schema、关联错误或 `usage_incomplete` 都表示事实未齐，不能当成零用量。

现有人工 resume payload 没有平台统一的通过/驳回语义，且不可变转移只保存 digest。所以 v1 只观察“人工已完成/超时”。如要观察 approved/rejected，须先新增 append-only human decision ledger，并由工作流显式声明 payload 映射。

现有交付物账本只覆盖 conversation workflow，且 candidate 产物会写入同表。v1 的“无交付物”规则仅对可证明来自生产 `conversation_explicit` 运行的样本启用，并排除 candidate/build run。其他触发方式在建立中性 workflow-output ledger 之前保持 `unknown`。

v1 健康度是 **operational health**，反映完成率、超时、耗时、人工完成和交付链路完整性，不承诺内容正确或没有幻觉。只有明确人工验收或可重放裁判才形成 outcome-quality 证据。样本门槛、时间窗和恢复规则必须配置化。

观察记录 append-only，每次计算保存 workflow/version/artifact hash、cutoff 或 watermark、入选 run ID 及事实 hash、ruleset 版本与配置 hash、样本窗口、命中规则和结论。`current_health` 只是可重建投影。

复用真实产物消除了为主链路重复生成候选内容的必要，但不等于评价成本必然为零。如果未来对真实交付物调用语义裁判模型，必须单独记账、限流和允许关闭。

### 3.4 认证：保留为高级能力

当用户需要上线前验证、回归测试、版本对比或合规证据时，可以显式发起认证运行。认证 attempt/report 为 append-only，绑定 `(workflow_id, workflow_version, artifact_content_hash, certification_run_id)`，不自动修改生产资产，也不阻塞正常使用。

版本摘要显示 `never_run / running / latest_passed / latest_failed`，同时保留历史报告，不用一个可覆盖三态丢掉“曾通过、后失败”的事实。现有 `team.evaluation` 降为兼容投影，不再作为权威事实源；没有完整 provenance 的历史 `evaluated` 不自动映射为 certified。

certified 版本仍可能因真实运行连续失败而 warning；unverified 版本也可能有稳定的 healthy 运行记录。

## 4. 状态与用户界面

普通用户只需看到：团队可用/需修复/已归档，当前工作流版本，近期健康度及证据，以及当前版本是否有认证报告。

BuildRun、candidate run、judge iteration、publish eligibility 等治理细节保留在管理面和审计 API，不再作为普通用户的必经操作或主状态。

## 5. 存量团队迁移

不得在存量团队仍只有 draft 时直接切换派活契约，否则它们会从“可以静默走 free-collab”变成“完全不能派活”。

迁移不能扫描“全部 active 且无 published workflow”就默认其损坏。合法的 free-collab-only 团队和平台内部团队可能天然没有 workflow。上线前先形成四类对账表：必须补齐 workflow、合法 free-collab-only、平台内部、需人工处置。

对“必须补齐”类执行可重放迁移：

1. 依据明确 dispatch policy 或可验证模板 lineage 确认迁移范围，显式排除平台内部团队；
2. 唯一选中目标 workflow identity；在同一事务内锁定 exact draft，完成静态校验和依赖冻结，用 draft `updated_at` CAS 防止并发修改；
3. 按原 workflow/version identity 发布 immutable artifact，不把存量 v3 重命名为 v1；记录迁移来源、内容 hash 和幂等键；
4. 无法唯一选择 workflow 的团队保持 active，workflow 模式返回 `no_default_workflow`，仍允许显式 free-collab；只有核心运行依赖确定性损坏才标记 `needs_repair`；
5. 迁移结果对账完成后，才允许切换新派活契约。

迁移账本自身是幂等事实源；不依赖“重放 InsertPublicationTx 自然成功”，因为已发布版本重放会发生状态冲突。

历史 `unevaluated` 映射为当前版本 `unverified`；历史 `evaluated` 只有证据可完整绑定到 exact artifact 时才迁移认证报告，否则仍为 `unverified`。健康度在没有真实运行证据时初始为 `unknown`。

## 6. 交付顺序

1. **原子发布基础**：新增模板专用最终提交能力；移除普通管理 publish API 的 team-level evaluation 前置；保留认证运行的 baseline proof、content hash 和 identity CAS。
2. **新建团队即时发布**：模板策略中 roster_set 不再提前激活；最终原子提交 active team、default workflow、published v1 和 passed BuildRun，全程零 LLM。
3. **统一派活入口**：在兼容模式下上线新 dispatch command，让 Workbench 经 MCP/API 在入队前固定模式和工作流版本。
4. **存量分类与补齐**：执行预演、四类分账、迁移和对账；保留旧客户端意图，不误伤 free-only 与平台团队。
5. **派活契约翻转**：新团队默认 workflow、free-collab 显式化、禁止静默回退；启动有截止日期的 legacy 兼容窗口。
6. **运行后观察与版本认证**：先建立可重放的 operational health，补齐 human decision/output ledger 后再扩展质量信号；认证改为版本级 append-only 证据。

第 1—4 步在内部可以用兼容模式上线；第 5 步是对外契约翻转点。

## 7. 验收标准

### 7.1 新建团队

- 合法模板建队完成后，团队 active，`default_workflow_id` 已设置，该 workflow 的 `published_version` 指向 v1；
- 建队不发起模型请求，不等待人工节点；
- 对外不可见“active 但无 published workflow”中间状态；
- 静态非法返回可修复问题，不产生表面可用团队。

### 7.2 存量与路由

- 迁移可预演、可重放、有审计，重复执行不产生新版本；
- 无 published workflow 的 active 团队都被归入“必须补齐、合法 free-only、平台内部、需人工处置”之一，不将后三类自动标记 needs_repair；
- 默认派活只读取团队默认 workflow identity 及它的当前 published version，发布 v2 后历史 v1 不会造成歧义；
- 无法选中时返回稳定错误码和修复建议，不触发 free-collab；
- 除兼容窗口内的旧客户端外，只有显式传入 `free_collab` 时才走自由协作；
- 兼容窗口内，旧客户端省略 mode 仍保持原派活语义，并收到可观测的废弃提示；
- 工作流指针损坏但 roster 完整的 active 团队，workflow 模式明确失败，显式 free-collab 仍可执行。

### 7.3 质量与认证

- 真实运行结束后，健康度异步更新，不影响原运行交付；事实不完整时保持 unknown/pending；
- 健康度结论可追溯到运行和规则；
- 切换到新工作流版本后健康度从 unknown 开始，旧版本结论仍可查但不污染新版本；
- 认证结果绑定不可变版本，不改变团队 active 状态和已发布版本；
- certified/failed 与 healthy/warning 可以交叉存在，不隐式覆盖。

### 7.4 工程门禁

- `make test`、`make depguard` 通过；
- 新老 API 契约、迁移预演、幂等、并发发布和崩溃恢复有自动化测试；
- 真库验收覆盖模板建队、存量补齐、两种派活模式、人工恢复、交付物和健康度。

必须有一条产品黄金旅程：

```text
模板建队 → 默认 workflow 派活 → 人工恢复（如有） → 取得交付物
```

全程断言：建队不创建 evaluation/candidate/judge，用户不执行 publish，Workbench 不要求先评测。

## 8. 非目标与边界

- 不删除不可变工作流版本、精确 Agent/模型绑定、幂等、运行快照、人工等待与恢复、审计、用量和交付物；
- 不用健康度代替受控认证，也不用一次认证代替持续观察；
- 不在 v1 自动封禁 warning 团队；未来如引入自动止损，必须单独设计权限、阈值、申诉和恢复契约；
- 不在这次轻量化中重写工作流执行引擎。

## 9. 工程归属

- `internal/base/db`：schema 与数据迁移；
- `internal/kernel/workflow` 与 `internal/kernel/org`：publication、版本认证事实和团队生命周期的原子存储能力；
- `internal/build/teamorch`：模板最终提交、存量补齐和认证编排；
- `internal/app`：统一 dispatch API、Workbench MCP/API 适配、迁移启动与健康观察调度。

健康度的底层事实与投影由下层持久化，不让 kernel/build 反向依赖 app。所有变更遵守 base ← kernel ← build ← app 的带层方向。

## 10. 互审记录（2026-08-29）

互审由产品契约、工程事实、质量数据三个独立视角完成。总结论为：**方向通过，v2 不可直接实施；以本 v3 修订为实施基线。**

| 审查结论 | 事实反查 | 裁决与修订 |
|---|---|---|
| 模板建队存在 active + draft-only 窗口 | `template_instantiate` 禁止 publish，roster_set 会提前激活，`MarkTemplateInstantiated` 只终结 BuildRun | 采纳；新增模板专用原子终结器，roster 后保持 building |
| MCP `team_dispatch` 没有经过现有固定工作流 selector | 当前 MCP 只传 team_id/task，client 转 lead 后调 `/v1/chat`，异步入队直接建 free-collab snapshot | 采纳；新建统一 dispatch command，入队前冻结模式与版本 |
| “唯一 published”会在发布 v2 后失效 | 当前查询依赖 published workflow 数量，且团队没有默认 identity 指针 | 采纳；引入 `default_workflow_id + published_version` 两级指针 |
| 全量 no-published 扫描会误伤合法 free-only/平台团队 | 真库存在无 workflow 的 active 普通与平台团队 | 采纳；迁移先四类分账，由 dispatch policy/lineage 限定范围 |
| 旧客户端省略 mode 的意图会静默改变 | 旧契约不含 mode，补发 workflow 后同一请求可从 free-collab 变为 workflow | 采纳；新增 `legacy_compatible` 窗口和废弃提示 |
| `needs_repair` 不应等同于 workflow 不可用 | roster 完整时 free-collab 仍可运行 | 采纳；只有核心依赖损坏才 needs_repair，workflow 缺失单独报错 |
| 健康度和认证必须归属 exact workflow version | 现有 `team.evaluation` 仅是团队级二值，无法表达多 workflow/version/多次认证 | 采纳；两类 append-only ledger 均绑定 version + artifact hash，team 只做当前版本投影 |
| 人工驳回和交付物不能直接作为全量可重放事实 | resume 不可变转移只存 digest；deliverable 仅覆盖会话工作流且混入 candidate | 采纳；v1 收缩为 operational health，限定可信样本，后续补 human decision/output ledger |
| “解除通用门禁”可能误删认证 CAS | 普通 publish 的 evaluation 判断在 app API；认证 baseline/content identity CAS 位于 build store | 采纳；只移除普通 publish API 的 team-level 前置，保留认证证据完整性 |

互审没有否定的核心决策：建队只做确定性校验并原子可用；evaluation 从准入门禁降为显式认证；availability/certification/health 三轴分离；workflow 为新团队默认且 free-collab 必须显式；存量补齐在契约翻转之前完成；治理实现从普通用户主链路隐藏。
