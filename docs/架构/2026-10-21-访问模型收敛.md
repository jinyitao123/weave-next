# 访问模型收敛

状态：2026-10-21 用户批准实施；按下文顺序分提交落地，每步的验证写在提交说明里。团队受众仍待产品决定。

## 为什么改

2026-10-21 对 `internal/app/api` 的 184 个已登录路由摸底：

- 角色、API key scope、Forge 权限集、产品权限四套词汇并存，靠硬编码互相翻译；路由里同义的角色列表有五种写法。
- 68 个路由写了 `owner`，员工会话从不产生它；`service` 只有已删除的受限选择决策接口在用。
- scope 只约束 API key，员工会话直接跳过；scope 为空的 key 能进所有带 scope 的路由。
- 91 个路由在路由层不限角色，其中 36 个是写操作；16 个允许成员改动同一工作区里别人的运行、agent、技能或记忆，或向任意团队派发。

问题大多不是角色不够，而是缺少"只能动自己的东西"。

## 模型

Weave 只回答三个问题。

| 问题 | 规则 |
|---|---|
| 调用方是谁 | 员工：Forge 会话交换得到的 Weave 会话。运维：API key |
| 能做哪一级事 | `member`（使用团队）< `developer`（开发团队）< `admin`（管理工作区）。员工的级别由 Forge 权限集决定：`weave_team_developer` → developer，`admin_full_access` → admin，与桌面得到的 `teams:use / develop / admin` 一一对应。API key 一律按 admin |
| 能动哪些资源 | 见下表 |

路由只声明最低级别（`RequireAtLeast`）；改动资源的 handler 再做归属检查。

| 资源 | 谁能改动 |
|---|---|
| 从员工个人工作台发起的运行 | 只有本人，管理员也不能代办 |
| 其他运行（开发试跑、代码任务等） | developer 及以上 |
| 任务队列中的任务 | 只有发起人：任务存储只读取当前调用身份的任务（现状，无须改动） |
| 暂停中的对话运行（resume） | 只有发起人；无发起人的运行只有 admin |
| agent、技能 | developer 及以上，属于工作区共享的开发资源 |
| agent 记忆 | 只能指向本工作区已有的 agent；写入和删除要求 developer |
| 团队派发 | 待定：由 Forge 配置的团队受众决定，见 `ensureTeamAvailable` |

## 删除的部分

- 角色 `owner`、`service`。已有 `owner` 密钥在认证时按 admin 处理，其他非 admin 密钥不再通过认证；数据行保留，便于审计。
- API key 的 scope 判断（`RequireScope` 及路由上的 scope 参数、能力接口里的 API key scope 分支）。scope 列和 bootstrap 写入的值暂时保留，不再参与授权。
- 新建 API key 只接受 `admin` 角色。

能力应用凭据 `wv_cap_`、运行时令牌、MCP 登录令牌不是 API key，不受影响。

## 落地顺序

1. 三级统一：`RequireAtLeast` 取代 `RequireRole` 与 `RequireAnyRole`。
2. 运行与 resume 的归属检查。
3. agent、技能要求 developer；上传校验 agent 名。
4. 记忆的 agent 名校验。
5. 删除 `owner`、`service` 与 scope。
6. 团队受众，待产品决定。

## 影响

- Forge、ObjectStack 不调用 Weave，不受影响。Kim 只读登录返回的 `permissions`，不受影响。
- 掼蛋的 `service` 密钥失效；它依赖的 `/v1/decisions` 已在 W10 删除。
- 上线前在生产库确认：`SELECT role, count(*) FROM weave_api_keys GROUP BY 1;`。经 MCP 工具 `apikey_create` 未填角色建出的密钥是 `service`，第 5 步后会失效。
