## W4 业务动作防重放按内容识别

**问题：** 防重放只按（节点、调用、模型生成的调用 ID）精确匹配，另拦截“同能力同记录且结果未定”的早先调用。成员被中断并重试后用新调用 ID 重发一个**已成功**的动作，两条规则都不拦，写请求会再次到达 Forge，是否重复只能靠各 Forge 动作自己的幂等。

**改动：**

- `ActionOutcomeEvent` 与团队运行详情新增 `params_sha256`：对最终发给 Forge 的请求（动作、对象、记录及全部参数，含平台注入的冻结材料参数）取 RFC 8785 规范化 JSON 的 SHA-256。只存摘要，不存参数、凭据或响应，原有“回执不含参数”的约束不变。
- 防重放增加第三条规则：同一运行、同一输入版本、同一能力、同一记录、同一摘要，且早先调用已确认成功，则不再调用 Forge，并向成员报告“同一运行已用完全相同的记录和参数成功执行过”。
- 三条规则按优先级取一：同一调用（原规则）、结果未定的同能力同记录调用（原规则，仍优先于成功，避免把未知说成成功）、相同请求已成功。失败后的相同请求允许重试；参数不同的调用互不影响，例如同一次运行调整同一报价的两行价格。
- `CheckBusinessActionReplay` 改为接收 `BusinessActionReplayCheck`、返回 `BusinessActionReplayDecision`；摘要为空或旧回执没有摘要时第三条规则不生效。

**取舍：** 同一运行内，对同一记录用完全相同的参数重复执行一个已成功的动作会被拦下，包括本意确实要办两次相同的动作。此时成员须先核对业务记录并调整参数。Weave 向 Forge 传稳定幂等键涉及 Forge 动作契约，未在本工作包，见问题清单 C21。

**验证（真实 PostgreSQL）：** 同摘要换调用 ID 被拦并标为同参数成功；不同参数放行；失败后相同请求放行；结果未定的早先调用优先于成功并报“未知”；摘要为空、旧回执无摘要均不触发；不跨记录、不跨运行。变异检验：临时关闭第三条规则，核心测试按预期失败，恢复后通过。调度器侧：摘要与调用 ID 无关、与 JSON 键顺序无关；被判同参数成功时不调用 Forge、不写回执，提示语与原规则区分；开始与结果回执摘要一致，字段名在写入、SQL 与投影三处一致，结果与其开始的摘要不同会被投影拒绝。

**局限（复查补充）：** 摘要覆盖的是最终发给 Forge 的完整请求，因此**模型每次重新生成的参数会让摘要不同**。例如报价调价动作要求成员提供 `idempotency_key`，成员重启后换了新的键，摘要随之改变，第三条规则不会命中；这种情形仍只靠 Forge 侧的核价版本检查兜底。真正的解决是 Weave 向 Forge 传由运行与输入版本派生的稳定幂等键（问题清单 C21，需要 Forge 动作契约配合），不在本工作包。

**未验：** 没有覆盖“真实成员运行时重启后重发”的整链测试（需要发布产物、委托和假 Forge MCP 的完整装配）；接缝由上述契约测试锁定。Forge 侧的实际重复写入行为未在 124 验证。

## W5 平台正确性小修（本批已完成部分）

- **删除死代码：** 队列 `Store` 中不检查租约的 `Complete`、`Fail` 已删除。全仓没有任何调用者或接口引用，整个工程编译通过；之后租约已过期的旧 worker 不再有一条能覆盖别人重新领取任务的写入路径。
- **永久投递失败可见、可重投：** 事件被 Forge 以 400/401/403/409/422 拒绝而永久失败时写错误日志。新增运维命令 `weave ops events list-failed` 与 `weave ops events redeliver [--event ID]`，只走 `DATABASE_URL` 直连数据库，不开放 HTTP。重投只移动 `permanent_failure` 行，已送达、待投递、投递中的事件不受影响，事件事实字段仍由触发器保护为不可变。真实 PostgreSQL 测试走通：真实运行终态 → 假 Forge 返回 401 → 永久失败且不被自动重取 → 运维列出 → 修复后重投 → 恰好送达一次。命令行冒烟验证了输出、退出码和非法 ID 的清楚报错。
- **资源条数在登记时拒绝：** 新增 `frozen.MaxDelegatedFiles = 10`（总资源 12 条含输入与业务记录）。登记超限时返回 **409** `dispatch_input_too_many_resources`，不写入任何输入版本；运行时解码使用同一常量。此前登记不限份数而运行时拒绝超过 10 条，员工会先收到“已接单”后运行失败。用 409 是因为桌面只把 409 当作对本次登记的明确拒绝并停止重试，其他状态一律当作“结果未知”，会让 Pi 陷入核对循环；错误码仍写明真实原因。**运行时上限同时放宽：** 原来运行时总共接受 10 条资源（含输入与业务记录，实际最多 8 至 9 份文件），现在是 12 条（10 份文件加输入与记录），这是有意的对齐，此前没有写明。**这是契约变化：** `contracts/v1/README.md` 中“材料不设文件份数上限”须在总仓改为最多 10 份文件；**桌面须在上传前按“新附件加复用的原材料”总数检查，并把该错误码显示为明确原因**，否则员工看到的是“已有更新输入或内容冲突”的泛化文案。该桌面改动未在本工作包，登记为总仓待办。
- **委托过期有明确原因：** 新增 `ErrDelegationExpired`，成员构建与每次调用前的过期检查都带上它，并与“动作超出范围”分开。**两处的效果不同：** 成员构建时过期，错误一路传到运行失败，`ClassifyFailure` 将其归为不可重试的基础设施失败，原因为需从原工作重新提交；调用途中过期，MCP 主机原先把守卫的原因吞掉，成员只看到通用的“业务动作返回失败”。复查发现后已改为保留原因（`http_host.go`），动作调度器对成员返回“员工对本次工作的授权已过期，业务动作没有执行；需要从原工作重新提交”，回执记为失败；这一路是给成员的工具结果，不会把整个运行标为该失败类别。此前过期与超范围共用同一条错误。新增测试覆盖：守卫拒绝时保持失败关闭、保留原因、且从不调用工具（该守卫此前完全没有测试，在未修复的代码上先复现了原因丢失）；成员得到明确提示。**未验：** `resolve`、`validate` 读取数据库的路径没有 PostgreSQL 测试；30 分钟有效期本身与续期路径未改。

**本批未做：** 运行级业务结果统一计算、开发试跑与正式运行共用记录器，二者依赖 W8 与 W6 的终态收拢，留到那时一并处理。
