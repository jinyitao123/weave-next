# 取值检查：失败与超时路由（#104）

## 来源

machine 第 8 阶段用支配关系判断一个结果是否可读。一个步骤带失败路由时，失败分支读取这个步骤的结果能通过校验；人工等待带超时路由时，超时分支读取等待结果也能通过校验。运行时走这两条路由，源节点都没有结果，读取失败。这个问题是在团队草稿“流程保证”的失败分支编辑中发现的。

## 改动

- `buildOutputAvailability` 按拓扑序计算每个节点的“结果可用”集合：取所有前向入边贡献的交集。普通入边贡献 `avail[from] ∪ {from}`，`failure`、`timeout` 入边只贡献 `avail[from]`。
- 取值检查的四处可读性判断（同循环本轮、上一轮、循环不变量、循环外）在原有支配检查通过后，再要求生产者的结果可用。不满足时报 `workflow_value_unavailable_on_route`，原有支配失败仍报 `workflow_value_not_dominating`。
- 循环结构检查（第 5 阶段）继续使用支配关系，不变。

## 兼容性

没有 `failure`/`timeout` 路由的图，可用集合恰好等于严格支配集，归纳可证：`avail[p] ∪ {p} = dom[p]`。所以改动只影响带这两种路由的图，而且只会收紧规则；新拒绝的图在对应路径上本来就会运行失败。冻结产物哈希不含校验结果，已发布版本不变；重新发布或重新准入时按新规则校验。

## 验证

- `TestValuesOnAFailureRouteCannotReadTheFailedStep`：失败分支读取任务输入通过；读取失败步骤的输入或交付被拒。
- `TestValuesOnATimeoutRouteCannotReadTheExpiredWait`：超时分支交付字面量通过；读取等待结果被拒。
- `TestOutputAvailabilityEqualsStrictDominanceWithoutFailureRoutes`：在代码验证回路样例和带失败分支的图上逐对核对，不经失败、超时路由的生产者，可用性与严格支配一致。
- 去掉修复（让所有路由都视为带出结果）后，前两项测试失败。
- `go build ./...`、`go vet ./...`、`go test ./internal/... ./cmd/...` 全部通过；以下两项失败是本机环境问题，与本改动无关：
  - 一项测试调用 `python3`，本机没有；
  - runtimehost 的一项测试需要创建符号链接，Windows 未授予该权限。
