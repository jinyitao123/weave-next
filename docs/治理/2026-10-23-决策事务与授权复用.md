## 职责、入口与合同

遵循[分层基线](../架构/2026-09-13-分层收敛与Loom职责基线.md)和[发布工作流的应用调用](../架构/2026-10-15-发布工作流的应用调用.md)：

- `internal/kernel/teamrun` 的原分支步骤事务负责分支完成事实；`internal/base/deliverable` 只提供加入该事务的存储方法，开发试跑记录器沿同一事务落产出。

## 授权复用与撤销

`weave_authorization_epochs` 以 `(workspace_id, scope_kind, scope_id)` 为主键。应用的启停、授权和凭据变化，团队成员/负责人/候选名单变化，以及供应方撤销、删除、启停或模型范围变化，在原变更事务内递增相应版本。

缓存按工作区、应用、运行、快照、源任务、冻结工作流版本、执行租约 epoch、主体和凭据引用隔离。首次调用先读版本，再完整校验；并发首次调用等待首个校验，随后各自重新读取版本和当前任务。后续每次调用只用一条查询读取相关版本和当前任务身份；版本改变就重做完整校验，失败即拒绝。进程重启、缓存容量淘汰或新尝试都重新校验。已提交的撤销在下一次调用的校验中生效；不声称能收回已经开始的外部模型调用。

精确成员版本不可变。发布后创建新成员版本不会原地修改已冻结的成员配置；团队成员停用、名单/负责人变更分别由团队版本失效。供应方密钥仍每次从当前存储读取。

真实 PostgreSQL 用例分别覆盖 grant、应用凭据、应用停用、成员停用、团队归档、负责人变化、供应方吊销、供应方停用、模型列表变化和供应方删除后的下一次调用。另覆盖无变更时复用、并发首调用、单连接池首调用，以及原 `TestWorkflowRuntimeCredentialRechecksApplicationGrantRealPG`。

## 分支产出与补充修复

分支输出及其附件通过 `RecordWorkflowOutputsTx` 和 `recordFanoutLegStep` 一起提交；产出写入失败时步骤不落地，仍报告 `delivery_unavailable`。开发试跑记录器使用调用方事务；声称支持事务的记录器不能退回另一连接写入。

接续核查还修复三处问题，均先用真实 PostgreSQL 回归复现失败，再复验修复：

1. 首次授权已持有 resolver 事务连接，却再次从池读取冻结产物。池大小为 1 时授权超时。产物读取现在复用 resolver 事务。
2. 已保存的分支步骤重放时，`INSERT ... ON CONFLICT DO NOTHING` 之后仍尝试写入重放产出。现在只有新插入步骤才写产出，既有步骤及其产出共同胜出。
3. 正常开发发布保留了候选名册，完整校验会用其中的启用记录兜底已停用的实时成员。现在仅草稿版本可使用候选名册；发布后保留的名册只是历史证据，不能恢复成员授权。用例 `TestRuntimeCredentialPublishedRosterCannotRestoreADisabledMemberRealPG` 覆盖这一形态。

## 测量口径与工具修正

- 每档从预热前到排空后的数据库快照统计 SQL、提交、回滚和主要查询指纹，扣除带驱动标记的语句/事务。每工作流的分母是同一完整区间内完成的工作流数；存在失败时这些是总体数据库工作除以完成数，不能解释为只属于成功调用的精确成本。
- 业务时延样本按测量窗口内发起的请求选取，覆盖完成、失败、主动取消、未确认和明确拒绝。窗口结束仍在途的样本单列，继续等待。吞吐分母为测量窗口加这些请求的排空时间，排除预热和报告整理耗时。
- HTTP 4xx 作为明确拒绝；5xx、受理响应无法解码或丢失响应属于未确认。未确认样本计入全量延迟的未知上界，且只要存在未确认就不得升档，即使成功率达到 99%、P95 落在成功样本上。
- 从 10、20、50 到 100 通道逐档运行；上一档全部结束、成功率至少 99%、全量 P95 不超过 30 秒才升档。全部配置档通过只说明已测到该档，不是容量结论。
- 每 500ms 采样 `pg_stat_activity` 与 `pg_locks`，区分 WAL、关系/元组/事务锁、NOTIFY 提交锁。采样次数乘周期是近似 backend-seconds，不是精确锁持有时长；未采到不能证明从未等待。
- pgxpool 累积计数相减得到 acquire、empty acquire、AcquireDuration 和 EmptyAcquireWaitTime。报告中的池等待用后者除以同区间完成数，单位毫秒。多个执行器进程时当前端口只覆盖 API 进程，不得当作所有池的总和。
- 排队时间从现有任务 `available_at` 到 `started_at` 估计，同一父任务的并行分支取最长等待；模型时间来自桩的真实请求回执。平台开销为服务端时长减模型关键路径和估计排队时间，受分支重试及关键路径近似影响，不能当作精确 CPU 时间。

Claude 原最后批次只有第一轮优化报告有效，后两轮因临时外部连接检查失败而未执行。故后续对照统一用修正后的驱动重新运行。检查现在只认客户端连接，不再把后台维护进程当作外部客户端；原失败时没有保留 backend 类型，不能据此确定当时一定是 autovacuum。

## 剩余只读事务与 NOTIFY（第 2、3 步收尾）

用本地事务追踪器（只在诊断时编入，未提交）按调用点归因 20 通道一轮约 313 次决策，结论如下：

- **每次模型调用的解析事务**：约每次决策 4.9 次，每次以回滚结束。尝试内的后续调用只有两条语句：读授权版本号、读供应方密钥（`FOR SHARE`）。该事务持有行锁，以回滚结束不必等 WAL 刷盘，保持不变。
- **带行锁、以提交结束的只读事务**：改为以回滚结束。行锁照样释放，结果不变，但不再等待 WAL 刷盘。行锁会分配事务号并写 WAL，提交时就要等刷盘，本机的瓶颈正在于此。共约每次决策 6.8 个，包括：
  - 汇合组恢复计划 `readResumePlan`；
  - 停放检查点 `GetYieldedCheckpoint`；
  - 创建者租约 `CreatorLeaseState`；
  - 对账器判组发现尚未就绪的 `tryDecideGroup`。
- **不带锁的单条读取**：准入栅栏在全部已存在时用一条语句读取，不再开事务，有缺失时才进入原来的建栅事务；运行活动列表 `PGActivityStore.List` 沿用 `CorrectionStore.GetActive` 的写法，能直接查询时不开事务。每次决策约少 2.9 个事务；其中活动列表的部分随调用方查询次数变化。
- 议题第 2 步原文是“以提交代替回滚”。本机受 WAL 刷盘限制，带锁的只读事务改成提交反而要多等一次刷盘，所以这里取相反方向：带锁的改为回滚，不带锁的去掉事务。回滚数因此上升，需要等刷盘的提交减少。
- **NOTIFY（第 3 步）**：带通知的提交约占全部提交的 2%（每次决策 3 次：准入、扇出激活、恢复），10 到 100 通道下等待通知提交锁的采样为 0 到 1 次。扇出的各条腿在激活事务内一起入队，PostgreSQL 只投递一次通知，`TestMaterialReadAllowsOnlyCurrentParkedFanoutLegOnPostgres` 断言两条腿只发一次。现有做法即方案 (a)，不新增第二套队列。
