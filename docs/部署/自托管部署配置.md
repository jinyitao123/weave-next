# 自托管部署配置

本文写给自行部署 Weave 的部署管理员：基础 Compose 需要哪些配置，组织连接文件和凭据密钥文件什么时候需要、由谁创建、怎样挂进容器，以及上线前怎样检查。

## 基础部署只运行 Weave 服务

`docker-compose.platform.yml` 单独就能运行 Weave 服务（数据库 + 服务端），不需要 Forge，也不需要任何额外文件。必填项：

| 变量 | 用途 |
|---|---|
| `JWT_SECRET` | 会话签名密钥 |
| `WEAVE_LOGIN_KEY` | 部署登录密钥，持有者以工作区管理员身份进入管理端（`openssl rand -hex 24`）。未设置、空白或设为 `admin` 时服务拒绝启动 |
| `WEAVE_ADMIN_PASS` | 启动时预置的管理员密码（用户名为 `WEAVE_ADMIN_USER`，默认 `admin`），登录密钥代表的就是这位管理员 |
| `WEAVE_SECRET_KEY` 或密钥文件 | 凭据加密密钥，二选一，见下文 |

管理端“部署连接”页面提示“部署连接尚未配置”，只说明可选的组织连接下载没有启用，不代表 Weave 不可用；纯服务部署可以不配置它。

## 五样容易混淆的东西

| 名称 | 配置 | 谁用、做什么 | 是否必需 |
|---|---|---|---|
| 组织连接下载 | `WEAVE_ORGANIZATION_CONNECTION_FILE`（组织连接文件） | 管理员在“部署连接”下载无凭据的连接文件，员工在桌面“导入组织连接” | 可选 |
| Forge 身份交换 | `WEAVE_FORGE_SESSION_URL` | 服务端向 Forge 核对已登录账号，员工和管理员以本人 Forge 账号进入 | 使用 Forge 账号时需要 |
| 管理端 Forge 登录 | `WEAVE_ADMIN_FORGE_URL`（浏览器可访问的 Forge 地址） | 管理端登录页的“账号登录”，以及允许这一个 Forge 内嵌管理端 | 可选，不设则只有密钥登录 |
| 部署运维凭据 | `weave bootstrap` 的输出（`wv_sk_` 开头的 API Key）、`WEAVE_LOGIN_KEY` | 部署管理员和运维脚本 | 登录密钥必需；bootstrap 输出存入私有秘密存储 |
| 应用凭据 | 管理端或 `/v1/capability-apps/actions` 签发（`wv_cap_` 开头） | 业务应用按授权调用能力，不能管理应用 | 接入应用时签发 |

组织连接文件里只有地址，没有任何凭据；它不能代替上面任何一种登录或凭据。

## 组织连接文件

只在需要从管理端下载组织连接时启用。文件由部署管理员在部署主机上创建，内容只能是下面三个字段（参考 [organization-connection.example.json](../../deploy/compose/organization-connection.example.json)）：

```json
{
  "version": 1,
  "forgeOrigin": "https://forge.example.com",
  "weaveOrigin": "https://weave.example.com"
}
```

- `version` 必须是数字 `1`，不能有其他字段，文件不超过 8 KiB。
- `forgeOrigin`、`weaveOrigin` 是员工的桌面和浏览器实际访问的外网地址，不是容器内的服务名（如 `http://weave:8080`）。
- 地址只能是 origin：`http` 或 `https`、主机名或 IP、可选端口；不能带路径、查询参数、片段或用户名密码。默认端口会被去掉。离开本机访问的部署应使用 `https`。

在部署主机上创建并启用：

```bash
sudo install -d -m 0755 /etc/weave
sudo install -m 0444 /dev/null /etc/weave/organization-connection.json
sudo tee /etc/weave/organization-connection.json >/dev/null < 你的文件.json

export WEAVE_ORGANIZATION_CONNECTION_HOST_FILE=/etc/weave/organization-connection.json
docker compose -f docker-compose.platform.yml -f deploy/compose/organization-connection.yml up -d
```

[organization-connection.yml](../../deploy/compose/organization-connection.yml) 把宿主文件以只读方式挂到容器内的 `/run/weave/organization-connection.json`，并设置 `create_host_path: false`：宿主文件不存在时启动直接报错，不会被自动创建成空目录。

- **读取权限**：服务镜像默认以 root（UID 0）运行，能读取 0444 的文件。如果在 Compose 里另设了 `user:`，或者 Docker 启用了 rootless、userns-remap，要让容器内实际运行的 UID/GID 能读这个文件（例如 `chgrp <gid>` 后改为 0440）。
- **更新文件**：下载接口每次都重新读文件。单文件挂载绑定的是文件本身，用编辑器另存会生成新文件，容器仍看到旧内容；请原地覆盖（`tee` 或 `cat >`），或者改完后重启服务。

## 凭据加密密钥文件

凭据加密密钥可以直接写在 `WEAVE_SECRET_KEY`，也可以放在宿主文件里，两者只能设置一个：同时设置或都不设置，服务都拒绝启动。

```bash
sudo sh -c 'umask 077; openssl rand -hex 32 > /etc/weave/secret-key'

export WEAVE_SECRET_KEY_HOST_FILE=/etc/weave/secret-key
docker compose -f docker-compose.platform.yml -f deploy/compose/secret-key-file.yml up -d
```

[secret-key-file.yml](../../deploy/compose/secret-key-file.yml) 把文件只读挂到 `/run/weave/secret-key`，设置 `WEAVE_SECRET_KEY_FILE`，并清空 `WEAVE_SECRET_KEY`，同样不会自动创建缺失的宿主文件。文件内容是 64 位十六进制或 32 字节的 base64，读取方式和环境变量完全相同。

- 从环境变量换成文件时，文件里必须放原来的同一个密钥；换了密钥，已加密保存的模型供应方凭据就无法解密。
- 密钥文件只给运行服务的用户读取（root 运行时用 0400 即可），并纳入私有备份。

## 组合方式

```bash
# 只运行 Weave 服务
docker compose -f docker-compose.platform.yml up -d
# 加组织连接
docker compose -f docker-compose.platform.yml -f deploy/compose/organization-connection.yml up -d
# 加密钥文件
docker compose -f docker-compose.platform.yml -f deploy/compose/secret-key-file.yml up -d
# 两者都加
docker compose -f docker-compose.platform.yml -f deploy/compose/organization-connection.yml -f deploy/compose/secret-key-file.yml up -d
```

## 上线前检查

用同一组 Compose 文件运行检查，它在容器里读取与服务完全相同的环境和挂载：

```bash
docker compose -f docker-compose.platform.yml -f deploy/compose/organization-connection.yml \
  run --rm --no-deps weave config-check
```

每项输出 `ok`、`off`（没有启用，不需要文件）或 `fail`，有任何 `fail` 时退出码为 1。输出不包含任何密钥或文件内容，能识别：

- 缺少登录密钥、JWT 密钥或数据库地址；
- 凭据密钥同时设了两处、都没设、文件缺失或格式不对；
- 组织连接文件不存在、挂载成了目录、不可读、超过大小、字段或地址不合规。

检查同时列出停机排空时间与慢运行告警阈值；各层时间上限的含义见 [模型调用与运行的时间预算](模型调用与运行的时间预算.md)。

检查通过只说明配置和文件可用，不代表登录、Forge 身份交换或员工设备导入已经验收；这些仍按正常的登录和导入流程验证。
