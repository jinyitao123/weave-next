# Weave 执行核心产品基线 v1

> 日期：2026-08-20  
> 状态：用户已裁决，现行产品 authority  
> 适用范围：产品取舍、代码深审、后续计划与删除判断

## 1. 裁决

Weave 下一阶段不再以完整 Agent 治理平台为建设目标，而收缩为一套能够创建、发布和运行真实业务团队的执行系统。

产品只保留三块一等能力：

1. **多运行时**：把工作可靠地交给实际 Runtime 和执行引擎，支持领取、执行、失败识别、恢复与交付。
2. **元团队**：只在创建或升级业务团队时出现，负责设计团队、生成可执行定义、验证候选版本并发布。
3. **业务团队**：使用已经验证和发布的冻结版本长期直接接单，通过多个成员和 Runtime 产生真实业务结果。

前端、逐动作人工停车、集中复核中心、完整问责产品、记忆与其他平台能力均不再自动获得主线优先级。它们可以保留为薄基础设施、冻结、隔离或删除，具体由代码勘查和主链依赖证据裁决。

## 2. 一句话产品定义

**Weave 用元团队创建和升级业务团队，再让已发布的业务团队通过多个 Runtime 持续完成真实工作。**

这里的“真实工作”包括两类结果：

- 可检查和复用的文件、代码、报告、数据与素材；
- 团队已获静态授权的外部动作，例如发布、发送、改库和业务系统写入。

能生成聊天回复不算完成。业务结果必须落到可读取交付物或可由外部事实验证的系统状态。

## 3. 双路径产品模型

### 3.1 低频创建与升级路径

```text
业务目标
  -> 元团队设计团队与工作流
  -> 创建候选团队版本
  -> 在冻结场景中验证
  -> 发布不可变业务团队版本
```

元团队是编译式控制面，不是每次任务的在线中间层。业务团队发布后，普通任务不得因为需要“再理解一次组织”而重新进入元团队。

### 3.2 高频业务执行路径

```text
任务输入
  -> 选择已发布业务团队版本
  -> 按冻结工作流分解和派发
  -> Runtime 执行
  -> 团队收敛结果
  -> 交付文件或外部业务状态
```

日常执行的正确性、可靠性、耗时和成本优先于建队过程的丰富度，也优先于控制台呈现完整度。

## 4. 三块核心能力的最小可运行边界

### 4.1 多运行时

多运行时只要求证明：

- 至少两个独立 Runtime 可以注册并真实领取业务团队任务；
- Runtime 使用的 engine 和实际执行结果可辨认，不由服务端冒充成功；
- 同一个已发布业务团队可以在不同 Runtime 上完成同一业务场景。

“多节点”和“多引擎”分开验收。两个 Codex Runtime 证明多节点；Codex、Claude 或其他 CLI 在相同团队合同下可替换，才证明多引擎。

### 4.2 元团队

元团队只要求证明：

- 明确的 build 或 upgrade 请求可以生成并发布一个机器可执行的业务团队版本；
- 已发布团队的普通任务不调用元团队；
- 升级产生新版本，不改写旧版本。

### 4.3 业务团队

业务团队只要求证明：

- 一个已发布版本可以反复直接接收任务；
- Runtime 实际执行团队工作流；
- 结果能够通过 RealReplicaBench 的原始 verifier 或等价业务事实检查。

上述边界是验收结果，不是新对象、新状态机或新页面的设计要求。现有实现能满足时不得重写；现有业务场景没有暴露的可靠性问题不得提前产品化。

## 5. 治理降级后的最小边界

逐个写动作人工停车不再是默认产品主链。团队版本在发布时冻结工具范围、凭据范围和 Runtime Policy，发布后的正常执行在这套静态授权内自动完成。

以下信息仍属于执行所必需的薄事实层，不因放弃重问责产品而删除：

- Work Request、TeamRun 和执行单元的稳定身份；
- 团队版本、工作流版本和 Runtime Assignment；
- 当前状态、终态、失败类别和重试关系；
- 输入哈希、交付物引用和外部工具回执；
- 防止跨租户、跨团队版本和迟到结果覆盖的必要约束。

它们用于回答“任务是否真的执行、由谁执行、结果在哪里、失败能否恢复”，不扩建为独立问责产品或复杂复核界面。

## 6. CLI 优先

当前阶段不要求完整前端。只要 CLI 或最小 API 能闭合主链，即可作为正式产品入口。

目标操作语义为：

```text
weave team build
weave team publish
weave run --team <team@version> --input <task> --output <directory>
```

命令名称和参数由后续实现合同确定；本基线只裁决操作边界。CLI 不得绕过团队版本、Runtime 调度或结果持久化，不能退化成直接启动一个本地 Agent 进程。

## 7. RealReplicaBench 证据与边界

RealReplicaBench 已提供以下正向证据：

- 外接 Codex Runtime 可以真实执行长链任务；
- 固定业务团队可以形成分工、执行、复核和交付；
- 元团队可以创建成员、团队和声明式工作流并发起候选运行；
- Gmail、Calendar 和 Google Docs 等 Mock MCP 状态发生过真实变化；
- 部分干净运行由原始 verifier 判定为满分。

这些证据足以结束“架构是否可能运行”的讨论，但尚不足以证明产品已稳定。当前剩余风险集中在：

- Runtime 断流、离线、配额和迁移恢复；
- 团队成员的输入与证据合同；
- reviewer 独立复核有效性；
- 元团队生成团队的业务质量稳定性；
- 交付物从 Runtime 工作区进入用户可取得位置的合同；
- 多节点和多引擎的重复验证。

后续使用 RealReplicaBench 时，它是外部业务裁判和回归工具，不是新的产品规格来源。

## 8. 下一阶段执行顺序

### M0：复现现有黄金路径

- 选择一个已经通过的 RealReplicaBench 场景；
- 不新增 API、CLI、数据表或通用协议；
- 使用现有入口、现有冻结团队和现有 Runtime 再运行一次；
- 记录真实调用路径、产出位置和唯一实际阻塞。

### M1：按真实可达性删减

- 保留 M0 实际经过的业务团队执行代码；
- 保留元团队 build/upgrade/publish 实际经过的代码；
- 其余入口先停止写入，再解除依赖，最后物理删除；
- 每次删减后只用对应业务场景判断是否破坏目标能力。

### M2：多 Runtime

- 使用第二个现有 Runtime 执行 M0 的同一团队和场景；
- 只有真实运行暴露阻塞时才修改调度代码。

### M3：元团队升级闭环

- 元团队只针对已知失败证据创建新团队版本；
- 新版本通过相同业务场景后发布；
- 旧版本、历史 Run 和交付物保持可读取；
- 新任务可以直接选择新版本执行。

## 9. 当前非目标

在 M1 至 M4 完成前，下列事项不进入主线建设：

- 新一轮前端视觉或信息架构重做；
- 集中人工停车、复核中心和通用问责台扩建；
- 为展示内部状态而增加新的产品页面；
- 与三块核心无直接关系的 Agent 配置丰富化；
- 把 benchmark、客户或行业知识写入 `internal/`；
- 为未来可能需要的治理场景提前增加状态机。

现有相关代码先冻结。是否删除，必须以执行主链依赖图和回归证据为依据。
