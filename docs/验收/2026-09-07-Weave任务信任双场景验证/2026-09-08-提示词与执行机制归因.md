# 提示词与执行机制归因

核验日期：2026-09-08。范围为电商首轮 `run-e659f172-6876-521c-a6d8-50642aca9c18` 与日冕历史最后一轮。此记录不代表阶段一到阶段三全部完成。

## 结论

两类问题同时存在。已发布成员的角色描述偏通用，可以补强工具使用和判断规则；但节点指令已经包含任务范围、禁止操作、独立复核和副作用检查。当前证据不支持把失败统一归因于“所有系统提示词不行”，也不支持重写整个架构。优先修复完成判定、预算耗尽语义及实际权限约束，再用同一隔离任务做提示词对照。

## 已核实事实

1. 电商执行员第一次创建日历事件时传入对象形式的 start/end，Mock 接受后存为 `[object Object]`；随后把原事件 id 传给 createEvent，实际生成第二条记录。复核查询确认畸变事件仍存在。模型的工具使用出错；外部 Mock 的宽松校验也参与了结果，不能把 Mock 行为全部算作 Weave 代码缺陷。
2. 复核员明确报告草稿为 UNVERIFIABLE、存在残留副作用，却把总体结论写为“PASS（限定范围）”。发布配置要求检查这些项目，但没有明确“任一必需项无法核实或存在未处理副作用时总体不得 PASS”的聚合规则。提示词应补强这条规则；平台也需要独立的完成判据，不能把自然语言标题作为业务通过证明。
3. 本次发布工作流是 execute → verify → deliver，verify 正常返回文本后直接交付，没有根据结构化验收结论分支。运行被记录为 succeeded。代码执行正常结束与业务验收通过在这条链路中没有形成充分的区分。
4. 复核员公开列出的工具仍包含 Gmail 写入和发送工具，只读靠提示词约束。此次记录没有显示它实际写入，但配置并未建立强制只读边界。给成员增加“禁止写入”文字不能证明权限隔离完成。
5. 日冕最后一轮的实际模型请求明确包含工具预算耗尽提示，记录为 20 rounds used，且请求没有工具。Weave 编译器固定配置 MaxIterations 为 20；当前依赖 Loom v0.8.1 在预算耗尽后要求模型总结，最后返回 nil error。该证据解释了这一次为何停止，不能外推为此前八轮所有故障的共同原因。
6. 日冕的 22 项模型测试已由宿主独立复跑通过，但图纸、应用、评审、完整验收导出仍缺失。测试通过不能证明全部交付完成。

## 修复与验证顺序

先落实任务结束语义。必需交付尚未齐全、必需事实无法核实、或仍有未处理副作用，应分别返回未完成、待核实或验收失败，并保留证据与接续入口。预算耗尽应成为可辨识的停止原因，不能仅因为总结调用成功就被当作业务完成。

再落实执行约束。复核身份应具有实际只读能力；写入应基于已发现的工具契约，回读核验结果，禁止猜测 create 等于 update。必须保留原始基准工具与判分契约；若加入平台拦截器，应另标实验条件，不能冒称未经改变的基准运行。

同步补强成员指令。要求先核对工具参数，区分创建、更新与重试；任一必需项缺证据时不得总体 PASS；完整报告异常状态及额外副作用。对比实际传入 Runtime 的最终提示内容，不能只检查团队配置摘要。

最后执行单变量对照。保留本轮原始样本，分别比较仅改提示词、仅改平台机制、两者同时修改后的新隔离样本；固定模型、输入、工具及判分规则，统计业务通过、额外写入、未完成误报成功和接续情况。当前尚未做该对照，因此不报告各层责任百分比或修复成功率。
