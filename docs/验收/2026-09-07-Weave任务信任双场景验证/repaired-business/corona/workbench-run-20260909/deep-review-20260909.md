# 日冕 v4 复验深度审视记录

日期：2026-09-09

对象：Workbench 任务“继续日冕速度对比并整理结果”

运行：`run-54e09b98-9f24-547e-afc7-e0937ada51e3`

团队：`082ed3e9-219c-41c0-9ed8-c7f5c0d94467`（日冕先期论证并行工程团队 v4）

## 当前结论

本次出现“打转”的主因不是单个模型失效，而是恢复型任务被送入了完整研究生成流程。流程没有把 v3 的既有产物作为冻结输入传给节点，只能依靠自然语言、文件系统搜索和事后纠偏恢复上下文。结果是负责人重新生成控制包，数字工程节点重新实现模型、图纸和应用，独立总装员也要重新搜索验收规则。

这证明当前系统能执行复杂并行任务，但还没有形成可信的“继承指定产物，只重跑受影响节点”能力。日冕 v4 不能作为无人工干预恢复能力的通过证据。

## 已确认问题

### 1. 恢复任务与工作流语义不匹配

- **现象**：v4 仍使用 `research_synthesis`。负责人固定先运行，随后六个专业节点并行，最后独立总装。
- **证据**：负责人从空工作目录开始搜索历史材料，重新生成了 15 个基线、变更、接口和调度产物；数字工程节点随后从头创建模型、页面、图纸和验证脚本。
- **影响**：用户要求“保留既有成果，只修受影响部分”，实际执行却接近完整重建。结果可能通过验收，但不能证明恢复与增量复验能力。
- **当前处置**：未停止原运行，因为发现问题时负责人已完成、并行节点已真实启动。后续不再把完整研究流程作为恢复验证入口。

### 2. 既有产物没有作为正式输入绑定

- **现象**：新节点只收到任务文字和上游文本，未收到 v3 `model/`、`drawings/`、`app/` 的冻结引用、内容摘要或校验值。
- **证据**：数字工程节点的初始工作目录只有 `inputs/`，之后重新实现 YAML 解析、计算模型、页面和图纸；独立总装员的输入中也没有 `acceptance.json`，先进行了多轮文件系统搜索，最终才找到 `<MAINTAINER_LOCAL_PATH>`。
- **影响**：节点无法证明自己复用了哪一版成果，也无法区分“修改旧成果”和“另写一套能过检查的成果”。这也是当前最主要的过拟合风险。
- **所需修复**：派发时绑定前序交付物引用、不可变摘要、目标目录和允许修改范围；运行快照必须记录这些引用，成员输入应直接包含或挂载相应产物。

### 3. 成员级纠偏被扩大为整组回退

- **现象**：只对“数字产品与工程图开发员”提交纠偏，要求复用 v3 数字成果并只修页面计算、三情景切换和 JSON 导出。
- **证据**：纠偏 `e114cbbd-8722-40e5-9eb8-cbff9c18cc8f` 在 `join` 安全点变为 `ready`，规划的 `restart_node_id` 是 `parallel`；受影响节点包含六个并行成员、`join`、`finalizer` 和 `deliver`，只保留负责人。
- **影响**：如果确认，将重复执行已完成的六个专业节点，放大时间和成本，违背最小重算原则。
- **当前处置**：已选择 `discard`，保留 7 个已完成成员结果，只继续独立总装。纠偏状态已变为 `discarded`。
- **所需修复**：纠偏规划应能以单个成员为重算边界，并基于实际数据依赖计算下游影响；无依赖的兄弟节点必须保留。

### 4. 纠偏不能及时止损

- **现象**：纠偏请求登记后，数字工程节点继续创建新的 YAML 解析器、模型、页面、图纸和验证脚本，直到节点完成才进入确认阶段。
- **影响**：平台能保证边界安全，却缺少“请求后尽快暂停当前节点并保留可用检查点”的能力。用户会看到系统明知偏航仍持续消耗。
- **所需修复**：为可中断节点增加受控取消、最近稳定检查点和中断回执；界面应显示预计冻结点与仍在执行的动作。

### 5. Workbench 的纠偏决定没有形成可见回执

- **现象**：在当前 13083 实例中点击“放弃纠偏并继续”后，页面仍显示“等待确认修改范围”，后端纠偏状态在约 30 秒内仍为 `ready`。
- **处置**：通过同一后端确认接口提交 `discard` 后立即返回排队回执，运行进入独立总装。
- **边界**：这是本次实例的可复现观察，尚未通过独立 UI 回归确定是前端调度、会话刷新还是操作绑定问题。
- **所需修复**：按钮操作必须显示客户端请求、后端受理和最终状态三段回执；失败时给出可重试错误，不能静默停留。

### 6. 并行等待状态容易被误读为停滞

- **现象**：父运行在等待并行成员时后端状态为 `parked`、`wait_kind=fanout`，Workbench 主区域显示“等待中”；第二运行环境的部分公开活动缺失。
- **证据**：同时可以从成员任务和本机进程确认第二运行环境正在执行成本风险、推进能源、需求工程和最终总装节点。
- **影响**：真实并行工作被呈现成停滞，用户难以判断是否需要介入。
- **所需修复**：父运行显示“并行执行中”，并列出活动成员、运行环境、最近进展时间和未记录事件提示；`parked` 只作为内部等待语义。

### 7. 测试数量没有完整继承

- **现象**：v3 模型曾有 34 项测试；v4 数字节点重建后的模型报告 26 项单测，另有 18 项综合检查。
- **影响**：即使 `acceptance.json` 的 11 个硬门槛最终通过，也不能声称测试覆盖度完整继承。测试数量本身不等于质量，但减少的 8 项需要逐项映射或说明。
- **所需修复**：恢复任务应携带旧测试清单和用例标识，最终报告给出保留、删除、替代和新增的逐项映射。

### 8. 仍存在场景过拟合风险

- **现象**：生产代码未发现电商或日冕路径硬编码，但验收层使用了专门的电商 fixture、日冕团队 YAML、材料路径和验收脚本；当前只有两个样本，且日冕运行经历了人工恢复团队、补充材料路径、纠偏与手动放弃纠偏。
- **影响**：可以证明通用机制在两个受控样本中工作，不能证明对未见任务、冷启动团队和无人工修复场景同样成立。
- **所需验证**：增加第三个保留样本，使用未修改的任务材料和团队定义，禁止人工补路径、恢复团队、修改验收脚本或手动修复交付；失败即记录真实失败，不为样本调整生产机制。

### 9. 独立验收脚本存在启动目录依赖

- **现象**：独立总装员首次运行跨产物扫描时曾把扫描根目录错误拼成不存在的 `outputs/outputs`；后续清理脚本后从 `outputs/verification` 再次执行，又因核心文件路径相对于当前启动目录解析而误报缺文件。
- **影响**：同一验收脚本从不同目录运行会得到不同结果，可能形成假通过或假失败，削弱验收证据的可重复性。
- **当前处置**：总装员识别到这是检查器路径缺陷，正在改为以脚本文件位置确定验收根目录，并在修改后重新运行全套检查。
- **所需修复**：所有验收入口必须与当前工作目录无关；验收记录应保存入口路径、实际解析根目录、命令退出码和机器可读结果，并增加从至少两个不同目录启动的复跑检查。

### 10. 综合检查报告的计数语义不准确

- **现象**：`run_checks` 实际执行的是 8 个数值字段乘 3 个速度情景，共 24 次 Python 与 JavaScript 对照；输出字符串却写成名义上的 `36 checked`。独立总装员最初据此在 `FINAL_ACCEPTANCE.md` 中写出不成立的“24 字段乘 3 情景、36 项”说明。
- **影响**：退出码仍可为零，但报告中的检查数量无法从实际循环复算，容易把绿色结论扩大为不存在的覆盖范围。
- **当前处置**：独立总装员已读取实现并把最终说明改为 8 个字段乘 3 个情景、24 次对照，最差偏差为 0；旧的 36 项措辞已清理。
- **所需修复**：检查数量必须由真实执行记录动态计算，机器结果同时输出用例标识和实际迭代次数，禁止维护独立的名义分母。

### 11. Workbench 交付合同未承载用户明确要求

- **现象**：运行完成后平台交付核验为 `unknown`，检查结果只有 `_output=passed`，而 `_coverage=requirements_not_explicit`、`_limitation:0=unsupported_requirement`、`_external_effects=external_effects_scope_unverified`。
- **证据**：用户在 Workbench 明确要求三速度、两个运行环境、真实页面修复、JSON 导出、独立总装和 11 项门槛；本次运行的交付合同摘要存在，但平台读回无法将这些要求映射为可核验条目。
- **影响**：团队内容层可以给出 11 项 PASS，Workbench 仍无法判定是否满足用户交付范围，执行成功与业务交付成功再次分离。
- **所需修复**：派发前把用户确认的范围结构化为交付合同，并保存在运行快照；至少包含最终目录、页面行为、导出文件、运行环境参与、独立验收、11 项门槛和外部影响范围。交付核验必须逐条引用证据，不得退化为仅检查输出类型。
- **2026-09-10 机制修复**：已在代码中增加 `team-template/v1 delivery.contract → TeamBlueprintV1 → 编译摘要 → 发布 GraphDefinition → 派发冻结合同` 的可信默认链路。普通自然语言派发会继承本次发布合同，精确用户输入合同仍优先；纯本地成果可用 `external_effects=none` 得到明确判定。严格解析、模板编译、机器图和真实 PostgreSQL 派发回归通过。
- **尚未闭环**：日冕 v4 是修复前运行，不能事后改写其合同或核验结论。新机制尚未部署并用保留样本完成冷启动业务验收，用户采纳仍缺失，因此本问题当前为“代码修复、业务复验待执行”。

### 12. 最终验收扩大了未被本轮证明的过程结论

- **现象**：`FINAL_ACCEPTANCE.md` 的过程表把“纠偏形成影响计划并在安全点恢复”和“失败/重启不丢交付物”写成达成。
- **反证**：本轮唯一纠偏在安全点形成影响计划后被 `discard`，没有应用或恢复；本轮也没有发生可用于验证失败后恢复和产物保留的成员失败。纠偏规划、放弃纠偏和正常完成不能证明恢复语义。
- **影响**：内容层 11 项通过被错误扩张为过程恢复能力通过，掩盖了本轮最关键的恢复入口缺口。
- **当前判定**：保留“两个运行环境真实参与”和“独立总装复算”两项过程证据；把纠偏恢复、失败恢复和增量继承标为未验证。

### 13. 自引用扫描导致最终计数再次漂移

- **现象**：`FINAL_ACCEPTANCE.md` 写“全包 41 个文本产物含真值标签”，外部在最终目录重跑同一脚本得到 42 个。新增的最终验收文档本身也带真值标签，因此被扫描计入。
- **影响**：总装员在写最终文档前反复校正计数，但最终文档加入扫描集合后又改变了被测对象。门槛的布尔结论未受影响，证据数字仍不自洽。
- **所需修复**：冻结待验收产物清单后再运行检查，最终报告不应改变被验收集合；若报告必须在集合内，计数器应明确排除自身或在写入后自动重跑并更新。

### 14. 自然团队名无法解析为派发身份

- **现象**：第三保留样本建立了 active 团队“服务事件复核团队”，数据库中的真实 ID 为 `5cbf562e-20d1-478a-92c2-a09011ea37fb`。Workbench 首次调用把展示名直接作为 `weave_dispatch.team_id`，服务端返回 `team_not_found`。
- **直接根因**：13083 实例的 `WEAVE_COMMAND=../bin/weave` 解析到仓库中不存在的文件，`weave mcp serve` 子进程没有运行。代码中已有的 `team_list` 因而没有进入模型工具面，另行注册的本地 `weave_dispatch` 却仍可用，形成部分连接。
- **证据**：[保留样本首轮记录](../../../held-out/incident-review/first-run-evidence.json)确认首个工具输入、错误、页面终态、缺失的 MCP 进程及数据库中的 TeamRun 数量 0。错误后模型搜索工作目录、源码、环境变量、本机进程和宽泛文件路径。
- **重复信号**：日冕 v3 自然派发也曾因团队名不能解析而失败，之后由操作方补入精确 UUID 才继续。本次冻结样本禁止人工补 UUID，因此真实保留了首次失败。
- **影响**：自然语言冷启动在运行建立前中断，已发布合同无法进入运行快照。此前成功样本依赖有效 MCP 配置或人工 UUID，因而高估了错误配置下的连接完整性。
- **修复**：Workbench `564bdc63` 启动时校验显式 MCP 二进制路径；路径缺失会直接失败。`weave_dispatch` 遇到精确 ID 不匹配时，还会在 workspace 的 active 团队清单内解析展示名或机器名，并对重名显式失败。这样不会通过宿主机搜索猜测身份。

### 15. 运行环境健康状态没有覆盖 Provider 凭据可执行性

- **现象**：修复后冻结样本通过 MCP 发现“客服队列复核团队”，以展示名派发后成功创建 `run-7cb5a00a-973a-578b-be4c-a5857254409a`。运行继承发布工作流 v1 和合同摘要 `a74e674e...`，但首位成员在 2.017 秒后以 `runtime_credentials_missing: ONEAPI_API_KEY` 失败，0/4 阶段完成。
- **直接根因**：团队构建把四名成员都绑定到 `Mac Local Runtime` 的 `engine=codex`、`auth_mode=provider` 组合；该运行进程没有所需 Provider 凭据，但运行环境目录在失败后仍报告 `health_status=healthy`。
- **影响**：团队可发布、运行环境可显示健康、自然派发和合同冻结也都能通过，真正执行到首个成员时才发现组合不可用。当前就绪信号不能回答“这个已选成员执行器此刻能否启动”。
- **证据**：[修复后保留样本首轮记录](../../../held-out/support-queue/first-run-evidence.json)保存了展示名派发回执、稳定团队 ID、运行转换、成员失败、合同摘要、空交付和页面三态。
- **所需修复**：把运行环境认证可用性纳入能力发布和团队构建准入。需要 Provider 凭据的 Codex 组合在凭据不存在时不得成为可用默认项；若认证状态只能在执行节点判定，发布或派发前必须返回明确不可执行，而不能继续显示为健康。

## 本轮继续验收的判定规则

独立总装员必须在第二个运行环境内完成唯一交付目录，并独立复跑 `acceptance.json` 的 11 项硬门槛。任何未运行或失败项均判失败。即使 11 项全部通过，本次结论仍限定为“本次完整生成流程形成了可验收结果”，不能扩张为“恢复型增量执行已通过”或“已排除过拟合”。

最终还需单独核对：

1. 页面能在真实浏览器中打开，三速度情景切换会改变派生结果。
2. JSON 导出由真实用户交互触发，文件可解析，情景和值与页面一致。
3. 两个运行环境均有真实成员任务和产物证据。
4. `FINAL_ACCEPTANCE.md` 由独立总装员生成，且与机器检查结果一致。
5. Workbench 交付核验完成后，再由用户给出采用或退回评价。

### 16. `outputs/` 合同路径与收集器身份不一致

- **现象**：第三个冻结样本的四名成员均在 Claude OAuth 运行环境完成，TeamRun 为 `succeeded`。最终成员实际写入 `outputs/inventory-batch-review.md`，收集候选却按保留目录的相对身份记录为 `inventory-batch-review.md`；发布合同保留前者，核验器逐字匹配后报告 `required_file_missing`。
- **伴随结果**：文件中的三项算术和两个业务判断经独立复算正确，但没有逐字包含冻结合同要求的五个英文标记；即使路径匹配，内容条件仍应失败。
- **影响**：模型正确写入规范物理目录也会因路径命名空间不同被判缺失；同时语义正确不能替代逐字合同遵从。Workbench 正确显示执行完成、核验未通过和用户尚未评价，没有制造业务成功。
