# 电商第二次任务复用审计

本样本为 **跨任务输入失败，业务交付未完成**。同一已发布团队和工作流成功复用，但新发票任务派发过程中，前两次运行携带了旧 VBR-52 输入，第三次才是 INV-440 正文；完整性事故发现后三次运行全部取消。不存在可验收的第二次成功交付。

## 身份与结果

目标任务为同一 benchmark 提交下 `api-gmail-invoice-hold-mcp`，独立 fixture 为 `trust-stage2-invoice-hold-20260908-remote002`。新任务输入文件及哈希见 [输入清单](input-manifest.json)。同类任务共享七个评分组和原子检查名，但第二次要求两封草稿，首次只要求一封，因此只能比较复用和输入隔离、评分类别，不能把耗时或 token 当成等工作量比较。

三次运行及其独立 client request ID、输入判定、后端终态均保留在 [派发记录](dispatch.json) 和原始 [事故记录](dispatch-incident.json)。前端工具参数本身已经包含旧任务。这证明模型选择了错误旧输入，派发路径接受了它；不能推断成后端将正确新输入替换成旧输入。一次正确正文派发也不能消除前两次违规。冻结输入应通过当前任务材料身份绑定，不能依赖前端模型每次重写一遍正文。

取消后的原 verifier 为 4/7，基线为 2/7。标签和已读项从不满足变为满足，星标、两封草稿和日历仍不满足；无邮件发送检查通过。此结果说明 fixture 已发生部分业务变化，未证明完整交付。现有成员工具轨迹不完整，不能把共享 fixture 变化精确归属到这三次中的某一次运行。见 [核验聚合](verification.json)、[取消后原 verifier](after-cancellation-verification.json)。
