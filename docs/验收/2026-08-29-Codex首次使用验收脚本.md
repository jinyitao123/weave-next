# Codex 首次使用验收脚本

> 日期 2026-08-29  
> 用途 验证真实用户能否通过 Weave MCP 完成团队匹配、派发、人工处理与交付  
> 执行端 Codex 桌面端

## 执行约定

每个场景都从一个新的 Codex 任务开始。测试人员只发送场景中的用户提示，不补充工具调用步骤。Codex 可以解释自己的团队选择，但不能要求用户理解内部评测、构建运行或发布机制。

验收人员记录实际工具调用、最终结果和失败分类。失败只归入匹配错误、能力缺失、执行失败或交付失败。

## 场景一 已有团队直接完成工作

### 前置条件

Weave 中存在一支目标、职责和交付标准都能覆盖任务的可用团队，并且默认工作流已经发布。

### 用户提示

```text
使用 Weave 团队完成下面的任务。

为 Weave 写一份面向首次使用者的产品介绍，说明它解决什么问题、四步主链如何工作，以及为什么用户不需要理解内部评测机制。

先判断现有团队是否明确匹配。只有匹配成立时才派发。遇到人工确认时再询问我。完成后返回本次运行对应的最终交付物。
```

### 通过条件

- Codex 先读取团队列表，再说明所选团队为何匹配。
- Codex 使用默认工作流派发，没有静默使用 `free_collab`。
- Codex 能处理等待、运行中和人工暂停状态。
- Codex 按本次运行找到最终交付物并返回内容。
- 回复没有要求用户理解评测、候选运行或发布门禁。

## 场景二 没有合适团队时讨论并建队

### 前置条件

Weave 中没有能同时完成访谈材料归纳、实施方案设计和风险审查的团队。

### 用户提示

```text
我需要用 Weave 完成一项新的客户现场工作。

请根据我随后提供的访谈记录，整理业务问题，形成可执行的实施方案，并单独列出证据不足和高风险判断。

先检查现有团队。如果没有明确匹配的团队，请诚实说明缺口，并在当前对话中和我讨论一支新团队应该怎样设计。在我明确确认以前不要创建团队，也不要改用相近团队凑合执行。
```

### 通过条件

- Codex 读取团队列表，没有合适团队时明确说明缺口。
- Codex 没有静默派发，也没有默认进入 `free_collab`。
- 团队讨论覆盖目标、成员职责、默认工作流和交付标准。
- 用户确认前没有调用 `team_create`。
- 用户确认后一次提交团队 YAML 和声明式工作流。
- 创建结果为 `ready`，无需评测、人工授权或手工发布。
- 新团队随后可以通过默认工作流接收一项小型验证任务。

## 场景三 复杂 FDE 项目使用多支团队

### 前置条件

准备一项真实 FDE 工作。任务至少包含三个职责边界清楚、可以分别验收的工作包。Weave 中可以有多支专业团队，也允许部分工作包没有匹配团队。

### 用户提示

```text
使用 Weave 协助我推进这项 FDE 工作。

先理解目标、材料和限制，把工作拆成可以独立验收的工作包。随后分别检查每个工作包是否有明确匹配的团队。匹配成立的部分可以使用默认工作流派发。没有匹配的部分请说明能力缺口，等我确认团队设计后再创建。

所有派发归入同一个项目。遇到人工节点时再询问我。最后读取各次运行对应的交付物，处理它们之间的依赖和冲突，形成一份可以继续执行的综合结果。
```

### 通过条件

- Codex 根据真实职责拆分工作，没有为了套用现有团队而改变任务含义。
- 每个工作包都单独完成团队匹配。
- 多个派发共享同一个 `project_id`。
- 每支团队只承担其职责范围内的工作。
- 缺失团队按场景二的方式处理。
- Codex 能把人工节点定位到具体运行和问题。
- 最终汇总能追溯到各团队交付物，并明确未解决的依赖与冲突。
- 整个过程没有创建项目监督 agent 或第二套编排状态机。

## 记录模板

```text
场景编号
用户原始提示
Codex 选择或拒绝的团队
派发运行标识
人工任务标识
最终交付物标识
是否通过
失败分类
复现步骤
最小修复建议
```

## 停止规则

同一种失败稳定复现两次后再进入产品修改。修改只覆盖已经复现的缺口，完成后重跑原场景和前面的通过场景。一次偶发模型表达问题先记录，不据此新增系统角色或持久化状态。
