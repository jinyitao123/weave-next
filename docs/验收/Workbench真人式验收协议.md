# Workbench 真人式验收协议

本协议规定产品验收如何模拟真实使用。它适用于桌面 Workbench、团队创建、团队运行、能力调用、恢复、交付和身份隔离验收。

## 操作原则

先启动当前桌面 Workbench，通过桌面窗口中的正常产品路径完成操作。内置浏览器或真实外部浏览器只用于复现同一套前端页面和辅助取证，不能替代桌面壳、桌面会话、连接管理与本地能力的验收。API、数据库、日志和代码只用于解释界面观察到的结果，不能替代用户路径。

每个场景至少经历四种角色：用户负责完成目标，任务负责人负责判断团队是否按目标推进，成果使用者负责判断产物是否可用，独立审计者负责重新核对事实、状态、来源和副作用。

测试者不替系统补全缺失信息，不把模型的自我描述当成事实，不因页面显示“完成”就接受交付。必须打开实际产物并核对关键内容。

## 场景选择

确定性任务直接执行，例如固定计算、既定格式转换、模板填写和文档明确的接口调用。外部访问、权限要求和副作用风险本身不触发方法研究。

只有具体未知阻止选择执行路径时，才安排有限的方法探索。探索必须说明未知问题、可用证据、允许的备选方法、尝试上限和停止条件。混合任务只探索未知分支，已知且独立的分支直接执行。

禁止联网、禁止研究、只能使用指定材料等用户约束优先。输入错误、权限不足、临时故障和方法失效分别处理，不能把所有失败都升级成探索。

## 最小测试轮次

先用理想输入跑通一次成功路径，再用新手输入、怀疑输入、缺字段输入、边界输入和中途变更输入各跑一次。对外部来源任务增加一次访问受限场景，对长任务增加一次中断恢复场景，对多用户场景使用两个独立身份交叉查看历史、团队和产物。

每轮记录操作、页面响应、实际状态、产物内容和判定。判定只能是通过、可疑或缺陷，并附可复现步骤。通过必须有观察证据，不能只写“模型表现正常”。

## 验收边界

执行完成、交付存在、交付可打开、交付通过核验是四个不同状态，页面必须分别呈现。团队角色名称和成员指令不能被当成顺序依赖、条件分支、循环或人工确认；这些行为只有在实际支持的工作流图中才算成立。

发现问题后按产品模块归档，至少标明复现输入、预期行为、实际行为、影响、证据和是否已经修复。修复后必须重新走一次桌面产品路径，并保留原问题的回归结果。

## 停止条件

如果页面状态、运行状态和交付内容互相矛盾，停止宣布验收通过。若无法确认来源、身份、权限、产物或副作用，报告“未确认”并说明缺口，不用推断填平缺口。
