# Workbench 目标驱动真人验收记录

日期：2026-09-13

证据范围：本文记录 Workbench 单场景观察。涉及其他智能体产品的比较属于产品感受，未做同任务竞品对照，不作为市场结论。

## 验收目标

用 Workbench 的正常页面路径创建并执行一个智能体团队，处理一批售后订单，生成可交给同事的中文报告。测试重点不是“模型会不会回答”，而是产品能不能像一个成熟工作台一样承接目标、组织团队、执行任务、呈现过程、交付成果，并把未完成和未核验说清楚。

## 场景材料

任务是整理 8 行售后订单。规则包括按品类汇总已确认实退金额、重复订单只计一次、实退为空或负数、状态未确认、申请金额与实退金额不一致均列为异常，异常不进入确认退款汇总。执行中追加要求：运费要按正常订单和异常订单单独列出，但退款汇总仍只统计实退金额。

独立核算基准：

- 正常计入订单：AF-1001、AF-1002 首次、AF-1003、AF-1006。
- 家电实退：120 + 50 + 45 = 215。
- 家居实退：80。
- 服饰实退：0。
- 已确认可计入实退总额：295。
- 异常订单：AF-1002 重复项、AF-1004 实退缺失、AF-1005 状态待确认且金额不一致、AF-1007 负数。
- 正常订单运费：10 + 0 + 5 + 0 = 15。
- 异常订单运费：0 + 12 + 8 + 0 = 20。

## 已观察到的产品行为

### 1. 运行失败没有被包装成成功

首次运行时，团队创建出来了，但执行在第一个成员阶段失败。页面把执行状态显示为“运行失败”，交付核验显示为“尚无法确认”，没有把“团队已创建”或“有运行记录”包装成业务完成。

这点是正向能力。成熟产品里，执行完成、成果存在、成果可打开、成果通过核验必须分开。Workbench 这次至少没有把基础设施失败说成业务成功。

问题在于失败原因偏运维语言：“runtime provider credential is missing”。用户能理解是“运行环境没准备好”，但不知道该由谁处理、下一步该点哪里。产品上应该给出更清楚的下一步，例如“当前运行环境缺少模型授权，请在运行环境设置中重新登录或配置模型服务”。

### 2. 本机配置修复后，团队能进入真实执行

修复本机 Codex 配置读取问题并重启运行环境后，同样材料的复验进入了真实执行：页面显示运行编号、运行时、团队默认流程和 4 个成员。成员从负责人到计算员、复核员、总装员逐步推进。

这说明 Workbench 不是只有“聊天解释”，它能把目标转成一个可观察的团队运行，并在页面上呈现每个成员的状态。

### 3. 过度确认打断了目标驱动

用户已经在原始任务中写明“已经确认创建、发布和本次执行”，模型仍停下来要求确认是使用现有团队还是另建团队。这个行为对生产化不理想。

合理的产品行为应该是：当用户已经明确授权执行，并且系统找到了高度匹配的现有团队，可以直接执行，同时在页面上说明“已复用现有团队”。只有当复用会改变用户目标、产生副作用或丢失约束时，才需要确认。

这类二次确认会让 Workbench 看起来像一个聊天机器人，而不是任务工作台。

### 4. 中途变更能进入后续执行范围

在确认消息里追加“运费按正常订单和异常订单单独列出，但退款汇总仍只统计实退金额”后，系统回执明确把这条要求纳入执行范围。

这是区别于普通一次性 agent 的产品点：任务不是发出去就黑盒运行，用户可以在执行前后通过同一对话纠偏或补充目标。后续还需要用最终报告验证它是否真的落实。

### 5. 团队拓扑清晰，但页面文案还有不一致

复验中可见团队是负责人、订单计算员、独立复核员、报告总装员。负责人完成后，计算员和复核员并行执行，最后进入报告总装阶段。这符合“负责人分工、成员并行、最终总装”的产品心智。

可疑点是，在成员并行执行时，页面顶部曾显示“执行状态：等待中”，但同屏又显示两个成员“正在执行”。对用户来说这会造成误解。更好的文案是“成员执行中，等待汇总”。

### 6. 小任务成本和等待感偏重

这批订单只有 8 行，但团队创建、确认、并行执行、最终总装持续数分钟。页面能展示阶段，但等待期间缺少更有用的进度解释，例如当前成员已经产出什么、是否正在等待模型、预计还剩多少。

这不是能力失败，但影响产品感。对于确定性小任务，产品应该有轻量路径，或者至少在创建团队前提示“复用团队会更快”“完整团队复核会更慢但更稳”。

### 7. 交付核验边界呈现正确

运行中页面持续显示“交付核验：等待核验”，并提示“成果可以打开不代表交付已通过核验”。这是少见但重要的产品特征：它没有把 agent 自己说 PASS 当作验收通过。

这点区别于市面上很多智能体产品。大多数产品只显示“任务完成”和一段输出，Workbench 把执行和交付核验分成了两个状态。后续关键是让核验结果可读、可追责，而不是只做状态标签。

### 8. 最终报告可打开，但业务核算未通过

最终报告可以在成果页直接展开，也提供下载入口。这说明“成果存在”和“成果可打开”通过。

但报告把 AF-1002 重复订单整单排除，导致家居品类 80 没有计入，最终合计写成 215。按用户原始规则，“同一订单号重复出现时只计入一次，并把重复项列为异常”，正确处理应是 AF-1002 首次记录计入一次，重复导出项列为异常。因此正确汇总应为：

- 家电：215。
- 家居：80。
- 服饰：0。
- 已确认可计入实退总额：295。

这是阻断级业务缺陷。报告虽然写了独立复核，但复核员和总装员一起接受了错误口径，把“重复项异常”扩大成“整单异常”。这说明团队里有复核角色，并不等于真的完成了语义纠偏。产品上需要把关键规则转成可核验的检查项，尤其是“重复项只排除重复记录，不排除首条有效记录”这类业务口径。

### 9. 平台核验边界是诚实的，但还不够业务化

页面显示“交付核验：尚无法确认”，核验记录中只有“输出类型符合交付要求”通过；覆盖、限制和外部影响仍显示无法确认。

这是正向特点：Workbench 没有因为 4/4 成员完成、报告可打开，就宣称交付通过。市面上很多智能体产品会在这里直接显示完成，然后把判断责任交给用户。Workbench 至少在产品层承认“有报告”和“报告可信”是两件事。

不足是核验还没有进入业务规则层。它能判断有没有输出，但没有自动发现金额汇总错误。下一步应把用户输入里的关键规则抽成核验清单，至少覆盖总额、分项金额、异常口径和禁止副作用。


### 10. 修订执行存在，但证据链丢失

在同一 Workbench 会话里要求团队修正 AF-1002 的重复订单口径后，页面生成了第二次运行记录，并产出《售后实退汇总报告-修订版》。运行历史能看到第 1 次和第 2 次均已完成，这说明 Workbench 具备“基于一次交付继续修订”的产品雏形，而不是只能重新开一个孤立任务。

修订版把核心金额改成了正确值：家电 215、家居 80、服饰 0、合计 295。

但修订版同时写明“本轮未获得原始订单”“不能表述为已从订单独立重算通过”，并把这些金额当成用户纠正后的目标值，而不是从原始 8 行订单重新核算得出。这是新的阻断点。原始订单明明在同一会话和同一任务链里出现过，修订执行却没有稳定继承原始材料、第一版报告和纠错要求之间的证据关系。

产品含义是：Workbench 已经有修订运行和历史记录，但还没有形成可靠的“交付版本链”。成熟形态应该让修订任务自动携带原始材料、上版成果、用户纠错点和本次复核结论，并在成果页清楚标出“已基于原始材料重新核算”或“只按用户指定结果改写，未完成复核”。

## 本轮结论

这轮验收没有通过业务交付验收。

通过的部分：

- Workbench 能通过普通页面承接目标、复用团队并执行真实团队流程。
- 执行过程能展示团队成员、阶段状态、运行编号、运行时、成果列表和两次运行历史。
- 运行失败、执行完成、成果存在、成果可打开、交付核验没有被混为一个状态。
- 中途补充的“运费单独列出”进入了任务范围。
- 纠错后可以触发第二次修订运行，并产出新的修订版成果。

未通过的部分：

- 原始任务已经授权执行，模型仍二次确认，打断目标驱动。
- 小样本任务耗时和 token 用量偏高，缺少面向用户的等待解释。
- 第一版最终报告业务口径错误，把重复订单整单排除，导致退款合计从正确的 295 写成 215。
- 第二版修订报告虽然改对了金额，但没有基于原始 8 行订单完成独立重算，而是把用户纠正值当成来源，证据链不完整。
- 平台核验没有捕获业务金额错误，也没有识别修订版证据链丢失，交付仍应标为不可采用。

## 当前未完成

下一步不是继续手工让模型改报告，而是需要补产品能力后再回归：

- 修订任务必须自动携带原始材料、上一版成果、用户纠错点和本次变更范围。
- 关键业务规则要转成可核验检查项，至少覆盖重复项口径、分类汇总、异常排除、运费拆分和总额一致性。
- 成果页要把“按用户指定值改写”和“基于原始材料重新核算通过”区分开。
- 对确定性小任务提供轻量执行路径，避免为了 8 行数据启动过重团队。

完成这些后，再用同一批材料做回归，合格标准是：修订版报告明确基于原始 8 行订单重算，金额为家电 215、家居 80、服饰 0、总额 295，异常清单保留 AF-1002 重复导出项，平台核验能说明关键规则均已覆盖。
