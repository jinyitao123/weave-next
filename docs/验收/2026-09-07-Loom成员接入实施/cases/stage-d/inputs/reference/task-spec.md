# 日冕计划复杂团队验收任务书

## 1. 验收目的

本任务同时验证两件事：

1. Weave 能否可靠组织一个长周期、多专业、多产物、可中途纠偏的复杂任务。
2. 团队成果能否作为日冕计划 Level-0 / Pre-Phase A 下一轮专家论证的直接输入。

本任务不声称形成施工级、制造级或飞行认证级设计。

## 2. 统一任务

基于仓库中的《日冕计划_任务背景与全程纪要_修订稿.md》和本目录的
`baseline.yaml`，比较以下三条可分离路线：

1. 激光光帆先锋探测器。
2. 无人文明档案载荷。
3. 载人星际飞行器。

形成统一、可计算、可追溯的先期论证基线，明确每条路线的任务终态、成立条件、
关键缺口、时间与能源数量级、成本研究方法、终止条件和下一阶段课题包。

## 3. 事实纪律

- 每条关键陈述必须标记为 `verified_fact`、`derived_result`、`assumption` 或 `unknown`。
- 不得把克级光帆探测器的可行性外推为大型无人载荷或载人飞船的可行性。
- 不得把自身动能下限表述为完整推进能源预算。
- 不得把概念图称为施工图、制造图或认证设计。
- 缺少退款时间、材料性能、尘埃通量、推进效率等直接证据时必须显式保留未知项。
- 关键数值必须有单位、公式、输入、输出和来源标识。

## 4. 必须交付的五类成果

### 4.1 统一计算模型

在 `outputs/model/` 中提供可运行源码、机器可读参数和测试，至少覆盖：

- 航行时间与光行时。
- 非相对论与相对论动能对照。
- 加速、减速、效率和质量情景。
- 人工重力半径与转速。
- 高速尘埃撞击能量。
- 目标方向夹角与速度增量转向上限。
- 先锋探测器到达和数据回传时间。
- 三路线敏感性比较。

### 4.2 概念工程图纸

在 `outputs/drawings/` 中至少提供：

- 三路线任务架构总图 SVG。
- 无人文明档案载荷功能分区图 SVG。
- 推进、能源、热控、通信与档案接口图 SVG。
- 一份可编辑的 OpenSCAD 或 DXF 概念模型。
- 图号、版本、单位、假设和参数追踪表。

### 4.3 数字决策应用

在 `outputs/app/` 中提供无需云服务即可本地运行的 Web 应用。应用必须：

- 比较 0.01c、0.03c、0.05c 三种巡航速度情景。
- 允许调整质量、推进效率、人工重力半径和转速。
- 实时显示航行时间、动能下限、等效能量、人造重力和尘埃撞击能量。
- 显示三路线的证据状态、成立条件、终止条件和主要未知项。
- 能打开概念图和导出当前情景 JSON。
- 所有计算与统一模型使用相同公式和参数。

### 4.4 正式论证包

在 `outputs/review/` 中提供：

- 任务需求基线。
- 三路线比较与建议。
- 假设、证据和未知项登记册。
- 技术成熟度、风险、成本研究与工作分解结构。
- 下一阶段研究课题包。
- 独立否定意见和未关闭问题。

### 4.5 验证包

在 `outputs/verification/` 中提供：

- 需求验证矩阵。
- 计算模型自动测试结果。
- 应用启动与核心交互测试结果。
- SVG/XML、OpenSCAD 或 DXF 可解析检查。
- 文档、模型、图纸和应用参数一致性检查。
- 不符合项、纠正记录和最终通过/不通过判断。

## 5. 受控变更

任务第一次并行分析开始后，由用户发起团队纠偏：

> 不再把 0.03c 作为唯一基线，统一改为 0.01c、0.03c、0.05c 三情景；所有模型、
> 图纸注记、应用、路线比较和验证矩阵都必须同步，旧的单情景结论不得残留。

Workbench 必须先展示安全点、影响范围和保留/重算范围；只有用户确认后才能继续。

## 6. 双层验收

### 6.1 Weave 过程验收

- 团队、阶段、成员、运行时、输入、输出和状态可见。
- 至少两个外部运行时参与真实执行，不以 Loom 代替专业成员。
- 并行成员能够独立完成工作并由最终汇总员整合。
- 纠偏形成可确认的影响计划，并在安全点恢复。
- 运行状态、成员状态和真实任务执行一致。
- 失败或重启后能够恢复，不丢失最终交付物。
- 最终交付物具有唯一当前版本，阶段产物与最终产物可区分。

### 6.2 专业成果验收

- `acceptance.json` 中全部硬性检查通过。
- 三个速度情景贯穿模型、应用、图纸注记和论证材料。
- 关键基线计算与独立复算容差一致。
- 应用能够启动并完成情景调整与导出。
- 图纸可打开、可编辑且明确标注概念级边界。
- 需求、证据、假设、未知项和验证结果可双向追踪。
- 独立否定员无未关闭的严重问题。
- 成果可以直接交给下一轮专家评审，无需重新整理结构。

## 7. 最终判定

只有过程验收和专业成果验收同时通过，才判定本轮复杂团队测试通过。某一层失败时必须
分别记录平台缺陷、团队设计缺陷、运行时缺陷、输入缺陷或专业成果缺陷，不得用综合表述
掩盖失败原因。
