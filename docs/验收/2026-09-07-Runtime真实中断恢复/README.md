本轮接替已作废的 Loom 采用价值对照，已完成真实成员链路的正常执行、协调端中断和成员进程中断，并保留一次计划外主机休眠。结论是继续使用现有 Runtime，先合入本轮确认的两处小修复；现有证据不足以启动新的 Loom 成员内部恢复接入。这里讨论的是扩大 Loom 的职责；系统已有对话图和非 CLI 成员图实际调用 Loom，不能理解为整个系统尚未使用 Loom。短时协调端重启能接回同一个成员进程，成员被杀后已有文件可以持久保留，但新阶段自动接续这些部分产物和长期离线恢复仍未实现。

## 修复与剩余边界

本轮代码只有 Ruby 依赖收集和原生进程中断分类两项修复。前者直接消除已完成源码依赖的遗失；后者保留正确失败原因，使现有阶段恢复逻辑能识别基础设施错误。本轮没有证明后者减少了模型重做，也没有实现私有 CLI 上下文续传、失败产物自动作为新尝试输入或长离线回执重新接收。

`make test` 在设置隔离 `TEST_DATABASE_URL` 后退出 0；`make depguard`、`make productguard`、`git diff --check` 均通过。Windows engine 分支交叉编译通过，仅代表编译兼容，不代表 Windows 运行验收。日志及退出状态位于 `evidence/final-checks/`。代码保留在当前工作区，未提交、未部署到业务服务；未改 Workbench，本轮不宣称其交互恢复验收通过。

下一步若要做自动续作，应限定为现有 Runtime 的失败产物接续入口，并另行验证新尝试读取什么、何时允许执行、如何处理过期回执。当前样本没有显示必须引入复杂的新恢复引擎，故按登记出口停止扩展，不启动新的 Loom 成员内部恢复对照试验，也不作收益排名。

## 证据边界

入口是成员级驱动器，真实调用当前 `runtimes.Executor.ExecRemote`、Runtime HTTP 接口、`weave runtime` 和原生 Claude CLI。父运行与上游回执是明示的输入夹具，未运行整队工作流；因此不能声称 Workbench 自助恢复或整个日冕团队验收已经通过。任务是原 `digital-engineering-builder` 的完整成员工作，沿用该历史节点批准的单一 `0.03c`、baseline `1.0.0`。

本轮正常组 CLI 报告 `k3[1m]`、`k3`、`kimi-for-coding-highspeed`；没有把别名当成固定模型版本。完成回执报告输入 2,556,099 tokens（含缓存）、输出 44,596 tokens，CLI 估算金额 2.848906 USD。此金额不是供应商账单，也不用于三组性能或投资回报排名。中断组若缺少整段用量回执，必须记未知。

## 观察器修正

N 尚在执行时，第一版触发检测把失败测试列表中的单个 `ok` 误当作整轮成功。未对 N 注入故障，也尚未启动 C/M。修正为必须存在完整、未截断的成功汇总，并拒绝失败、错误和零测试；六个回归用例全部通过。保存旧观察器与错误里程碑，并将 N 的有效里程碑定位到实际成功的事件序号 50。原登记哈希未覆盖写，修正时间和新源码哈希单独记录于 `evidence/observer-correction-before-fault-runs.json`。

C 采用自写 `run_tests.py`，以 `[summary] 17/17 checks passed -> PASS` 和 `EXIT=0` 输出整轮成功，第一版修正后的识别器未覆盖这种格式。故障前补充该格式，只重载观察器，成员、Runtime 与协调驱动器均继续运行；增加的计数、非零测试与退出状态反例合计八个测试通过。因观察器修正，实际注入距成功事件延迟 130.2 秒，此时仍未完成全部交付。旧源码、重载记录、真实进程与哈希均保留。此偏差使 C 只适于定性恢复结论，不能与其他组作精确故障时点性能对照。

## 文件入口

- `plan.md`：模型执行前登记的输入、故障位置、验收规则和决策出口。
- `inputs/manifest.json`：原成员任务、冻结记录、参考文件与上游文本的来源和哈希。
- `evidence/preregistered-manifest.json`：第一轮执行前的输入、驱动器与二进制哈希。
- `probe/control.py`：实际服务、执行、故障注入及状态记录。
- `probe/verify_delivery.py`：独立产物检查；浏览器操作证据另记，不能以引擎完成自动判通过。
- `probe/summarize_case.py`：从任务回执和文件哈希汇总，不把未知用量记为零。

四个样本的事件、回执、原始输出与独立核验均保存在 `cases/`，每组有逐文件 SHA-256 归档清单。两项补丁的前后证据分别在 `evidence/patch-ruby/` 与 `evidence/patch-signal/`。实验服务、数据库和工作目录均隔离，清理记录见 `evidence/cleanup.json`，业务服务未纳入故障注入。

时间记录只支持各组机器执行区间及已记录的故障/重启时点。输入冻结、观察器修正、核验、修复和等待相互交叠，未设置持续人工工时计量，人工分类工时和前期探索成本均记未知，不反推人力 ROI。
