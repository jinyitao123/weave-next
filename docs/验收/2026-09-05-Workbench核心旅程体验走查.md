# Workbench 核心旅程体验走查

2026-09-05 · 已完成主路径走查 · 本机隔离环境

## 走查范围

本记录只评价 Workbench。覆盖从开始交流、团队推荐或新团队构建、确认与派发、团队运行、用户干预到成果交付的完整体验，并单独记录视觉层级、信息架构、交互反馈、动效与等待感受。

- Weave 后台：`http://127.0.0.1:18081/`

- 浏览器：Codex 内置浏览器，默认视口与缩放

- 真实性：模型凭据复用本机已有配置；团队、运行记录和成果使用隔离数据库，不读取或修改现有业务数据

## 总体判断

Workbench 已经有一套可信的视觉底子：黑白灰层级克制，主要动作、次要动作和危险动作大体能区分；对话、紧凑任务卡和工作现场形成了“开始工作—快速跟踪—深入查看”的三级结构；成员公开更新、阶段产物保留、最终成果入口和运行节点中心都具备真实产品价值。

当前最主要的问题是状态与控制权没有形成同一套产品模型。一次团队工作会同时出现在侧栏、会话顶栏、模型正文、提问卡、紧凑任务卡和工作现场中，这些位置会使用不同词汇，甚至呈现不同事实。用户经常需要自己判断哪一层更新、哪一层只是历史文字，以及系统是在运行、等待团队、等待自己、自动重试还是已经失败。

团队构建与选择仍然主要依赖模型正文和通用工具展示。候选目录被包装成“团队匹配”，英文思考、工具名、UUID、原始 JSON 和后端错误会进入业务界面；确认有时是结构化卡，有时是自由文本；团队方案、创建和派发的门禁也无法稳定映射到界面。结果是内容上看起来很智能，关键控制点却不够可预测。

运行页最有价值的是成员状态与公开更新，它们让用户能看到团队正在做什么。现在缺少的是交接事件、依赖关系和统一时间线。阶段直接从一个状态替换为另一个状态，两名成员并行启动只能通过卡片变化推断；失败、重试、停止确认和恢复分散在不同区域。动效数量较多，但对“刚刚发生了什么”的解释反而不足。

从审美体验看，当前页面的主要瑕疵也来自信息架构：长职责和长阶段产物被直接铺在窄工作面板中，状态词重复，灰色说明密度很高，警告在多个位置重复。少数布局出现挤压断字、悬浮层覆盖相邻内容和中英文混用。视觉系统本身不需要推倒重做，优先把事实、状态、动作和时间关系收束后，页面会自然变得更安静、更高级。

## 优先级整改建议

### P0 状态与控制权

1. 建立唯一任务状态源，并让侧栏、顶栏、紧凑卡、工作现场和恢复会话都读取同一份产品状态。每个时刻只允许一个主状态，例如“2 名成员并行执行”“等待你确认范围”“原节点离线，等待停止确认”“构建失败，可重试”。模型正文只作为历史内容，不得承担当前状态。
2. 区分三类等待：系统处理中、团队内部等待、等待用户。只有等待用户时使用醒目的待处理样式，并给出唯一主操作；“等待团队继续”应改为具体的成员执行状态。
3. 固化四道门禁：选择团队、确认团队方案、创建完成、派发任务。每道门禁都使用同一类结构化摘要卡，明确本次点击会发生什么；确认结果以人话写入对话时间线。用户要求分两次确认时，工作现场不能提供越过门禁的“选择并准备派发”。
4. 构建失败必须成为工作现场的真实状态。显示失败步骤、可读原因、已保留内容、自动重试次数和“重试创建／修改方案／退出构建”动作。禁止对话说失败而工作现场继续说“正在匹配”。
5. 默认业务界面隐藏模型私有思考、MCP 工具名、UUID、原始 JSON、后端枚举和原始错误。需要诊断时放入明确的技术详情层，并以用户可理解的摘要作为入口。

### P1 旅程与运行表达

1. 把“团队匹配”改成真正的推荐界面：展示需求摘要、匹配理由、覆盖项、缺口、默认工作流、健康度和推荐结论；当用户明确不复用时，不再展示可选择的现有团队。
2. 为团队构建提供可持久恢复的构建现场，至少包含“定义已确认—模板构建—成员创建—工作流校验—团队可用”五步，以及预计时间、当前步骤和失败重试。自动恢复必须在页面上有次数和结果。
3. 在团队总览增加事件时间线和交接提示，例如“负责人完成协调 → 两名评审员开始并行 → 终审等待输入”。阶段列表显示序号、负责人、依赖和结果，避免多个同名“分工执行”。
4. 保留公开更新，但把长阶段产物收进独立阅读层。总览只显示结论摘要、证据状态和下一步；长表格与报告通过“打开阶段产物”进入完整页面。
5. 中断恢复要解释绑定关系。新节点上线但无法接管旧执行时，明确告诉用户原因；运行节点中心提供受影响任务数量及入口，并说明故障接管组的作用。
6. 用量说明按推荐、团队构建、诊断重试和实际运行拆分。数值异常高时给出可展开来源，帮助用户判断是长上下文、重复检索还是重试造成。

### P1 动效与可访问性

1. 任何时刻只保留一个主要运行信号。团队运行时以状态点或进度变化为主，停止团队卡、工具行、Todo 和正文扫光同时循环。
2. 用一次性短过渡表达阶段完成和成员交接，例如新成员卡短暂高亮并出现事件文字；不要只做瞬时替换，也不要在完成时自动切换成果页或改变阅读位置。
3. 给 ToolRow、bash、Todo、StateDot 和子智能体连线补齐 `prefers-reduced-motion`；减少动态效果时仍保留文字、图标和时间变化。
4. 保留公开记录的“离开底部后停止跟随”和“回到最新”设计，解决嵌套滚动区拦截外层滚动的问题；统一状态区域的读屏播报，避免重复或遗漏。

### P2 视觉与文案收口

1. 统一“进行中／任务执行中／运行中／正在执行”“准备中／正在匹配”“等待继续／等待阶段完成”等词表，并统一中文产品名与友好团队名。
2. 修复窄面板中运行位置和阶段状态的断字，限制职责摘要行数；让阶段、成员和状态列保持稳定对齐。
3. 减少重复出口和重复提示。工作现场保留一个主返回动作；相同失败原因只在页首给摘要，在对应成员或阶段给细节。
4. 悬浮预览不得覆盖当前任务的核心内容，也不能让另一任务的状态看似属于当前会话。

## 建议验收标准

- 任意时刻从侧栏、对话卡和工作现场读取到的主状态完全一致。
- 用户能在 5 秒内回答当前团队、当前阶段、正在工作的成员、是否需要自己操作以及下一步会发生什么。
- 团队创建失败后，无需输入自然语言即可重试、修改方案或退出；刷新页面后仍停留在同一失败步骤。
- 现有团队选择、新团队创建和任务派发分别留下可回看的确认摘要，任何按钮都不会越过用户指定的门禁。
- 默认视图不出现英文私有思考、MCP 名称、UUID、原始 JSON 或后端错误码。
- 两名成员并行、一次交接、一次失败恢复和最终完成的全过程可在一条时间线中复原。
- 开启系统“减少动态效果”后无循环扫光、旋转或追逐动画，状态信息仍完整。
- 运行节点离线时能明确区分可接管与不可接管，并提供受影响任务入口。

### 团队选择与构建

- 团队列表当前更接近全量候选目录，卡片没有展示与当前请求的推荐理由、匹配度和健康结论，标题“团队匹配”容易让用户误以为已经完成智能推荐。
- 同一列表可能同时出现在对话内联卡和工作现场中，造成重复。工作现场有防重复选择状态，内联列表没有 pending、disabled 和失败反馈。
- 点击候选后，会生成一条包含内部 `team_id` 的可见用户消息；这与主界面隐藏内部编号的产品表达不一致。
- 团队、任务范围和预期交付物的确认依赖模型自由文本，没有结构化确认卡。用户不容易看清自己究竟确认了什么，也难以逐项修改。
- `team_create` 和构建状态没有专用产品界面，可能落入通用工具调用行，出现工具名、标识符、预算和 JSON 等内部信息。
- 新团队创建是异步过程，当前缺少可持久恢复的“构建现场”。如果模型在“正在构建”处结束当前轮次，页面没有明确机制保证构建完成后继续派发。
- 团队构建期没有阶段进度、失败原因和接下来是否自动派发的清晰表达，工作现场可能只显示笼统的“正在匹配合适团队”或“准备中”。

### 运行动效与滚动

- 团队运行时可能同时出现 Todo 旋转、状态点追逐、对话状态扫光、任务状态点脉冲、工具扫光和团队列表扫光。复杂任务越多，循环动效越容易同时争抢注意力。
- Workbench 任务面板自身和团队列表已经部分尊重“减少动态效果”，但工具行、Todo、共享状态点和部分子智能体动效仍缺少统一兜底。
- 成员、阶段、进度条和工具状态大多瞬时替换，没有“谁刚完成、谁开始接手”的状态迁移提示。任务完成时还可能自动从进度切换到成果页，存在阅读位置突然变化的风险。
- 公开工作记录会在用户离开底部时停止自动跟随并提供“回到最新”，这是应保留的设计。主对话也实现了阅读锚点保护。
- 公开记录自身是最高 480 像素的独立滚动区，并阻止滚动继续传递到外层；嵌在对话或详情滚动中，触控板和滚轮可能被困在局部区域。
- 对话任务卡、完整工作现场、待处理状态和阻断提示可能同时作为状态区域出现，读屏存在重复播报风险；公开记录关闭了自动播报，另一方面又可能漏掉新活动。

### 可复用历史运行证据

本机另一套既有 Workbench 数据包含以下真实任务，可用于补看当前空白隔离环境暂时无法自然制造的状态：

- “创建Workbench恢复验收四人组”：运行、并行等待、失败、阶段重试、恢复、完成，4 名成员和 7 份成果。
- “创建Workbench人审验收0905团队”：运行、等待人工回答、继续、完成，2 名成员和 2 份成果。
- “派发读书会简报任务”：运行、并行等待、停止中、已停止和停止未确认，4 名成员和 2 份成果。
- “Workbench轻量验收组任务派发”：运行、并行等待、恢复运行和完成，4 名成员和 6 份成果。

历史会话只能看到最新投影；中间状态需结合主对话中的操作回执和时间线判断，不能冒充实时转场证据。本次应优先用当前代码复制既有数据后查看，并把历史证据与实时操作分开记录。
