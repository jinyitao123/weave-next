# 卡片视觉细则 · 基于用户提供的参考图

用户提供的三张截图已原样保存在[参考目录](参考/)。它们作为目标效果参考，与[真实现状证据](证据索引.md)分开。这里提炼视觉规则，不把参考界面的品牌、功能或布局直接搬进 Weave。

## 从参考图提取什么

[图一](参考/R01-对话与输入卡片.png)中，用户消息靠柔和底色区分，输入卡片以薄边界和轻阴影突出可操作性；两者同属圆润、简洁的语言，但没有使用完全一样的容器。

[图二](参考/R02-浮层与分组.png)的浮层边缘清楚且柔和，分组靠留白和很轻的分隔线建立，图标、文字、右侧数量及加号各有稳定的对齐位置。顶部焦点轮廓清楚，辅助文字退后，但正文仍然容易读。

[图三](参考/R03-并置参考.png)用于比较整体密度和层级。右侧 Weave 处于47%显示比例，不能直接比较两边截图的物理字号、图标像素、线宽或圆角大小，也不能从静态截图判断动效。

## 当前 Weave 的落差

[A18](证据/A18-final-deliverable.jpg)、[A19](证据/A19-creation-failure.jpg)、[A23](证据/A23-stopped-conversation.jpg)显示成功、创建失败和已停止卡片的信息结构差异较大。已停止是短状态加小按钮，创建失败变成团队名、标题、两段说明和折叠入口；成功卡则让成果名称、阶段入口和查看入口竞争。它们都能表达事实，但尚未形成统一的“结果摘要卡”语言。

输入区、状态卡、文件展开区和按钮的圆角与留白也没有被明确组织成一套可解释的尺度。问题不是所有卡片必须一样大，也不是圆角越大越精致。需要先确认每种容器负责什么，再统一它们的边界、内容起线与操作位置。这是截图支持的视觉判断，不是数据或业务功能故障。

## 三类容器，分别有清楚的角色

| 容器 | 视觉处理 | 内容顺序 |
|---|---|---|
| 任务状态／结果卡 | 平静的底面、很轻的边界，默认不用明显投影 | 状态结论 → 有效结果或失败影响 → 主动作 → 次级详情 |
| 输入卡片 | 边界略清楚，轻阴影或层次突出可操作性 | 输入正文 → 附件 → 稳定底部工具行 |
| 浮层／菜单 | 比页面卡片有更明确的浮起感，柔和投影，内部以留白分组 | 分组标题 → 可操作行 → 补充入口 |

文件阅读区域以标题和正文组织，不为每个段落再加卡片。消息气泡保留与上述容器的视觉亲缘，但不套用状态卡的动作框架。

## 样板的具体尺度

这些是待打样的初始值，不是从缩放截图中量出的参数，也不是系统规范。

- 任务卡内边距从16像素起步，标题与正文相隔6—8像素，正文与操作区相隔12像素。按内容自然增高，不强行统一成功和失败卡的高度。
- 任务卡圆角先试12—14像素，输入卡试20像素左右，浮层试16—20像素；小按钮与分组控件使用更小尺度。各档有用途，不随机选值。
- 默认边界使用一条低对比细线。页面内卡片少用阴影；浮层使用低透明度、柔和扩散的阴影，不使用厚重描边和强投影双重强调。
- 卡片状态标题约14—15像素、适度加重，说明约13—14像素，低优先信息12—13像素。层级先靠内容和间距建立，再调整字重；不能把次要文字淡到难读。
- 图标16像素为基础，与文字视觉中心对齐，固定占位；小状态点只表达状态，不替代结果标题。操作区保持同一高度与排列基准。
- 每张卡有一个视觉最明确的主动作。次要详情使用轻量入口；关键失败原因仍可读，技术编号与完整执行记录放到其后。

第一轮至少并排看成功、创建失败、执行失败、已停止、等待和运行中这六种卡片。使用真实长中文名称和两三行原因复验，不能只用短占位词验证美观。

## 开合与动效上的细腻程度

展开入口整行可点、箭头不换位置；打开后标题与内容之间的间距稳定，收起后回到同一标题。不要在悬停时突然换内容图标，也不要让文件名跟着按钮出现而挤缩。

状态变化时优先维持卡片所在位置、主动作对齐和输入区稳定。执行指示停止之后，终态信息清楚落位；过渡是否自然必须用连续录像看，不能只提交首尾截图。点击响应要先于较长的网络等待，加载反馈留在相关区域。

## 单独验收卡片品质

视觉验收逐项看外轮廓、内边距、文字起线、图标重量、按钮基线、分隔线和阴影。必须在100%正常显示与实际使用窗口检查，追加长文案、中文换行、深色和高对比场景；不能用小比例缩略图作最终判断。

交互验收看悬停不位移、按下反馈清楚、展开边界可辨、返回不迷失、结束后动作与状态准确。第一轮把这张卡和成员／成果阅读连起来复验，完成后再扩展到其他业务卡片。
