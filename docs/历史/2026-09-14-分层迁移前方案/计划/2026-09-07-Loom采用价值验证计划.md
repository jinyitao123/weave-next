# Loom 采用价值验证计划

2026-09-07 · v0.1 · 原始验证设计。

执行状态附记：本计划后已启动实验；2026-09-07 的[执行记录与停止结论](../验收/2026-09-07-Loom采用价值验证/README.md)优先描述实际状态。下文保留制定时的条件与时态，不追溯改写门槛。

要回答的问题是：在实际值得恢复的成员任务上，Loom 相比现有方式和最小恢复补丁，是否提供足够的额外收益，值得增加接入与维护成本。

本计划是 [成员执行补齐方案](2026-09-07-Loom成员执行补齐方案.md) 的采用决策前置验证。该方案保留为候选设计，不是默认实施路线。依据 [已有验证报告](../验收/2026-09-06-Loom替换验证/README.md)，目前只证实了内核机制可用；CLI 与 Loom 原实验使用不同工具条件，不能作为性能、质量或投资收益对照。

**一、先检查问题是否真实存在**

执行验证时，先从最近 30 天可访问的运行记录中按时间倒序取至多 20 个成员任务，包含成功、中断和失败，公布纳入/排除规则与缺失记录。不得专挑 Loom 擅长的样本。

记录成员任务时长、实际模型与工具消耗、中断原因、已有回执/产物、是否真的返工、人工干预时间，以及中断后仍可利用的结果。将发布配置错误、模型内容错误、工具不可用与进程中断分开，Loom 恢复不能解决的故障不计入潜在收益。

若现有日志无法关联重复执行，就标为未知，不能把整次失败任务的全部成本算作浪费。若观察期没有真实长任务或中断返工，只能得出“当前需求证据不足”；机制实验可以保留，但不能据此启动整套产品改造。

根据该样本选择一个最有代表性的真实任务作为 T2，并在实现候选前锁定任务、输入快照、正确结果判据和实验条件。真实收益不通过增加 sleep、重复无意义计算或故意放大工具成本制造。

**二、比较三个候选，而不是只比较接入前后**

| 候选 | 实际含义 | 允许增加的机制 |
|---|---|---|
| A：现有路径 | 当前 CLI/Runtime 成员执行，保留已有恢复、任务回执和产物能力 | 仅加入三组共有的观测与故障注入，不故意关闭现有恢复能力 |
| B：最小补丁 | 在 A 上增加稳定任务操作身份、持久化工具回执，以及复用现有阶段/产物的恢复入口 | 可为已声明阶段保存结果索引；不新建通用图引擎、DSL、历史分支或第二套团队调度器 |
| C：Loom 原型 | 同一成员任务由 Loom 推进，保存图状态并从明确边界恢复 | 仅实现实验所需的持久化入口与步骤边界；不先实现完整 Workbench、任意分支或全量迁移 |

B 和 C 使用相同的外部工具幂等与回执基础设施。若 B/C 相比 A 的收益来自这份共同基础，应归因于回执机制；Loom 的增量收益只看 C 相对 B。

B 原型优先复用现有执行任务、结果回传和阶段输出。不得假定现有路径完全没有恢复能力，也不得把 B 故意写成必然从头重跑。B 若已演化成一套通用调度框架，应暂停并重新界定“最小补丁”，不能继续以“小补丁”名义比较。

原型的首个可运行版本建议每个候选最多投入一个工程日，单独记录实际耗时；超过这个探索上限时，先报告成本与阻塞点，不无上限补齐。该时间盒是计划预算，不是工期承诺。共同实验设施成本另列，已有 Loom 实验代码可复用，但相应开发工作不能被当作完全免费。

**三、任务与对照条件**

| 任务 | 用途 | 验证内容 |
|---|---|---|
| T1：日冕基线复算 | 可独立核验的控制样本 | 读取同一基线、复算三速度、独立复核、生成报告；数值、输入哈希与文件均可核对 |
| T2：从历史样本选出的真实多步骤任务 | 主要业务收益样本 | 已有实际用途，工作量和中断损失由记录说明；不能用 T1 的人为延长版替代 |
| T3：第二个未参与原型调试的真实任务 | 候选通过后检验迁移成本 | 看是否需要再次修改执行框架、增加专用恢复逻辑，记录接入与排障成本 |

三组固定相同输入快照、业务目标、允许的工具实现与参数 schema、输出契约、模型配置和资源上限。每轮使用独立目录和数据库命名空间，隔离缓存、结果与调用身份；保留同一轮中恢复所需的持久化数据，清空不应跨轮继承的结果。

A/B 的 CLI 也必须通过相同工具完成指定操作。若 C 使用受控 MCP，而 A/B 自行写代码计算，两组数据不能进入正式比较。预检确认工具集合与权限可对齐；无法对齐时直接报告不具备严格对照条件，不能强行排出优劣。

保持共同业务提示与预算；适配器必须的协议说明差异另行归档。模型提供方如能固定版本和随机性设置则固定，否则记录实际回执及变化。配置同名不能保证底层模型完全相同。三组不同的循环与提示封装是候选方案的组成部分，端到端结果评估整个候选路径，不冒充对 Loom 库本身的纯因果测量。

故障按共同工具事件的位置触发，例如“第 N 个工具效果已提交”或“该回执已被候选确认”，不按固定秒数触发。所有比较使用相同逻辑工作位置。三组运行顺序在每个任务/场景/重复批次中随机化，串行运行，减少负载和时间段偏差。记录机器负载、CLI/模型回执、工具版本、代码提交与工作区差异。

**四、分开验证机制正确性和实际收益**

先做不调用真实模型的机制实验，使用预先定义且与候选无关的响应序列，验证 B/C 的崩溃处理。它只回答恢复机制是否可靠，不能用来计算真实模型质量或用户收益。A 的已知行为也保留作对照。

机制实验至少覆盖以下窗口，每个 B/C 场景重复 3 次。

| 故障 | 必须证明的行为 |
|---|---|
| 工具效果已提交、回执尚未送达 | 从执行任务或幂等键找回同一操作；查不到就进入结果待核对，不盲目重复写入 |
| 回执已持久化、图或阶段检查点未保存 | 复用原回执补齐状态，不能再次执行已确认工具 |
| 检查点已提交、成员结果未被团队接收 | 新进程读到完整状态，团队只接受一次成员结果 |
| 两个恢复者同时接管，旧进程随后返回 | 只有一个有效所有者，旧结果不能覆盖进度或重复交付 |

工具写入实验只操作实验目录和隔离计数器。恢复使用真实新进程，记录 PID、退出原因、检查点和回执身份，不把旧进程内存搬回去。也要确认子进程是否仍存活：先测协调进程死亡但工具服务继续运行的情况，核心候选通过后再增加执行进程一同死亡的情况。

随后做真实模型对照。T1/T2 各跑三种场景。

| 场景 | 主要问题 |
|---|---|
| S0：无故障完成 | 增加恢复机制后，正常任务变慢多少、多耗多少、质量是否变化 |
| S1：工具效果完成但回执返回前中断 | 会不会重复操作，是否能找回结果，何时需要人工核对 |
| S2：一段有效工作已确认后中断 | 新进程能保住多少已完成工作，是否还要重复推理或调用工具 |

先做 `2 个任务 × 3 个候选 × 3 个场景 × 1 次 = 18 轮`，检查对照条件、证据完整性和明显失败。条件成立且仍有比较价值，再补足每格 3 次，总计 54 轮。若某候选触犯正确性门槛，不再为凑满次数继续消耗，报告实际分母及停止原因。

未到故障位置就因其他原因失败的运行也保留并计入端到端完成情况；不能无限补跑直到获得好看的故障样本。恢复时间从所有候选共同的“新进程可用”事件开始计算，并另报包含故障检测与重新拉起的总停顿时间。

54 轮是探索性对照，不足以证明生产故障率或严格统计非劣效。关键结果接近门槛或批次间反向时，判为证据不足；可对争议场景预先登记增加 5 组配对重复，仍不清楚则停止，不循环抽样直到出现胜利结果。

**五、到底量什么**

| 指标 | 计算与证据 |
|---|---|
| 最终完成与正确性 | 是否交付实际可读文件、输入来源正确、数值/功能独立检查通过；所有失败均入表 |
| 重复执行量 | 对已有有效回执的逻辑操作，恢复后实际重复派发/执行的次数与耗时；显式请求再次运行的合法操作不算重复 |
| 丢失的推理工作 | 已有可用模型响应却重新请求的次数、输入输出 token；不声称能测量私有推理内容 |
| 恢复耗时 | 从统一恢复起点到最终正确交付，另列故障检测、工具核对、重新推理与工具执行时间 |
| 正常开销 | S0 的端到端耗时、模型调用与 token、持久化次数和失败；报告原始值、配对差值、中位数与范围 |
| 人工负担 | 需要人介入的次数、原因和实际处理分钟数，不能把所有人工修复时间隐藏在恢复计时之外 |
| 工程成本 | 公共设施、候选专属开发、故障修复、数据库/状态迁移、新增协议和测试分别登记；代码行数只作参考 |
| 泛化成本 | 接入 T3 需要的框架改动、任务专用代码、耗时和新增失败；复用成功须由实际任务证明 |

T1 的计算用独立实现验证，报告的额外事实也检查；数值正确但文字产生实质错误不能算正确交付。T2 的判据必须在看结果前制定。报告评阅去掉候选名称后按同一标准核对，缺少合适的独立评阅时明确标注，不能声称做了盲评。

实际费用只有取得可核对的价格与计费回执时才计算。拿不到费用就报告 token 和调用数，不编造金额；按次费用、等待时间与工程人时分别列出，不把三种单位相加成一个“收益分”。

**六、预先写下采用和停止判据**

下面数值是建议的工程决策门槛，必须在正式运行前固定，不是已测得的结果，也不是统计显著性声明。若任务背景要求调整，应在看对照结果前记录理由。

首先是正确性门槛：已确认工具不重复产生副作用、来源与产物不串运行、进度不被旧执行者覆盖、无假成功、预算不因恢复重置。任一候选出现这类问题，应先修复并重跑受影响场景；未修复不能成为胜出候选。

然后作以下决策。

| 结果 | 决策 |
|---|---|
| 缺少真实返工需求，或 A 的现有恢复已满足任务 | 保留 A，不立项完整接入 |
| B 已取得 C 相比 A 的至少 80% 的恢复耗时收益，正确性相当且工程成本更低 | 优先 B |
| C 相对 B 的关键中断场景恢复耗时中位数减少至少 30%，已确认工具无重复副作用、返工量不更差；S0 耗时和 token 中位数增长各不超过 15%；正确性无新增实质问题 | C 获得继续验证资格，进入 T3 与真实产品路径，不直接批准全量采用 |
| C 达不到耗时门槛，但宣称任务泛化明显更便宜 | 只允许进入 T3 验证该假设，另记收益；不能宣称已通过恢复收益门槛 |
| B/C 都有关键正确性问题，或收益差异不稳定 | 修复后再评估或停止，保留 A；不强行选胜者 |

B 收益覆盖率只在 A 比 C 的恢复耗时确有改善时计算：`(A恢复耗时 - B恢复耗时) / (A恢复耗时 - C恢复耗时)`。按任务和场景分别计算；分母接近零或为负时不使用该比率。

T2 是业务决策的主要样本。T1 用于检查机制和结果，不能用它的好成绩掩盖 T2 的退步。涉及真实任务的收益外推还要参考样本中的中断发生率：故障稀少时，正常开销可能抵消全部恢复收益。

建议按观察期做一份成本账：实际中断任务数量 × 每次减少的重复计算/推理消耗，分别列出正常运行新增消耗、每月维护工时、一次性开发与迁移工时。观察数据不足时给出盈亏平衡所需的任务量或中断频率，不捏造业务规模，不把模拟的高故障率当作生产发生率。

**七、候选通过后，才验证产品和迁移成本**

仅将表现最好的候选和有必要保留的比较对象接入 T3。先锁定任务与验收标准，记录不修改框架是否能直接使用；如果必须再增加专用步骤，计入真实成本。

若 C 胜出，再补最小产品路径中的工具冻结与成员身份接线，通过实际发布和 Workbench 跑一个限定成员任务。验证配置中的工具确实进入发布产物、工具回执能关联原成员运行、重启后状态可继续、最终文件可打开。已有内核原型成功不能替代这一关；修复产品接线的成本计入 C。

这一阶段先复用现有界面和操作入口，必要操作可由维护者验收接口触发并明确标注。若没有用户可操作的继续入口，只能叫“产品后台链路通过”，不能叫 Workbench 自助恢复可用。新增用户交互按迁移边界另行安排。

历史分支、任意状态修改、整个团队切换和跨主机迁移均不进入首轮。只有真实使用记录提出独立需求，才为这些能力增加单独的采用验证。

**八、交付物、证据与收尾**

最终交付一份可以直接做决策的比较报告，明确写出采用 A、采用 B、继续 C 小范围试用或证据不足，并附以下材料。

1. 历史样本清单、任务选择依据、事先锁定的实验清单与门槛。
2. 每轮候选、输入哈希、代码/模型/工具版本、执行顺序、PID、故障位置、回执、检查点、输出和独立核验结果。
3. 所有成功与失败轮的原始指标表；模型、工具、正常开销、恢复和人工处理分别记账。
4. 按 A→B 的共同基础收益、B→C 的 Loom 增量收益，解释结果归因。
5. 共同与专属工程投入、T3 接入工作、尚未覆盖的产品缺口。

实验数据与业务任务隔离，保持当前业务团队配置。保留复跑必要的探针、结果和哈希清单；停止本轮服务，清理无用临时文件，不在证据中保留凭据。只有执行后拿到实际退出状态和独立证据，才把对应项标为通过。

本轮只制定验证计划，未启动候选开发、历史数据抽样、真实模型实验或生产切换。
