# Weave 任务信任契约与双场景三阶段验证方案

2026-09-07。状态：已授权执行。本文定义产品收束目标、用户信任条件、平台证据义务，以及电商与日冕两类真实任务的三阶段验证。实施只使用 Workbench 业务入口；命令行只用于读取、归档和独立核验，不替代用户在 Workbench 中完成任务。

## 1. 产品决策

Weave 收束为面向明确交付工作的任务执行与证据系统。用户交付的是一件工作，不需要先理解团队图、运行时或恢复机制。平台承诺持续推进、保留已确认工作、在需要决定时准确停下，并且只在交付约定得到满足时报告成果可验收。

Loom 是 Weave 内部的成员执行机制。是否扩大 Loom 使用范围，以真实任务相对现有路径或更小恢复方案的增量价值为准；团队数量、图节点数量、检查点数量和工具调用次数本身不构成产品价值。

本阶段不新增通用工作流编辑器、自动造团队、更多运行时、跨主机迁移、任意历史分支或插件市场能力。若验证暴露产品缺口，先判断它属于任务契约、执行、交付验证或专业判断，再决定是否修改产品。

## 2. Weave 任务信任契约

每个可被放心交付的 `WorkTask` 必须具有一份可审查的任务契约。契约由六部分组成：

1. **任务适配**：任务类型、预期用户、可交给 Weave 的工作和必须由用户或专业角色承担的决定。
2. **输入基线**：材料范围、来源、版本、内容摘要或哈希、只读与可写边界、允许发生的变更。
3. **交付约定**：实际要获得的文件或结构化结果、质量条件、机器检查、专业复核和用户接受方式。
4. **执行边界**：可用团队、运行时、工具、预算、超时、允许自动修复的范围和必须停下提问的条件。
5. **证据义务**：平台需要保存的来源、过程、结果和用户证据，以及每类证据的归属身份与版本。
6. **退出条件**：`执行结束`、`部分完成`、`成果待复核`、`已接受`、`失败`分别在什么事实成立时产生。

任务契约不得把“调用了模型”“阶段节点完成”“生成了最终文字”作为成果满足的充分条件。文件任务必须核验文件；计算任务必须保留实际测试及退出结果；涉及专业判断的任务必须展示未知项、反对意见和接受主体。

## 3. 信任状态与证据等级

产品层分开表达三类事实：

| 维度 | 回答的问题 | 可用状态 |
|---|---|---|
| 执行 | 运行是否仍在工作，为什么停止 | 准备、执行中、等待决定、已停止、执行失败、执行结束 |
| 交付 | 约定成果是否实际满足 | 未形成、部分完成、待核验、核验不通过、核验通过 |
| 接受 | 谁确认结果可以进入下一环节 | 未请求、待接受、已接受、退回修改 |

证据按强度分为四级：

| 等级 | 定义 | 能支撑的声明 |
|---|---|---|
| 可见 | 页面或模型输出中出现 | 只能说明曾展示 |
| 已记录 | 平台持久化并有任务、运行、成员、attempt 和版本归属 | 可以说明发生过 |
| 已核验 | 机器检查或独立复核得到明确结果 | 可以说明约定的可检查条件成立 |
| 已接受 | 用户或授权专业角色明确接受 | 可以说明结果进入下一业务环节 |

Workbench 的“完成”文案必须能够追溯到相应证据等级。无法得到强证据时，应降低结论，不以文案补齐证据。

## 4. 双场景职责

### 4.1 电商场景

电商代表高频、结构化、周期短、同类任务可重复的工作。历史样本来源已确认为 GitHub 开源项目 RealReplicaBench，当前上游名称为 CommerceAgentBench。本机验证 checkout 位于 `/Users/jinyitao/Developer/RealReplicaBench`，远端为 `https://github.com/Accio-org/RealReplicaBench.git`，本轮冻结提交为 `084489800bfd3f9f239503eda9e754bc267e98f5`。只有任务定义、运行环境、verifier 和执行证据可追溯时才称为“复验”。

电商主要回答：

- 用户是否可以用较少说明发起同类任务。
- 第二次任务是否复用契约和团队，而不复用错误数据。
- 结果是否可直接采用，用户需要修改多少。
- 平台是否能区分输入问题、执行问题、结果问题和用户偏好。
- Weave 相比直接单 Agent 处理是否减少人工组织、检查和返工。

阶段一固定首个样本为 `api-gmail-vendor-brief-mcp`。它要求从 Gmail Mock MCP 中识别 VBR-52 当前有效线索，正确标记邮件、保存未发送草稿并创建会议事件；原始 verifier 检查标签、已读、星标、草稿、日历和“没有发送邮件”。该样本同时覆盖正向动作、跨对象信息综合和负向克制，且无需生产账户。阶段二优先复用同类 Gmail/Calendar 任务；若要比较相同契约下的新输入，应选择同一 benchmark 版本中工具面和验收结构相近的任务，并明确哪些检查可直接比较。

### 4.2 日冕场景

日冕代表长周期、多材料、多阶段、多专业成果和中断接续。固定使用现有真实材料和现有验收规则，保留历史失败，不用新的简化夹具替代。

日冕主要回答：

- 多成员任务是否能按冻结输入执行并保持路线、单位和追溯一致。
- 已确认工具效果是否在中断后复用，未知副作用是否准确停住。
- 运行结束时，平台是否能识别缺少的模型、图纸、应用、复核和验证成果。
- 用户能否在一个监督对话中完成确认、纠偏、继续和验收。
- 过程可靠性与专业成果质量是否分别得到结论。

## 5. 共用证据包

每个样本建立独立目录，至少包含：

- `contract.json`：任务契约、样本身份、基线版本和验收规则。
- `input-manifest.json`：实际输入文件、大小、哈希或来源标识。
- `dispatch.json`：Workbench 派发事实、团队、工作流、运行和时间。
- `activity.json`：成员、阶段、工具、检查点、重试和终态活动。
- `deliverables.json`：平台记录的全部成果及其运行归属。
- `verification.json`：逐项机器检查和独立复核结果；未执行项为 `NOT_RUN`。
- `user-decisions.json`：确认、纠偏、继续、接受或退回等用户事实。
- `assessment.md`：从产品角度判断用户是否可以放心交付、证据缺口和下一步。

证据包不保存凭据，不根据 token 推算无来源的费用，不把旧任务产物登记为当前运行产物。

## 6. 阶段一：建立契约并完成首轮真实性审计

### 工作

1. 从 Workbench 历史定位原电商任务，并与 RealReplicaBench `0844898` checkout 的任务定义、团队、成果和 verifier 交叉匹配；记录哪些事实可恢复。
2. 读取现有日冕真实材料、历史运行和已交付文件，形成当前基线，不覆盖失败记录。
3. 为两类任务分别生成 `contract.json` 和 `input-manifest.json`。
4. 通过内置 Workbench 浏览器各发起一个独立样本。派发前确认任务契约；派发后保存运行身份和页面证据。
5. 检查 Workbench 是否能准确表达执行、交付和接受三类事实。

### 出口

- 两个场景都能回答“交了什么、依据什么、要得到什么、怎样算通过”。
- 历史电商任务是否真实可复验得到明确结论。
- 当前页面没有把阶段完成或文本总结误报为成果核验通过。
- 所有未取得的证据明确记为缺失或 `NOT_RUN`。

阶段一不因任务成功派发而完成，必须取得首轮终态或明确的可复现阻塞。

## 7. 阶段二：验证重复使用与中断接续

### 电商重复任务

在相同契约下替换一份可识别的新输入，保持任务类型和验收规则不变。验证团队和流程可复用，而输入、结果和证据不会串用。记录首次与第二次的说明工作、用户介入、交付耗时、结果修改和失败处理差异。

### 日冕中断任务

在取得已核验检查点、且最终交付未完成时中断承载成员执行的进程。通过 Workbench 继续，验证：

- 同一逻辑成员由新的 attempt 继续。
- 已确认工具效果不重复产生。
- 预算、剩余工作和未解决问题跨恢复连续。
- 无法确认副作用时进入待核对。
- 用户无需重述完整任务或重新建立团队。

### 出口

- 电商第二次任务无需重新设计流程，且没有跨输入污染。
- 日冕恢复后的重复副作用为零，运行身份和接续关系可审计。
- 两类任务均记录真实用户介入次数、人工处理时间、总耗时和调用消耗。
- 普通可修复错误在契约预算内由系统继续推进，不依赖用户反复输入“继续”。

## 8. 阶段三：收束 Loom 边界和产品路线

阶段三不直接扩大产品能力，先依据阶段一、二证据比较：

| 候选 | 含义 |
|---|---|
| A | 现有 CLI/Runtime 路径和已有回执恢复 |
| B | 在现有路径上补最小的契约、回执和接续机制 |
| C | Loom 成员工具循环、检查点和恢复 |

只比较两类任务中可对齐的部分。模型、工具、输入和交付契约不同的运行不得用于候选排名。共同的文件、回执、版本和交付验证收益不得归因于 Loom。

### 决策规则

- 若 A 已满足用户信任条件，保留 A，不增加执行层复杂度。
- 若 B 获得至少 80% 的 C 恢复收益，且实现、运维和正常任务成本更低，优先 B。
- 只有 C 在真实关键中断中的恢复中位时间比 B 至少快 30%，正常任务时间与 token 增长分别不超过 15%，且没有新增正确性、重复副作用或误报交付缺陷，才扩大 Loom 使用范围。
- 若证据不可比、样本不足或专业结果仍需大量外部返工，结论保持“证据不足”，不得按技术偏好切换。

### 产品固化方向

无论采用哪条执行路径，Weave 固化以下产品能力：一件持久 WorkTask、一个监督对话、任务契约、运行证据、可继续检查点、交付核验和用户接受记录。成员图、Loom 状态和运行时选择作为按需查看的实现详情。

### 出口

- 形成 `loom-boundary-decision.md`，逐项说明保留、扩大、冻结或退出的能力。
- 决策引用两个场景的真实证据，不引用模型自评作为采用依据。
- 列出下一阶段唯一主线、明确冻结项和重新考虑冻结项的触发条件。

## 9. 零容忍项与停止规则

以下任一问题出现，相关样本直接判为不可信，先修复或收窄承诺：

- 不同任务之间输入、结果或工具回执串用。
- 已确认副作用在恢复后重复执行。
- 文件缺失、测试失败或专业严重问题未关闭，却显示成果已核验通过。
- 运行或成果不能归属到明确任务、成员、attempt 和版本。
- 用户已停止任务，旧执行者仍能覆盖新状态。
- 凭据进入冻结包、证据文件或最终产物。

出现三次同类普通任务仍需人工反复推动、每个新任务都要修改运行框架，或者过程证据增加但用户返工不下降时，暂停功能扩张，重新收窄任务类型或采用更简单的执行路径。
