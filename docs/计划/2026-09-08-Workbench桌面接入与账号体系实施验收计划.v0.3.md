# Workbench 桌面接入与账号体系实施验收计划

日期：2026-09-08  
版本：v0.3，增加分层与部署边界验收  
状态：S1–S3 真实链路与桌面验收尚未执行；并行准备中的独立客户端夹具已验证，详见并行任务计划。

本版配套[产品技术方案 v0.3](../架构/2026-09-08-Workbench桌面接入与账号体系产品技术方案.md)。[v0.1 计划原文](2026-09-08-Workbench桌面接入与账号体系实施验收计划.v0.1.md)和 [v0.2 计划原文](2026-09-08-Workbench桌面接入与账号体系实施验收计划.v0.2.md)保留。其中“35–60 人日”、动态 Host 管理前置和跨设备完整对话必做的安排，不再作为当前首期基线。本轮增加单仓与职责边界约束，延续 S0–S3 的纵向交付顺序，不启动独立分仓或全仓重构。

执行顺序补充：Loom 与 CLI 闭环修复期间，按[并行任务计划](2026-09-08-Workbench桌面接入并行任务计划.md)划分独立准备与后续接入；v0.3 的目标与最终验收条件不变。

## 1. 从横向铺模块改为验证完整的小链路

第一条样本必须同时出现真实用户身份、Host 对话、MCP、材料、Weave 派发、异机 Runtime 和成果。可以用静态用户 Host、简单桌面窗口和管理员预置模型；不能用全局管理员 key、共享文件路径或伪造完成状态替代核心接缝。

两账号隔离是多人发布条件，不推迟到一般上线之后。框架打包小样尽早进行，但不单独占用第一阶段去完成整个桌面设置产品。

## 2. 阶段、输出与出口

| 阶段 | 工作 | 产物与出口 |
|---|---|---|
| S0. 合同冻结 | 明确角色真相源、来源会话、接收与提交边界、材料权限、Host 所在地、模块归属及首发平台 | 路由/权限/职责矩阵；3 个接收状态定义；单写者政策；受影响依赖清单；待决产品项记录 |
| S1. 一条真实纵向链路 | 固定专属 Host、个人账号、身份接线、持久输入、材料派发、异机执行、成果 | 实际 actor 正确；材料摘要相同；业务副作用可对账；桌面能默认连接并登录 |
| S2. 第二用户与故障 | 第二个独立 Host；撤权、双设备来源、断线重试、进程崩溃、切服、升级独占 | 本表所有首期硬门槛通过；明确发现的缺陷及修复 |
| S3. 可安装试点发布 | 真实目标平台安装、稳定入口、连接保存、签名更新、迁移演练与容量观测 | 干净设备完成从安装到取回成果；试点规模受实测容量约束 |
| S4. 按需扩展 | 动态 Host、无人在线监督、多组织、本机 Runtime 等 | 每项单独证明需求与价值，不默认进入 |

S1 不是“多人生产可用”，S3 才是首期试点交付。全量云服务商业化、全平台发布另有范围。

## 3. S0 必须冻结的最小合同

### 3.1 授权

- 当前账号启停、组织成员资格、组织角色和资源动作分开判定。
- cookie、JWT、个人 API key 与内部请求使用同一政策；兼容运维路径有明确例外名单。
- 普通成员、管理员、owner 的动作矩阵由现有接口逐路核对，不能把历史两套角色取并集。
- 移除成员、禁用账号、角色降级对新命令的效果必须一致；与命令接受发生竞态时有持久排序依据。

### 3.2 接收与幂等

- Host 输入接收回执、Host 待提交业务操作、Weave 业务接受回执是三个不同事实。
- 稳定 input_request_id 和 operation_id 由客户端/可信入口按契约生成并持久关联；不同内容复用同一 ID 返回冲突。
- 来源 AuthSession 由认证层绑定，跨 RPC、后台队列和 MCP 传递，不能由模型或任意前端字段指定。
- 关窗不等于撤销；退出原设备后，不借另一设备继续原操作的新写入。
- 提交结果未知时先向原服务对账，不能重新换 ID 派发。

### 3.3 材料

- 明确个人草稿与组织共享附件；created_by 不直接当权限规则。
- 复用现有附件目录，增加派发结构化引用、摘要和授权快照。
- 派发指纹包含材料集合/版本，Runtime 用任务授权读取。
- 不把 Host 路径作为跨机器文件传输。

### 3.4 Host 与数据

- 首期固定单机/少量专属 Host，无自动租约故障接管。
- 旧进程未确认退出时不启新写者；记录升级的独占证据。
- conversation_id = SessionId；不新增第二份对话状态/版本数据库。
- Host 重启首期至少支持重新打开后对账；无人打开主动监督是额外承诺。

### 3.5 单仓与职责约束

- S0 为本次涉及的“用户动作 → API/MCP → 领域服务 → 运行合同”标出唯一负责方，明确 Session 接收事实与 Weave 业务接受事实。
- Workbench 保留监督 Agent 和对话队列；团队调度、业务 run 恢复和最终交付记录由 Weave 负责。运行投影可重建，不能成为第二个执行控制器。
- cookie、桌面连接偏好、公开服务 origin、Host 固定路由留在应用/客户端边界；内部运行合同不依赖这些表现形式。
- 服务端与 HTTP/MCP 消费侧的合同修改同仓交付、共同验证；按真实使用提取窄接口，维持 API 兼容和原操作身份。
- 本次触及的历史反向依赖逐项评估、登记保留或迁移理由；不新增例外，不以完成 11 条历史债务清理作为首期前置条件。
- Runtime 镜像与中心镜像分离只在执行依赖盘点后安排；Workbench 所需 MCP 二进制和中心端仍在使用的执行能力必须保留。

## 4. 实现接缝与可复用部分

| 接缝 | 修改位置 | 复用对象 | 首期不要增加 |
|---|---|---|---|
| 当前主体与动作政策 | internal/app/api/middleware.go、auth.go、users、org 与相关业务路由 | 现有用户/成员/运行关系 | 第二份用户或角色真相源 |
| 设备登录 | internal/app 账号 API 与 Workbench Connection 认证 provider | 用户密码校验、现有 HTTP 服务 | 完整 OAuth/SSO 平台、花哨设备管理页 |
| 输入持久接收 | session-controller、Session 事件与 persistence 接缝 | 现有日志、flush、序号及请求 ID | 独立且双写的输入任务库 |
| 请求来源传递 | Connection/Gateway、工具执行上下文、MCP tools/call、weaveclient | 现有协议/工具语义 | 模型可填的授权参数、永久 Host 写入 token |
| 命令与观察分离 | workbench-app 当前 poll 与 pendingAction | WorkTask、原 run/operation 身份 | 新产品任务状态机 |
| 材料进入派发 | attachments、team_dispatch、weaveclient、MCP schema、执行快照 | 现有附件/任务下载机制 | 新通用材料平台 |
| 固定 Host 接入 | 统一入口、部署清单、独立卷、串行替换脚本 | 现有 Workbench 镜像/profile | 动态调度、跨主机 leases、集中对话库 |
| 桌面 | workbench/apps 下产品桌面入口、连接/下载/发行 | 现有 Web UI | 同期维护两个正式框架 |

涉及 Session 新事件时，验证既有严格事件词汇与历史回放要求。涉及 kernel/base 时保持依赖方向；授权/产品装配不得向下散落为全局特殊规则。

## 5. 首期硬门槛与反例

所有用例初始状态为未执行。只有源码证据不能填写 PASS。

| ID | 操作 | 必须观察到的结果 |
|---|---|---|
| G01 | 干净设备安装，无连接偏好 | 使用预置服务，真实账号登录，用户不填平台 key |
| G02 | 用户改服务、重启、升级应用 | 选择保持；失败不自动跳回默认或本地 |
| G03 | 同用户 UI/MCP/直接 API 操作，随后移除成员或降权 | 所有入口遵循同一现行政策 |
| G04 | 同账号设备 A/B 共享 Host，A 发待提交操作后退出 | A 来源操作停止新写入；B 正常；不借 B 续 A |
| G05 | 分别在 Host 接收前、落盘后、Weave 接受后退出 | 三个阶段的回执和继续/停止行为符合合同 |
| G06 | 收到输入回执立即强杀 Host；再使用原 ID 重试 | 无静默丢输入；同内容返回原接收事实；不同内容冲突 |
| G07 | Weave 已提交但响应丢失，随后断网/重开/切服 | 原服务对账；一个业务运行；新服务不重放旧请求 |
| G08 | A/B 不同账号使用独立 Host，猜对话/附件/导出/设置/目录引用 | 按明确个人或共享政策访问；无隐式共用管理员凭据 |
| G09 | 上传真实材料，Runtime 位于另一主机 | 获取字节的摘要与派发快照一致；客户端路径未被当作远端路径 |
| G10 | 相同任务文字和请求 ID，更换材料集合 | 幂等冲突；不能复用旧结果冒充新材料已执行 |
| G11 | 当前节点在线但没有所需能力或可用资源 | 不显示为可派发；监督模型未配置时也明确阻断依赖动作 |
| G12 | 关闭桌面端，运行结束后重开同一对话 | 对账同一 run，真实成果可下载并打开；无重派发 |
| G13 | Host 重启，重新打开持久对话 | 历史与关联恢复，观察与写操作分开；不擅自恢复旧 Agent 写入 |
| G14 | 暂停旧 Host，尝试启动替代者，再恢复旧进程 | 仅一个进程可写同一卷；无法证明独占时替代启动被拒绝 |
| G15 | 服务描述通过后、更改实例，再提交请求 | 业务入口拒绝旧 expected_instance；凭据与数据不混用 |
| G16 | 切服务时旧响应、续期、上传和事件迟到 | 新页面不被覆盖；旧操作回执仍能在原归属下查询 |
| G17 | 对应平台安装/更新/中文输入/下载失败和取消 | 用户可操作，连接与数据保留，错误签名包不可安装 |
| G18 | 旧数据迁移与降级演练 | 无双写；已知不兼容日志不被旧 Host 打开；备份可恢复 |
| G19 | 丢弃可重建的 WorkTask 展示缓存后重新读取，分别停止前台 turn 与指定业务 run | 投影从权威记录收敛；停止前台 turn 不冒充停止 run；业务停止回执能关联服务端命令及结果 |
| G20 | 检查本次变更的依赖图、API/MCP 合同与实际命令调用路径 | 无新增向上依赖；Web/桌面调用遵循同一业务入口；cookie/页面配置未进入运行内核，未新增平行团队调度器 |

G08 的“个人材料”需以实现后显式权限政策为前提；现有 tenant 共享文件不得因测试预期而被误称为历史漏洞。G06 保证持久接收和业务副作用去重，不承诺故障下模型调用数量恰好一次。

## 6. 条件性能力验收

仅在该能力进入范围时执行以下出口：

| 条件 | 新增验收 |
|---|---|
| 完整对话跨设备 | 第二台干净设备登录后读取同一持久 Session；同账号并发输入有 busy/conflict/幂等规则 |
| Host 重启后无人在线监督 | 所有页面关闭，重启 Host，观察未终态任务仍恢复；不靠用户打开页面激活，不为读取状态重启 LLM turn |
| 完全退出账号后后台通知 | 独立只读授权覆盖已关联 build/request/run，不能写命令；成员移除立即终止访问 |
| 动态 Host 接管 | 旧进程与控制面隔离、lease 过期、旧进程恢复后，存储仍强制唯一写者；只加数据库 epoch 不算通过 |
| 本地 Host | 真正的目标平台安装物包含必要依赖；凭据不入渲染进程；配置分区及休眠/退出行为可复现 |
| 本机 Runtime | 明确启用、目录授权、独立节点凭据、停止/注销、休眠恢复逐项验证 |
| 分离中心/Runtime 发布物 | 盘点依赖后，用对应镜像完成团队构建/评估、派发、节点执行与成果读取；Workbench MCP 仍能启动，不依赖被移除的引擎或构建阶段 |

## 7. 验证范围与交付证据

代码实现后按改动执行 make test、make depguard、make productguard；数据库集成必须设置 TEST_DATABASE_URL；Workbench 依照根 make workbench-install workbench-check 和作用域内 GUI/组装浏览器规则；Compose 使用 make compose-check 并做真实部署验证。

本次仅修订文档，检查引用、版本归档及审查结论一致性。没有为文档改动运行整套业务测试，也没有启动多用户服务器或创建桌面安装包。

真实验收保存准确的软件 SHA、镜像/安装包摘要、匿名化账号代号、实例和操作身份、材料摘要、页面证据及实际可打开的成果。凭据不得写入报告。每个结果明确是代码检查、小样实测、故障注入还是生产验证。

## 8. 估算与停止规则

不沿用 v0.1 的总人日或冷启动数字作为当前承诺。S1 后至少取得三组证据：

1. 身份和持久接收改动实际涉及哪些包、协议与迁移。
2. 一个目标平台安装包是否可以稳定使用当前 Host 能力。
3. 固定用户 Host 的空闲/活跃资源占用、启动时间以及真实试点用户数。

据此给出剩余工作分解和有依据的工期区间。若静态部署已满足用户数和资源预算，就停在静态部署；没有跨设备完整对话需求且本地材料成本显著时，改测本地 Host；一个框架通过必要发行与交互检查后停止无收益的框架比较。

遇到共享管理员 key、来源会话丢失、材料未进快照、回执不能持久、卷可能双写任一问题，先修该接缝。不能通过弱化 UI 文案或减少反例把它标为完成。

## 9. 尚需产品输入

- 首期是否必须跨设备看到同一份完整对话。
- 首发桌面平台和真实使用人数。
- 正式服务域名与发行签名条件。
- 普通成员是否需要操作其他成员发起的业务运行。

这些是可审查方案中的具体选择，不是本次分析的前置审批。当前推荐保留远程路线并先做固定专属 Host 试点，尚未实施；实际选择改变时，按第 6 节增减能力验收，不重写账号、任务和材料的共同核心。
