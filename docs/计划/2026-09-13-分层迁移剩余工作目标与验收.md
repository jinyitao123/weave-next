# 分层迁移剩余工作目标与验收

日期：2026-09-13

状态：执行中。代码分层和五个独立仓已经形成，四个模块已有首轮候选标签；Server 发布、固定版本组合、部署验收与最终产品验收仍未完成。本文是这些剩余工作的唯一状态清单。

## 总目标

把 Workbench、产品服务、团队构建、平台内核、执行 Host 和 Loom 的职责拆清，并让能力调用、团队运行和建队试运行使用同一套平台执行治理。保留 Loom、Codex、Claude、OpenCode 及其组合方式。迁移直接采用新契约，不处理旧数据、旧快照、旧 Host 或旧在途运行兼容。

完成不能只依据代码编译、测试通过、运行状态完成或模型自述。全部开发、分仓和部署完成后，必须通过 Workbench 正常页面、真实模型、实际产物和独立复核。

## 执行节奏

1. 迁移前只记录保护职责边界所需的行为基线。
2. 开发中运行与当前改动相称的工程回归，防止把错误带到下一批。
3. 各模块收敛并完成分仓、部署后，再集中执行完整真人式产品验收。
4. 发现阻断缺陷后回到所属模块修复，重新部署，再从受影响场景起点复验。

## 第二批：平台执行受理与尝试契约

责任层：Weave kernel。事实所有者：平台执行记录。复用入口：现有 `taskqueue`、runtime 领取世代、成员运行 journal、用量回执与停止回执。

本批先完成：

- 定义产品域无关的执行请求、冻结输入、任务、物理尝试和终态回执。
- 能力步骤携带稳定的逻辑执行标识和绝对期限进入现有 runtime/taskqueue。
- 成功与失败路径都保存物理尝试及用量；远程结果未知时保持未知，不自动重派。
- 平台关闭只中断 worker，不把仍可能执行的任务直接恢复为可领取。
- 能力调用首先接入共同底座；确认语义后移除其独立物理队列。

本批不把建队领域阶段或产品调用记录伪装成普通任务。它们保存自己的业务状态，但实际试运行必须提交共同执行入口。

完成证据：并发领取、迟到回执、未知结果、期限、取消、重启、用量和版本绑定的真实 PostgreSQL 回归；远程 Host 进程停止与补报回执测试；depguard 不新增例外。

## 第三批：基础层与 Builder 收敛

责任层：kernel 与 builder。事实所有者分别为平台执行记录和建队候选记录。

- 将 `base/teamrun` 的执行、fanout、恢复、取消及状态决策整体迁入 kernel，不建立转发包。
- 抽出 builder 的目录读取、候选写入、评估执行和证据读取端口；移除 `pgx.Tx`、连接池和产品 Store 的跨边界传播。
- 建队候选评估通过共同执行入口运行；builder 不领取物理任务、不写平台终态。
- 将 runtime wire payload 从 registry、taskqueue、execenv 和 Loom 内部类型中解耦为版本化 Host 协议。
- 将 Loom 的冻结计划编解码、图装配和执行端口，与成员 journal、PostgreSQL 事务及平台终态分开。

完成证据：depguard 11 条例外归零；base dependency guard 通过；builder/kernel/runtime 的契约测试不依赖 app；全仓工程回归通过。

## 第四批：工具、额度、恢复与身份

- 指定工具请求只能进入任务授权范围内的工具端口；记录幂等标识、实际回执、外部影响和未知结果。
- 每个循环迭代及内部模型重试产生可归属的物理尝试，用量缺失保持未知；父预算只向内收紧。
- 平台使用绝对总期限，恢复不会重新获得完整时长。
- Host 回报 `completed`、`failed`、`stopped` 或 `stop_unconfirmed`；取消不被展示成自动回滚。
- 执行请求携带服务端签发的用户委托和资源范围。同一 Host 上不同用户使用独立工作目录、凭据会话、浏览器会话、产物和历史视图。

完成证据：真实工具副作用测试、循环与重放测试、预算耗尽、进程强杀、断网补报、跨用户交叉访问拒绝。

## 第五批：产品链路

- 产品任务维护版本化材料集合；修订明确引用原材料、上版成果和本轮修改要求。
- 执行快照保存本轮实际输入版本，成果引用实际运行与材料版本。
- 核验器接收任务验收规则和证据，输出通过、未通过、缺少依据或未执行；成员自述不能代替核验。
- 固定机械任务默认直接执行。研究、额外复核、人工等待和自动返工由任务需要或明示策略启用。
- Workbench 只呈现业务动作、阶段、待处理事项、成果和核验，不暴露面向普通用户的模型配置或内部协议字段。

## 第六批：分仓与部署

按以下顺序实施，每次都先在当前仓形成公开边界，再迁入独立仓库：

1. `workbench` 与 `weave-runtime`：分别形成交互产品和执行 Host；保留两种 Codex 用法及 Loom 远程执行。
2. `weave-kernel`：发布 Host 协议、能力/团队执行契约及 Loom 执行适配；不依赖 server 或 builder。
3. `weave-builder`：发布候选构建与评估策略库；不直接访问产品数据库。
4. 当前组合根收敛为 `weave-server`，维护产品 API、部署和经过验收的版本组合。

分仓完成以独立检出、无相邻目录捷径的构建测试为准。六个源码仓不要求六个部署服务；kernel、builder 和 Loom 默认以库形式装配。

## 最终集中验收

开发及部署完成后，启动桌面 Workbench，并可用内置浏览器或真实外部浏览器辅助观察同一套页面，按[Workbench 真人式验收协议](../验收/Workbench真人式验收协议.md)执行。测试者依次扮演普通用户、任务负责人、成果使用者、独立审计者，并加入新手、怀疑者、越权用户和中断恢复操作者。

每个场景记录页面动作、系统响应、实际运行、产物、核验、用量、身份和副作用。完整通过要求：

- 页面、平台运行与实际产物状态一致。
- 真实模型和声明的运行时路径有可核对证据。
- 条件、循环、人工确认和工具调用由流程事实证明。
- 中断后不丢失已确认工作，不重复未知副作用。
- 两名用户互相看不到任务、材料、凭据、执行环境和产物。
- 机械任务没有被强制建队研究或多层复核。
- 订单修订场景重新核算得到正确结果且保留原材料证据。

完成后更新统一验收记录，合入主干并启动固定版本组合供试用。任何一项缺少证据时，目标保持执行中。
