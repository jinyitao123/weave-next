# Weave 交付核验状态与契约接入设计

2026-09-08。状态：首批共用核验机制已实现并通过机制回归，尚未部署本批代码或完成业务验收。源码核对基线为 `ce5fe66701083237398df038998899aa6d57fe7c`。本文细化[共用信任边界方案](2026-09-08-Weave共用信任边界与Loom修复方案.md)第 2 节，范围为现有 `fixed_workflow` 的 CLI、Loom 两条执行路径。第 2、5.1 节保留实施前问题基线，实际落地字段及验证范围见第 10 节。

## 1. 目标与首批边界

用户于 2026-09-08 明确先完善 weave-next 团队能力，Workbench harness 后续单独处理。本批不改前台 Agent 循环、标准预设、子 Agent 或独立工作流能力；仅将团队的权威核验结果和交付版本投影至既有界面。

在现有 WorkTask、TeamRun 和成果记录上增加可核实的交付判定。引擎正常结束、交付满足冻结要求、用户愿意接受，分别记录。首批接入真实的文件和结构检查、可信检查回执以及严格汇总规则；只有改界面为“未知”，不算实现本设计。

沿用现有发布工作流、成员执行、attempt、任务队列、恢复检查点和最终 `deliver` 节点。核验是该交付边界上的确定性操作，不增加业务任务类型、核验节点、通用任务平台或新调度系统。工作流中的复核员可以继续提出意见，但自然语言 `PASS` 不授予系统核验通过。

| 维度 | 权威来源 | 示例 | 不会自动改变的维度 |
|---|---|---|---|
| 执行结果 | 原引擎回执及现有 TeamRun 状态转换 | 正常结束、失败、取消、停放 | 交付核验、用户接受 |
| 交付核验 | Weave 对冻结契约及具体交付版本的检查报告 | 待核验、通过、未通过、未知 | 原引擎结果、用户接受 |
| 用户接受 | 用户对具体交付版本作出的评价 | 未评价、已采纳、需修改 | 系统检查结论 |

三个维度可以出现“执行已结束、交付未通过、用户未评价”。核验通过也不自动成为已采纳。已经产生的成果和已观察外部效果，在失败或取消后仍保留。

## 3. 冻结交付契约

### 3.1 来源与责任

`DeliveryContractV1` 是运行输入的组成部分，随当前输入修订和已发布工作流冻结。核验期间不读取工作流的新 head，也不让成员输出修改契约。

| 信息 | 首批来源 | 可承担的判据 |
|---|---|---|
| 已发布输出 `type`、`schema` | 本次快照实际引用的发布制品 | 最终值结构有效 |
| `deliver` 的 `ValueRef`、节点输出声明 | 同一冻结 graph | 哪个节点及其物理结果有资格成为最终候选 |
| 必需文件的精确相对路径、内容类型、必要内容条件 | 与已授权输入一起保存的明确机器可读清单 | 实际文件存在、归属正确及已声明内容条件成立 |
| 必需检查及 verifier 标识、版本、参数 | 可信应用注册表支持的契约项 | 对指定成果或对象执行指定检查 |
| 外部对象、允许效果和检查范围 | 已授权任务的明确结构化要求 | 必需对象正确，规定范围内不存在未处理的额外效果 |
| 所有业务要求已覆盖 | 有来源的结构化范围声明及相应 verifier 能力 | 只对该明确范围形成整体结论 |

当前发布格式中的 `result_requirements`、`success_criteria` 等自由文本不能自动转成完整文件清单或必需检查集合。输出 schema 中普通的字符串字段也不能自动解释为实际文件。若以后希望在发布制品中声明业务契约，应增加有版本的明确字段并走发布验证；首批不通过偷偷改变 schema 含义完成接入。

用户已经同意的范围沿用现有审阅和派发授权。契约清单可在同一次任务说明或现有审阅界面中展示并固定，不因新增字段再增加一轮确认。可信代码可以继承已发布的结构约束；模型建议新增、删减或放宽业务要求时，不能自行声明清单完整或替用户授权。

对历史运行、兼容入口或只有自由文本的任务，继续支持原执行路径，保存可确定继承的结构约束，并标记 `coverage=incomplete`。系统不能为了获得 `passed` 而补写一个空清单、让模型声称检查完成，或把“未配置核验”解释成“无需核验”。

### 3.2 建议字段

以下是新结构的设计字段，不是当前 API 已存在的承诺。

| 字段 | 含义及约束 |
|---|---|
| `schema_version` | 固定为已支持的契约版本 |
| `source` | 来源输入修订、发布制品标识与摘要，以及明确结构化范围的来源引用 |
| `coverage` | `explicit` 或 `incomplete`；明确记录未覆盖要求，不允许模型自行提升 |
| `output` | 继承的输出结构和最终节点选择约束 |
| `required_artifacts[]` | 稳定 `id`、规范化相对路径、内容类型和受支持的内容规则；禁止任意主机路径 |
| `required_checks[]` | 稳定 `id`、注册的 `verifier_id`、版本、目标引用和经过 schema 校验的参数 |
| `external_effects` | 是否涉及外部写入、必需对象、允许的创建/更新/删除范围，以及额外写入检查范围 |
| `limitations[]` | 尚无 verifier、证据不可获得或格式不支持的要求 |
| `contract_digest` | 可信代码对规范化冻结内容计算的摘要 |

契约中的 verifier 是受控注册项，不能提交任意 shell、脚本或 URL 让核验服务执行。空的业务范围不形成完整任务核验；确实只有结构化文本输出的任务，也应明确声明范围、检查内容及适用的外部效果边界。

## 4. 核验状态与证据

### 4.1 逐项结果和汇总

逐项检查为 `passed | failed | unknown`，并记录 `check_id`、目标版本、verifier 版本、证据引用、观察时间和原因码。整体为 `pending | passed | failed | unknown`。

| 整体状态 | 条件 |
|---|---|
| `pending` | 运行尚未到交付边界，或确实已有有界核验调用正在进行；不表示存在新后台任务 |
| `failed` | 任一必需条件已被证据证明不成立，或存在已确认但未处理的越界效果；其余未知项仍列出 |
| `unknown` | 没有明确契约、范围不完整、必需检查未运行、证据缺失或过期、外部范围无法覆盖、格式或能力不支持 |
| `passed` | 契约范围明确，全部必需项有适配且可信的通过证据，外部效果边界已核实，无未处理越界效果，并且报告精确绑定当前交付版本 |

汇总次序为“已知失败优先；否则有未知则未知；全部满足才通过”。实际核验结束后的未检查项为 `unknown`，不能永久停留在 `pending`。运行已终止且没有最终候选时，有明确缺失证据的必需项记失败，其余记未知。

核验报告独立描述交付事实，不改写运行状态。报告已保存而执行状态尚未完成终态转换时，API 可以呈现“执行中、交付核验通过”，但不能据此提前宣布执行结束。取消后已有报告可保留；取消或失效 attempt 的迟到结果不得成为新的当前交付版本。

### 4.2 首批真正执行的检查

1. 校验冻结输出结构。沿用现有 schema 检查，并将实际结果纳入报告；原有解析、协议及 schema 错误仍保留其执行错误原因。
2. 在选中的物理结果中寻找必需文件，验证规范路径、内容类型、字节摘要及明确的内容规则。检查实际回传内容，不能只搜索总结中的文件名。
3. 验证每个文件的来源任务或成员、父运行、快照及已完成结果身份，拒绝跨运行、跨快照和失效结果。
4. 执行已注册、只读且有界的 verifier，或接受由这些可信适配器生成、绑定目标版本的检查回执。超时、不可用或版本不匹配记未知。
5. 汇总全部必需检查和外部效果范围，再生成不可变报告。复核员意见可作为辅助材料，不可作为上述证据的替代。

没有外部适配器时，文件任务仍能得到真实的逐项文件检查，但不能虚构外部效果检查通过。首批可以让一个能力受限、无外部写入通道的隔离文件任务，或具有完整外部状态查询适配器的固定样本，通过其明确范围的全部检查。

### 4.3 只读 verifier 与额外写入

只读性由实际可用工具、凭据和执行环境决定。普通成员被提示“只读”，或使用名为 reviewer 的角色，不足以形成只读保证。首批确定性 verifier 由应用注册的代码执行，只持有查询所需能力；不得复用可写成员的通用凭据执行模型编排。

注册表属于受信应用代码，不对 Go 函数闭包实施权限沙箱。只读性与取消响应由适配器实际持有的查询客户端、凭据和实现保证。核验框架限制等待时间并控制报告提交，不能撤销已经发生的外部效果，也不能强制停止忽略取消的闭包。当前生产内置项仅为输出结构核验，外部适配器目前以隔离测试验证。

外部证据至少包含系统和租户范围、对象身份、可信查询返回的状态及修订、观测窗口、查询覆盖范围、适配器版本和完整度。必需对象检查回答“要求的对象是否正确”，额外写入检查回答“规定范围内还发生了什么”，两者分开记录。

用于额外写入判断的证据，可以是支持完整枚举及归属的外部查询、隔离场景的前后快照，或具有完整效果归属的服务端回执。仅查询预期对象、仅看到一次工具成功，均不能证明没有其他写入。发现错误对象时应失败；没有发现错误但枚举不完整时应未知。

前后快照只能证明其范围内的最终状态差异，不能证明中途未创建后删除对象、未发送消息或未发生其他短暂效果。契约若要求覆盖这些过程效果，必须有完整事件记录或等价服务端证据；仅有快照仍为未知。回执的可信生成方、目标版本和适配器规定的时效均须由代码验证，不能接受模型自行填入的“检查完成”。

当前有两个明确限制：

- [audit/store.go](../../internal/kernel/audit/store.go) 的记录与查询实现不能提供完整调用审计，条目也没有本设计要求的 run/attempt 归属；空返回不能证明零写入。
- 运行活动记录是尽力写入的观察。CLI 内部 Bash、Python 或 curl 可以绕过受管工具边界；缺少可证明的限制时，不能依据 Weave 工具日志宣称覆盖所有外部效果。

因此首批电商验收使用全新隔离范围及实际外部状态查询，保存完整额外对象清单。历史取消样本缺失的归属继续保持未知，不事后猜测。原 benchmark 的 7/7 单独保留；新增业务信任检查失败不会改写原评分，也不会让原满分覆盖额外错误日历事件。

## 5. 原引擎结果与成果能力

### 5.1 保留引擎事实

[runtimes/artifacts.go](../../internal/kernel/runtimes/artifacts.go) 当前会在引擎正常结束但文案声称的文件未收集到时，覆盖 `RunResult.Status` 和 `Err`；该诊断经 [runtime_loader.go](../../internal/kernel/workflow/runtime_loader.go) 转成 `DeliveryError`，最终 `deliver` 会返回执行错误。

接入时将原始引擎结果和成果收集证据分开保存、传递。原 `Status`、`Err`、session 身份、停止原因、usage 和已观察回执不得因业务核验而被重写。明确契约要求的文件实际缺失，应产生交付核验失败；只有自然语言声称文件存在时，保留诊断，不能据此臆造任务必需项或完整核验结论。

具体需要同时调整成果收集时覆盖状态的路径，以及共同 `deliver` 中将业务缺项 `DeliveryError` 升格为执行错误的路径，改为传递结构化收集证据并交给上述汇总。结果损坏、归属不合法、文件传输或存储失败仍保留相应技术错误，不能一律吞掉旧错误。

CLI 与 Loom 都向共同的交付边界提供实际输出、文件和来源证据。现有执行解析错误、存储错误、结果归属错误和真实引擎失败仍保留错误类别，不把基础设施故障伪装成引擎正常成功。Loom 停止语义和预算修复另按原方案推进，本设计不通过核验字段修补或覆盖原停止原因。

### 5.2 当前成果通道的限制

[fileartifact/artifact.go](../../internal/base/fileartifact/artifact.go) 当前接收有效 UTF-8 的有界文件，最多 128 个、单文件 256 KiB、合计 512 KiB。Loom 从明确的成员成果导出回执获取内容，服务端不会在恢复时任意读取运行主机文件系统。

这条通道不能承载一般二进制 PDF、CAD、图片及较大应用资源。HTML、JavaScript 等文本可能符合限额，但文件存在不等于应用能启动、依赖齐全、浏览器交互正确或性能达标。文件型图纸也不等于工程专业内容通过复核。

首批将这些未支持要求列入 `limitations` 和未知项。完整目标需要二进制及大文件的不可变存储和摘要引用、格式与完整性检查、应用实际运行和浏览器验收、图纸及专业成果核验。相关能力未完成前，日冕完整交付保持未完成，不能用少量文本文件样本替代。

## 6. 交付版本、存储与事务

### 6.1 版本身份

`delivery_revision_id` 由冻结的候选清单确定。清单包含 workspace、run、snapshot、被选中的 `deliver` 节点及输出引用、最终值摘要，以及排序后的文件路径、内容类型、字节摘要和物理来源身份。总结中的通过措辞、检查时间和用户评价不参与版本计算。

同一次成果的重复记录或核验重试保持同一版本。实际内容或所选物理结果变化则产生新版本，即使 run 没变。文件列表读取被截断时，不能用页面返回的前 100 条计算版本；版本清单由运行侧完整结果形成，API 只投影其摘要和引用。

`verification_id` 绑定契约摘要、交付版本、verifier 集合及版本和证据摘要。同一请求重试可幂等返回原报告；外部状态重新观察产生新证据及新报告。旧报告保留，不覆盖历史结论。

### 6.2 最小持久化结构

建议增加两类绑定既有运行的记录，不增加新任务实体。实现命名可调整，以下职责和约束保持不变。

| 记录 | 内容 | 不可变与并发规则 |
|---|---|---|
| `weave_run_delivery_state` | workspace/run/snapshot、输入修订、发布版本与摘要、契约 JSON 及摘要、当前交付版本、当前报告引用、独立选择序号 | 冻结契约列不可改；当前引用只能以 CAS 更新，更新前检查现有运行的 generation、execution lease、resume generation |
| `weave_run_delivery_verifications` | 报告 ID、契约摘要、交付版本和完整候选清单、可见成果行引用、逐项结果、汇总、证据、verifier 版本、观察时间及提交来源 | 追加不可变；相同身份幂等，不允许报告绑定另一运行、契约或候选 |

候选清单随报告保存，复用原最终成果内容，避免另建一套文件存储。`current_verification_id` 是当前视图指针，旧报告仍可查询。该子记录的选择序号不承担 TeamRun 生命周期，也不通过改写 TeamRun generation 打断正常终态转换。

首批使用有实际报告记录的引用表示核验；存储失败不能合成“通过”。历史运行可返回兼容的未知视图及原因，但不批量回填伪造检查记录。

### 6.3 事务与恢复顺序

1. **输入注册。** 在现有输入修订中保存明确提供的机器契约及来源，并把它计入修订的不可变事实。正文和既有来源消息保持原样。兼容输入只继承能确定的约束，覆盖度为不完整。
2. **派发事务。** 在当前冻结快照、入队和消费输入修订的同一事务中，写入运行契约绑定。发布输出约束必须取本次实际使用的发布制品；任何一步失败都不能留下已入队但契约绑定不同的运行。
3. **交付收集。** 现有 `deliver` 收集最终值和精确物理来源，构建完整候选清单。外部查询、格式检查和有界 verifier 在数据库事务外进行。
4. **交付提交事务。** 扩展现有批量成果写入入口，将该候选的最终文件、总结、核验报告和当前引用原子写入。锁定并核对当前运行与执行 fence；对重复候选和报告幂等。不得出现部分成果已作为当前版本，而报告误指向另一批文件。
5. **执行终态。** 继续使用现有 frozen terminal 和 `SucceedTx` 等路径记录执行事实，不由核验结果替换 `succeeded/failed/cancelled`。业务检查未通过不阻止正常结束被如实记录。
6. **独立复核。** 首批允许应用针对同一当前版本发起有界只读重查，不重跑生产成员或重放写入。提交时以契约摘要、当前候选及选择序号 CAS；若已更换版本，结果只保留历史，不能覆盖当前视图。

当前成果批量事务和执行成功事务本来就是分开的。若交付提交后、执行终态前崩溃，已经提交的报告只证明该版本的交付检查，不能让 API 合成执行成功。恢复必须从现有检查点选回同一物理结果并幂等复用报告；不得重新执行已确认生产效果。若结果还未提交，旧 lease 的迟到提交必须被拒绝。

取消与交付提交使用同一运行行上的状态和 fence 检查决定先后。先提交的交付保留，后取消如实反映在执行状态；先取消后到达的成果不得提升为当前最终候选。换代恢复后可以复用同一候选及证据，但必须重新取得当前提交资格，不能仅凭相同 run ID 放行。

首批核验同步接在现有边界，使用有界超时。需要长时间外部专业复核的任务先明确未知及原因，后续方案另行决定如何接入；不在本批创建没有真实工作支撑的长期 `pending`。

## 7. API、Workbench 与用户接受

run activity 增加服务端权威的 `delivery` 摘要，至少返回 `revision_id`、`contract_digest`、`verification_id`、`verification_status`、必需项计数、未知或失败原因、证据读取完整度，以及当前成果是否可用。`status` 继续是现有运行状态，列表 `completeness` 继续是读取完整度。

Workbench 展示执行结果、交付核验和用户评价三个维度。`final` 或 `summary` 仅表示成果可打开，不再直接决定“核验通过”。详情可查看缺失文件、尚未执行检查、不可核实外部对象或已发现额外写入。Host 以 API 结果投影，不能根据关键词、文件数量、总结或 Reviewer 文案自行判定。

Host 监控不能在执行终态且成果补读完成后，忽略仍在进行的实际核验。首批同步核验正常应已完成；遇到读取落后需继续补读，直到明确报告或未知错误，不无限轮询没有后台作业的状态。

用户评价沿用现有 `weave-assess` 入口，扩展为绑定 `{run_id, delivery_revision_id, outcome, note}`，保存已有可用的评价人及时间信息。首批可以继续持久化于当前 Host 的 WorkTask 存储；跨 Host 权威评价需要新增服务端持久化和 API，属于后续完整目标，不能声称当前已经具备。

评价规则如下：

- 用户可以独立评价已完成运行中的实际交付；机器核验为未知或未通过不替代用户判断，用户采纳也不改写检查结果。
- 新交付版本的当前评价为 `unrated`，保留旧版本评价历史；不能沿用当前“同一 run 即继承 outcome”的逻辑。
- 同一版本只重查证据时不清空用户评价。若外部状态变化导致核验下降，界面同时保留评价与新检查结论。
- 提交评价时核对当前交付版本，拒绝旧页面把旧版本评价写给新版本。该核对是身份校验，不是新增审批步骤。

## 9. 四格验收与必要恢复检查

CLI 与 Loom 均通过真实运行适配、成员结果加载和最终交付记录路径执行以下四格。可以用固定模型响应消除随机性，但不能直接写一个通过的报告绕过核验器。

| 样本 | 实际证据 | 执行结果 | 交付核验 | 用户接受 |
|---|---|---|---|---|
| 正常结束但缺必需文件 | 契约明确要求文件；选中物理结果中确实没有 | 保留原正常结束，TeamRun 可成功结束 | `failed`，指出具体缺失项，保留已有文件 | `unrated` |
| 复核文字为 PASS，必需检查未执行 | 输出中有 PASS；必需 verifier 无可信回执 | 保留原正常结束 | `unknown`，列出未执行项 | `unrated` |
| benchmark 7/7，但多写错误对象 | 原 verifier 原样得分；隔离外部状态查询发现额外错误日历事件 | 保留原正常结束 | `failed`，保留独立原评分及额外对象证据 | `unrated` |
| 明确范围全部满足 | 文件与来源正确；全部必需检查通过；外部效果范围完整且无未处理越界效果 | 保留原正常结束 | `passed`，指向完整报告与同一交付版本 | `unrated`，用户采纳后单独变化 |

另需针对本设计的实际风险验证：

- 契约变更、跨运行成果、失效成员结果和伪造检查回执不能成为当前通过证据。
- 原子提交失败不留下跨版本引用；提交成功但响应丢失可幂等重试；交付与执行终态之间崩溃不会虚构终态或重放写入。
- 旧 lease、恢复前 generation 和取消后的迟到结果不能覆盖当前交付；相同候选恢复不会产生另一个版本。
- 同一 run 新成果清除当前旧采纳，旧版本评价被拒绝；同版本重查保留用户评价。
- API 与 Workbench 对四格显示一致；成果列表截断、报告读取失败、历史无契约及不支持格式均不能显示核验通过。

代码实施后运行与改动相称的单元、真实数据库事务及运行/API/Host 集成验证，并执行仓库要求的 `make test`、`make depguard`、`make productguard`、`make workbench-install workbench-check`。只有出现新失败或未解疑点才扩大检查。

上述验收证明共用核验机制的具体能力。完整目标仍要求全新隔离电商业务样本的原 verifier、全部额外写入及取消效果检查，日冕完整文件、可运行应用、图纸与专业验收，以及真实中断接续。二进制通道、完整效果归属、跨 Host 用户评价或专业 verifier 未完成时，应逐项记录缺口，不将首批机制通过写成完整业务闭环通过。

## 11. 已发布模板默认合同补充实施

2026-09-10 针对日冕 v4 暴露的 `explicit_user_delivery_scope_missing` 根因补充实现。此前 Workbench 的普通确认只冻结用户消息，API 只从消息中的 `weave-delivery-contract-v1` 技术围栏读取合同；团队模板的 `delivery.success_criteria` 只生成评测 rubric，未进入发布工作流的交付合同。因此用户已经在界面确认范围，运行仍只能冻结空合同并返回 `unknown`。

补充后的权威顺序如下：

1. `team-template/v1` 可在 `delivery.contract` 中声明有版本的文件、可信检查、覆盖度、限制和外部副作用模式。内置模板编译器负责绑定 `output`，模板调用方不能另写输出类型或 schema。
2. 类型化合同进入 `TeamBlueprintV1`、模板编译输入和编译摘要，最终成为发布 `GraphDefinition` 的冻结内容。未知字段、无效路径、重复标识、未注册关系和输出不一致在发布前失败。
3. 派发时优先采用精确用户输入修订中的结构化合同；用户没有逐次覆盖时，采用本次实际发布制品中的默认合同；两者都没有时继续保持 `coverage=incomplete`。模型工具参数不能替代这两个来源。
4. `external_effects=none` 明确表示这次合同限定为本地成果且不要求外部写入，核验器记录 `no_external_effects_required`。`external_effects=required` 必须引用一个注册为外部效果能力的必需检查。旧合同未声明模式时继续保持原来的未知或显式检查语义。

针对性回归覆盖严格解析、冻结合同深拷贝、模板到发布图的传递、纯本地交付判定、真实 PostgreSQL 普通中文派发继承发布合同，以及精确用户合同覆盖发布默认值。仓库级 `make test`、`make depguard` 和 `make productguard` 通过。本补充解决合同来源链路，不解决日冕 v4 已记录的既有产物绑定、成员级纠偏半径、无人工修复冷启动或用户采纳；这些仍需新的保留样本验证。

当前应用只注册输出结构核验器。外部效果适配器通过隔离数据库表验证读取、失败和重查行为，还没有接入真实电商系统。严格汇总仍要求外部范围有可信覆盖；文件存在或模型输出 `PASS` 不会绕过未知项。
