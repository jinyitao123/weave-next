# 内核边界契约差距与第一批实现

日期：2026-09-12  
关联文档：[Weave 内核边界与开发者契约](../架构/2026-09-12-Weave内核边界与开发者契约.md)  
状态：合同层、应用受理层、PostgreSQL 持久化、HTTP 受理、持久调用队列、查询取消与执行状态回写已实现，真实 Runtime 编译适配与 Workbench 适配待进行

## 1. 当前判断

仓库已经具备若干目标机制，但它们服务于不同的旧业务路径，尚未形成统一的开发者能力契约。本阶段先做合同收敛和 characterization tests，再做代码迁移。

| 契约部分 | 当前可复用实现 | 当前差距 | 第一批动作 |
|---|---|---|---|
| 定义与校验 | `internal/build/teambuild` 的 blueprint、declarative workflow 校验 | 定义对象没有统一的开发者能力 API | 抽出不依赖 HTTP 的 `CapabilityDefinition` 校验接口 |
| 调试 | Workbench 与 workflow/session 已有未发布状态和观察能力 | 没有统一的 `debug` 运行边界、预算和产物命名空间 | 先定义 DebugRun 输入输出和隔离规则，暂不搬页面 |
| 发布冻结 | blueprint revision、frozen declarative workflow、provider revision | 发布对象、修订号、摘要和调用绑定没有统一命名 | 定义 `PublishedCapabilityRevision` 最小字段并建立读取测试 |
| 调用幂等 | `weaveclient`、evaluation idempotency 和运行记录已有幂等字段 | 不同入口的 key、错误和返回身份不一致 | 统一 `request_id`、`invocation_id` 和冲突语义 |
| 运行事实 | `teamrun`、workflow runtime、deliverable 和审计记录 | 业务运行、调试运行、能力调用的终止状态未统一 | 先列状态机和终止字段映射，不改变旧状态值 |
| 权限 | 应用凭据已有 `invoke/read/cancel` 范围，部分管理路径固定 `admin` | 人员权限、应用权限、运行时权限没有一个公开授权合同 | 建立统一授权输入结构，先兼容现有 admin 和三种应用范围 |
| 多运行时 | runtime registry、engine capability 和 Loom/外部引擎适配 | 开发者声明的运行需求与实际调度约束未统一 | 定义 capability requirement，不在公开 API 暴露供应商私有配置 |

上述判断来自当前源码盘点，不能替代完整测试结果。未列入“当前可复用实现”的内容，不应在产品说明中宣称已经完成。

第一批合同层已落在 `internal/base/capability`，提供定义校验、发布修订、严格 JSON 摘要和不可变性校验；它尚未连接 API、Workbench 或数据库。

应用受理层已落在 `internal/app/capabilities`，提供可替换的存储接口和内存实现，固定了草稿保存、发布修订、调用受理、`invocation_id` 生成及 `request_id` 幂等冲突语义。当前调用结果为 `accepted/unavailable`，尚未接入执行调度。

迁移 `0135_capabilities.sql` 和 `PGStore` 已将草稿、发布修订和 invocation 持久化到 PostgreSQL；幂等键为工作空间、应用和 `request_id` 的组合，重启后仍能读取原 invocation。

HTTP 适配已加入 `Server`，提供草稿保存、发布修订和 invocation 受理三条受保护路由。路由只做身份、绑定和错误映射；目前 invocation 仍返回 `accepted/unavailable`，尚未创建运行任务。

迁移 `0136_capability_invocation_queue.sql` 增加了独立的能力调用队列表。首次受理会与 invocation 在同一事务中写入一条 `queued` 任务并保存 `task_id`；相同 `request_id` 重试只读取原任务。该队列尚未连接 Agent/Runtime 执行器，`queued` 不能解释为已执行。

HTTP 已提供 invocation 查询和取消接口。取消会在同一事务中把 invocation 与排队任务标记为 `cancelled`，终止状态不能重复取消；这为后续执行器提供了明确的干预边界。

`RunOne`、`ClaimTask` 和 `CompleteTask` 已形成可替换执行器边界：领取时将 invocation 与任务置为 `running`，执行器返回结果后写入 `completed/available`，失败写入 `failed/unavailable`。当前测试使用 fixture executor，尚未把能力步骤编译成真实 Loom/Codex 任务。

## 2. 第一批实现边界

第一批只做一个内核合同层，不做目录大搬迁，也不接入 License 加密。目标是让下面的纯 Go 合同可以被 API、Workbench 和运行时共同使用：

```text
CapabilityDefinition
  -> ValidateDefinition
  -> DebugRunRequest / DebugRunResult
  -> PublishCapabilityRevision
  -> InvokePublishedRevision
```

合同层只包含结构、状态和错误语义，不持有 Echo、Workbench、数据库连接、供应商 SDK 或套餐名称。

第一批必须覆盖：

1. 草稿可变，发布修订不可变。
2. 发布修订带能力 ID、修订号、定义摘要、输入输出 schema 摘要和运行约束。
3. 调用必须绑定实际发布修订，并返回稳定的 `invocation_id`。
4. 相同工作空间、应用和 `request_id` 重复调用返回同一业务运行或明确的冲突错误。
5. 应用凭据只能调用、读取和取消授权范围内的运行。
6. 调试运行与正式调用拥有不同运行类型和产物命名空间。

## 3. 暂不做的事情

- 不删除现有 workflow、teamrun、evaluation 或 Workbench 入口。
- 不把 Loom 强制设为唯一执行引擎。
- 不在内核实现套餐、账单、组织层级或自定义角色。
- 不为 License 引入加密协议或离线授权文件。
- 不在没有真实开发者旅程验收前宣称“发布能力平台已完成”。

## 4. 验收顺序

先做合同单测和跨入口幂等测试，再接一个最小 API 适配，最后用 Workbench 完成真实旅程：创建草稿、调试、发布、调用、修改草稿、再次发布，并确认旧运行仍绑定旧修订。该旅程通过后，才进入统一权限适配和商业授权外围。

每一步都要记录实际实现入口、测试命令和未覆盖的运行时或部署条件。健康检查、HTTP 202 和单个内核单测不能单独代替业务闭环验收。
